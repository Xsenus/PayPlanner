## Проверки и критерии общего выпуска

Никаких проверок, меняющих скопированные рабочие записи, в основной локальной `payplanner`: для них отдельная одноразовая БД и синтетические данные. Перед любым локальным запуском явно задать `BackgroundServices__Enabled=false` и `Email__Enabled=false`; в скопированной БД выключены email, отправители и очереди, SMTP очищен.

Для узкого исправления во время работы — связанные unit/component/controller/permission/boundary проверки. Высокорисковые финансовые и ролевые ошибки проверять сразу. Финальный применимый frontend/backend gate собрать один раз после связанных изменений перед выпуском. Для текущего объединения 142 с ускорением пользователь отдельно выбрал адресные локальные проверки и затем один полный обязательный CI, без полного локального дубля; успешный полный прогон не повторять без изменения соответствующего кода, конфигурации, зависимостей или тестовых данных. Очистка и этот Markdown не требуют повторения 9309 backend-проверок. CI не ослаблять.

Пользовательский результат должен иметь понятную отдельную запись «Что нового», если формат уже согласован. В кассовом сценарии ранее выбраны отдельные записи для двух исправлений; текущая очистка/планирование новых продуктовых релизов не создаёт. Коммит, push и доступность на сервере — разные состояния. Любые ответы YouGile сначала готовятся локально и публикуются только отдельной командой.
