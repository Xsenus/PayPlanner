# План устранения предупреждений EF и nginx после деплоя 22.06.2026

## Контекст

После деплоя ревизии `310492f485f06a9ab464ff7e71133d9c507e1640` сервис на VPS работает штатно: критических `Unhandled`, `Exception`, `fail`, `error` в логах приложения после текущего деплоя не найдено. Health-check API отвечает `200 OK`, фронтенд и service worker доступны.

В логах остались неаварийные предупреждения, которые нужно закрыть как технический долг, чтобы снизить риск скрытых проблем с данными и производительностью.

## Найденные предупреждения

- [x] `Model.Validation[10622]` - 22 предупреждения при старте приложения.
  - Причина: у части сущностей включён глобальный фильтр мягкого удаления `IsDeleted = false`, а связанные дочерние сущности имеют обязательную связь с таким родителем. EF предупреждает, что при скрытом родителе дочерние записи могут неожиданно исчезать из результатов запросов.
  - Затронутые связи:
    - `Act` -> `ActLineItem`
    - `ClientCase` -> `ClientCaseCourtComplaint`
    - `ClientCase` -> `ClientCaseCourtEventHistory`
    - `ClientCase` -> `ClientCaseCourtInstance`
    - `ClientCase` -> `ClientCaseDocument`
    - `ClientCase` -> `ClientCaseRelatedParty`
    - `ClientCase` -> `ClientCaseWorkOrder`
    - `Client` -> `ClientContract`
    - `Act` -> `ContractAct`
    - `Contract` -> `ContractInvoice`
    - `Contract` -> `ContractPayment`
    - `TaskJournalItem` -> `GoogleCalendarTaskLink`
    - `ClientCase` -> `InvoiceClientCase`
    - `Contract` -> `LegalEntityContract`
    - `Payment` -> `PaymentRemainderTransfer`
    - `Payment` -> `PaymentResponsible`
    - `StickyNoteBoard` -> `StickyNoteBoardMember`
    - `TaskJournalItem` -> `TaskJournalComment`
    - `TaskJournalItem` -> `TaskJournalFile`
    - `TaskJournalItem` -> `TaskJournalParticipant`
    - `LegalEntity` -> `UserCompanyAccess`
    - `TaskJournalItem` -> `YandexCalendarTaskLink`
  - Решение: для дочерних сущностей добавлены согласованные фильтры. Записи актов, дел, договоров, платежей, задач, календарных связей, заметок и доступов скрываются вместе с мягко удалённым родителем.

- [x] `Microsoft.EntityFrameworkCore.Query[20504]` - 8 предупреждений после старта и во время фоновых задач.
  - Причина: запросы загружают больше одной коллекции через `Include` в одном SQL-запросе. EF может собрать большой join и получить дубли/тормоза на объёмных данных.
  - Вероятные зоны по коду и времени логов:
    - синхронизация Google/Yandex календарей;
    - фоновые задачи уведомлений и автоматизации задач;
    - тяжёлые карточки актов/клиентов/платежей, где есть несколько коллекций (`LineItems`, `Participants`, `Comments`, `TaskLinks`, `Calendars`, `Addresses`, `Passports`).
  - Решение: добавлен локальный диагностический режим и адресные `AsSplitQuery()` для тяжёлых загрузок календарных соединений, автоматизации задач, стикер-напоминаний и синхронизации дедлайнов.

- [x] `Microsoft.EntityFrameworkCore.Query[10103]` - 1 предупреждение после деплоя.
  - Причина: один EF-запрос использует `First` или `FirstOrDefault` без фильтра и сортировки. Такая запись зависит от произвольного порядка БД.
  - Решение: добавлен локальный диагностический режим для перевода этого warning в исключение. На локальном запуске с временной SQLite-базой предупреждение не воспроизвелось.

- [x] `nginx connect() failed (111: Connection refused)` около 06:27.
  - Причина: nginx пытался обратиться к backend в момент предыдущего рестарта, когда процесс уже был остановлен или ещё не поднялся.
  - После текущего деплоя повторов нет.
  - План решения: оставить как низкий приоритет. Если хотим убрать такие краткие окна, отдельно улучшить деплой: readiness-check перед переключением трафика или более мягкий restart.
  - Проверка 09.07.2026: на VPS `payplanner.service` активен и включен, `REVISION` и `.deploy-revision` совпадают. В логах nginx за 09.07.2026 повторов `connect() failed (111: Connection refused)` не найдено; найденные записи 08.07.2026 совпадают с окнами рестарта backend и завершились после старта приложения.
