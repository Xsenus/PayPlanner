# Диагностика дат на серверной копии, 05.06.2026

Проверка выполнена в режиме только чтения по текущей серверной базе PostgreSQL.
Данные не пересчитывались и не изменялись.

## Окружение

- Сервер приложения: `/opt/payplanner/app/backend/PayPlanner.Api.dll`.
- База данных: PostgreSQL, база `payplanner`.
- Использованный скрипт: `docs/date-time-data-diagnostics.sql`.

## Результаты

- Некорректные значения `profile.timeZoneId`: `0`.
- Активные задачи со временем и без часового пояса исполнителя: найдено не менее `200` записей, выборка ограничена диагностическим лимитом.
- Активные задачи около полуночи по локальному дню: `0`.
- Кандидаты старого правила с фиксированным `+07:00`: найдено не менее `200` записей, выборка ограничена диагностическим лимитом.
- Судебные заседания около границы дня: `0`.
- Связанные события Google/Yandex для ручной сверки: найдено не менее `200` записей, выборка ограничена диагностическим лимитом.

## Примеры найденных записей

- Задача `272`, исполнитель `Диденко Анна Владимировна`, срок `2028-01-27T09:00:00`, часовой пояс исполнителя не задан.
- Задача `271`, исполнитель `Диденко Анна Владимировна`, срок `2026-12-27T09:00:00`, часовой пояс исполнителя не задан.
- Задача `162`, исполнитель `Диденко Анна Владимировна`, срок `2026-12-21T07:00:00`, часовой пояс исполнителя не задан.
- Google-событие для задачи `312`, срок `2026-06-08T06:00:00`, ссылка активна.

## Вывод

Серверная проверка подтвердила, что проблема не в некорректных строковых значениях часового пояса, а в незаполненных профилях у части исполнителей.
Автоматически пересчитывать такие даты нельзя: среди них могут быть корректные UTC-инстанты и старые значения, созданные по прежнему правилу.

Чтобы новые операции не зависели от настроек операционной системы сервера, backend закреплен на явный резервный часовой пояс `Europe/Moscow`.
Для точного отображения по регионам нужно заполнить `profile.timeZoneId` у сотрудников, у которых он отсутствует.
