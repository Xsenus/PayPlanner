## Реализация

Прежняя проверка изменённых платежей вынесена в `PaymentCreditInvariantScope`. Она используется основным writer-scope и управляемым/старым Apply обоих контроллеров баланса. События tracker сохраняют фактически изменённые объекты между Save; перед commit проверяются PaidAmount и Amount относительно дебетов CreditApplied. Для любого затронутого InvoiceId дополнительно читается каноническая основная запись и суммируются самостоятельные дебеты основной и дочерних записей. Совпадение прежнего и нового итога не пропускает проверку. Одна оплаченная сумма не покрывает несколько самостоятельных списаний.

Группировка выполняется на сервере пачками до 500 ID, только для затронутых счетов; один представитель на счёт сопоставляется через словарь. N+1 и загрузки истории нет. Только прочитанные соседние записи не исправляются; их дебеты участвуют в общем ограничении. Подписки освобождаются до уведомлений/окончания запроса. Выбор представителя сохраняет правила `InvoicePaymentStateService`: неотменённый, затем большая сумма и меньший ID. Антисоединение использует числовые сравнения decimal без неподдерживаемой SQLite сортировки. Проверены равная сумма с записью `100.00`, большая сумма и отменённый дубль. Прежние строки, номера и редакторская идентичность не меняются.

Оба формата Apply используют существующий `BalanceApplicationLease`: Serializable/SHARE NOWAIT прав и FOR UPDATE NOWAIT цели на PostgreSQL, BEGIN IMMEDIATE на SQLite. Проверяются актуальный активный согласованный сотрудник и неразорванная принадлежность счёта. Права и владелец проверяются до блокировки платежа. В основном Payments runner CanEdit/видимость также перенесены до identity-lock. Отказ на занятой недоступной строке возвращает 403/404, а не выдаёт её занятость через 409. `SET LOCAL lock_timeout='2s'` ограничивает неявные ожидания связанных строк только текущей транзакцией; автоматического повтора записи нет.

Управляемый запрос сохраняет UUID/hash/CommandVersion, внешний ключ источника, неизменяемый результат и квитанцию. Проверка выполняется после Save до commit: отказ откатывает денежную запись и новую квитанцию. Неисполненную попытку можно закрыть без потери прежней квитанции основной записи. Старый запрос сохраняет поля ответа appliedAmount/balance без квитанции; повтор без UUID по-прежнему отдельная операция. При неизвестном исходе COMMIT ошибка связи не превращается в повторяемый конфликт. Грязный контекст/внешняя транзакция отклоняются без сохранения, очистки и завершения чужой работы. Обе формы клиента/организации используют общий путь; структура API не расширялась.

## Следующая очередь

Прямой `ApplyCounterpartyCreditAsync` остаётся в `InvoicesController` при перераспределении полученной оплаты во время аннулирования. Сначала разобрать транзакцию, компенсационные записи и правила отмены; простой перенос минимального ограничения на отменяемые платежи без проверки компенсаций недопустим. Затем V1/V2, delete и advance accept/ignore/refund/backfill, остальные банковские/фоновые писатели. Отдельно проверить допустимость целевого платежа, включая отменённый статус, по существующим продуктовым правилам. Общий guard не заменяет предварительную защиту удаления дебетов. Вся финансовая граница открыта до квалификации оставшихся входов.
