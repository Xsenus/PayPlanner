## Что стоит добавить к работе по этому файлу

Чтобы план был не только подробным, но и исполнимым без лишних догадок, для каждого крупного этапа ниже лучше вести одинаковую структуру детализации:

- backend: какие сущности, сервисы, фоновые задачи и endpoints надо сделать;
- database: какие таблицы, индексы, ограничения и миграции появляются;
- frontend: какие новые страницы, вкладки, формы, таблицы и сценарии нужны;
- permissions: какие роли что видят, создают, редактируют и удаляют;
- notifications/jobs: какие фоновые процессы и триггеры должны появиться;
- integrations: какие внешние API нужны и что делать при их недоступности;
- tests: какие unit, integration и e2e проверки считаются обязательными;
- release: как включать функциональность флагами и как выкатывать без поломки текущих данных.

Ниже план уже дополнен так, чтобы при дроблении этапов на отдельные задачи было понятно не только "что сделать", но и "как проверить, что этап действительно завершен".

## Базовое архитектурное решение

Рекомендуемая стратегия: не вводить отдельную сущность "новое юридическое дело" параллельно текущему `ClientCase`, а эволюционно расширять существующий `ClientCase` до полноценной карточки дела. Это позволит:

- сохранить уже существующие финансовые связи дела со счетами и платежами;
- не плодить дублирующие сущности;
- не делать лишнюю миграцию данных между "старыми делами" и "новыми делами";
- постепенно наращивать функциональность вокруг уже существующего маршрута `/cases`.

Дополнительное архитектурное правило:

- `ClientCase` остается корнем агрегата для юридического модуля;
- задачи, документы, судебные события, сроки, комментарии и уведомления должны быть связаны с делом явно, а не через разрозненные nullable-поля;
- текущий платежный контур не переносится в новый модуль, а встраивается в карточку дела через уже существующие связи;
- все внешние интеграции должны строиться как отдельные сервисы с журналом синхронизаций, а не как логика внутри контроллеров.

### 4.1. Основная роль модуля задач

- [ ] Модуль задач должен работать не как "напоминалка", а как основной механизм исполнения работы по делу.

- [ ] Архитектурно модуль задач должен быть независимым от судебной синхронизации, документов и внешних календарей, чтобы его можно было выпустить раньше.

- [ ] Несколько пользователей могут быть вовлечены в задачу в разных ролях.
- [ ] Задача может уходить на согласование и возвращаться на доработку.
- [ ] Без обязательного прохождения согласования задача не может считаться завершенной.

## Этап 8. Судебный блок и синхронизация с сайтами судов

Цель: автоматизировать обновление дела из внешних судебных источников.

- [ ] Сделать раздел настроек "Синхронизация с судами".
- [ ] Добавить поддерживаемые источники и статус подключения к каждому.
- [ ] Реализовать привязку дела к карточке суда по ссылке и по номеру дела.
- [ ] Реализовать журнал синхронизаций.
- [ ] Сделать ручной запуск синхронизации по делу.
- [ ] Сделать планировщик фоновой синхронизации.
- [ ] Реализовать обновление движения дела, заседаний, решений, судьи, секретаря, статуса.
- [ ] Реализовать расчет сроков обжалования на основе полученных решений.
- [ ] Реализовать автоматическое создание задач и событий календаря на основе событий суда.
- [ ] Добавить блок "Данные из суда" в карточке дела.
- [ ] Добавить историю судебных обновлений и ошибок синхронизации.
- [ ] Сделать стратегию graceful degradation: если источник недоступен, система не ломается и показывает понятный статус.

### 8.1. Цель этапа без завышенных ожиданий

- [ ] Судебная синхронизация должна помогать юристу, но не становиться единственным источником правды без контроля.
- [ ] Не все источники будут одинаково стабильны, поэтому проектировать нужно под частичную доступность и периодические поломки внешних сайтов.
- [ ] Блок суда должен работать и без автосинхронизации:
  - ручная привязка;
  - ручной ввод сведений;
  - ручной запуск обновления.

### 8.2. Поддерживаемые источники и архитектура провайдеров

- [ ] Не вшивать логику всех судов в один сервис.
- [ ] Сделать provider-модель:
  - `GasPravosudieProvider`
  - `KadArbitrProvider`
  - другие провайдеры по мере подтверждения.
- [ ] У каждого провайдера должен быть единый контракт:
  - проверить доступность;
  - найти дело;
  - получить карточку дела;
  - получить события;
  - получить документы/метаданные;
  - нормализовать результат.
- [ ] Если часть источников поддерживается только полуавтоматически, это должно быть отражено в настройках и UI честно, без имитации полноценной синхронизации.

### 8.3. Привязка дела к судебному источнику

- [ ] Поддержать привязку:
  - по ссылке на карточку дела;
  - по номеру дела;
  - по внешнему идентификатору, если он есть.
- [ ] В карточке дела должно быть видно:
  - к какому источнику привязано;
  - когда было последнее успешное обновление;
  - когда была последняя ошибка;
  - кто привязал;
  - можно ли перепривязать.
- [ ] Привязка должна проходить валидацию, чтобы не связать дело с чужой/неподходящей карточкой суда без предупреждения.

### 8.4. Нормализация данных суда

- [ ] Независимо от провайдера результат синхронизации должен приводиться к общей модели:
  - судебный статус;
  - суд;
  - судья;
  - секретарь;
  - заседания;
  - решения;
  - документы;
  - публикации;
  - процессуальные сроки.
- [ ] Внутренняя модель не должна повторять сырой формат внешнего сайта.
- [ ] Сырые данные или hash полезно хранить для диагностики, но UI должен работать на нормализованной модели.

### 8.5. Ручная и фоновая синхронизация

- [ ] Ручной запуск синхронизации из карточки дела обязателен.
- [ ] Фоновая синхронизация нужна по расписанию, но должна быть:
  - лимитированной;
  - идемпотентной;
  - с учетом частоты обновления источника.
- [ ] Нельзя запускать фоновую синхронизацию всех дел без ограничений, иначе можно быстро упереться в блокировки или нестабильность источников.
- [ ] Нужны политики:
  - как часто проверять активные дела;
  - как часто проверять архивные;
  - как обрабатывать подряд падающий источник.

### 8.6. Что именно обновляет синхронизация

- [ ] Статус судебного дела.
- [ ] Сведения о суде и составе.
- [ ] Даты и время заседаний.
- [ ] Переносы и отмены заседаний.
- [ ] Публикации решений и определений.
- [ ] Судебные документы и ссылки на них.
- [ ] Иные значимые события, влияющие на процессуальные сроки или действия юриста.

### 8.7. Правила обработки изменений

- [ ] Если источник вернул новое заседание, система должна:
  - создать или обновить `CourtEvent`;
  - обновить `NextHearingAt`;
  - при необходимости создать уведомление;
  - при необходимости создать событие календаря.
- [ ] Если источник вернул решение:
  - создать событие;
  - обновить судебный статус;
  - рассчитать сроки обжалования по правилам;
  - уведомить ответственного.
- [ ] Если источник вернул то же событие повторно:
  - обновить по fingerprint/hash;
  - не плодить дубли.

### 8.8. Расчет процессуальных сроков

- [ ] Расчет сроков должен быть отделен от парсинга судебного источника.
- [ ] Входные данные для расчета:
  - тип судебного события;
  - дата публикации;
  - дата изготовления мотивированного текста, если доступна;
  - вручную подтвержденные даты, если автоматике нельзя доверять.
- [ ] Результат расчета:
  - запись `ProceduralDeadline`;
  - напоминания;
  - отображение в карточке и календаре.
- [ ] Если правило расчета не удалось применить уверенно, система должна показывать статус "требует проверки юристом", а не молча придумывать дату.

### 8.9. Автоматическое создание задач и уведомлений по событиям суда

- [ ] По значимым событиям суда уметь автоматически создавать:
  - задачу подготовить документы;
  - задачу проверить публикацию решения;
  - напоминание о заседании;
  - напоминание о сроке обжалования.
- [ ] Автоматизация должна быть настраиваемой:
  - включено/выключено;
  - какие типы событий порождают задачи;
  - какие типы событий порождают только уведомления.
- [ ] Создание задач и уведомлений должно быть идемпотентным и не дублироваться при повторной синхронизации тех же данных.

### 8.10. Журнал синхронизаций и диагностика

- [ ] Для каждого запуска синхронизации сохранять:
  - источник;

## Этап 9. Двусторонняя синхронизация с Google и Яндекс календарями

Цель: синхронизировать CRM-календарь с внешними календарями пользователей.

- [ ] Добавить подключение Google календаря.
- [ ] Добавить подключение Яндекс календаря.
- [ ] Сохранять пользовательские токены и настройки синхронизации безопасно.
- [ ] Реализовать CRM -> внешний календарь.
- [ ] Реализовать внешний календарь -> CRM.
- [ ] Для обратной синхронизации добавить защиту от ошибок: подтверждение пользователем для спорных обновлений.
- [ ] Добавить выбор синхронизируемых типов событий.
- [ ] Добавить пользовательские напоминания и цветовые настройки.
- [ ] Добавить лог конфликтов и повторных попыток синхронизации.

### 9.1. Реальная цель этапа

- [ ] Этот этап не должен ломать внутренний CRM-календарь и не должен делать внешний календарь единственным источником правды.
- [ ] CRM-календарь остается основным источником рабочих событий.
- [ ] Внешние календари нужны как удобный дублирующий и синхронизируемый слой для конкретного пользователя.

### 9.2. Что уже можно переиспользовать в проекте

- [ ] В проекте уже есть инфраструктура настроек в `AppSettings`.
- [ ] В проекте уже есть OAuth-паттерны и хранение внешних identity через внешнюю авторизацию.
- [ ] В проекте уже есть `UserSetting`, значит часть пользовательских настроек синхронизации можно хранить без немедленного ввода новых сложных таблиц.
- [ ] Значит календарную интеграцию нужно проектировать в стиле:
  - отдельные provider-сервисы;
  - пользовательские подключения;
  - фоновая синхронизация;
  - журнал конфликтов.

### 9.3. Модель подключения календарей

- [ ] Подключение внешнего календаря должно быть пользовательским, а не глобальным на всю систему.
- [ ] Один пользователь может подключить:
  - Google Calendar;
  - Яндекс Календарь;
  - позже несколько календарей одного провайдера, если это потребуется.
- [ ] Для каждого подключения хранить:
  - провайдера;
  - внешний account id;
  - refresh/access token или эквивалент;
  - срок действия токена;
  - выбранный внешний календарь;
  - активность подключения;
  - время последней успешной синхронизации;
  - время последней ошибки.

### 9.4. Что именно синхронизировать

- [ ] На первом этапе синхронизировать только CRM-события из юридического календаря:
  - задачи;
  - судебные заседания;
  - процессуальные сроки;
  - напоминания, если они представлены как календарные события.
- [ ] Не синхронизировать финансовый календарь во внешние персональные календари без отдельного решения.
- [ ] Пользователь должен выбирать, какие типы событий уходят во внешний календарь.

### 9.5. Направления синхронизации

- [ ] `CRM -> внешний календарь` обязательно для первой рабочей версии.
- [ ] `внешний календарь -> CRM` допустимо только для ограниченного набора сценариев и с контролем конфликтов.
- [ ] Для первой итерации безопаснее сделать:
  - полноценный push из CRM;
  - ограниченный pull только по ранее синхронизированным CRM-событиям;
  - не импортировать все внешние события пользователя как задачи CRM.
- [ ] Это важно, иначе CRM быстро засорится личными событиями пользователя.

### 9.6. Внешний идентификатор и mapping

- [ ] Для каждого синхронизированного события нужен mapping:
  - внутренний `sourceType`;
  - внутренний `sourceId`;
  - провайдер;
  - внешний `eventId`;
  - hash последней отправленной версии;
  - время последнего sync.
- [ ] Без mapping-table двусторонняя синхронизация будет ненадежной и склонной к дублям.
- [ ] Если используется агрегированный `CalendarEventDto`, mapping все равно должен ссылаться на первичный источник события.

### 9.7. Стратегия разрешения конфликтов

- [ ] Нужно зафиксировать модель приоритета изменений:
  - CRM authoritative;
  - внешний календарь authoritative;
  - гибрид с подтверждением пользователя.
- [ ] Для юридического контекста безопаснее считать CRM основным источником правды.
- [ ] Изменения из внешнего календаря без подтверждения допустимы только для полей с низким риском:
  - напоминание;
  - цвет;
  - возможно личная заметка пользователя.
- [ ] Изменение времени судебного заседания из внешнего календаря не должно автоматически переписывать данные суда.

### 9.8. Синхронизация Google Calendar

- [ ] Реализовать отдельный provider-адаптер Google Calendar.
- [ ] Поддержать:
  - OAuth-подключение;
  - выбор внешнего календаря;
  - создание событий;
  - обновление событий;
  - удаление/отмену событий;
  - проверку webhook/changes feed, если это потребуется.
- [ ] Все Google-специфичные детали держать в адаптере, а не размазывать по общему сервису.

### 9.9. Синхронизация Яндекс Календаря

- [ ] Реализовать отдельный provider-адаптер Яндекс Календаря.
- [ ] Поддержать ту же общую модель, что и для Google:
  - подключение;
  - выбор календаря;
  - push;
  - ограниченный pull;
  - лог ошибок.
- [ ] Если API Яндекса будет беднее или нестабильнее, это должно быть отражено в настройках и диагностике.

### 9.10. Пользовательские настройки синхронизации

- [ ] Пользователь должен уметь настроить:
  - включен ли провайдер;
  - какой внешний календарь использовать;
  - какие типы событий синхронизировать;
  - создавать ли напоминания во внешнем календаре;
  - цветовую схему;
  - односторонняя или двусторонняя синхронизация;
  - поведение при конфликте.
- [ ] Эти настройки логично показывать либо в профиле пользователя, либо в отдельном разделе интеграций пользователя, а не только в общей админке.

### 9.11. Фоновые процессы синхронизации

- [ ] Нужны отдельные jobs:
  - push pending changes;
  - poll external updates;
  - retry failed sync;
  - cleanup stale sync mappings.
- [ ] Синхронизация должна быть идемпотентной.
- [ ] Нужен lock от параллельного запуска sync для одного и того же подключения.
- [ ] Нужен limit и backoff при ошибках внешнего API.

- [ ] Настраиваемый порог в днях.
- [ ] Исключения:
  - дело завершено;
  - дело архивировано;
  - дело проиграно/закрыто;
  - есть длинная активная задача без ожидания промежуточных действий;
  - пользователь в отпуске или недоступен, если такой контур появится.
- [ ] Отдельно решить, считать ли судебное событие само по себе активностью без открытия дела пользователем.

### 14.4. Эскалации

- [ ] Уровень 1:
  - уведомление ответственному;
  - мягкое напоминание.
- [ ] Уровень 2:
  - повторное напоминание через заданный интервал;
  - при необходимости авто-задача.
- [ ] Уровень 3:
  - уведомление старшему юристу/руководителю;
  - более явная эскалация.
- [ ] Правила эскалации должны быть настраиваемыми и идемпотентными.

### 14.5. Автоматическая задача по неактивности

- [ ] При первом серьезном срабатывании система может создавать задачу:

  - обновить стратегию;
  - подтвердить дальнейший план.
- [ ] Такая задача должна иметь особый тип, чтобы не путаться с обычными пользовательскими задачами.

### 14.6. UI и аналитика
