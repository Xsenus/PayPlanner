# Claude: компании, первичные документы, КУДиР и банки

Декомпозиция PAY-33–36 с учётом **уже сделанного в Claude**. [Общий индекс](claude-yougile-development-handoff-2026-10-10.md) содержит ревизии, ограничения свежести и все карточки. Word-ТЗ и извлечённый текст лежат в репозитории: [manifest с путями и SHA256](yougile-sources/2026-10-10/attachments-manifest.json). Семь исходных ссылок соответствуют шести уникальным документам; дублирующий «Счёт» не является второй версией требований.

Этот документ определяет задания и проверочные инварианты. Он не устанавливает налоговые правила и не разрешает банковские платежи. Устаревшие ставки, форматы и утверждения из исходного Word необходимо проверить по актуальным официальным источникам перед реализацией и согласовать с ответственным бухгалтером. Противоречия не закрывать предположениями.

## Общий сквозной путь и модель ответственности

Собственная компания/филиал → действующий банковский счёт → документ с фиксированными реквизитами продавца → платёж/распределение → первичный документ → допустимая запись КУДиР. Эти этапы связаны, но имеют разные состояния и права. Выписка банка не сама по себе утверждённый налоговый доход; «Отправлен» не равен «Оплачен»; скрытый документ не равен удалённой денежной операции.

Использовать имеющиеся сущности клиента/контрагента/дела/договора/счёта/акта/денежной операции. Не добавлять второй источник остатков и второй реестр собственных компаний. Суммы хранить и рассчитывать в существующем точном денежном формате, не через floating point. Контроль компании, доступа, суммы и concurrency находится на сервере. UI не может обходить его скрытыми кнопками.

## PAY-33

**Собственные компании и филиалы.** [Исходная карточка](yougile-sources/2026-10-10/cards/PAY-33.md), [roadmap 9/10, 90%](company-profile-yougile-roadmap-2026-10-09.md), [gap-матрица](company-profile-gap-matrix-2026-10-09.md), [журнал фактической реализации](pay-33-36-implementation-log-2026-10-09.md).

### Подтверждённое состояние ветки

Пункты 1–9 уже завершены в Claude-основе; остаётся ручная приёмка пункта 10 и квалификация будущего интегрированного выпуска. Не откатывать план к исходным 10% и не переписывать реализованные сущности заново. Более поздние шаги журнала важнее ранней фразы «договоры ещё не подключены»: выбор продавца в договорах затем реализован.

Есть отдельный общий справочник собственных организаций, банковские счета со стабильным ID, филиалы/точки, наследование реквизитов, управляемые изображения, предупреждения о реквизитах, выбор продавца для счетов/актов/договоров, парные миграции и фиксированные снимки документов. Кодовые опорные точки: `OwnCompaniesController`, `CompanyRequisitesSnapshot`, `SellerLegalEntityComposer`, `DocumentSellerService`, `src/components/Documents/DocumentSellerPicker.tsx`, существующие формы счетов/актов/договоров.

### Уже закрытые решения владельца

- Общий справочник собственных организаций управляется администратором. Это не личный отдельный список каждого сотрудника и не новый реестр клиентов. Существующие роли ограничивают действия сотрудников.
- У разных собственных юрлиц уникальный ИНН. Филиал всегда наследует ИНН компании, может иметь собственный КПП; если он не заполнен, используется КПП компании.
- Нумерация документов сохраняет действующую общую организационную модель и ручное управление. Не вводить новую независимую последовательность для каждого филиала без отдельного требования.
- Проверки ИНН/КПП/ОГРН/счёта дают предупреждения согласно принятой модели; не превращать их в новый блокирующий запрет для импортированных данных. DaData не отменяет ручной ввод при недоступности.
- Налоговые ставки/правила относятся к PAY-34 и не объявляются закрытыми одним внедрением профиля компании.

### Приёмка, которую нужно завершить

| Сценарий | Ожидаемый результат |
| --- | --- |
| Две собственные компании | Разные действующие реквизиты; сотрудник не меняет запрещённую организацию |
| Филиал без переопределений | ИНН и незаданные поля наследуются от компании |
| Филиал с КПП/адресом/счётом/подписантом | Только разрешённые поля заменяются; счёт принадлежит своей компании и активен |
| Несколько счетов | Один активный основной; архивирование сохраняет историю и не выдаёт архивный счёт в новом документе |
| Автозаполнение ИНН/БИК недоступно | Возможен принятый ручной путь, понятная ошибка, введённое не теряется |
| PNG/JPG/WebP логотип/печать/подпись | Допустимый файл проходит, запрещённый размер/формат не проходит, доступ защищён |
| Предпросмотр документа | Показывает выбранного продавца и не фиксирует снимок преждевременно |
| Выгрузка и изменение компании после неё | Ранее сформированный документ сохраняет исторический снимок, новый использует согласованные текущие реквизиты |
| Архив компании/филиала | Старый документ остаётся читаемым; новый выбор исключает архивную сущность |
| Старый документ без продавца | Применяется реализованный fallback без утраты данных и без подмены уже фиксированного снимка |

Проверить исходный документ, печатную форму и повторное открытие UI; не ограничиваться POST/GET профиля. Для всех связей — прямые разрешительные и отказные запросы. Миграции проверить upgrade и чистая БД в обеих поддерживаемых СУБД при будущей интеграции, не на production.

## PAY-34

**Счета, входящие/исходящие документы, НДС и печатные формы.** [Карточка](yougile-sources/2026-10-10/cards/PAY-34.md), [активный план 1/12, 8%](accounting-documents-yougile-roadmap-2026-10-09.md). Три уникальных ТЗ: «Счёт», «Создание документов, входящие/исходящие», «Документы CRM»; требования шрифтов, масштаба печати/подписи и проверки актов содержатся также в сообщениях.

### Сначала карта существующего поведения и решения

Для каждого типа документа указать: нынешнюю сущность, экран, API, связанные деньги, текущую печать, статус и доступ; затем отметить «есть / частично / отсутствует / противоречие». Предложенный набор типов из ТЗ: счёт, акт, счёт-фактура, УПД, ТОРГ-12, договор и производные, сверка. Не выдавать существующий счёт/акт за готовность всех остальных.

До изменения бизнес-логики зафиксировать решения:

1. Допускается ли акт до полной оплаты и в какой сумме при частичной оплате/этапе? Тексты ТЗ различаются; UI не должен произвольно выбирать строгое правило.
2. Когда присваивается номер: создание, утверждение или выпуск? Кто может менять, как закрывается период, что происходит при отмене и как сохраняется уже действующая модель PAY-33?
3. Какая версия PDF хранится и является неизменной: в одном ТЗ упоминается отсутствие хранения, в другом — версии/архив. Определить отличие preview, выданного оригинала и новой версии.
4. Как сопоставляются жизненные циклы счёта/акта/входящего документа, частичная оплата, аванс, возврат, аннулирование и просрочка? Конфликтующие 5/10 дней в исходных правилах не реализовывать наугад.
5. Какие действия разрешены менеджеру, координатору, бухгалтеру, секретарю, администратору: отдельно просмотр, preview, создание, редактирование, отправка, выгрузка, проведение, аннулирование и платёж.
6. НДС: система налогообложения компании, даты применимости, льгота/без НДС, включённый/начисленный, поддержанные ставки и переходы. Фразу исходника «УСН = Без НДС» нельзя превращать в универсальное юридическое правило.

### Данные и финансовые инварианты

Счёт связан минимум с разрешённым клиентом, при предусмотренной договорной работе — с договором/делом. Один счёт не принадлежит нескольким делам одновременно. Продавец — собственная компания и при необходимости филиал PAY-33; её счёт не подменяется счётом клиента. Выбор защищён сервером, не только options в форме.

Позиции содержат наименование, единицу, количество, цену и согласованные скидку/налог; итог строится из позиций. Задать точный порядок округления и проверить граничные суммы. Сумма прописью совпадает с итогом и валютой. Ручное изменение «Оплачен» не является заменой реального подтверждения денег: сохранять событие, основание и аудит согласно действующим правилам.

Оплата, частичная оплата, рассрочка, аванс и распределение используют существующий money/payment-механизм. Одно поступление может распределяться по согласованным документам, но сумма распределений не превышает поступление. Нельзя оплатить документ чужой компании/дела. Повтор импортного события или двухкратное подтверждение не создаёт новую денежную операцию. Возврат/отмена снимает именно свои распределения, сохраняя аудит; проведённую историю не стирать.

Статусы из ТЗ сопоставить с действующим enum/полями до миграции. Как минимум отделить черновик, отправку, согласование, срок, частичную/полную оплату и аннулирование. Доставку документа фиксировать только по фактическому действию/результату, с каналом, временем, сотрудником и безопасным повтором. Просрочку считать в часовом поясе/по сроку без повторного ежедневного создания одинаковых записей.

### Печатная форма и первичка

- Сделать общий согласованный набор шрифтов/размеров для счёта и актов. Проверить исходный размер логотипа, печати и подписи при масштабе PDF **100%**, прозрачность, чёткость и пропорции; не растягивать до произвольного блока.
- Шапка, номер/дата, продавец/покупатель, банк/счёт, договор/основание, таблица, итог/НДС/пропись и подписант берутся из подтверждённого снимка. Незаполненный необязательный реквизит не превращается в «undefined» или выдуманный ИНН.
- Длинные названия, адреса и 1/50/много строк: переносы, повтор заголовка таблицы, поля страницы, итог и подписи не обрезаются. Проверить кириллицу, копирование текста и страницы печати.
- Создание акта/накладной/счёта-фактуры/УПД из основания копирует разрешённый состав один раз с собственной историей; последующее изменение исходного счёта не переписывает выпущенный документ. Частичное закрытие не допускает повторного списания количества/суммы сверх основания.
- Для договоров/допсоглашений сохранить текущее управляемое хранилище и выбор продавца, сверку строить по подтверждённым операциям выбранного периода/сторон.

### Входящие документы, автоматизация и внешние границы

Входящий документ может быть введён вручную, загружен файлом или принят из подтверждённого ЭДО. Определить поставщика, компанию-получателя, вид/номер/дату, сумму/налог, связанные платежи/основания и оригинал. Разделять регистрационную запись, согласование, проведение/принятие и отклонение; право просмотра не даёт принятие. Повтор файла/события ЭДО не создаёт второй документ. Незавершённую публикацию файла нельзя считать сохранённым оригиналом.

Пакетная обработка, повторные документы, напоминания и отправка должны использовать существующие jobs/notifications с идемпотентностью. Разнести ошибки по документам, показывать частичный успех и сохранять прогресс. Не держать HTTP-запрос на полной обработке тысяч документов. Ссылка клиенту имеет согласованный срок/отзыв/доступ; интеграция 1С/ЭДО требует реального поддержанного протокола, а не декоративной кнопки.

### Проверки и готовность

Адресные случаи: без НДС и утверждённые варианты ставок/дат, включённый и начисленный налог, дробное количество и округление, ноль/отрицательное значение по утверждённому правилу, частичные оплаты/возвраты, две компании, архив филиала, изменение реквизитов после выпуска, длинный PDF, повтор отправки/импорта, конкурентное проведение, роли Анны/бухгалтера/менеджера. Проверить старые данные до новой версии.

Налоговые/денежные изменения — высокий риск: expanded finance/security/concurrency проверки сразу, полные применимые frontend/backend gates перед push, парные миграции при изменении схемы. Визуальный PDF-результат проверяется отдельно. Готовность — согласованные противоречия, сквозные действующие документы и деньги, сохранённые снимки, права, корректная печать, будущий выпуск и ручная приёмка; перечень новых типов указывать честно.

## PAY-35

**КУДиР и книга учёта/продаж.** [Карточка](yougile-sources/2026-10-10/cards/PAY-35.md), [roadmap 1/11, 9%](kudir-yougile-roadmap-2026-10-09.md), исходный «Модуль КУДиР» в manifest. Не заменять налоговый регистр существующим списком банковских операций и не считать фразу «есть в любом банке» техническим API банка.

### Решения и модель

Уточнить режим/период учёта, список включаемых/исключаемых операций, момент признания дохода/расхода, правила частичной оплаты, аванса/возврата, документы-основания, корректировки/закрытие года, роли бухгалтерского утверждения и поддержанные форматы. Название «книга продаж» не даёт основания смешать её с КУДиР; определить, нужен ли самостоятельный регистр и для каких компаний.

Действующая `MoneyOperation` имеет собственные Posted/Processing/Error. Это не то же самое, что предложенные DRAFT/APPROVED/ARCHIVED налоговой записи. Сохранить единственный денежный источник и добавить согласованную связь/проекцию налогового признания, если её действительно нет. Для записи нужны компания, исходная операция, дата денег и дата учёта, доход/расход, категория/основание, клиент/дело/документ, статус, автор и история. Не хранить полный второй баланс отдельно.

### Реализация по блокам

1. Матрица существующих источников: ручные деньги, выписка PAY-36, подтверждение счёта PAY-34, возвраты. Для каждого показать, что создаёт кандидата, что утверждает и что исключается.
2. Ограниченная загрузка кандидатов с серверной фильтрацией по компании/периоду. Не раскрывать чужие деньги пользователю без доступа к финансовому разделу.
3. Бухгалтер проверяет и утверждает по заданным правилам. Утверждение транзакционно; уникальный ключ исходной операции/части/правила препятствует дублю при retry и concurrency.
4. Частичный доход/расход и изменение распределения имеют точное основание. Один платёж не признаётся повторно при смене счёта или повторном банковском импорте.
5. Возврат и исправление проведённой записи оформляются допустимой связанной корректировкой; закрытый период не редактируется молча. Право открытия периода и последовательность поправок определить отдельно.
6. Журнал: страницы, диапазон дат, компания, категории, статус, источник; итоги считаются по тому же серверному фильтру, а не только по загруженным строкам. Показать откуда взялась сумма и чем обоснована.
7. Экспорт PDF/Excel/при необходимости XML соответствует согласованному актуальному формату, сортировке/нумерации и правам. Наличие XML не означает прямую сдачу в ФНС; такую интеграцию не обещать без отдельного протокола.

**Проверки:** пустой период, две компании, дробные суммы, аванс/частичное погашение/возврат/исключение, повтор импорта, два бухгалтера, rollback, закрытый год, поздняя операция, отказ доступа, много страниц, итоги/экспорт. Проверить индексы, запросы и предельный размер выгрузки. Готовность — утверждённые правила, один источник денег, достоверная прослеживаемая книга, корректировки без утраты истории и ручная приёмка бухгалтера.

## PAY-36

**Точка/Сбер: счета, выписки, дальнейшее разнесение.** [Карточка](yougile-sources/2026-10-10/cards/PAY-36.md), [roadmap 2/12, 17%](bank-integrations-yougile-roadmap-2026-10-09.md), [пакет проверки API](bank-integrations-api-verification-2026-10-09.md). Исходное Word-ТЗ v2 лежит в репозитории; просьба «по аналогии с КУБом» не является разрешением создавать банковские поручения.

### Что действительно уже есть

Общий `IBankProvider`, `BankSyncService`, модели `BankConnection`, `BankConnectionAccount`, `BankStatementOperation`; защищённое хранение токена/состояние переавторизации, индексы, ограничение компании по ИНН, постраничная идемпотентная загрузка, изоляция ошибки счёта, watermark после подтверждённой записи. В текущей основе **нет** реальных адаптеров Точки/Сбера, готового OAuth/callback/webhook, законченного HTTP/UI, фонового расписания и автоматического разнесения денег. Не публиковать утверждение «банки подключены» по этому каркасу.

### Предварительные данные

Для каждого банка: официальный кабинет/контракт API, версия/дата документации, sandbox, согласованные scopes и счёт собственной компании, redirect/webhook, формат страниц/курсов/операций, ограничения частоты, классификатор состояний счёта и операций. Секреты вводить через защищённую среду, не в ТЗ/Git. Без подтверждённой документации не угадывать пути, подписи webhook, формат OAuth или refresh policy.

### Дальнейшие блоки

| Блок | Реализация | Отказ/инвариант |
| --- | --- | --- |
| Подключение | Реальный адаптер каждого банка поверх общего интерфейса; company/scopes/consent | Пользователь не привязывает чужой ИНН; отсутствие доступа к одному счёту не трактуется как его закрытие |
| Авторизация | Подтверждённый flow, защищённый refresh, подтверждённый callback/state и reauth | Не логировать токен, повтор callback идемпотентен, refresh выполняется безопасно при конкуренции |
| Список счетов | Все разрешённые страницы, стабильный bank account-ID, currency/status, связь со своим профилем | Неполный ответ/отзыв согласия не архивирует молча весь справочник |
| Изменение состояния | Открыт/ограничен/предварителен/закрыт/недоступен согласно реальному ответу | История сохраняется; неподходящий счёт не выбирается для нового документа |
| Выписка одного счёта | Подтверждённый async-flow Точки и все страницы Сбера; нормализация и долговременное хранение | Повтор периода/API/webhook не создаёт вторую операцию; незавершённая не превращается в подтверждённую |
| Все счета/фон | Bounded scheduler, backoff/limits, отдельные прогресс и ошибки, watermark после commit | Отказ одного счёта не останавливает успешные; timeout не пропускает страницу |
| Разнесение | Общий существующий payment-механизм; номер/ИНН/сумма/валюта/основание | Неоднозначность → ручное «Уточнить», запрет чужой компании, сумма распределений ≤ поступление |
| UI и мониторинг | Подключить/переавторизовать/синхронизировать, доступы, last success/error, счёт/операция/документ | Не показывать зелёный успех только после enqueue; не раскрывать банковские данные лишней роли |

При авторизации не смешивать разные организации и сотрудников. Согласие на чтение не разрешает вывод денег. При фильтре «все счета» показывать, какие доступны и какие получили ошибку. Текущий файловый импорт сохраняется самостоятельным рабочим механизмом, не удалять его из-за появления API.

Для автоматического разнесения сначала доказать надёжное однозначное совпадение. Номер счёта в назначении может повторяться у разных компаний; один платёж может закрывать несколько документов или стать авансом. Не разносить спорную сумму по FIFO без утверждённого правила. До подтверждения кандидат не изменяет баланс и налоговый регистр. Входящие/исходящие деньги и документы поставщиков проверяются отдельно.

### Проверки и приёмка

Fake/sandbox adapter: несколько страниц, перекрывающиеся периоды, duplicate ID, изменение pending→confirmed, две компании, foreign account, смена валюты, неполный список, 401/429/5xx, refresh concurrency, callback replay/signature, webhook out of order, сбой одной из N записей/счетов, restart/checkpoint, конкурентное разнесение, отмена и возврат.

Реальный sandbox каждого банка квалифицируется отдельно. После разрешённого подключения production для чтения подтвердить набор счетов и полную выписку согласованного периода, без финансовых поручений; не проводить destructive проверки на настоящих деньгах. Ролевые/финансовые/API и парные миграционные gates обязательны до выпуска. Приёмка карточки сообщает только реально работающие банки, ограничения доступа и подтверждённое разнесение, а не общий план.

## Интеграционная приёмка и производительность

Согласованный сценарий: две собственные компании → филиал и его активный счёт → счёт клиенту → частичное поступление → подтверждённое разнесение → разрешённый акт/первичка → утверждённая запись учёта → корректировка/возврат. Затем сменить реквизиты и убедиться в сохранности старого документа. Проверить ограниченного секретаря, менеджера, бухгалтера и admin прямыми запросами.

Измерить запросы списка/деталей, загрузку реквизитов и документов, размер PDF/ответа/выгрузки, объём памяти, время полной выписки и очереди. Составные индексы должны соответствовать company/account/date/status/remote-ID фильтрам; payload списков не содержит все файлы и историю. Разные банковские страницы обрабатываются ограниченно; провайдер не получает бесконечный burst на retry. Уникальность и атомарность не заменять cache-only проверкой.

Четыре старых roadmap сохраняют свои итоги; новые реализации обновляют каждый затронутый план с доказательствами. Перед будущим выпуском объединить изменения main (особенно права preview/export), разрешить конфликт версии «Что нового», пройти полный применимый CI и проверить установленную ревизию. Этот документальный handoff не закрывает ни один финансовый пункт реализации или производственной приёмки.
