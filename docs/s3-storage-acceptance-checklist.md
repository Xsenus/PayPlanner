# Чек-лист приемки S3-интеграции

Этот чек-лист нужен для финальной проверки S3-интеграции PayPlanner на реальном HOSTKEY bucket или другом S3-совместимом хранилище.

## Что подготовить

- Администраторский доступ в PayPlanner.
- Bucket в HOSTKEY S3.
- Access Key и Secret Key с правами на чтение, запись, удаление и просмотр объектов bucket.
- Endpoint `https://s3-nl.hostkey.com`.
- Region `nl`.
- Рабочий префикс для теста, например `payplanner-acceptance`.

## Автоматические проверки перед ручной приемкой

Выполнить в корне проекта:

```powershell
dotnet test backend/PayPlanner.Api.Tests/PayPlanner.Api.Tests.csproj --filter "S3StorageServiceTests|S3StorageControllerTests|DatabaseBackupServiceS3Tests" -p:BaseOutputPath=.codex-build/bin/ -p:BaseIntermediateOutputPath=.codex-build/obj/ --logger "console;verbosity=minimal"
npm run test:unit -- src/components/S3Storage/S3Storage.test.tsx src/components/Settings/DatabaseMaintenanceSettings.test.tsx
npm run build
```

Ожидаемый результат: все команды завершаются без ошибок.

## Сценарий 1. Подключение HOSTKEY S3

1. Открыть раздел `S3-хранилища`.
2. Создать подключение с провайдером `HOSTKEY S3`.
3. Заполнить endpoint, region, bucket, root prefix, Access Key и Secret Key.
4. Сохранить подключение.
5. Нажать `Проверить`.

Ожидаемый результат:

- подключение сохраняется;
- Secret Key не отображается в открытом виде;
- проверка проходит шаги list, upload, download и delete;
- служебный тестовый файл удаляется после проверки.

## Сценарий 2. Ошибочные настройки S3

Проверить по отдельности:

- неверный Secret Key;
- несуществующий bucket;
- endpoint с ошибкой в адресе;
- ключ без прав на запись или удаление.

Ожидаемый результат:

- пользователь видит понятную ошибку;
- приложение не зависает;
- рабочие подключения и ранее созданные настройки не повреждаются.

## Сценарий 3. Файловые операции S3

1. Открыть рабочее подключение в разделе `S3-хранилища`.
2. Создать папку.
3. Загрузить текстовый файл.
4. Открыть и изменить текстовый файл.
5. Скачать файл и проверить содержимое.
6. Скопировать файл в другую папку.
7. Переместить файл.
8. Удалить файл и тестовые папки.

Ожидаемый результат:

- все операции выполняются внутри заданного root prefix;
- пути с `..` не принимаются;
- после удаления тестовых объектов они исчезают из bucket.

## Сценарий 4. Ручная резервная копия БД в S3

1. Открыть `Настройки` -> `Обслуживание базы данных` -> `Резервные копии`.
2. Включить `Загружать новые резервные копии в S3`.
3. Выбрать рабочее S3-подключение.
4. Указать папку, например `backups/database/{yyyy}/{MM}/`.
5. Сохранить настройки.
6. Нажать `Создать и скачать`.
7. Проверить, что backup скачался локально и появился в S3 bucket.

Ожидаемый результат:

- локальный backup создается и скачивается;
- в истории S3-выгрузок появляется статус `Загружено`;
- путь в S3 соответствует выбранному шаблону;
- размер в истории совпадает с размером созданного backup-файла.

## Сценарий 4A. Ручная резервная копия БД на Яндекс.Диск

1. Убедиться, что в разделе `Я.Диск` сохранен OAuth-токен и проверка подключения проходит успешно.
2. Открыть `Настройки` -> `Обслуживание базы данных` -> `Резервные копии`.
3. Включить `Загружать новые резервные копии на Яндекс.Диск`.
4. Указать папку, например `backups/database/{yyyy}/{MM}/`.
5. Сохранить настройки.
6. Нажать `Создать и скачать`.
7. Проверить, что backup скачался локально и появился на Яндекс.Диске.

Ожидаемый результат:

- локальный backup создается и скачивается;
- в истории выгрузок на Яндекс.Диск появляется статус `Загружено`;
- путь на Яндекс.Диске соответствует выбранному шаблону;
- S3-хранилища и Яндекс.Диск могут быть включены одновременно.

## Сценарий 5. Повтор неудачной S3-выгрузки

1. Временно испортить Secret Key или права на запись.
2. Создать резервную копию БД.
3. Убедиться, что локальный backup создан, а S3-выгрузка получила статус `Ошибка`.
4. Вернуть корректный Secret Key или права.
5. Нажать `Повторить` у ошибочной S3-выгрузки.

Ожидаемый результат:

- повторная отправка использует уже созданный локальный backup;
- статус меняется на `Загружено`;
- в S3 появляется тот же backup-файл;
- новая локальная копия при retry не создается.

## Сценарий 5A. Повтор неудачной выгрузки на Яндекс.Диск

1. Временно удалить или испортить OAuth-токен Яндекс.Диска.
2. Создать резервную копию БД.
3. Убедиться, что локальный backup создан, а выгрузка на Яндекс.Диск получила статус `Ошибка`.
4. Вернуть корректный OAuth-токен.
5. Нажать `Повторить` у ошибочной выгрузки на Яндекс.Диск.

Ожидаемый результат:

- повторная отправка использует уже созданный локальный backup;
- статус меняется на `Загружено`;
- файл появляется на Яндекс.Диске;
- новая локальная копия при retry не создается.

## Сценарий 6. Автоматическая резервная копия

1. Включить автобэкапы.
2. Установить ближайшее время расписания в локальном часовом поясе сервера.
3. Дождаться выполнения фоновой задачи.
4. Проверить раздел `Фоновые сервисы`.
5. Проверить S3 bucket.

Ожидаемый результат:

- автоматическая резервная копия создается по расписанию;
- файл отправляется в выбранное S3-хранилище;
- диагностика фоновой задачи показывает последний статус S3-выгрузки;
- старые локальные backup-файлы очищаются по сроку хранения.

## Что зафиксировать по итогам приемки

- Дата и время проверки.
- Endpoint, region и bucket без секретных ключей.
- Root prefix, в котором проводилась проверка.
- Результат проверки подключения.
- Имя файла ручного backup и путь в S3.
- Имя файла ручного backup и путь на Яндекс.Диске, если включена отправка на Я.Диск.
- Имя файла автоматического backup и путь в S3.
- Имя файла автоматического backup и путь на Яндекс.Диске, если включена отправка на Я.Диск.
- Ошибочный сценарий, который был проверен, и текст ошибки в интерфейсе.
- Результат retry для неудачной выгрузки.

## Очистка после приемки

- Удалить тестовые файлы и папки из S3.
- Вернуть рабочее расписание backup.
- Убедиться, что в настройках не остались тестовые ключи или временные подключения.
