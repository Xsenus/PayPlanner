# Аудит текущих шаблонов задач

Дата: 9 июля 2026.
Связанный roadmap: `docs/task-template-design-roadmap-2026-07-09.md`.

## Короткий вывод

В проекте пока нет полноценного модуля редактируемых шаблонов задач. Есть два близких механизма:

- статические подсказки типовых задач по этапу дела в карточке дела;
- автоконтроль дел без активных задач, который создает фиксированную контрольную задачу.

Оба механизма полезны как база, но они не закрывают замечание клиента про конструктив и дизайн шаблонов задач: нет списка шаблонов, CRUD API, отдельной таблицы, формы редактирования, поиска, фильтров, привязки участников, согласующих, наблюдателей, файлов или чек-листа.

## Где сейчас используются шаблонные задачи

### Карточка дела

Файлы:

- `src/utils/caseTaskPayload.ts`;
- `src/components/Cases/CaseDetailPage.tsx`;
- `src/utils/caseTaskPayload.test.ts`;
- `src/components/Cases/CaseDetailPage.test.tsx`.

Механика:

- `getCaseStageTaskTemplates(caseItem)` подбирает статические подсказки по `case.stage` и `case.caseType`;
- `buildCaseTaskPayload(caseItem, timeZoneId, template)` превращает выбранную подсказку в payload новой задачи;
- во вкладке "Задачи" карточки дела отображается блок "Подсказки по этапу";
- при смене этапа дела показывается блок действий "Этап дела изменён" с кнопками создания типовых задач и процессуальных сроков.

Текущий состав статического шаблона:

- `key`;
- `stageLabel`;
- `title`;
- `description`;
- `priority`;
- `plannedDurationMinutes`;
- `tags`;
- внутренние `aliases` для поиска по свободному тексту этапа.

Поля, которые попадают в создаваемую задачу:

- клиент/юрлицо и дело из карточки дела;
- название и описание из шаблона;
- исполнитель из ответственного по делу;
- срок: завтра в 10:00 по часовому поясу пользователя;
- длительность из шаблона или 60 минут;
- тип `task`;
- приоритет из шаблона или приоритет дела;
- статус `new`;
- напоминание `atDue`;
- канал `inApp`;
- теги из шаблона.

Что не поддерживается в этих подсказках:

- сохранение и редактирование шаблонов пользователем;
- поиск и фильтры по шаблонам;
- согласующие и наблюдатели;
- срок от даты создания как настраиваемое правило;
- срок согласования;
- чек-лист;
- файлы;
- результат;
- оплата исполнителю;
- связь с конкретным типом дела или этапом как справочник, а не текстовый alias;
- применение к уже открытой новой задаче без перезаписи ручных правок.

### Автоконтроль дел

Файлы:

- `backend/Controllers/TasksController.cs`;
- `backend/Models/Responses/TaskJournalDtos.cs`;
- `backend/Models/Requests/TaskJournalSettingsRequest.cs`;
- `src/components/Tasks/TaskJournal.tsx`;
- `src/services/api.ts`.

Механика:

- `GET /api/tasks/automation/case-candidates` возвращает дела без активных задач;
- кандидат содержит `suggestedTitle`, `suggestedDescription`, `suggestedDueAt`, `suggestedPriority`;
- `POST /api/tasks/automation/case-candidates/{clientCaseId}/task` создает одну фиксированную контрольную задачу;
- `POST /api/tasks/automation/case-candidates/tasks` массово создает такие задачи.

Текущая контрольная задача жестко задана:

- название: "Проверить движение по делу";
- тип: `control`;
- статус: `new`;
- длительность: 60 минут;
- теги: `автоконтроль`;
- напоминания: `before1d`, `atDue`;
- канал: `inApp`;
- исполнитель берется из настроек автоконтроля или ответственного по делу;
- при эскалации добавляется наблюдатель.

Это не является общим шаблоном задач: пользователь не может создать несколько вариантов, настроить состав полей, сохранить шаблон или применить его из карточки задачи.

## Где шаблонов задач сейчас нет

- В backend нет моделей `TaskTemplate`/`TaskJournalTemplate`.
- В `PaymentContext` нет `DbSet` для шаблонов задач.
- В миграциях нет таблиц для шаблонов задач.
- В `src/services/api.ts` нет методов `/tasks/templates`.
- В `TaskJournal.tsx` нет выбора шаблона при создании новой задачи.
- В старой и новой карточке задачи нет сценария "применить шаблон".
- В настройках задач есть параметры карточки, результата, автоконтроля и прав исполнителя, но нет настроек библиотеки шаблонов.

## Что уже можно переиспользовать

- `TaskJournalUpsertPayload` как базовый контракт применения шаблона к задаче.
- `TaskJournalParticipant` и недавнюю доработку согласующих/наблюдателей для состава участников шаблона.
- `buildCaseTaskPayload` как пример преобразования шаблона в задачу.
- UI выбора участников из новой карточки задачи.
- API `createTaskJournalItem` как конечную точку создания задачи после применения шаблона.
- Автоконтроль дел как источник требований к массовому созданию типовых задач.

## Риски и пробелы

- Состав полей шаблона требует бизнес-решения: особенно согласующие, наблюдатели, чек-лист, файлы, срок от даты создания и связь с этапом дела.
- Если сделать только frontend-шаблоны без backend-хранения, шаблоны не будут общими для команды и не переживут работу с разных устройств.
- Если применять шаблон простым присваиванием формы, есть риск стереть ручные правки пользователя в новой задаче.
- Старую и новую карточку задачи нужно проверять вместе, иначе шаблоны будут работать только в одном режиме окна.
- Текущий UI подсказок по этапу использует карточки без поиска и фильтров; для библиотеки шаблонов этого недостаточно.

## Рекомендуемый следующий шаг

Перед реализацией UI и API нужно зафиксировать минимальный состав шаблона:

- обязательные поля: название, описание, тип, приоритет, длительность, теги, напоминания, каналы, срок от даты создания;
- участники: исполнитель, согласующие, наблюдатели;
- привязка: общий шаблон, шаблон для типа дела, шаблон для этапа дела;
- дополнительные поля по решению заказчика: чек-лист, файлы, срок согласования, оплата исполнителю.

После этого можно проектировать модель БД и компактный рабочий интерфейс списка шаблонов.
