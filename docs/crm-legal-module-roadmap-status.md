# Roadmap и статус реализации юридического модуля CRM

Дата фиксации состояния: 20.05.2026

Документ описывает, что уже сделано по ТЗ "Дела + Задачи + Календарь", что закрыто частично, что еще не закрыто и каким порядком это нужно доводить дальше.

Основной детальный план находится в `docs/crm-legal-module-implementation-plan.md`. Этот файл является управленческой сводкой и roadmap поверх детального плана.

## Короткий вывод

ТЗ пока не закрыто на 100%.

Закрыта большая базовая итерация: создан рабочий каркас юридического модуля, расширены дела, добавлены реестр дел, карточка дела, задачи, согласования, документы, часть уведомлений, календарь и отчеты первой очереди.

Не закрыты полностью: внешние интеграции с судами, Google/Яндекс календарями, финальная ролевая модель заказчика, полный audit-log критичных действий, управленческие журналы, расширенная аналитика, финальная бизнес-модель статусов заказ-наряда и полноценная библиотека шаблонов документов.

## Как отмечать статус

В документе используется простой формат отметок:

- `[x]` - сделано и проверено.
- `[~]` - сделано частично, нужна доработка.
- `[ ]` - не закрыто.
- `[?]` - нужен ответ заказчика или уточнение.

## Что уже сделано

### Backend и база данных

- Расширена существующая модель `ClientCase`, без создания параллельной сущности `LegalCase`.
- Добавлены поля и связи для юридического дела: реестровые данные, расширенная карточка, активность, документы, связанные лица, процессуальные сроки.
- Добавлены миграции для SQLite и PostgreSQL:
  - `AddClientCaseRegistryFields`;
  - `AddClientCaseDetailFields`;
  - `AddClientCaseDocuments`;
  - `AddClientCaseActivityFields`;
  - `AddClientCaseRelatedParties`;
  - `AddClientCaseProceduralDeadlines`.
- Обновлены snapshot-файлы EF Core для обеих БД.
- Расширен `CasesController`.
- Добавлен/расширен `CasesV2Controller` для новых сценариев дел.
- Доработан `TasksController` под новые сценарии задач и согласований.
- Добавлен `NotificationInboxController`.
- Расширен `ReportsController` под юридическую отчетность первой очереди и отчет-диагностику активности/неактивности дел.
- Добавлен storage-layer для документов дела: `CaseDocumentStorage`.
- Добавлены DTO для документов дела, связанных лиц, уведомлений и юридических отчетов.
- Добавлены сервисы синхронизации задач с делами и процессуальными сроками:
  - `ClientCaseTaskSyncService`;
  - `ClientCaseDeadlineTaskSyncService`.
- Добавлены сервисы уведомлений:
  - `NotificationService`;
  - `TaskJournalReminderNotificationService`;
  - `NotificationContracts`.
- Доработан scheduler для автозадач: `TaskJournalAutomationSchedulerService`; он создает контрольные задачи по неактивным делам и отправляет ответственному отдельное уведомление `Автоконтроль дела`.
- Правило активности дела унифицировано для фонового scheduler и ручной панели журнала задач: учитываются активные задачи, дата последней задачи, просмотр карточки ответственным, ручное подтверждение активности и выключатель `InactivityRemindersEnabled`.
- В реестр дел добавлены индикатор активности, фильтр `Активные / Нет движения` и колонка просмотра ответственным, которые считают последнее движение по задачам, ответственным просмотрам и ручному подтверждению активности.
- В настройках журнала задач добавлено управление автоконтролем дел: включение, период неактивности, лимит задач за запуск, резервный исполнитель, порог эскалации и ответственный за эскалации.
- В настройки журнала задач добавлена админская диагностика автоконтроля: текущее состояние, количество видимых кандидатов, количество эскалаций, созданные задачи за 7 дней, последнее срабатывание и выбранные ответственные.
- Backend добавил endpoint `GET /api/tasks/automation/case-control/diagnostics`, который считает диагностику с учетом прав видимости дел и данных `ObjectAuditEvents`.
- Для долгой неактивности добавлена эскалация: контрольная задача становится срочной, выбранный пользователь добавляется наблюдателем и получает уведомление вместе с исполнителем.
- Срабатывания автоконтроля дел фиксируются в `ObjectAuditEvents` по делу с действием `Автоконтроль`, ID созданной задачи, исполнителем и количеством дней без движения.
- Для дел добавлено исключение из автоконтроля: `InactivityRemindersEnabled` можно выключить в карточке/реестровом bulk-update, изменение попадает в историю и аудит.
- Добавлены расширения для фильтрации видимости данных и запросов:
  - `DataVisibilityQueryExtensions`;
  - `QueryExtensions`.
- Для дел добавлен отдельный раздел прав `cases`: реестр, карточка, документы дела, отчеты и переходы больше не завязаны на право `clients`, при этом для старых ролей работает fallback на прежние настройки клиентов.
- Финансовые отчеты первой очереди теперь применяют object-level видимость: денежные отчеты фильтруются по видимым платежам/счетам, отчеты по статусам счетов, актов и договоров используют права своих разделов.
- Backend отчетов проверяет право роли на раздел `reports`: прямой запрос к API теперь возвращает `403`, если отчеты скрыты для роли.
- Backend денежных выгрузок и печати журнала (`CSV`, `XLS`, `PDF`, печатная версия) теперь проверяет `CanExport` по разделу платежей, а `ICS` календаря задач - `CanExport` по разделу задач.
- Backend реестра дел теперь отдает `CSV` и печатную HTML-версию по текущим фильтрам, применяет object-level видимость дел и проверяет `CanExport` раздела `cases`.
- Массовые изменения в реестре дел теперь оставляют понятную причину в `ObjectAuditEvents`: в audit-log видно, что это была bulk-операция, какие поля массово менялись, и скрытые дела в нее не попадают.
- Подготовлены эксплуатационные документы:
  - `docs/crm-legal-module-user-guide.md` - инструкция по юридическому модулю для администратора, руководителя и исполнителя;
  - `docs/crm-legal-module-release-runbook.md` - порядок проверки, dry-run, выкладки, мониторинга и отката.

### Frontend

- Добавлен маршрут и экран реестра дел.
- В реестр дел добавлены серверные выгрузка `CSV` и печатная форма; кнопки скрываются, если у роли нет `CanExport` по делам.
- В реестр дел добавлены сохраненные представления фильтров: пользователь сохраняет текущие фильтры/сортировку/размер страницы, выбирает представление из списка и может удалить лишнее.
- В карточке дела финансовая вкладка получила расширенный платежный календарь: сводка по плану/оплате/остатку, группировка платежей по месяцам и явные статусы `Оплачено` / `Ожидает` / `Просрочено` / `Отменено`.
- В карточке дела добавлена судебная хронология: иск, ближайшее заседание, решение, процессуальные сроки и ручные проверки суда собираются в единую временную ленту.
- В карточке дела добавлена настройка `Скрыть от исполнителя`: такие дела исключаются из object-level видимости ограниченных пользователей, но остаются доступны ролям с полным обзором.

## Критерии, по которым ТЗ можно будет считать закрытым

ТЗ можно считать закрытым только когда выполнены все пункты ниже:

- все основные разделы работают в UI;
- backend является главным источником прав и видимости;
- пользователи не видят чужие данные без разрешения;
- дела, задачи, документы, сроки, уведомления и финансы связаны между собой;
- согласование задач имеет понятные статусы, сроки и уведомления;
- документы имеют шаблоны, версии и права;
- судебные события попадают в карточку дела и календарь;
- внешние интеграции либо реализованы, либо явно выключены feature flag с объяснением;
- уведомления можно читать, архивировать, фильтровать и открывать связанный объект;
- есть аудит критичных действий;
- есть отчеты и управленческие журналы;
- миграции проходят на SQLite и PostgreSQL;
- старые данные открываются в новых экранах;
- есть e2e и нагрузочные проверки;
- есть пользовательские инструкции;
- есть план отката.
