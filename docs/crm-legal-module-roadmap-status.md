# Roadmap и статус реализации юридического модуля CRM

Дата фиксации состояния: 19.05.2026

Документ описывает, что уже сделано по ТЗ "Дела + Задачи + Календарь", что закрыто частично, что еще не закрыто и каким порядком это нужно доводить дальше.

Основной детальный план находится в `docs/crm-legal-module-implementation-plan.md`. Этот файл является управленческой сводкой и roadmap поверх детального плана.

## Короткий вывод

ТЗ пока не закрыто на 100%.

Закрыта большая базовая итерация: создан рабочий каркас юридического модуля, расширены дела, добавлены реестр дел, карточка дела, задачи, согласования, документы, часть уведомлений, календарь и отчеты первой очереди.

Не закрыты полностью: внешние интеграции с судами, Google/Яндекс календарями, финальная ролевая модель по всем объектам, полный аудит, полный центр уведомлений, напоминания о неактивности, управленческие журналы, расширенная аналитика, e2e и нагрузочные проверки.

## Как отмечать статус

В документе используется простой формат отметок:

- `[x]` - сделано и проверено.
- `[~]` - сделано частично, нужна доработка.
- `[ ]` - не закрыто.
- `[?]` - нужен ответ заказчика или уточнение.

## Что закрыто не полностью и требует особого внимания

### 1. Права доступа и видимость данных

Сейчас это самый критичный риск перед боевым расширением.

Нужно:

- описать полную матрицу прав по разделам;
- разделить видимость на уровни:
  - только ответственный;
  - ответственный и его отдел;
  - все;
  - руководитель/администратор;
- применить это к:
  - клиентам;
  - физическим лицам;
  - юридическим лицам;
  - делам;
  - задачам;
  - счетам;
  - актам;
  - договорам;
  - платежам;
  - документам;
  - отчетам;
  - экспортам;
- обеспечить фильтрацию на backend, а не только скрытие кнопок на frontend;
- покрыть сценарии тестами по ролям.

### 2. Уведомления

Сейчас есть первая версия, но полноценный центр уведомлений еще не готов.

Нужно:

- добавить типы уведомлений;
- добавить фильтры;
- добавить архив;
- добавить удаление;
- добавить признак прочитано/непрочитано;
- добавить переход к задаче/делу/документу;
- добавить delivery log;
- добавить повтор отправки при ошибках;
- добавить настройки пользователя по типам уведомлений;
- определить, нужен ли web push.

### 3. Согласования задач

Базовая логика есть, но нужно завершить бизнес-процесс.

Нужно:

- добавить отдельные сроки согласования;
- добавить уведомления исполнителю после согласования;
- добавить уведомления согласующему при поступлении задачи;
- добавить прозрачный статус для исполнителя: `На согласовании`, `Согласовано`, `На доработке`;
- описать поведение при нескольких согласующих;
- добавить аудит всех решений согласующих.

### 4. Судебный блок

Пока это не полноценная внешняя интеграция.

Нужно:

- определить источники судов;

- добавить диагностику и повтор ошибок;

### 5. Документы и шаблоны

Первая версия документов есть, но workflow не полный.

### 6. Внешние календари

Пока есть внутренний календарь, но нет Google/Яндекс синхронизации.

Этого блока пока нет в полном виде.

## Ближайший рекомендуемый порядок работ

### Итерация 1. Закрыть права и безопасность

Цель: чтобы пользователи видели только свои данные, свой отдел или все - строго по настройкам.

Задачи:

- финализировать справочник отделов;
- привязать пользователей к отделам;
- расширить настройки ролей;
- применить object-level access к делам, задачам, клиентам, юрлицам, физлицам, счетам, актам, договорам и платежам;
- покрыть API тестами по ролям.

Почему это первым:

- заказчик уже несколько раз указывал, что пользователи видят лишние данные;
- это риск безопасности и доверия к системе;
- без этого нельзя безопасно расширять документы, отчеты и экспорт.

### Итерация 2. Довести задачи и согласования

Цель: сделать понятный lifecycle задачи для исполнителя и согласующего.

Задачи:

- формализовать статусы;
- добавить сроки согласования;
- добавить уведомления по каждому переходу;
- добавить аудит решений;
- проверить UI для исполнителя, согласующего и руководителя.

### Итерация 3. Довести уведомления

Цель: сделать полноценный центр уведомлений.

Задачи:

- типы уведомлений;
- прочитано/непрочитано;
- архив;
- удаление;
- фильтры;
- переход к объекту;
- настройки пользователя;
- delivery logs.

### Итерация 4. Довести документы и шаблоны

Цель: превратить текущую первую версию документов в рабочий document workflow.

Задачи:

- библиотека шаблонов;
- renderer;
- права на шаблоны;
- печатные формы;
- связь с задачами и судебными событиями;
- аудит документов.

### Итерация 5. Судебный блок

Цель: добавить события судов и синхронизацию.

Задачи:

- модель судебных событий;
- ручное добавление событий;
- календарь судебных событий;
- внешний provider-layer;
- логи синхронизации;

### Итерация 6. Внешние календари

Цель: синхронизация с Google/Яндекс после стабилизации внутреннего календаря.

Задачи:

- однонаправленная синхронизация первой очереди;
- конфликт-стратегия;

### Итерация 7. Отчеты, журналы и ввод в эксплуатацию

Цель: закрыть руководительский контур и подготовить модуль к боевому использованию.

## Критерии, по которым ТЗ можно будет считать закрытым

ТЗ можно считать закрытым только когда выполнены все пункты ниже:

- все основные разделы работают в UI;
- backend является главным источником прав и видимости;
- пользователи не видят чужие данные без разрешения;
- дела, задачи, документы, сроки, уведомления и финансы связаны между собой;
- согласование задач имеет понятные статусы, сроки и уведомления;
- документы имеют шаблоны, версии и права;
- судебные события попадают в карточку дела и календарь;
- внешние интеграции либо реализованы, либо явно выключены feature flag с объяснением;
- уведомления можно читать, архивировать, фильтровать и открывать связанный объект;
- есть аудит критичных действий;
- есть отчеты и управленческие журналы;
- миграции проходят на SQLite и PostgreSQL;
- старые данные открываются в новых экранах;
- есть e2e и нагрузочные проверки;
- есть пользовательские инструкции;
- есть план отката.

## Текущий практический статус

Текущий модуль уже можно рассматривать как рабочую основу для продолжения разработки.

Но показывать его заказчику как "ТЗ полностью закрыто" нельзя. Правильная формулировка:

> Базовый юридический контур реализован и проверен. Следующий фокус - права доступа, уведомления, согласования, документы, судебные события и финальная эксплуатационная подготовка.
