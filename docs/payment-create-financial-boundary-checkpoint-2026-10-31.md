## Подтверждённый дефект и реализация

`baseline-v1.trx`: 16 failed из 16 за 7 секунд. Обычный Create и commit create-attempts принимали новую оплату закрытого/компенсированного счёта по ID. Если прежний поиск номера не находил привязку, мог появиться отдельный несвязанный платёж с номером закрытого счёта. Тесты и хеши исходного кандидата сохранены отдельно.

Обычный Create теперь использует существующий VersionedPaymentWriteBoundary и BalanceApplicationLease: собственный чистый контекст, Serializable/SQLite BEGIN IMMEDIATE, реальный активный согласованный сотрудник, CanCreate/видимость, блокировки актуальных прав и общий инвариант зачтённой оплаты. Проверка номера/родителя выполняется после прежней нормализации через явно внутренний deferInvoiceValidation; это не клиентский параметр. Поведение V1/V2 по умолчанию не меняется: дополнительный флаг false, Scope сохраняет прежний callback и получает только делегат для точечных блокировок.

CreatePaymentCoreAsync больше не завершает чужую транзакцию и не отправляет уведомления внутри неё. Он выполняет прежние проверки обязательных полей/атрибуции и сохраняет финансовые данные, затем готовит AfterCommit. Обычный путь и первая успешная попытка проверяют CreditInvariant и сохраняют всё целиком: платёж, баланс, кассовые записи, переплату и пересчёт счёта. Уведомления идут после commit/dispose. Повторный запрос готовой попытки не входит в core, возвращает существующий canonical ID и не создаёт деньги/уведомления повторно, даже после последующей отмены счёта при сохранённом доступе.

ValidateNewPaymentFinancialScopeAsync блокирует выбранную основную запись и проверяет прежний IsCancellationProtectedAsync. Для неразрешённого номера проверяются только выбранный контрагент, направление, дело и год: canonical номер и прежние поля номера. На сервере выбираются максимум два различных InvoiceId, а не две строки: дубликаты основной записи не скрывают вторую группу. Видимость/однозначность проверяется одним ограниченным запросом. Несколько групп требуют явного выбора; закрытая/компенсированная группа отклоняется. Чужой/недоступный документ не раскрывается. Прежний алгоритм связывания и исторические связи не переписываются, активная неразрешённая ссылка автоматически не назначается этим guard.

При переносе переплаты в рассрочку проверяются видимость и блокировка выбранного взноса, отсутствие прежней компенсации и актуальный остаток. Выбранный ID закрепляется до присвоения ID новому платежу; последующее сохранение не выбирает другой взнос. Ошибка/конфликт откатывает действие до появления новой записи, не оставляет параллельный лишний аванс.

Попытки используют собственный PaymentCreateAttemptLease без вложения второго финансового lease. PostgreSQL-изоляция повышена до Serializable, строки сотрудника/роли/прав/доступа блокируются до повторной проверки; lock_timeout 2s, NOWAIT. Активность и согласование проверяются по БД. UUID, identity, expiry, seller/primary scope, отмена и tombstone сохраняются. Достоверный серверный abort COMMIT может вернуть конфликт; неизвестный транспортный исход не объявляется безопасным повторным созданием.

Запросы ограничены выбранными строками/индексированным владельцем и агрегатом; нет обхода всех платежей/истории или N+1 по списку счетов. Ранее дублировавшаяся проверка CanCreate удалена из core, потому что обе внешние границы проверяют её под собственным допуском. Схема, миграции, зависимости, frontend, старые суммы/номера/связи и установщик не менялись.

Явно выбранный положительный InvoiceId сохраняется до нормализации: если выбранный счёт отсутствует, удалён или стал недоступен и нормализатор потерял/заменил ID, возвращается NotFound до записи. Такой платёж не превращается в несвязанный аванс.
