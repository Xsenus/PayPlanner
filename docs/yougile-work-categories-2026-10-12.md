# PayPlanner — категории задач и доступы исполнителей

Дополнение к [общему Roadmap](yougile-roadmap-2026-10-12.md) и [подробным заданиям](yougile-execution-roadmap-2026-10-12.md). Сверка 12 октября: **38/38 карточек классифицированы, 100% охвата**. Это план распределения работы, а не повышение готовности продукта. Шесть больших планов остаются **21/81, 26%**; новый календарный объём **0/6, 0%**, ИИ **1/12, 8%**. Новых карточек сверх уже учтённой PAY-38 в повторно просмотренном списке чатов/доске не обнаружено; скрытые/архивные карточки полной серверной выгрузкой не проверялись.

## Сложность и готовность — разные признаки

Категория относится к **ближайшему полезному этапу**, а не ко всему ТЗ. Маленький UI-этап большого финансового задания не превращает весь финансовый блок в простой. Уже выпущенное не реализовывать заново. Перевод YouGile в «Тестирование» означает передачу опубликованной части/консультации на проверку, а не закрытие оставшегося ТЗ.

| Категория | Карточек | Что делать |
| --- | --- | --- |
| S — быстрый ограниченный UI-этап | 3 | Небольшой макет/карта действий поверх прежней логики; один компактный результат |
| M — несколько этапов интерфейса | 10 | Каркас, поля, состояние, права кнопок, адресные проверки; полноценная визуальная приёмка отдельно |
| H — сложная логика/данные/интеграция | 9 | Предметные решения, backend/контракты, финансовые/ролевые/конкурентные регрессии, безопасная БД |
| A — рабочая приёмка/диагностика | 8 | Две роли, конкретное устройство или внешний канал; код менять после доказанного дефекта |
| D — решение/входные данные | 7 | Уточнить правило, протокол или область пилота; независимую подготовку можно выполнить без production |
| Z — принято, нового задания нет | 1 | Сохранить регрессии; не создавать искусственную доработку |

Оценка «быстро» означает небольшой следующий этап с имеющимся API. Точную длительность определить после инвентаризации выбранного компонента; эти категории не являются обещанием срока всей карточки.

## Какие доступы нужны Claude Code

**C0 — репозиторий и frontend, без БД и рабочей системы.** Чтение исходников/сохранённых ТЗ/макетов, React/TypeScript/CSS, существующие компоненты, адресные frontend-тесты с mock API, lint/types/build. Backend не запускается, данные/миграции/permission keys/API contracts не меняются, секреты не требуются. Состояния loading/error/empty и отказ ролей моделируются в тестах. Результат — проверенный ограниченный UI-пакет и честно оставленная серверная/рабочая приёмка. Если API не покрывает требование, исполнитель фиксирует пробел и передаёт его отдельным блоком, не придумывает новый контракт незаметно.

**C1 — безопасная локальная тестовая БД/сервер.** Backend и обе стороны контракта, транзакции, миграции, финансовая логика/роли, fake adapters и синтетические данные. Это уже не режим «без БД». Нужны SQLite/PostgreSQL по требованиям изменения, почта/фон явно выключены. Копия production без санитизации запрещена. Доступ к VPS/рабочей БД для этой стадии не требуется.

**C2 — рабочая система или внешний согласованный пилот.** Реальные роли, устройство Анны, бот MAX, Google/Яндекс, банковский sandbox/разрешённое чтение, бухгалтерская сверка. Только такой исполнитель может подтвердить фактическую доставку/полный живой сценарий. Секреты не помещаются в промпт, Git или YouGile. Подготовленный C0/C1 пакет не объявляется прошедшим C2.

## Очередь небольших пакетов для Claude без БД и production

Начинать можно после чтения источников/макета. Не требуется получать SQL/VPS credentials. Пакеты ограничены C0; отсутствие возможности C2 не блокирует подготовку проверенного кода, но оставляет приёмку открытой.

1. **C0-01 — PAY-19/6, карта журнала.** Сохранить поиск/фильтры/колонки/sort/views, составить old → new actions, затем компактный каркас верхней области без изменения handler/API. Результат: карта + UI layout + 390/1024/1440. PAY-15 accepted не переписывать.
2. **C0-02 — PAY-21, общий каркас дела.** Прочитать последний макет, разместить существующие вкладки и правое меню ЕФРСБ/Почта/Финансы. Контент тяжёлых вкладок загружается по требованию. Результат: готовый каркас с прямым переходом/empty/error/loading, без новых backend endpoint.
3. **C0-03 — PAY-23/25, по одной секции.** После 02 перенести действующие кнопки/поля документов или событий, без changes storage/time rules. Не брать две секции одним бесконтрольным переписыванием. Результат: ограниченный макет одной секции, сохранённые actions и UI-тесты.
4. **C0-04 — PAY-32, полный inventory полей.** Сопоставить каждое старое личное поле и новое место, затем «Дополнительную информацию» свернуть по требованию заказчика. Скрытое значение не стирается при save. Если текущий API не позволяет безопасный partial update — отдельный C1 блок, не обход.
5. **C0-05 — PAY-20, карта двух форм.** Сначала таблица каждой кнопки/условия/permission, затем по одному визуальному блоку. Общие business handlers не переписывать; подтвердить одинаковое место/смысл старой и новой формы. Полное включение дизайна остаётся C2.
6. **C0-06 — PAY-29, мессенджер.** Inventory списка заказчика относительно существующего PAY-1 → макет основных областей. Optional calls/export/неподтверждённые функции отметить решениями, а не имитировать кнопками. Черновики/непрочитанное/скролл и доступ сохраняются.

После этих пакетов можно брать отдельные C0 части PAY-22/24/26/27/28, затем UI существующих API заявок/регистра/банка. Любое затрагивание денежного расчёта, protected data, роли, API contract или миграции повышает доступ/риск до C1 и требует соответствующего gate.

Если нужен server change или business decision, подробно зафиксируй отдельный блок и продолжай независимую часть. В конце обнови профильный roadmap, приложи карту действий/полей, результаты проверок и непройденную C2 приёмку. Не публикуй YouGile без новой команды.

## Передача C1/C2

Для H брать один согласованный сквозной сценарий, не всю карточку сразу: оплата → заявка → одно дело; первая выдача → immutable snapshot; один банк → все страницы выписки; признание одной подтверждённой операции → корректировка; одна cancelled task → hide/restore во всех календарях. C1 подтверждает invariants на synthetic, C2 подтверждает живой результат. Решение владельца и доступы фиксируются до зависимой работы. Завершённый небольшой пакет не закрывает больший пункт, пока весь его DoD не выполнен.
