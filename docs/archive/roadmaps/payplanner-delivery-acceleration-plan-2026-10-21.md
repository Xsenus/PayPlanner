## Как проверять во время работы

1. Перед изменением назвать конкретный результат и затрагиваемую область. Не начинать большой соседний блок ради небольшого дефекта.
2. В ходе разработки запускать связанные unit/component/controller/service проверки и нужные статические проверки. Для денег, доступа, данных и контрактов сразу проверять существенные ошибки, границы, права и регрессии.
3. Собрать несколько связанных исправлений в законченный пакет выпуска. Не ждать готовности всех банковских, судебных или визуальных задач одновременно.
4. На окончательном кандидате выполнить **один полный применимый барьер**: frontend для frontend, backend для backend, обе стороны при изменении общего поведения/контракта, специализированные проверки по реально затронутым границам. Документация не требует тестирования приложения.
5. Сохранить ревизию, входы, артефакты, полный каталог тестов и результаты. Успешный полный прогон повторно использовать для commit/push/установки/передачи при совпадении влияющих входов. При изменении причины проверить затронутое и заново квалифицировать окончательный кандидат.

Полностью откладывать все проверки до выпуска нецелесообразно: маленький адресный тест быстрее обнаруживает ошибку, чем разбор множества накопленных отказов. Полные проверки, покрытие, финансовые/защитные утверждения и обязательный CI сохраняются. Политика уже закреплена в `AGENTS.md`; здесь описано практическое применение.

## Как ускорить сами тесты

| Очередь | Изменение | Условие готовности |
|---|---|---|
| Первое | Добавить воспроизводимый отчёт времени по классам/методам/подготовке, используя TRX; хранить агрегаты без рабочих данных | Видны самые дорогие шаги и сравнение до/после; измерение не требует отдельного полного прогона |
| Первое | Проверить дорогие fixtures и запуск синтетического backend; расширить использование существующих PostgreSQL/SQLite migrated templates там, где миграция не является предметом теста | Каждый изменяющий данные сценарий имеет собственную одноразовую БД; повторное выполнение всех миграций при обычном старте устранено там, где безопасно; clean/upgrade/restart проверки сохранены |
| Следующее | Балансировать четыре части по сохранённой длительности, сохраняя атомарные группы и точный каталог | Те же ID и строки параметров, нет потерь/дублей, проверка manifest/union остаётся обязательной; предсказуемый fallback для новых тестов |
| Следующее | Проверить изоляцию портов, файлов, окружения, БД и процессов, затем измерить ограниченный параллельный запуск | Нет общей изменяемой БД, конфликтов и утечек; количество работников определяется доступной памятью; изменение каталогизатора учитывает коллекции/группы |
| Затем | Привести выбор областей CI к правилам AGENTS: документация, frontend, backend, общие изменения | Общая конфигурация/зависимости/неопределённая область включают расширенный барьер; затронутые обязательные jobs не теряются из-за path filters; итоговый gate явно подтверждает полноту |

Шаблоны БД уже существуют — создавать второй механизм не нужно. Вспомогательный синтетический backend сейчас выполняет `MigrateAsync()` при старте: это кандидат для измерения, а не доказательство, что все миграции можно пропустить. Планировщик сейчас отвергает xUnit collections; простое включение параллельности без доработки учёта групп небезопасно.

По исходному замеру четыре независимых работника теоретически сократили бы запуск примерно до длины самой долгой части — 1 часа 47 минут, без учёта накладных расходов и конкуренции. Это **историческая оценка, не достигнутый результат**. На ILYA установлено 32 ГБ RAM, но свободный объём существенно меняется из-за общей нагрузки. Текущий локальный runner ограничивает запуск одним или двумя работниками по фактически доступной памяти. В pipeline 08b полный backend выполнялся с одним работником; wall четырёх частей составил **4:22:30.791**. При старте было примерно 8.72 ГиБ свободной RAM; измеренные ресурсы всего интервала приведены в отчёте о внедрении.

Безопасная работа с реальной БД требует изоляции тестовых данных; подход описан в [документации EF Core](https://learn.microsoft.com/en-us/ef/core/testing/testing-with-the-database). Ограничения параллельности и групп — в [документации xUnit](https://xunit.net/docs/running-tests-in-parallel). Использовать тот же движок БД означает синтетическую одноразовую БД, а не разрушающие тесты на производственной копии `payplanner`. Все локальные backend-процессы запускаются с `BackgroundServices__Enabled=false` и `Email__Enabled=false`.

4. Срочная массовая смена типа учёта задач — самостоятельный следующий выпуск. Это средняя задача с высоким финансовым риском: нужны правила для выставленных/оплаченных/завершённых работ, построчные права, история и частичные отказы.
5. Остальные самостоятельные средние сценарии; затем единый финансовый журнал, смысл дат/план-факт, большие банковские, судебные и интеграционные блоки, разбитые на независимые выпуски.

Активное нарушение сохранности денег или доступа поднимается выше обычной очереди независимо от сложности. Неясное бизнес-решение не должно удерживать независимый готовый результат. Не обещать заказчику целый модуль по готовности одной кнопки.

Оптимизацию тестов тоже делать ограниченными этапами: сначала убрать повторные прогоны и измерить тяжёлую подготовку, затем улучшить её и распределение работы. Большая перестройка всей тестовой системы не должна задерживать первые короткие исправления. Фактическое ускорение подтверждается замерами на тех же сценариях и ресурсах, а не уменьшением числа проверок.
