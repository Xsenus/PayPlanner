- Перед началом любой задачи по этому направлению обновлять этот файл: переводить пункт в `[~]`, фиксировать дату, риск и ожидаемую проверку.

- Не брать задачи из `docs/archive/roadmaps/`, если пользователь прямо не попросил открыть конкретный архивный roadmap.
- Не переписывать уже работающие модули ради соответствия формулировкам ТЗ, если текущая реализация закрывает сценарий пользователя.
- Пользовательские изменения сопровождать записью в `backend/AppReleases/releases.json`.
- Если roadmap будет закрыт, принят или поставлен на паузу пользователем, перенести его в `docs/archive/roadmaps/`.

## Этап 1. Судебная синхронизация и судебные источники

Цель: довести судебный блок от текущей СУДРФ-интеграции до сценария из ТЗ: выбор источника, поиск карточки суда, привязка к делу, периодическая проверка, журнал изменений и уведомления.

- `[ ]` Инвентаризировать текущий судебный контур: СУДРФ-провайдер, справочник судов, карточка дела, судебные события, история, планировщик, настройки и тесты.
- `[decision]` Получить от заказчика список обязательных судебных источников: СУДРФ, КАД/арбитраж, ГАС Правосудие, мировые судьи, региональные сайты или другой перечень.
- `[decision]` Подтвердить юридически допустимый способ получения данных для каждого источника: официальный API, публичная страница, ручная ссылка, импорт файла или отказ от автоматизации.
- `[ ]` Спроектировать общий интерфейс провайдера судебной синхронизации, чтобы новые источники добавлялись как адаптеры, а не отдельные ветки логики в карточке дела.
- `[ ]` Реализовать мастер поиска и привязки судебной карточки: параметры поиска, список найденных вариантов, подтверждение пользователем, сохранение источника и внешнего идентификатора.
- `[ ]` Добавить или расширить провайдеры по подтвержденным источникам.
- `[ ]` Синхронизировать найденные изменения с карточкой дела: заседания, статусы движения, судья, зал, документы, процессуальные сроки и история.
- `[ ]` Настроить уведомления по судебным изменениям: новое заседание, перенос, решение, новый срок, ошибка синхронизации.
- `[ ]` Покрыть backend-тестами успешную синхронизацию, отсутствие изменений, ошибку источника, дубли событий и права доступа.
- `[ ]` Покрыть frontend-тестами мастер привязки, ручную проверку, журнал синхронизации и отображение ошибок.
- `[acceptance]` Проверить на реальных судебных карточках заказчика минимум по одному делу на каждый обязательный источник.

Definition of done:

- Пользователь может найти судебную карточку из CRM или привязать ее вручную.
- Изменения из источников попадают в дело, журналируются и не создают дублей.
- Ошибки источников видны администратору и не ломают карточку дела.

## Этап 2. SMS и MAX messenger

Цель: закрыть неподтвержденные каналы коммуникаций из ТЗ, не ломая существующие уведомления in-app, Web Push, email и Telegram.

- `[decision]` Подтвердить, нужен ли SMS как обязательный production-канал или достаточно оставить его как необязательный будущий канал.
- `[decision]` Выбрать SMS-провайдера, получить API-доступы, лимиты, стоимость, требования к подписи отправителя и шаблонам.
- `[ ]` Добавить backend-абстракцию канала SMS в существующую систему уведомлений, с выключенным состоянием без настроек.
- `[ ]` Добавить настройки SMS-отправителя для администратора и диагностику готовности канала.
- `[ ]` Добавить пользовательские предпочтения по SMS там, где SMS разрешен бизнес-правилами.
- `[ ]` Добавить шаблоны SMS для срочных событий: срок дела, судебное событие, задача, клиентское согласование.
- `[ ]` Покрыть SMS unit/integration-тестами: выключенный канал, невалидные настройки, успешная отправка, ошибка провайдера, журнал доставки.
- `[decision]` Подтвердить, что под "MAX messenger" заказчик имеет в виду мессенджер MAX, и получить доступ к документации/API/боту.
- `[decision]` Определить сценарии MAX: только уведомления, отправка документов клиенту, переписка по делу или авторизация клиента.
- `[ ]` Реализовать MAX как отдельный интеграционный канал только после подтверждения API и сценариев.
- `[acceptance]` Проверить SMS/MAX на тестовых получателях заказчика и зафиксировать ограничения доставки.

Definition of done:

- Канал можно включить/выключить без риска для остальных уведомлений.
- Ошибки отправки видны в журнале доставок.
- В CRM понятно, какие события уходят в SMS или MAX.

## Этап 3. Переписка по делу и внешнее согласование заказ-наряда

Цель: довести карточку дела до сценариев ТЗ по обсуждению в рамках дела и согласованию заказа клиентом.

- `[ ]` Проверить текущую переписку дела: модель сообщений, права, уведомления, история, связь с пользователями.
- `[ ]` Добавить вложения к сообщениям переписки, если текущая модель хранит только текстовые записи.
- `[ ]` Связать вложения переписки с документами дела без дублей и с понятным источником файла.
- `[ ]` Добавить уведомления участникам дела о новом сообщении и вложении.
- `[ ]` Добавить frontend-тесты переписки: отправка сообщения, вложение, ошибка загрузки, права доступа.
- `[decision]` Подтвердить способ клиентского согласования заказ-наряда: публичная ссылка, личный кабинет, email-подтверждение, SMS-код или только внутреннее согласование.
- `[decision]` Уточнить, какие данные заказа можно показывать клиенту вне CRM: услуги, суммы, сроки, персональные данные, документы.
- `[ ]` Реализовать внешний или внутренний сценарий согласования заказ-наряда по выбранному способу.
- `[ ]` При согласовании заказ-наряда создавать событие истории дела и предлагать создание счета/договора/акта по текущей логике.
- `[ ]` Добавить аудит согласования: кто согласовал, когда, через какой канал, какая версия заказа была согласована.
- `[acceptance]` Проверить согласование на реальном сценарии клиента заказчика.

Definition of done:

- Переписка по делу хранит текст, вложения и историю без потери прав доступа.
- Заказ-наряд можно согласовать выбранным заказчиком способом, а результат виден в карточке дела.

## Этап 4. Финансовые сценарии аннулирования, зачета и ограничений

Цель: закрыть тонкие сценарии DOCX по счетам, актам, договорам, рассрочкам, возвратам и зачётам.

- `[ ]` Сверить текущие сценарии аннулирования счета с ТЗ: полный счет, счет с рассрочкой, частично оплаченные графики, оплаченные платежи, неоплаченные остатки.
- `[ ]` Проверить и при необходимости доработать мастер выбора действия с полученными деньгами: возврат, оставить авансом, зачесть в другой счет.
- `[ ]` Реализовать или доработать зачет полученной суммы в другой счет с явной связью между старым счетом, новым счетом и денежной операцией.
- `[ ]` Проверить цепочку аннулирования: счет, платежи/ПКО/РКО, акты, календарь платежей, финансы дела, история.
- `[ ]` Проверить договоры: запрет создания новых счетов по расторгнутому договору, проверка неоплаченных счетов, соглашение о расторжении, история.
- `[ ]` Проверить акты: корректировочный акт, связь с договором и счетом, предупреждения по суммам выполненных услуг.
- `[ ]` Добавить недостающие backend-тесты по финансовым цепочкам.
- `[ ]` Добавить frontend-тесты мастеров аннулирования/зачета, чтобы пользователь не мог выбрать конфликтующий вариант.
- `[acceptance]` Проверить на локальной копии БД сценарии: рассрочка, частичная оплата, аннулирование, возврат, зачет, договор с фиксированной суммой.

Definition of done:

- Деньги не теряются между счетами, платежами, кассой, банком и делом.
- Каждый финансовый поворот оставляет понятную историю и audit.
- Пользователь видит предупреждение до действия, которое меняет финансовую цепочку.

## Этап 5. Статусы дел, внесудебные сценарии и шаблоны задач

Цель: закрыть описанную в ТЗ логику разных типов дел: внесудебное производство, подготовка к суду, судебное производство, апелляция/кассация.

- `[ ]` Сверить текущие статусы дела, этапы и судебные вкладки с типами дел из ТЗ.
- `[decision]` Утвердить справочник этапов по типам дел: внесудебное, подготовка к суду, первая инстанция, апелляция, кассация, исполнение.
- `[ ]` Добавить подсказки или шаблоны задач по этапам дела, если их нет в текущей реализации.
- `[ ]` При смене этапа предлагать создание типовых задач и процессуальных сроков.
- `[ ]` Для внесудебных дел оставить судебную вкладку в безопасном режиме без лишних обязательных полей.
- `[ ]` Проверить, что уведомления по внесудебным делам идут только по внутренним задачам и срокам.
- `[acceptance]` Проверить с юристом заказчика реальные этапы на 3-5 типах дел.

Definition of done:

- Пользователь не вынужден заполнять судебные поля там, где дело внесудебное.
- При переходе к суду CRM помогает создать нужные задачи, сроки и судебную привязку.

## Этап 6. Приемка, стабильность и выпуск

Цель: не просто реализовать пробелы, а довести их до проверяемого production-состояния.

- `[ ]` Для каждого этапа добавить записи в "Что нового" человеческим языком.
- `[ ]` Проверить кодировку измененных файлов и русские тексты в UI/API.
- `[ ]` Прогнать релевантные frontend unit/integration тесты по измененным экранам.
- `[ ]` Прогнать релевантные backend-тесты по измененным контроллерам, сервисам и моделям.
- `[ ]` Проверить сценарии на локальной БД, включая миграции и существующие данные.
- `[ ]` Проверить права доступа: пользователь без прав не видит и не вызывает новые действия прямым API.
- `[ ]` После push дождаться GitHub Actions, исправить ошибки при необходимости и проверить деплой.
- `[acceptance]` Проверить production health, frontend entry point, service worker при изменении уведомлений и статус VPS-сервиса.
- `[acceptance]` Получить ручное подтверждение заказчика по SMS/MAX, судебной синхронизации и клиентскому согласованию.

Definition of done:

- Все новые сценарии покрыты тестами и проверены на локальной БД.
- GitHub Actions и deploy завершились успешно.
- В "Что нового" описаны видимые изменения.
- Roadmap обновлен: проценты, закрытые пункты, оставшиеся решения и acceptance.

## Открытые решения заказчика

- `[decision]` Какие судебные источники являются обязательными для первой версии расширенной синхронизации.
- `[decision]` Можно ли использовать парсинг публичных страниц судов, если официального API нет.
- `[decision]` Нужен ли SMS в production и какой провайдер использовать.

- `[decision]` Как клиент должен согласовывать заказ-наряд: ссылка, кабинет, email, SMS-код или внутренний менеджер.
- `[decision]` Какие данные дела и заказа можно показывать клиенту вне авторизованной CRM.
- `[decision]` Нужны ли типовые шаблоны задач для каждого этапа дела или достаточно ручного создания.
- `[decision]` Какие финансовые действия при аннулировании должны быть обязательными, а какие только доступными.
- `[decision]` Кто со стороны заказчика принимает каждый блок на реальных данных.

## Риски

- `[!]` Судебные источники могут не иметь стабильного API; сроки зависят от подтвержденного способа интеграции.
- `[!]` SMS и MAX требуют внешних доступов, тарифов, технической документации и тестовых получателей.
- `[!]` Внешнее клиентское согласование может потребовать отдельной модели безопасности, если клиент работает без аккаунта CRM.
- `[!]` Финансовые сценарии аннулирования затрагивают деньги, кассу, банк, счета, акты, договоры и отчеты; доработка должна идти маленькими проверяемыми шагами.
