## Реализованное поведение

CompanyBankAccountBindingService — вызываемый серверный сервис без HTTP-маршрутов. Bind/revoke владеют короткой Serializable-транзакцией через существующий DocumentSellerLease. Грязный tracker и чужая транзакция не принимаются и не поглощаются. Сначала удерживаются пользователь/роль и проверяются текущие IsActive/IsApproved/admin и AuthTokenVersion через существующие помощники, затем реестр/компания/подключение, выбранный банковский и связанный денежный счёт. Автор берётся из БД, не из имени claim. На отказе/отмене транзакция откатывается; новые подтверждения не остаются в переиспользуемом контексте.

Явные локальный и банковский ID должны принадлежать текущей собственной активной компании, реквизиты — совпадать по прежним нормализаторам номера/БИК/валюты, источник — быть известным Provider/ExternalAccountId. Архив профиля счёта, скрытый/закрытый банковский счёт и недоступное подключение не создают подтверждение. Некорректная существующая денежная ссылка отклоняется. Несколько совпадающих локальных/банковских кандидатов допускают только явный выбор, без слияния ручных MoneyAccount. Произвольное поле банковского ID в JSON не читается как authority. Отзыв закрывает только свою строку подтверждения, включая случай закрытия/изменения банковского источника; финансовые ссылки не переписываются.

Версия сверки v2 включает происхождение банка, активные подтверждения и максимальный исторический ID собственной компании. Exact known-result replay проверяет полный ID/источник/кортеж и прежнюю базовую версию; повтор bind после revoke старой версией отклоняется. Повтор revoke прежнего ID не затрагивает более новое подтверждение. Это не решение прежней общей задачи keyless unknown commit. Историю подтверждений нельзя автоматически удалять или реактивировать, иначе нарушится защита от повторного использования старой версии; будущая очистка требует отдельного сохраняемого поколения.

Новый CompanyBankAccountBindingProfileGuard подключён к LegalEntitiesController.Update, SaveImportedChangesAsync общего merge, ApplyCounterpartyAsync табличного/1С-импорта и RestoreLegalEntitySnapshotAsync отката. У активного подтверждения нельзя удалить/сменить стабильный локальный ID и известный кортеж. Название, основной/архивный признаки и посторонний ещё не настроенный счёт не переносят связь на другой ID. При отсутствии подтверждений прежние некорректные legacy-списки этим guard не нормализуются и не отвергаются. Новая связь/отзыв в PostgreSQL делает no-op UPDATE компании, сохраняя все бизнес-поля: старый Serializable-снимок писателя не пропустит новую связь. Общий merge читает/блокирует компании партиями по 16, а не двумя запросами на каждую.

Парные миграции `20261101000824_IndexCompanyBankBindingHistory` и `20261101000834_IndexCompanyBankBindingHistoryPostgreSql` добавляют только два неуникальных индекса истории. Прежние partial unique, FK и CHECK сохранены; backfill, исправления номеров/сумм и переносы документов отсутствуют. Индекс (LegalEntityId, Id) обслуживает последний исторический ID и FK компании; обычный BankConnectionAccountId — отозванную историю банковского FK. Чтения кандидатов по-прежнему конечные, общие группы передаются один раз; исторические строки для версии не материализуются.
