## Проблема клиента

Сейчас при запросе переноса срока по задаче непонятно, что происходит дальше: кто получает запрос, где он находится, как постановщик должен его обработать и как исполнитель должен объяснить причину переноса.

## Целевое решение

Запрос переноса срока должен стать отдельным управляемым процессом задачи:

- исполнитель запрашивает перенос только через окно с обязательной причиной;
- постановщик задачи получает заметное принудительное окно по центру экрана;
- запрос также виден в разделе "Согласования" и в карточке задачи, чтобы его можно было найти позже;
- постановщик может согласовать перенос с выбором новой даты и времени либо отказать с комментарием;
- все действия фиксируются в истории задачи, уведомлениях и счетчиках.

Выбран отдельный объект `TaskJournalDeadlineChangeRequest`; контракт, статусы, правила создания/согласования/отказа и API первого этапа описаны в `docs/task-deadline-change-model-design-2026-07-09.md`.

Запрос теперь сохраняется в отдельной таблице `TaskJournalDeadlineChangeRequests` со статусом `pending`, фиксирует инициатора, постановщика, текущий срок, запрошенный срок и причину; пустая причина и повторный активный запрос по одной задаче отклоняются.
- `[x]` Добавить backend API для согласования переноса с выбором новой даты и времени. Постановщик задачи или администратор может согласовать pending-запрос, указать утвержденную дату и время, обновить срок задачи, закрыть запрос статусом `approved` и оставить системную запись истории с деталями решения.
- `[x]` Добавить backend API для отказа с обязательным или рекомендуемым комментарием. Постановщик задачи или администратор может отклонить pending-запрос только с причиной отказа; срок задачи не меняется, запрос закрывается статусом `rejected`, а в истории появляется системная запись с деталями решения.
- `[x]` Сделать запрос доступным в карточке задачи и в истории задачи, чтобы было понятно, где он находится и кто должен действовать. В старой и новой карточке задачи добавлен блок "Запросы переноса срока" со статусом, инициатором, текущим сроком, запрошенным сроком, причиной и ответственным за решение; backend отдает список запросов только для видимых пользователю задач.
- `[x]` Добавить отображение активных запросов в разделе "Согласования" или отдельном фильтре согласований задач. Раздел "Согласования" теперь запрашивает активные pending-запросы переноса срока вместе со списком задач, показывает задачи с такими запросами постановщику или администратору и помечает их бейджем "Запрос переноса срока".
- `[x]` Сделать принудительное центральное окно для постановщика: "У вас запросили перенос срока по задаче", с кнопками согласования и отказа. В разделе "Согласования" постановщику или администратору автоматически показывается центральное окно с задачей, инициатором, текущим сроком, запрошенным сроком, причиной и кнопками "Согласовать перенос" / "Отказать"; отказ требует комментарий, согласование применяет запрошенный исполнителем срок.
- `[x]` При согласовании показывать выбор новой даты и времени, по умолчанию предлагать дату из запроса исполнителя. В центральном окне решения добавлено поле "Новый срок задачи": оно автоматически заполняется датой из запроса исполнителя, но постановщик может выбрать другую дату и время перед нажатием "Согласовать перенос".
- `[x]` При создании запроса показывать исполнителю всплывающее текстовое окно для причины переноса и не отправлять запрос без причины. В старой и новой карточке задачи кнопка "Запросить перенос" теперь открывает центральное окно причины; отправка доступна только после заполнения текста причины.
- `[x]` Настроить уведомления и счетчики для постановщика, исполнителя и наблюдателей после создания, согласования и отказа. Добавлены отдельные типы уведомлений для входящего запроса переноса срока, согласования и отказа; входящий запрос помечается как требующий действия, а решения отправляются исполнителю и наблюдателям через центр уведомлений, toast/web push и пользовательские настройки каналов.
- `[x]` Покрыть сценарии тестами: создание, повторный запрос, согласование, отказ, права доступа, уведомления, старая и новая карточка задачи. Backend-сценарии покрывают создание, запрет при отключенной настройке, повторный pending-запрос, согласование, отказ, права доступа и уведомления; frontend-сценарий проверяет запрос переноса из старой и новой карточки задачи.
- `[x]` Проверить вручную на локальной БД: исполнитель создает запрос, постановщик видит окно и раздел "Согласования", принимает/отказывает, срок и история обновляются ожидаемо. Приемочный smoke на временной локальной SQLite-БД подтвердил применение миграции `AddTaskDeadlineChangeRequests`; backend-сценарии подтвердили создание, видимость запроса для постановщика, согласование, отказ, изменение срока, запись истории и уведомления, а frontend-сценарии подтвердили окна и обе карточки задачи.

## Definition of Done

- Запрос переноса срока нельзя "потерять": он виден в карточке задачи, в согласованиях и в принудительном окне постановщика.
- Без причины запрос не отправляется.
- При согласовании срок задачи реально меняется и фиксируется в истории.
- При отказе срок не меняется, исполнитель получает понятное уведомление.
- Старая и новая карточка задачи работают одинаково.
- Добавлена запись в "Что нового".
