## Подтверждённая исходная граница

В `CasesV2Controller` генерация шаблона отдельно вызывает `_caseDocumentStorage.SaveAsync`. Общий `SaveGeneratedCaseDocumentAsync` используется пятью путями: печатная форма заказ-наряда, создание счёта, акта, договора и сводка судебного события при синхронизации. Все шесть путей проходят прежний атомарный файловый helper, но пока не создают managed intent/binding и не проверяют обязательные копии.

Подключённый managed upload уже имеет durable intent, проверку SHA/size/generation, capacity reserve, copy gate, retirement, case lock и точный published receipt. Однако его durable consumer вызывает `PersistUploadAsync`: история и audit различают загрузку/новую версию, а не генерацию. Простая передача HTML как FormFile не сохраняет смысл аудита и восстановления этих путей.

Дополнительная сверка1 октября: `UploadAsync` возвращает invalid при заданном DocumentKey, если его первой версии ещё нет (`latest == 0`). Generated пути заранее задают стабильный DocumentKey, поэтому их первая версия требует отдельного доверенного server-generated режима, а не снятия ограничения с публичной upload ветки. Повтор с тем же request identity должен читать/возобновлять прежний intent до нового рендеринга; сравнение повторно сформированного HTML с прежним SHA даст ложный conflict из-за часов или изменившегося источника. Нужны fingerprint исходного запроса и frozen server metadata/bytes, разные для разных типов операции; старые intents должны оставаться читаемыми.

Судебная синхронизация к моменту вызова generated helper уже имеет другие tracked source изменения (участники, данные дела и счётчики). Нельзя без проверки заменить её callback на upload-specific Reload/SaveChanges, потерять эти изменения или зафиксировать их в чужой публикации. Сверка transaction calls контроллера не показала общей финансовой транзакции вокруг CreateInvoice/Act/Contract; точные rollback/visibility границы должны быть доказаны новыми baseline tests, а не предположены по существующему файловому helper.

Создание счёта сохраняет финансовые записи до вызова общего generated helper; акт и договор также имеют отдельные доменные операции. Их успешные ответы включают финансовый объект и DocumentId. Отложенная публикация только файла не обеспечивает целостность всей операции. Судебная синхронизация дополнительно обновляет SourceType/данные источника и счётчики результата; её нельзя считать обычной ручной загрузкой.

Сверка финансовой генерации 1 октября: методы `BuildWorkOrderInvoiceDocumentHtml`, `BuildWorkOrderActDocumentHtml` и `BuildWorkOrderContractDocumentHtml` не используют ID новой финансовой записи в HTML. Байты можно сформировать до её сохранения, зафиксировав номер, даты, строки, суммы и время генерации. Однако ID входит в окончательные DocumentKey и OriginalFileName (`invoice-{id}`, `act-{id}`, `contract-{id}` и соответствующие имена HTML). `ProductStorageBindingService` и `ProductStorageReader` строго сопоставляют LogicalName с именем доменного документа. Поэтому подготовка байтов сама по себе не решает публикацию: требуется доверенное назначение окончательного ключа/имени и владельца в общей короткой транзакции, с сохранением точного receipt и проверенных копий. Ослаблять проверку имени или предварительно показывать финансовую запись ради получения ID нельзя. Номер до публикации также требует проверки конкурентного резервирования; текущее вычисление номера по уже созданным финансовым записям не доказывает отсутствие конфликта двух ожидающих попыток. Эти условия ещё не реализованы и не проверены baseline-тестами.

Клиентские API генерации сейчас не передают стабильный идентификатор попытки. Шаблон доступен в CaseDetailPage и CaseModal; операции заказ-наряда вызываются в CaseDetailPage. Повтор запроса должен отличаться от намеренного создания новой версии и сохранять уже сформированные байты, включая время и значения исходных данных.

Сверка замороженных финансовых данных 1 октября: `CreateInvoiceFromWorkOrder` создаёт Invoice/Payment, ссылки на дело, исполнителей и строки, нормализует платёж и переводит наряд в invoice_created до отдельного вызова файлового helper. Durable финансовая попытка должна сохранять этот согласованный набор, а не только HTML и сумму. `CreateActFromWorkOrder` исключает строки по SourceKey уже действующих актов; ожидающие попытки ещё не участвуют в этой проверке. При переносе публикации нужна конкурентная проверка/резервирование этих SourceKey, чтобы разные ожидающие попытки не актировали одну услугу дважды; отменённые/прекращённые акты сохраняют текущую семантику. `CreateContractFromWorkOrder` сохраняет сроки, открытый срок, описание и связи с клиентом/юрлицом/делом. Все три операции используют отдельный SaveChanges до generated helper; тестовый baseline проверяет отсутствие этой преждевременной видимости при двух copies. Эти требования пока не реализованы; нельзя подменять их сериализацией только печатных байтов или потерять существующие связи при повторе.
## Решение владельца и выбранное поведение

1 октября пользователь делегировал выбор: «не знаю, сделай как лучше или оба варианта». Выбран один целостный режим: **финансовая запись и её документ публикуются вместе только после готовности обязательных копий**. При сбое хранения незавершённая финансовая операция не показывается как успешно созданная. Durable попытка и проверенные материалы сохраняются для точного повтора; после потери ответа повтор не создаёт второй счёт/акт/договор.

Это согласованное требование, а не уже реализованное поведение. Альтернативный режим «финансовая запись сразу, документ позже» не вводится. Конкретный безопасный порядок получения доменных идентификаторов, фиксации попытки и короткой финансовой транзакции требуется спроектировать и проверить; provider I/O нельзя удерживать внутри этой транзакции. Сроки хранения, обязательные destinations/copies и иные решения родительского плана не подменяются этим выбором.

## Подготовка HTTP template consumer — история этапа

Расширенная регрессия ключей начата на неизменных compiled outputs; наблюдение session53574 подтверждает активный testhost34288, итоговый TRX пока отсутствует. Код до завершения проверки не меняется. Сверка следующих call sites уточнила необходимые гарантии:

- Существующий GenerateDocumentTemplate загружает case includes, resolve/render и сразу сохраняет legacy document/history/audit/notifications; обе кнопки UI не передают stable request identity. Baseline24 уже доказал отсутствие managed binding/copy gate, повторять этот исходный baseline без новых assertions не нужно.

- Generic resume должен передавать HTTP consumer доверенный сохранённый source вместе с полями intent, необходимыми для сопоставления case/key/file/type/status/content type. Проверки source выполняются до provider read, перед публикацией и при подтверждении receipt. Ни заново выбранный шаблон, ни CasesEdit отдельно не доказывают исходную связь.
