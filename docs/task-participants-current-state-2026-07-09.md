# Аудит участников задачи: согласующие и наблюдатели

Дата: 9 июля 2026.

Связанный roadmap: `task-participants-approvers-observers-roadmap-2026-07-09.md`.

## Что проверено

- `backend/Models/Requests/UpsertTaskJournalItemRequest.cs`: создание и редактирование задачи принимают массив `participants`.
- `backend/Models/TaskJournalParticipant.cs`: участник хранит роль, пользователя, имя, email, порядок, статус согласования, резолюцию и дату ответа.
- `backend/Controllers/TasksController.cs`: создание и обновление задачи проходят через `ResolveParticipantsAsync`.
- `src/components/Tasks/TaskJournal.tsx`: старая и новая карточка используют общий `form.participants`, `addParticipant`, `removeParticipant`, `normalizeParticipants`.
- `src/utils/taskJournalStore.ts` и `src/services/api.ts`: frontend payload передает `participants` в общий API создания/редактирования задачи.

## Текущее состояние backend

Backend уже поддерживает несколько участников:

- роли нормализуются по справочнику `assignee`, `approver`, `observer`;
- согласующий обязан быть выбран из пользователей системы;
- наблюдатель может быть пользователем системы;
- основной исполнитель добавляется автоматически, если его нет в массиве участников;
- дубли удаляются по ключу `role + userId` или `role + displayName`;
- при создании и редактировании задача сохраняет участников как коллекцию `TaskJournalParticipant`;
- при чтении задачи участники возвращаются в DTO в порядке роль -> `sortOrder` -> `id`.

Backend-контракт в целом подходит для целевого multi-select. Риск находится не в схеме данных, а в том, что frontend не во всех окнах одинаково показывает и редактирует выбранных участников.

## Текущее состояние старой карточки

Старая карточка задачи уже ближе всего к требованию клиента:

- есть секция "Участники и согласование";
- роли `Исполнители`, `Согласующие`, `Наблюдатели` показаны отдельными колонками;
- выбранные участники отображаются списком под ролью;
- у выбранного участника есть кнопка удаления;
- добавление идет через выпадающий список доступных пользователей;
- при повторном открытии существующей задачи `form.participants` заполняется из `state.task.participants`.

Что нужно проверить и усилить на следующих пунктах:

- сохранение нескольких согласующих и наблюдателей после редактирования;
- отсутствие потери выбранных участников при смене исполнителя;
- корректность удаления участника, у которого уже есть `id` из базы;
- сохранение очереди согласования и статусов при редактировании без перезапуска согласования.

## Текущее состояние новой карточки

В новом окне задачи есть общий state и добавление участников, но UI не доведен:

- блок "Участники" показывает только строки-счетчики "Согласующие" и "Наблюдатели";
- выбранные согласующие и наблюдатели не отображаются под кнопками/селектами;
- удалить выбранного согласующего или наблюдателя из нового окна нельзя;
- добавление выполняется через `select`, но после выбора пользователь видит только изменение счетчика;
- при редактировании существующей задачи данные в state приходят, но пользователь не видит список выбранных людей.

Именно это совпадает с жалобой клиента: "при добавлении ты не видишь кого добавил", "удалить тоже нельзя", "корректировать тоже нельзя".

## Текущее состояние payload

Перед сохранением frontend вызывает `normalizeParticipants(form, assignees)`:

- добавляет основного исполнителя, если его нет среди участников;
- дополняет `displayName`, `name`, `email`, `sortOrder`, `approvalStatus`, `resolution`;
- удаляет дубли по роли и пользователю/имени;
- отправляет итоговый массив в `createTaskJournalItem` или `updateTaskJournalItem`.

Потенциальный риск: при исправлении нового окна нельзя заводить отдельный state для согласующих и наблюдателей. Нужно переиспользовать общий `form.participants`, иначе старая и новая карточка снова разойдутся.

## Рекомендованный порядок доработки

1. Вынести компактный повторно используемый блок выбора участников для ролей `approver` и `observer`.
2. Подключить его в новое окно вместо счетчиков без списка.
3. Оставить старую карточку на том же общем поведении или заменить ее внутренние колонки на общий блок, если это не сломает дизайн.
4. Добавить тесты на создание, редактирование, удаление и повторное открытие в обоих режимах карточки.
5. Проверить backend-сохранение несколькими участниками через существующий `UpsertTaskJournalItemRequest`.

## Вывод

Первый пункт roadmap закрыт аудитом: backend уже умеет хранить и нормализовать несколько согласующих и наблюдателей, старая карточка частично реализует требуемый список, а новая карточка требует основной UI-доработки — видимого списка выбранных людей с удалением и сохранением через общий `form.participants`.
