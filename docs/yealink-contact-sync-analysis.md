# Синхронизация контактов PayPlanner с телефонами Yealink

## Контекст задачи

Сейчас критичный для работы сценарий выглядит так:

- в компании используется IP-телефония;
- на рабочих местах стоят телефоны Yealink;
- раньше контакты для телефонов обслуживались через amoCRM;
- на REG.RU размещён файл и/или веб-страница, из которых телефоны получают контакты;
- при входящем звонке на аппарате должен отображаться клиент;
- теперь источник данных должен переехать в PayPlanner;
- синхронизируются только физические лица;
- если контрагент является организацией, синхронизация всё равно должна идти по физическому лицу, привязанному к этой организации.

## Что уже есть в PayPlanner

### 1. Базовая сущность для физического лица уже существует

В проекте физическое лицо уже хранится как `Client`:

- имя: `Client.Name`
- основной телефон: `Client.Phone`
- email: `Client.Email`
- связь с юрлицом: `Client.LegalEntityId`

Это хорошая стартовая точка, потому что именно `Client` соответствует требованию "синхронизируются физлица".

### 2. Организации уже связаны с физлицами

Юрлица уже хранятся отдельно как `LegalEntity`, а привязанные к ним люди идут через `Client.LegalEntityId`.

Это совпадает с требованием:

> если это организация, то синхронизация всё равно происходит по физлицу, привязанному к организации.

### 3. Ограничение текущей модели

Сейчас для клиента в модели есть только один нормализованный телефон `Client.Phone`.

При этом в интерфейсе уже используются расширенные контактные данные, и часть из них хранится не как отдельные нормализованные записи, а внутри расширенного профиля клиента. Для телефонии это слабое место, потому что:

- нет явного списка телефонов клиента в БД;
- нет признака "этот номер нужно отдавать на телефоны";
- нет явного правила, какой номер основной;
- нет отдельной телефонной книги как целевой проекции для Yealink.

## Что официально умеют Yealink

### Вариант 1. Remote Phone Book

Yealink официально поддерживает удалённую телефонную книгу по URL.

Из документации и админ-гайдов:

- можно подключать удалённые телефонные книги через URL;
- для Remote Phone Book используется XML-структура с `Menu.xml` и `Department.xml`;
- в автопровижининге есть параметры вида `remote_phonebook.data.X.name` и `remote_phonebook.data.X.url`;
- есть функция `Match Remote Phone Book`, которая позволяет при входящем звонке искать имя абонента в удалённой книге;
- у функции есть интервал обновления локального кэша.

Практический смысл:

- PayPlanner может отдавать Yealink-совместимый XML по HTTPS;
- телефоны будут брать книгу напрямую из CRM;
- можно разбить книгу по группам, например `Все контакты`, `Контакты организаций`, `Частные клиенты`.

### Вариант 2. LDAP

Yealink официально поддерживает LDAP-директорию.

Из официальной документации:

- LDAP поддерживает поиск контактов;
- есть режим `LDAP Lookup For Incoming Call`;
- для входящего звонка могут использоваться LDAP-атрибуты, связанные с телефонными номерами.

Практический смысл:

- можно поднять LDAP-источник и отдать его телефонам как корпоративную директорию;
- это хороший вариант для централизованного поиска и больших справочников;
- но он заметно сложнее в разворачивании и сопровождении, чем обычный HTTP/XML feed.

### Вариант 3. Local Directory через provisioning

Yealink также умеет работать с локальной телефонной книгой через XML-файл `contact.xml`:

- телефон может скачивать локальные контакты с сервера;
- по отдельным сценариям возможно и выгружать локальные контакты обратно;
- файл можно раздавать по модели или даже по MAC-адресу аппарата.

Практический смысл:

- подходит, если нужны разные списки по отделам, сотрудникам или аппаратам;
- но это хуже как основной источник, если нужна единая централизованная книга.

## Какой вариант лучше для вашей задачи

### Рекомендуемый вариант: Remote Phone Book по HTTPS из PayPlanner

Это лучший основной сценарий для вас.

Почему:

1. Он максимально близок к тому, как вы уже жили с REG.RU и внешним файлом.
2. Не нужно поднимать отдельный LDAP-сервер.
3. Его можно реализовать прямо внутри текущего backend PayPlanner.
4. Его проще сопровождать и диагностировать.
5. Можно оставить REG.RU только как временный или резервный канал, но не как источник истины.

### Когда стоит смотреть в сторону LDAP

LDAP имеет смысл, если:

- контактов станет очень много;
- потребуется полноценный корпоративный поиск по каталогу;
- нужно будет интегрировать одну и ту же директорию сразу с несколькими системами, а не только с Yealink.

На текущем этапе LDAP я бы рассматривал как вторую фазу, а не как стартовое решение.

## Как лучше хранить контакты в CRM

### Не делать Excel или файл источником истины

Excel, выгрузка на REG.RU или ручное редактирование веб-страницы не должны быть главной базой контактов.

Источник истины должен быть один:

- физлица в PayPlanner;
- плюс отдельные признаки, определяющие, что именно попадает в телефонию.

### Рекомендуемая модель хранения

Нужна отдельная нормализованная сущность для телефонной книги, а не только чтение из `Client.Phone`.

Минимально:

- `PhoneDirectoryEntry`
- `PhoneDirectoryEntryPhone`

Или, если хотите жёстко привязать к существующим сущностям:

- `ClientPhoneContact`
- `ClientPhoneContactNumber`

### Что должно быть в записи телефонной книги

Для каждой записи:

- `ClientId`
- `LegalEntityId` при наличии
- `DisplayName`
- `OrganizationName` при наличии
- `IsEnabledForPhoneSync`
- `IsPrimaryForLegalEntity`
- `Priority`
- `Comment`
- `LastExportedAt`
- `LastSyncError`

Для каждого номера:

- `RawPhone`
- `NormalizedPhone`
- `DisplayPhone`
- `Type` (`mobile`, `work`, `home`, `other`)
- `IsPrimary`
- `IsEnabledForCallerId`

### Почему это лучше одного общего списка в заметках

Потому что сразу появляются:

- нормальный источник для телефонии;
- независимость от того, как отображаются контакты в UI;
- возможность держать несколько номеров на одного человека;
- контроль, какие номера реально участвуют в caller ID.

## Как хранить физлиц и контакты организаций

### Правильная логика

В системе должна быть одна общая "телефонная книга", но с разными источниками:

1. Физлица без привязки к организации.
2. Физлица, привязанные к организации.

При этом синхронизация всё равно идёт только по физлицу.

### Что делать с организациями

Для организаций я бы не отправлял в Yealink отдельную карточку юрлица как телефонный контакт.

Вместо этого:

- у организации могут быть один или несколько контактных людей;
- один или несколько из них могут быть помечены как допустимые для синхронизации;
- у одного из них можно поставить флаг "основной для caller ID".

### Как это будет выглядеть на телефоне

Примеры отображаемого имени:

- `Иванов Иван Иванович`
- `Иванов Иван Иванович — ООО Ромашка`
- `Петров Пётр — ЭлитПраво / Клиент`

Я бы рекомендовал именно второй вариант для контактов организаций:

- сначала имя физлица;
- потом короткое имя организации.

Так оператор сразу понимает, кто звонит и к какой компании относится контакт.

## Как должна работать синхронизация

### Источник

Источником должна быть выборка из PayPlanner:

- только активные физлица;
- только записи с валидным номером;
- только те, у кого включён флаг синхронизации;
- для организаций только по привязанным физлицам.

### Направление

Основное направление синхронизации должно быть односторонним:

- `PayPlanner -> Yealink`

Почему:

- телефоны не должны становиться источником данных;
- ручные правки на аппаратах трудно контролировать;
- при одностороннем потоке намного проще поддерживать порядок.

### Частота

Нужно два режима:

1. Автоматическая синхронизация:
   - при изменении клиента/контакта;
   - при изменении привязки к организации;
   - при включении/выключении синхронизации.

2. Плановая пересборка:
   - раз в 5-15 минут
   - либо по расписанию cron/HostedService

### Что реально пересобирать

Не нужно "толкать" обновление в каждый телефон.

Лучше:

- CRM пересобирает XML/JSON-представление;
- телефоны получают его по URL и обновляют кэш по своей логике;
- в админке остаётся кнопка "Пересобрать телефонную книгу сейчас".

## Как лучше реализовать на стороне PayPlanner

### Backend

Нужен отдельный модуль телефонии, например:

- `Services/PhoneDirectory`
- `Controllers/PhoneDirectoryController.cs`

Основные задачи backend:

1. Сбор телефонной книги из клиентов.
2. Нормализация номеров.
3. Формирование Yealink-совместимого XML.
4. Отдача по защищённому URL.
5. Логирование сборки и ошибок.

### Рекомендуемые endpoint'ы

Пример:

- `GET /api/phonebook/yealink/menu.xml`
- `GET /api/phonebook/yealink/all.xml`
- `GET /api/phonebook/yealink/organizations.xml`
- `GET /api/phonebook/yealink/private-clients.xml`

Или ещё лучше:

- `GET /phonebook/yealink/{token}/menu.xml`
- `GET /phonebook/yealink/{token}/department/{key}.xml`

### Безопасность

Лучше не делать полностью публичный URL без защиты.

Рекомендую:

- длинный токен в URL;
- whitelist по IP АТС/VPS при возможности;
- отдельный read-only токен для телефонии;
- журнал доступа к endpoint'ам;
- ограничение только на `GET`.

## Как лучше обрабатывать номера

### Нормализация обязательна

Чтобы caller ID работал стабильно, номера нужно приводить к единому виду.

Минимум:

- сохранять исходный номер;
- сохранять номер только в цифрах;
- отдельно формировать канонический формат для телефонии;
- учитывать российские варианты `+7`, `8`, `7`.

### Что лучше использовать

У вас уже есть интеграция с очисткой телефона через DaData в backend.

Поэтому лучший путь:

1. На вводе чистить и нормализовать номер.
2. В записи телефонной книги хранить уже нормализованный вариант.
3. При экспорте при необходимости формировать несколько пригодных для сопоставления представлений.

### Важное замечание

Если АТС передаёт номер в одном формате, а в CRM он хранится в другом, caller ID может не совпасть.

Поэтому до запуска нужно обязательно проверить:

- в каком виде номер приходит на аппарат;
- в каком виде номер лежит в текущем REG.RU-источнике;
- в каком виде Yealink делает совпадение на вашей прошивке.

## Что делать с REG.RU

### Лучшее решение

Сделать REG.RU необязательным.

То есть:

- источником становится PayPlanner;
- телефоны читают XML прямо с `crm.elitpravo.com` или `api.elitpravo.com`;
- REG.RU больше не нужен для ручного редактирования контактов.

### Переходный режим

Если нужно мягко перейти:

1. PayPlanner начинает собирать XML.
2. Старый файл на REG.RU ещё остаётся резервным.
3. На 1-2 аппаратах тестируется новый URL.
4. После проверки новые URL раскатываются на все телефоны.

### Если очень нужно оставить REG.RU

Тогда PayPlanner может:

- по кнопке или по расписанию формировать файл;
- выгружать его на хостинг;
- REG.RU будет только местом публикации, но не местом ручного управления.

Но это слабее, чем прямой feed из CRM.

## Какой UI нужен в CRM

### В карточке физлица

Нужно добавить блок телефонии:

- участвует ли контакт в синхронизации;
- основной ли это контакт для организации;
- какое отображаемое имя пойдёт в Yealink;
- список телефонов с типами;
- какой номер используется для caller ID;
- результат последней синхронизации.

### В карточке организации

Нужно добавить блок:

- привязанные физлица;
- кто из них синхронизируется на телефоны;
- кто основной;
- быстрый переход к их карточкам.

### В настройках

Отдельный раздел:

- `Интеграции -> IP-телефония`

Что там настраивать:

- включение синхронизации;
- режим `Remote Phone Book` / `LDAP` / резерв;
- токен URL;
- базовые группы;
- период пересборки;
- лог последней сборки;
- кнопка "Пересобрать сейчас";
- тестовый предпросмотр XML;
- список исключённых контактов с причинами.

## Рекомендуемый сценарий реализации

### Этап 1. Быстрый и безопасный запуск

Сделать:

- нормализованную проекцию телефонной книги из физлиц;
- экспорт Yealink Remote Phone Book по HTTPS;
- настройки синхронизации;
- ручной rebuild;
- лог сборки;
- тестовую группу аппаратов.

### Этап 2. Доработка бизнес-правил

Сделать:

- несколько телефонов на физлицо;
- явный выбор основного номера;
- отображаемое имя для организаций;
- фильтры по активным/неактивным;
- исключения из синхронизации.

### Этап 3. Расширение при необходимости

Дальше можно добавить:

- LDAP;
- разные книги по отделам;
- разные книги по аппаратам;
- персональные книги;
- выгрузку резервного XML-файла.

## Что я рекомендую как итоговое решение

### Коротко

Лучшее решение сейчас:

1. Не продолжать жить на Excel как на главной базе.
2. Источником истины сделать PayPlanner.
3. Синхронизировать только физлиц.
4. Для организаций синхронизировать привязанных физлиц.
5. Реализовать Yealink Remote Phone Book по HTTPS как первый этап.
6. Добавить нормализованную телефонную проекцию, а не собирать всё из случайных полей.
7. Оставить LDAP как возможную вторую фазу, если потребуется.

### Почему это лучший путь

- самый дешёвый по внедрению;
- максимально близок к вашей текущей привычной схеме;
- не требует отдельной LDAP-инфраструктуры;
- хорошо ложится в текущую архитектуру PayPlanner;
- позволяет потом вырасти в более сложную модель без переделки всего заново.

## Что нужно уточнить перед реализацией

Чтобы внедрение прошло без сюрпризов, нужно заранее собрать:

1. Точный URL текущего источника на REG.RU.
2. Пример текущего файла, который реально читает телефон.
3. Модель и прошивку хотя бы одного Yealink-аппарата.
4. Экспорт конфигурации одного телефона или скриншоты настроек Remote Phone Book / LDAP.
5. В каком формате АТС передаёт номер на телефон при входящем звонке.
6. Нужна ли единая книга для всех аппаратов или разные книги по сотрудникам/отделам.
7. Нужны ли внутренние контакты сотрудников в той же телефонной книге.
