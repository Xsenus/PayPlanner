# Roadmap: модернизация карточки задачи

Статус: `[~]` в работе. На 24 июня 2026 пользователь подтвердил старт разработки по этому roadmap; создана ветка `feature/task-card-new-window`.

Последнее обновление: 24 июня 2026.

Документ фиксирует задачу по обновлению карточки задачи. К реализации перешли после прямого решения пользователя начать разработку в новой ветке.

## Цель

Сделать карточку задачи проще, компактнее и понятнее для ежедневной работы юристов и сотрудников, не меняя бизнес-логику задач без отдельного согласования.

Основная проблема от заказчика: текущая карточка задачи кажется сотрудникам сложной, из-за этого они неохотно заполняют задачи. Нужно обновить конструктив, добавить визуальные акценты, уменьшить лишние действия и оставить привычную логику работы там, где она уже используется.

## Принципы

- `[ ]` Не переделывать текущую форму карточки задачи в рамках первой реализации: старая форма должна остаться рабочей и доступной.
- `[ ]` Делать новую карточку как отдельное окно/компонент, чтобы можно было безопасно переключаться между старым и новым интерфейсом.
- `[ ]` Добавить глобальную настройку выбора формы карточки задачи: старое окно или новое окно.
- `[ ]` Переключать старую и новую форму должен администратор или пользователь с отдельным правом доступа к настройке; выбранный вариант применяется для всех пользователей.
- `[ ]` Если меняется бизнес-логика задач, правила сохранения, права, уведомления, статусы, файлы, комментарии или API, одинаково обновлять старую и новую форму, пока обе формы существуют.
- `[ ]` Сохранять текущую бизнес-логику задач, статусов, сроков, исполнителей, напоминаний, файлов и комментариев, если изменение не согласовано отдельно.
- `[ ]` Делать карточку компактной: основные действия должны быть видны без лишней прокрутки.
- `[ ]` Не перегружать форму обязательными полями для простых задач.
- `[ ]` Использовать цветовые акценты для статуса, приоритета, меток и важных действий.
- `[ ]` Поддержать два режима: компактный для быстрой работы и расширенный для подробной карточки.
- `[ ]` Проверять изменения на реальных сценариях: создание задачи, редактирование, завершение, комментарии, файлы, подзадачи, уведомления.

## Оценка Макета И Уточнения От Заказчика

На 24 июня 2026 заказчик передал набор скриншотов с предлагаемым новым видом карточки задачи и пояснил, что текущая карточка слишком сложна для ежедневной работы сотрудников, особенно юристов. Основная идея макета правильная: оставить существующую логику задач, но перестроить экран так, чтобы самые частые действия были видны сразу, а редкие настройки не мешали созданию и закрытию задачи.

- `[ ]` Новую карточку реализовать рядом со старой формой, без переписывания текущего окна.
- `[ ]` Старое окно оставить как fallback на случай регрессии, сложного сценария или необходимости быстро откатить новый UI через настройку.
- `[ ]` Добавить административную настройку, которая включает новое окно карточки задачи для всех пользователей CRM.
- `[ ]` Доступ к переключателю ограничить правами администратора или отдельным правом на системные настройки.
- `[ ]` При выключенной настройке все пользователи продолжают работать в старой карточке без изменения привычного поведения.
- `[ ]` Макет компактного вида принять как ориентир первой версии: широкая рабочая область слева, быстрая колонка параметров справа, верхняя панель действий, чат-комментарии снизу.
- `[ ]` Для создания новой задачи предусмотреть чистое начальное состояние: выбор проекта/дела, пустое название с понятным placeholder, "Без статуса", пустое описание и недоступный результат.
- `[ ]` Верхнюю строку использовать для контекста задачи: выбор проекта, дела, контакта и организации должен быть заметен до заполнения остальных полей.
- `[ ]` Если для сохранения текущей логики нужны отдельные действия "Дело" или "Контакт", размещать их сверху рядом с контекстом, а не в середине рабочей области.
- `[ ]` При выборе дела подтягивать связанные контакт и организацию автоматически только там, где это однозначно. Если вариантов несколько, показывать выбор пользователю.
- `[ ]` В правой колонке отдельно показать тип задачи, если он используется текущей моделью задач.
- `[ ]` В правой колонке оставить понятное действие подтверждения/сохранения изменений, если текущая логика карточки требует явного применения статуса или параметров.
- `[ ]` Правую колонку строить как набор коротких раскрывающихся строк: статус, исполнитель, дата, подзадачи, файлы, приоритет, тип задачи, пользовательские поля.
- `[ ]` Цветовые акценты использовать не как украшение, а как рабочие подсказки: статус, срок, приоритет, метки, подтверждение завершения и важные уведомления должны считываться быстрее.
- `[ ]` В первой версии не менять бизнес-логику задач без отдельного решения: новая карточка должна переиспользовать текущие статусы, права, файлы, комментарии, подзадачи, уведомления и связи с делами.
- `[ ]` Убрать визуальные дубли: если загрузка файла доступна через общий блок файлов, не добавлять вторую равнозначную кнопку загрузки в другом месте карточки.
- `[ ]` Поле "Результат" показывать или активировать только при завершении задачи. До завершения пользователь не должен вводить результат заранее.
- `[ ]` При завершении задачи результат должен становиться активным в карточке или открываться отдельным окном, как в текущей логике завершения.
- `[ ]` Для выбора исполнителя, согласующих и наблюдателей использовать компактное выпадающее окно с поиском и выбором галочками там, где допускается несколько сотрудников.
- `[ ]` В выпадающем окне участников показывать короткий список подходящих сотрудников и поиск; выбранных сотрудников подставлять в кнопку или строку поля с возможностью удалить и заменить.
- `[ ]` Выбранных участников можно показывать строками под соответствующей кнопкой в правой колонке, если чипы не помещаются компактно.
- `[ ]` Для даты использовать календарь с временем начала и длительностью в одном рабочем блоке, чтобы не разносить расписание по нескольким местам.
- `[ ]` Поведение даты взять из старой формы задачи: календарь, под ним время, ниже длительность.
- `[ ]` Если в текущей карточке есть отдельное действие "Расписание", сохранить его рядом с датой или внутри блока даты, чтобы пользователь не искал планирование в другом месте.
- `[ ]` Контрагента, если он нужен текущей логике задачи или комментариев, показывать как короткий выпадающий список, а не отдельную длинную форму.
- `[ ]` Подзадачи показывать прямо в карточке, но финально подтвердить модель: полноценные связанные задачи или легкий чек-лист.
- `[ ]` Меню дополнительных действий держать в верхней панели: добавить обложку, дублировать, сделать подзадачей, архив, удаление. Опасные действия должны иметь подтверждение.
- `[ ]` Упоминания через `@` должны открывать понятный список с вкладками, чтобы пользователь быстро нашел сотрудника, команду, проект, задачу или документ.
- `[ ]` Во всплывающем окне упоминаний предусмотреть вкладки по макету: "Везде", "Команда", "Проекты", "Задачи", "Документы"; количество рядом с вкладкой показывать только если оно не шумит.
- `[ ]` Добавление меток и выбор приоритета делать через короткие выпадающие списки с цветными чипами.
- `[ ]` Выбранные метки должны удаляться через крестик прямо на чипе.
- `[ ]` Пользовательские поля показывать компактным блоком, с возможностью добавить поле только при наличии права.
- `[ ]` Быстрые напоминания в верхней панели оставить как действие конкретной задачи, но не смешивать их с персональными правилами уведомлений.
- `[decision]` Решение по переключению старой и новой карточки: глобальная административная настройка, выбранный вариант отображается у всех пользователей.
- `[decision]` Рекомендация по настройкам уведомлений: профиль пользователя, а не роль. Уведомления зависят от личного режима работы, поэтому роль может создать конфликт между сотрудниками.
- `[ ]` После переноса персональных настроек уведомлений в профиль убрать их из карточки задачи, чтобы карточка не выглядела перегруженной.

Предварительная оценка: направление макета хорошее и соответствует цели упростить работу. Главный риск не в дизайне, а в объеме первой версии. Чтобы не растянуть задачу, сначала нужно собрать отдельное новое окно с текущей логикой, результатом при завершении, быстрыми параметрами, файлами и комментариями. Старую форму не трогать, кроме общих изменений логики, которые должны работать одинаково в обеих формах. Расширенный вид, профильные настройки уведомлений и спорные модели подзадач можно вести отдельными этапами.

## Сверка По Скриншотам

- `[ ]` В верхней части окна показать хлебные крошки: дело или проект, доска/раздел, название задачи и номер задачи, если он есть.
- `[ ]` Оставить кнопку закрытия окна в привычном верхнем правом углу.
- `[ ]` В верхней панели показать только короткие иконки действий, а текст использовать там, где без него действие непонятно, например "Запустить".
- `[ ]` После копирования ссылки показать короткое всплывающее подтверждение.
- `[ ]` Для переключения компактного/расширенного режима показать выбранный вариант галочкой в меню, если будет персональный режим внутри нового окна.
- `[ ]` Статус в правой колонке показывать как заметную строку с цветным маркером и быстрым выбором.
- `[ ]` Если для применения изменений используется отдельная зеленая кнопка подтверждения, она должна быть визуально связана с редактируемым параметром и не путаться с завершением задачи.
- `[ ]` В правой колонке под основными быстрыми параметрами показать метаданные: метки, дата создания, создатель, проект/дело.
- `[ ]` Метаданные внизу правой колонки должны быть компактными и не конкурировать с основными рабочими действиями.
- `[ ]` Для комментариев, файлов, таймера и активности показывать вкладки со счетчиками, если счетчик помогает понять объем данных.
- `[ ]` В комментариях показывать разделители дат, например "Сегодня", "Вчера", если такая группировка есть в текущем интерфейсе.
- `[ ]` В активности группировать события по датам и показывать время события, если это уже поддерживается текущей логикой.
- `[ ]` В блоке файлов предусмотреть переключатель списка/плитки только если он реально нужен; иначе не добавлять лишнее управление в первую версию.
- `[ ]` Для пустой карточки показывать действия "Добавить описание" и "Добавить результат" так, чтобы результат был неактивен до завершения задачи.
- `[ ]` Если в макете есть отдельный блок "Контрагент", проверить, является ли это текущим полем задачи или частью комментариев/связей, и не добавлять новое поле без подтверждения.
- `[ ]` Если в макете есть оранжевый индикатор/иконка рядом с правой колонкой, уточнить его смысл перед реализацией: уведомление, важность, изменение или другое состояние.

## Область Работ

### 1. Анализ Текущей Карточки

- `[ ]` Найти текущие компоненты создания и редактирования задачи.
- `[ ]` Зафиксировать текущую форму как legacy-окно, которое остается рабочим после добавления новой карточки.
- `[ ]` Описать текущие поля, обязательность, зависимости и права доступа.
- `[ ]` Проверить, какие поля реально используются в журнале задач, календаре, уведомлениях, делах и карточках клиентов.
- `[ ]` Зафиксировать, какие действия нельзя ломать: создание, изменение статуса, назначение исполнителя, перенос срока, завершение, файлы, комментарии, напоминания.
- `[ ]` Составить карту API и моделей, которые затрагивает карточка задачи.
- `[ ]` Выделить общую бизнес-логику, которую должны использовать обе формы, чтобы не появлялись расхождения.

Definition of done:
- `[acceptance]` Есть список всех текущих полей и действий карточки.
- `[acceptance]` Понятно, какие изменения являются только UI, а какие затрагивают бизнес-логику.
- `[acceptance]` Понятно, какие части остаются в legacy-окне, а какие относятся только к новому окну.

### 2. Новый Компактный Вид

- `[ ]` Сделать новый компактный вид карточки задачи как отдельное окно, не изменяя текущую форму.
- `[ ]` Для новой задачи сохранить понятные пустые состояния: "Введите название задачи", "Добавить описание", "Без статуса", отсутствие исполнителя, отсутствие даты и недоступный результат.
- `[ ]` Разместить сверху путь/контекст: дело, доска или источник задачи.
- `[ ]` В верхнем контексте показать выбранный проект/дело и дать быстрый переход к выбору, если задача создается без привязки.
- `[ ]` Сделать крупное поле названия задачи.
- `[ ]` Оставить описание задачи в основной области.
- `[ ]` В правую колонку вынести быстрые параметры: статус, исполнитель, дата, подзадачи, файлы, приоритет, тип задачи, пользовательские поля, метки, создатель и проект/дело.
- `[ ]` Быстрые параметры в правой колонке должны открывать popover/dropdown рядом с выбранной строкой, без перехода в отдельную длинную форму.
- `[ ]` Для статуса и быстрых параметров предусмотреть понятное сохранение или мгновенное сохранение по текущим правилам, чтобы пользователь видел, когда изменение применено.
- `[ ]` Сделать блок комментариев похожим на чат: поле ввода, кнопка отправки, прикрепление файла, упоминания.
- `[ ]` Нижнюю часть карточки не перегружать полями, которые пользователь заполняет редко; редкие настройки держать в правой колонке или меню.
- `[ ]` Проверить, что карточка помещается на типовых экранах без избыточной пустоты.

Definition of done:
- `[acceptance]` Сотрудник может быстро создать или открыть задачу и понять, что нужно заполнить в первую очередь.
- `[acceptance]` Основные параметры задачи доступны без поиска по длинной форме.

### 3. Расширенный Вид

- `[ ]` Добавить расширенный режим карточки.
- `[ ]` В расширенном режиме разделить карточку на две рабочие зоны: слева поля задачи, справа комментарии, файлы, таймер и активность.
- `[ ]` В правой зоне расширенного режима показать вкладки: комментарии, файлы, таймер, активность, с количественными счетчиками там, где они есть.
- `[ ]` В левой зоне расширенного режима показать основные поля строками: статус, исполнитель, дата, приоритет, метки, пользовательские поля и описание.
- `[ ]` Добавить действие "Добавить поле" в расширенном режиме только если текущие пользовательские поля и права это поддерживают.
- `[ ]` Добавить переключатель "Компактный вид" / "Расширенный вид".
- `[decision]` Решить, нужен ли персональный переключатель компактного/расширенного режима внутри нового окна, если само включение новой карточки задается глобально администратором.
- `[ ]` Запоминать последний выбранный режим после согласования места хранения.

Definition of done:
- `[acceptance]` Пользователь может переключаться между компактным и расширенным видом без потери данных.
- `[acceptance]` Выбранный режим не мешает текущим сценариям создания и редактирования задачи.
- `[acceptance]` Глобальное переключение старого и нового окна не зависит от персонального компактного/расширенного режима.

### 4. Связь Задачи С Объектами CRM

- `[ ]` Добавить удобный выбор связанного дела, клиента/контакта и организации.
- `[ ]` Поддержать сценарий "Выберите проект" при создании задачи, чтобы пользователь сразу видел, к чему относится задача.
- `[ ]` Если заказчик подтвердит, добавить сверху отдельные быстрые кнопки или селекторы "Дело", "Контакт", "Организация", чтобы не нарушать текущую логику задач.
- `[ ]` Если дело выбрано, автоматически подтягивать доступные связанные данные, где это безопасно.
- `[ ]` Если организация или клиент выбирается вручную, не перезаписывать выбор без подтверждения пользователя.
- `[ ]` Если организация определяется по делу автоматически, показать это пользователю как выбранное значение, а не скрытую подстановку.
- `[ ]` Если в задаче нужен контрагент, связать его с выбранным делом/контактом/организацией и дать заменить вручную через выпадающий список.
- `[ ]` Проверить права доступа к связанным объектам.
- `[decision]` Уточнить окончательный набор связей: проект, дело, клиент, контакт, контрагент, юридическое лицо, договор, счет или только часть из них.

Definition of done:
- `[acceptance]` Задачу можно связать с нужным рабочим объектом без длинного поиска по форме.
