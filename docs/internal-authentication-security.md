# Внутренняя авторизация PayPlanner

Документ описывает вход и самостоятельную регистрацию сотрудников во внутренней CRM. Клиентский кабинет и вход через внешних провайдеров используют отдельные контуры.

## HTTP-контракты

| Метод и маршрут | Доступ | Назначение |
| --- | --- | --- |
| `POST /api/auth/login` | публичный, 30 попыток в минуту с одного IP | Проверка email и пароля, выдача JWT. |
| `POST /api/auth/register` | публичный, 5 попыток за 10 минут с одного IP | Создание учётной записи в состоянии ожидания одобрения. |
| `POST /api/auth/refresh` | только действующий JWT | Повторная проверка аккаунта и перевыпуск JWT. |
| `GET /api/auth/me` | только действующий JWT | Загрузка профиля текущего пользователя. |

## Проверка входа

1. Email нормализуется: удаляются внешние пробелы и регистр приводится к нижнему.
2. Пользователь загружается вместе с ролью, организациями и внешними идентификаторами, необходимыми для ответа CRM.
3. Пароль проверяется до возврата состояния аккаунта. Неверный пароль всегда даёт одинаковый ответ `InvalidCredentials`, даже если аккаунт отключён или ещё не одобрен.
4. Для неизвестного email выполняется фиктивная криптографическая проверка пароля. Это выравнивает время ответа и затрудняет подбор существующих адресов.
5. При верном пароле отдельно проверяются признаки активности и одобрения.
6. Успешный вход одной SQL-командой обновляет время последнего входа и активности, после чего формируется JWT.

## Серверная валидация

- email обязателен, должен иметь корректный формат и длину не более 320 символов;
- пароль входа обязателен и ограничен 512 символами, чтобы не принимать неограниченный объём данных;
- пароль новой учётной записи содержит от 8 до 128 символов;
- полное имя содержит от 2 до 200 символов и не может состоять только из пробелов;
- регистрация системного адреса запрещена;
- при отключённой самостоятельной регистрации проверка завершается до запроса к базе данных.

Frontend повторяет эти ограничения для быстрой подсказки, но авторитетной остаётся серверная проверка.

## Защита через nginx

Backend доверяет заголовкам `X-Forwarded-For` и `X-Forwarded-Proto` только для одного локального proxy-перехода с адреса loopback. Поэтому rate limit разделяет внешних клиентов по реальному IP, но не принимает поддельный адрес от прямого внешнего подключения. В nginx должны сохраняться заголовки из `docs/deploy-runbook.md`.

## Стабильные ошибки

- `InvalidCredentials`, HTTP 401 — email не найден или пароль неверен;
- `PendingApproval`, HTTP 403 — пароль верен, аккаунт ожидает одобрения;
- `UserInactive`, HTTP 403 — пароль верен, аккаунт отключён;
- `RegistrationDisabled`, HTTP 403 — самостоятельная регистрация выключена;
- `UserAlreadyExists`, HTTP 409 — email уже занят;
- `ProtectedUserEmailReserved`, HTTP 409 — системный email зарезервирован.

Непредвиденные внутренние сообщения исключений не передаются анонимному пользователю.

## Инварианты для дальнейших изменений

- нельзя проверять `IsActive` или `IsApproved` до проверки пароля;
- нельзя удалять rate limit с публичных endpoint;
- имена политик берутся из `AuthRateLimitPolicies`, чтобы атрибуты и параметры не расходились;
- все операции EF Core получают `CancellationToken` HTTP-запроса;
- изменение минимальной длины пароля выполняется одновременно в API и формах регистрации.
