## Реализация в работе

У приватного результата зачёта подготовлены два терминальных состояния: `Committed` и `Cancelled`. Существующие записи получают `Committed` при обновлении. Ограничение БД требует положительную сумму/хеш для выполненного зачёта, а для отменённой попытки — отсутствие команды/хеша и нулевые поля результата. Глобальный UUID и проверка первого отправителя сохраняются. Таблицы платежей, журнала, документов, задач и связей не меняются.

Маршруты отмены: `POST /api/clients/{clientId:int}/balance/applications/{requestId:guid}/cancel` и `POST /api/legal-entities/{legalEntityId:int}/balance/applications/{requestId:guid}/cancel`.

Отмена проверяет текущие права и использует ту же транзакцию/блокировку доступного платежа, что Apply и Inspect. Если результат уже есть, он только возвращается: выполненный зачёт не обращается вспять. Если результата ещё нет, создаётся приватная запись `Cancelled`, которая запрещает любой поздний Apply с тем же UUID. Неудачный/неизвестный COMMIT нельзя выдавать за подтверждённую отмену; состояние проверяется повторным чтением. Произвольная очистка записи в браузере до серверного подтверждения по-прежнему запрещена.

Чтение теперь различает `Committed`/`Cancelled`/`Unconfirmed`. Только первые два терминальны; неизвестное состояние остаётся202 без разрешения нового списания. Для Cancel подготовлены отдельные клиентские методы: только metadata `paymentId` в теле, исходный UUID в маршруте, запрет кеширования, отмена транспорта и строгая проверка HTTP200/идентификаторов/терминального состояния. Сумма, описание, токен и финансовая команда не сохраняются в браузере. Экран восстановления и стабильный ключ в существующем Apply UI ещё не включены.

## Очередь и прогресс

**Новая обязательная предпосылка до UI:** старый backend может проигнорировать неизвестный `requestId` в прежнем `/balance/apply`. Один GET-пробник не защищает от смены версии между запросами. Нужен отдельный managed Apply маршрут с UUID, который старая версия не сможет выполнить как legacy денежное действие; без fallback на старый POST, с проверкой ACK/ключа. Это следующий этап, пока новый UI не включён.

После выделенного managed Apply — metadata-only устойчивый ключ до отправки, явное восстановление/отмена в UI, read-back/защита между вкладками/тайм-аут и канонические платежи/баланс вместо повторного прибавления старого результата. Затем контекст внешних callbacks/refresh, оставшаяся матрица CMP-05 (поля/архив/назначения/подразделения/роли, обе БД), справочники, CMP-04/CMP-06. Linux native CMP-01 подготовлен, не выполнен.

Общий прогресс **9/167 (5.4%)**, 94 в работе /25 не начато; CMP **0/6 (0%)**, 5 в работе /1 приёмка; SEC **0/4 (0%)**. Полные пакеты остаются открыты. Только адресные локальные проверки; один полный обязательный CI всех семи jobs перед выпуском. Не повторять успехи без изменения влияющих входов. Push/merge/деплой не выполнять.
