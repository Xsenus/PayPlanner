## 2. Как читать статусы

- [x] Завершено и квалифицировано в области исходного плана. Это не автоматическое подтверждение всей новой версии на VPS.
- [~] Есть реализация или выполненная часть; остальная работа/квалификация открыта.
- [ ] Ещё не реализовано.
- [!] Блокер с явно указанной причиной.
- [decision] Нужен выбор владельца или внешние исходные данные.
- [acceptance] Нужна рабочая приёмка на согласованных данных/ролях/среде.

Проценты относятся к своим исходным планам. Пересекающиеся планы не складываются в общий процент CRM. Чтение макета, написание теста и подготовка ответа не равны реализации функции или её установке.

## 3. Что разработано в текущем кандидате

Ниже полный пользовательский состав локальной 1.14.56 из файла выпусков. Формулировки описывают реализацию; доступность на рабочем сервере и общая квалификация ещё не подтверждены. Их нельзя отправлять как сообщение «уже установлено».

1. **Улучшено.** При открытии задачи по ссылке CRM выполняет меньше лишних загрузок. Список задач, сводка и очередь автоконтроля обновляются при возвращении в журнал. Если новая задача создана, а её файлы ещё ожидают обязательных копий, открытая карточка остаётся доступной без обновления скрытого списка. Это работает в обеих формах карточки. Проверка актуальных прав сотрудника при открытии карточки выполняется без лишних повторов. При переходе по ссылке загрузка самой задачи начинается раньше вспомогательных настроек журнала. При добавлении файла CRM выполняет меньше лишних загрузок связанных карточек. При проверке состояния вложений сокращена повторная загрузка сведений о сотруднике; изменения его доступа по-прежнему учитываются. Если более ранних незавершённых загрузок нет, лишняя кнопка перехода больше не появляется.
2. **Исправлено.** После перезагрузки CRM сохранённые уведомления, включая сообщения о готовности файлов задач, восстанавливаются без ожидания подключения к моментальной доставке. Сообщения, появившиеся во время подключения, также сохраняются; повторная доставка не создаёт лишнюю всплывающую карточку. Окна обязательных действий по задачам открываются после загрузки прав сотрудника. Обязательные сообщения по задачам загружаются без лишних повторов при входе и новых событиях. После смены сотрудника CRM открывает его очередь обязательных сообщений.
3. **Исправлено.** Улучшена надёжность сохранения данных при одновременной работе сотрудников. Резервное копирование и проверка восстановления теперь поддерживают длинные пути к папкам в Windows.
4. **Улучшено.** Улучшена совместимость тем оформления со старыми браузерами: в настройках и журнале задач сохраняются цвета выбранной темы и выделение полей.
5. **Исправлено.** Исправлена отправка сообщений и файлов в браузерах без нового способа создания идентификаторов. При повторной отправке документа сохраняется прежняя попытка, чтобы не создавать дубликат.
6. **Исправлено.** При неудачной подготовке отправки документа исправлена очистка файлов: CRM удаляет только подтверждённую копию этой попытки и сохраняет файлы, которые были заменены после подготовки.
7. **Исправлено.** При повторной подготовке документа для отправки клиенту CRM проверяет временную копию перед удалением. Если файл подменён или изменён, он сохраняется; ранее подготовленный документ остаётся доступен. При ошибке подготовки без резервирования места очистка также затрагивает только подтверждённый файл этой попытки.
8. **Исправлено.** При подготовке документа для отправки клиенту с включённым учётом места CRM сохраняет сведения о записанных частях временной копии. Если чтение прервалось, непроверенный файл и его резерв остаются до восстановления. Очистка подтверждённой копии проверяет исходный файл перед удалением.
9. **Исправлено.** Исправлена подготовка PDF для электронной подписи в Windows, когда документ сохраняется в глубоко вложенном каталоге с длинным путём. Проверка свободного места и регистрация документа теперь работают для таких каталогов.

11. **Исправлено.** При повторной подготовке PDF электронной подписи и при отмене неудавшейся регистрации CRM проверяет исходный файл перед удалением. Подменённый или изменённый файл, а также файл в заменённом каталоге сохраняется. Очистка не затрагивает ранее зарегистрированный документ.
12. **Исправлено.** Если подготовка PDF для электронной подписи прервалась при выключенном резервировании места, CRM удаляет временный файл только после проверки, что это исходный файл этой попытки и его содержимое не изменилось. Посторонние файлы сохраняются.
13. **Исправлено.** При подготовке PDF для электронной подписи с включённым учётом места CRM сохраняет сведения о записанных частях временного файла. Если чтение документа прервалось, неполный файл и его резерв сохраняются до безопасного восстановления.
14. **Исправлено.** При подготовке вложений чата CRM проверяет оригинал перед передачей для отправки и сохраняет сведения о записанных частях временной копии. Файл, подменённый или изменённый после проверки, не используется для отправки и не удаляется автоматически.
15. **Исправлено.** При формировании доказательного архива электронной подписи CRM сохраняет файлы прежних прерванных попыток. Они больше не удаляются автоматически только потому, что были созданы больше суток назад. Новый архив формируется без перезаписи уже сохранённых данных.
16. **Исправлено.** Карточка задачи открывается в выбранном администратором виде после загрузки настройки, без временного переключения на другую форму. Если настройку не удалось получить, загрузку можно повторить или вернуться в журнал.

Подменённый служебный файл не используется для освобождения резерва и не удаляется автоматически; при отсутствии подтверждения прежний резерв сохраняется. При изменении минимального свободного места подготовка вложения чата также учитывает резервы других незавершённых записей на том же диске. Расчёт также включает место для ожидающих копий документов и их временных файлов на этом диске. Пока отправка не подтверждена, текст, ответ на сообщение и выбранные файлы сохраняются в редакторе; подтверждение прежней отправки не стирает изменённый черновик.
24. **Исправлено.** При повторной отправке сообщения в чате CRM проверяет содержимое вложений. Замена файла другим файлом того же имени и размера больше не подтверждается как прежняя отправка. Если сохранённое вложение временно недоступно, сообщение и файлы сохраняются, а проверку можно повторить позже.
25. **Исправлено.** Закрытие вкладки или переход на другую страницу больше не прерывают запись уже выполненного действия в журнал активности.
26. **Исправлено.** Если файл документа из шаблона, печатной формы заказ-наряда или судебной сводки сохранился, но подтверждение записи потерялось, CRM автоматически продолжает сохранённую попытку. Исходное содержание сохраняется; документ появляется в деле после подготовки обязательных копий. Прекращённая попытка не возобновляется, а перед продолжением CRM повторно проверяет права автора на дело.
27. **Улучшено.** При создании счёта, акта или договора из заказ-наряда финансовая запись и печатный документ становятся доступны вместе после подготовки обязательных копий. Во время ожидания сохраняются исходные услуги, суммы, номер и содержание документа; повтор после временной ошибки продолжает ту же попытку без лишней финансовой записи.
28. **Исправлено.** Если связь прервалась после создания счёта, акта или договора, CRM подтверждает готовый результат при обновлении документов. Повторно создавать финансовую запись не требуется; несохранённые поля дела сохраняются.
29. **Исправлено.** После готовности счёта статус заказ-наряда обновляется и при возврате из редактирования дела, даже если закрыть редактор до завершения загрузки списка документов. Кнопка создания счёта отражает актуальный статус наряда; введённые поля дела сохраняются во время обновления.
30. **Исправлено.** При переходе к другому делу редактор больше не переносит несохранённые поля предыдущего дела.
31. **Добавлено.** В списке документов обеих карточек дела видно состояние ожидающего счёта, акта или договора. Сотрудник может прекратить свою попытку формирования; уже созданный результат сохранится. Несохранённые поля окна редактирования дела сохраняются при обновлении состояния документа.
32. **Правило работы.** Для одного заказ-наряда допускается одна незавершённая попытка создания счёта. Повтор того же запроса продолжает её; чтобы начать другую попытку, сначала явно прекратите прежнюю.
33. **Улучшено.** При обязательной копии документов на Яндекс Диске CRM проверяет фактическое свободное место перед сохранением. Подключения к одному аккаунту учитываются вместе; если квоту не удалось получить или места недостаточно, сохранение останавливается до устранения причины.
34. **Улучшено.** В обеих карточках дела повтор формирования того же документа после временной ошибки использует сохранённую попытку. Когда CRM уже приняла подготовленный документ на хранение, сохраняются его исходное содержимое и имя, даже если шаблон изменился во время ожидания; лишняя версия документа и повторные уведомления не создаются.
35. **Добавлено.** В обеих карточках дела видно состояние ожидающего формирования документа из шаблона. Сотрудник может прекратить свою прежнюю попытку; уже добавленный документ сохранится, а новое формирование запускается отдельным действием.
36. **Улучшено.** В карточке дела при сохранении заказ-наряда в документы проверяются обязательные копии. После того как CRM приняла печатную форму на хранение, повтор продолжит ту же попытку с исходным содержимым и статусом наряда. Состояние ожидания и прекращение своей попытки доступны в списке документов.
37. **Исправлено.** У судебного срока сохраняется связь с исходным событием: повторная синхронизация такого срока не создаёт дубль после удаления сводки. Вручную изменённые дата и заметки сохраняются; если старые сроки неоднозначны, CRM показывает конфликт и не выбирает один из них автоматически.
38. **Улучшено.** При синхронизации суда предварительные процессуальные сроки, уведомления и контрольные задачи сохраняются до записи сводок. Если запись сводки завершилась ошибкой, контроль сроков продолжает работать; повторная синхронизация использует прежние сроки и уведомления.
39. **Улучшено.** При ручной и автоматической синхронизации суда сводка добавляется в документы и связывается со сроками после подготовки обязательных копий. Во время ожидания сохраняется исходное содержание принятой сводки; повторная проверка суда не заменяет его. В обзоре и режиме редактирования судебного блока видно, сколько сводок ожидают копирования, а конфликты источника показаны отдельно.
40. **Исправлено.** Если судебная сводка удалена и подходящего документа в деле больше нет, новая успешная проверка источника может сохранить заменяющую сводку после подготовки обязательных копий. Прежний процессуальный срок, его вручную уточнённая дата, заметки и закрытый статус сохраняются.
41. **Исправлено.** Совпадение имени судебной сводки с ручным документом больше не мешает создать процессуальный срок и не архивирует уже созданный срок при повторной проверке суда. Ручной файл остаётся без изменений и не привязывается автоматически к сроку; конфликт виден в результате проверки.
42. **Исправлено.** Судебные сводки разных событий с одинаковым именем файла сохраняются отдельно: прежняя сводка и её источник остаются без изменений. Старые сводки также не объединяются только из-за замены недопустимых символов в имени файла. Если после удаления прежней сводки в деле сохранилась подходящая версия, повторная проверка суда использует её без создания новой попытки сохранения, в том числе при уточнении результата судебного акта.
43. **Улучшено.** Если судебное событие снова появляется при проверке суда, сохранение ожидающей сводки может продолжиться с прежними копиями и исходным автором. Прекращённая попытка не возобновляется; для продолжения у исходного автора должны сохраняться права на дело.
44. **Исправлено.** В обеих карточках задачи новый файл остаётся в списке, даже если предыдущая загрузка списка завершилась позже или связь прервалась после отправки. CRM обновляет список вложений, сохраняя прежние файлы; повторная отправка уже добавленного файла не требуется. Если одна и та же сохранённая загрузка завершается одновременно, CRM распознаёт уже добавленный файл после проверки доступа и обязательных копий, без ложного сообщения о недоступности. После подтверждённого сохранения файла обе карточки сразу показывают ожидание копий. Файл не отправляется повторно, а завершение задачи и отправка на согласование ждут его готовности.
45. **Исправлено.** После смены учётной записи в обеих карточках задач можно сразу прикреплять файлы. Незавершённая отправка предыдущего сотрудника больше не оставляет кнопку загрузки заблокированной.
46. **Исправлено.** При открытии задачи по ссылке карточка больше не начинает загрузку заново из-за обновления журнала. Это сокращает ожидание в обеих формах, в том числе для завершённых задач. После перехода к другой задаче или смены сотрудника CRM загружает её отдельно и не показывает прежний ответ.
47. **Правило работы.** При включённой проверке копий документы из шаблонов, печатные формы заказ-нарядов и судебные сводки появляются в деле после подготовки всех обязательных копий. Если хранилище временно недоступно, карточка показывает причину. Для шаблонов и заказ-нарядов, которые CRM ещё не смогла принять на хранение, повторное формирование использует актуальные данные дела, шаблона или наряда.
48. **Исправлено.** Быстрый переход из журнала в отдельную карточку задачи работает надёжнее в старой и новой формах. Поздняя загрузка списка задач и автоконтроля дел не влияет на открытую карточку и не подменяет свежие данные при возвращении в журнал.

Техническая основа разработанного: каталог объектов/поколений/реплик, парные SQLite/PostgreSQL migrations, durable очередь и lease, проверка ёмкости и обязательных копий, защищённое чтение/повторы/прекращение попытки, восстановление документов и резервов. В клиенте используются общие механизмы старой и новой карточек, свежие права и изоляция сменившегося сотрудника. Для задач уменьшены лишние чтения и сохранено точное подтверждение принятой загрузки. Доработаны проверка зависимостей, изолированные стенды и перенос сборки на D. Эти части имеют разную степень квалификации — остаток ниже.

## Детали текущих подпланов

**Формируемые документы — 7/11 (64%).** Завершены инвентаризация, общая основа durable recovery, template/work-order/court writers и связанные локальные UI-этапы по исходному плану. Финансовый пункт7 остаётся в работе: право прекращать попытку чужого/отключённого автора не определено. Расширенная квалификация9 и итоговый gate10 открыты; 11 — рабочая приёмка. Завершить: решение о cross-actor retirement без автоматической подмены автора; exact replay/flags/cancellation/lease/rights на обеих БД; browser всех форм; полный gate; реальные обязательные копии. Одну активную попытку счёта и немедленные судебные сроки повторно не согласовывать.

**Новая попытка загрузки — 8/9 (89%).** Завершены marker/guards, собственный endpoint, очистка точного browser retry key, подтверждение/общая панель обеих карточек и локальная связанная квалификация. Остались полный gate/Linux и рабочая приёмка новой версии/скана/отзыва прав/сети/рестарта. Прежняя попытка не должна публиковаться после прекращения, новая создаётся только явно.

**Управляемые вложения чата — 7/10 (70%).** Завершены frozen агрегат, SHA всех файлов, хранение originals, атомарный message/attachments/bindings, bounded recovery, typed HTTP/client identity и адресная matrix. П.8: native Яндекс-квота/two-copy/lost ACK/browser/restart/Linux; п.9: полный применимый gate, diff и release notes; п.10: два реальных сотрудника. Нельзя признать сообщение готовым по одной из обязательных копий либо отправить его частично.

**Мессенджер — 30/31 (97%).** Основа локально реализована. ## 6. Принятые решения и то, что ещё требует выбора

## Принятые решения — повторно не спрашивать

- Обязательная облачная копия прежде всего на Яндекс Диске; получать фактическую квоту.
- Счёт, акт и договор в управляемом режиме публикуются вместе с финансовой записью после обязательных копий; исходная попытка сохраняется.
- Судебные сроки и напоминания сохраняются сразу по событию; документ привязывается после копирования.
- Одна активная попытка счёта на заказ-наряд; точный повтор разрешён, новая — после явного прекращения.
- «Что нового» дополняется одной общей неопубликованной записью 1.14.56.
- Сохранять браузеры начала 2022 года: Chrome/Edge 97+, Firefox 96+, Safari/iOS 15.2+; Tailwind 3.
- Сейчас завершить последний этап и подготовить выпуск/ответы. Карточки с реализованными изменениями в дальнейшем направлять в «Тестирование», после разрешённого ответа и сверки.

## Что ещё требуется по бизнесу и внешним доступам

Свежая [сверка YouGile 6 октября](yougile-payplanner-release-audit-2026-10-06.md) выявила открытое уточнение PAY-7: периодический поиск дублей, ручной запуск/остановка автоматики и выбор получателя списка. Ручное объединение не закрывает это требование. Также подтверждено актуальное задание PAY-21 на редизайн дела и видны дополнительные задания редизайна/ТЗ CRM; их полный объём и соответствие коду ещё не сверены. Сейчас новые бизнес-механизмы и редизайн не начинаются: это оставшиеся задания, которые нужно подробно разобрать после подготовки выпуска. Проценты исходных планов не повышены.

- `[decision]` Прекращение чужой финансовой попытки: администратор с доступом к делу или только исходный автор. Не реализовано без решения.
- `[decision]` RPO/RTO, независимость обязательных копий, хранение/восстановление ключей, юридическая retention/hold/delete/version policy, сценарии прекращения подписи и утраты прав. Без ответа зависимое удаление/экспорт ключей/включение не выполнять.
- `[decision]` PAY-3: прекращение мониторинга через десять дней требует надёжного статуса судебного источника; это отличается от уже подготовленной задачи итогового отчёта.
- `[!]` Судебные внешние адаптеры: согласованные обезличенные дела/эталонные ответы/способ доступа для КАД, Мосгорсуда, мировых/региональных судов, ФССП и ЕФРСБ. OCR и правовой режим документов ещё не определены.
- `[!]` MAX/SMS/квалифицированная подпись: настоящий выбранный provider/sandbox/бот/модерация/webhook/получатели/сертификаты. Локальная очередь не доказывает внешнюю доставку и юридическую силу подписи.
- `[!]` Шифрование полей: состав полей, маскирование/права, production KMS/Vault identity и DR; не запускать backfill/удаление plaintext без решения и отдельного разрешения.
- `[acceptance]` Реальные роли, клиентское согласование, портал, календарь и offline-конфликты — перечень в подробном приложении.
- PAY-2 ждёт ТЗ по зарплате; PAY-8/PAY-9 отложены владельцем. Не возобновлять их из-за общего поручения подготовить выпуск.

Неизвестные решения нельзя закрыть кодом «как удобнее»: RPO/RTO и допустимая потеря данных, отдельное хранение ключей/retention, право прекращать финансовую попытку чужого автора, доступы/провайдеры судебных источников, SMS/MAX/подпись и спорные правила PAY-31 остаются у владельца и соответствующих ответственных. Предварительный выбор ниже наследуется из исходных планов; новый ответ от пользователя этим документом не имитируется.

- `[x]` Реализовать утвержденные конечные статусы и приостановление. Статусы «Приостановлено», «Закрыто» и «Проиграно» централизованно исключаются из preview, одиночного и массового ручного запуска, фонового создания и повторной эскалации.
- `[x]` Учитывать активную задачу с будущим сроком по точному правилу ТЗ. Любая задача в рабочем статусе блокирует создание автоконтроля независимо от срока; завершённая или отменённая задача не блокирует контроль только из-за будущей даты. Правило одинаково для preview, одиночного, массового и фонового запуска.
- `[x]` Учитывать отпуск/отсутствие ответственного из доступного источника. Используется период отпуска из личной настройки «Не беспокоить» с часовым поясом сотрудника. На время отпуска исключаются preview, одиночный, массовый и фоновый запуск, а повторная эскалация приостанавливается; после даты возвращения проверка возобновляется автоматически.
- `[x]` Решить, считать календарные или рабочие дни. Принят совместимый с текущими настройками календарный отсчёт: пороги считаются непрерывными сутками, выходные не вычитаются. Это едино для первого контроля, повторов и ожидания нового цикла.
- `[x]` Учитывать часовой пояс пользователя и запуск в утвержденное время. Администратор задаёт локальное время и часовой пояс в настройках журнала задач; фоновый сервис проверяет расписание коротким запросом и выполняет полный проход один раз в сутки. После рестарта дата последнего успешного прохода восстанавливается из состояния системной задачи.
- `[x]` Не создавать эскалации задним числом пачкой после долгой остановки сервиса. Повторная проверка, просроченная более чем на 36 часов, переносится на свежий срок через два дня без комментария, уведомления и повышения приоритета; недавние просрочки обрабатываются штатно.
- `[x]` Показать понятные значения «первый контроль», «повтор», «критическая эскалация». В настройках журнала задач добавлена компактная сводка трёх этапов; фиксированные интервалы передаются backend вместе с настраиваемыми порогами, поэтому интерфейс показывает фактическое правило из единого источника.
- `[x]` Добавить per-case выключатель с обязательной причиной и аудитом. В старой и новой карточках дела выключение требует непустое пояснение; причина хранится в деле, отображается рядом с настройкой и попадает в аудит. Повторное включение очищает исключение, а миграции совместимо помечают ранее отключённые дела.
- `[x]` Показывать в реестре последнюю активность, следующий контроль и причину исключения. Колонка «Автоконтроль» использует единый перечень значимых сигналов и показывает дату следующего первого контроля или сохранённого повтора. Для исключённых дел выводится конкретная причина; данные также входят в CSV, Excel, PDF и печать.
- `[x]` В уведомлении добавить открыть дело, отложить и подтвердить активность. Уведомления автоконтроля связаны непосредственно с делом и сохраняют связь с контрольной задачей. В центре уведомлений и realtime-toast доступны переход в карточку, подтверждение активности и серверная отсрочка на 30 минут; отложенные уведомления временно исключаются из активной ленты и счётчика на всех устройствах.
- `[x]` Ограничить право изменения глобальных правил администратором. Раздел глобальных настроек журнала задач доступен только роли администратора, а backend проверяет актуальную роль пользователя из БД перед любым сохранением. Полные права на задачи не позволяют обойти ограничение; отказ не изменяет ни одно системное значение.
- `[x]` Показывать полную очередь открытых дел без активных задач. Журнал разделяет дела на готовые к созданию контроля, ожидающие порога и временно приостановленные; дневной лимит ограничивает создание, но не скрывает остальные дела. Сервер возвращает точные общие счётчики, отдельные категории и страницы по 100 карточек, поэтому очередь свыше 100 дел доступна полностью без неограниченной загрузки. Поиск учитывает дело, контрагента и ответственного, а массовое действие доступно только для наступивших сроков.
- `[x]` Сопоставить существующие автоконтрольные задачи с циклами. При первом проходе старые задачи без сохранённого состояния получают цикл 1, 2 или 3 по фактической истории системных повторов; следующая дата восстанавливается от даты создания задачи. Сопоставление идемпотентно и не создаёт новых задач или комментариев.
- `[x]` Не создавать дубли при изменении defaults. После изменения периода неактивности, критического порога, лимита и резервного исполнителя фоновый проход повторно проверяет наличие активной задачи по делу и не создаёт новый цикл. - `[x]` Подготовить preview числа дел, которые попадут под новое правило. В настройках администратор запускает безопасный расчёт по ещё не сохранённым значениям первого и критического порога. API одним агрегированным запросом возвращает общее число кандидатов и число критических дел, учитывая статусы, активные задачи, отпуск, индивидуальные исключения и все значимые сигналы.
- `[x]` Вводить строгие значения постепенно, с дневным лимитом. Автоматический проход запускается один раз в сутки и ограничивает число новых контрольных задач на уровне индексированной выборки кандидатов. В настройках лимит явно назван дневным и сопровождается пояснением; перед изменением администратор может выполнить preview и начать с минимального значения 1.
- `[x]` Unit-тесты всех переходов state machine и граничных дат. Покрыты ожидание, первый контроль, обычный и критический повторы, reset, подавление активной задачей, завершение повторов, точные 24-часовые границы, календарные выходные, будущее время сигнала и восстановление после простоя на границе 36 часов.
- `[x]` Интеграционные тесты сигналов, исключений, повторов и идемпотентности. Единый профиль из 55 сценариев проверяет задачи, комментарии, документы, судебные события, просмотр и подтверждение; статусы, отпуск и индивидуальное отключение; одиночное, массовое и фоновое создание; восстановление и повтор циклов; параллельные и повторные запуски без дублей.
- `[x]` Тест часового пояса, рабочих/календарных дней и простоя сервиса. Проверены разные локальные зоны, суточное окно, пропущенный запуск, календарный переход через выходные, точная граница допустимой задержки и восстановление давно просроченной проверки без уведомления.
- `[x]` Нагрузочный тест не менее 10 000 дел. На локальной SQLite создано 10 000 неактивных дел; preview корректно посчитал все 10 000 кандидатов и критических случаев одним агрегированным запросом. Полный тест с подготовкой данных занял около 10 секунд, непосредственно расчёт уложился в защитный предел 30 секунд.
- `[x]` Тест миграции существующих контрольных задач. SQLite разворачивается полной реальной цепочкой миграций через проектный SQL-генератор, после чего legacy-задача без состояния восстанавливает цикл по существующей истории эскалаций. Повторный проход не меняет результат и не добавляет комментарии.

- `[x]` Введены immutable snapshot, версия, размер, MIME и SHA-256 checksum отправляемой версии.

- `[x]` Контакт клиента/представителя хранится отдельно и не переиспользует внутреннюю подписку сотрудника.
- `[x]` Подготовка доступна только администратору и проверяет принадлежность документа и подтверждённого контакта одному клиенту.

- `[x]` Прямые вложения закрыты единым fail-closed шлюзом: без одновременно включённого антивируса, MIME allowlist и положительного provider limit фактическим режимом остаётся только защищённая ссылка.

- `[x]` Контакт защищён Data Protection, в списках и истории возвращается только маска; чувствительная отправка требует повторного подтверждения.

- `[x]` Мастер показывает документ, точную версию, получателя, канал и предварительный текст.
- `[x]` Мастер требует подтверждённый контакт, повторное подтверждение пары «документ + получатель» и предупреждает о юридическом значении статусов.
- `[x]` В мастере показываются очередь, отправлено, доставлено, прочитано и ошибка; выключенные каналы явно обозначены и недоступны.
- `[x]` Повторная подготовка переиспользует idempotency key и immutable snapshot без дублирования отправок.
- `[x]` История связана с клиентом и документом, показывает маскированного получателя, канал и технический статус.
- `[x]` Telegram-клиентский сценарий использует явную администраторскую привязку подтверждённого chat id и существующий официальный Bot API; канал остаётся выключенным до credentials и тестового адресата.
- `[x]` MAX подключён к общему контуру через защищённую одноразовую ссылку и проверенный аккаунт клиентского кабинета; production-отправка остаётся выключенной до официального API и credentials.
- `[x]` Неподдерживаемый канал не имитируется ручной ссылкой: каждая подготовленная ссылка имеет запись аудита, checksum, получателя и срок.

- `[x]` Frontend-тесты проверяют безопасное выключенное состояние, обязательное подтверждение и постановку выбранной версии в очередь.

## 10. Обновление плана и окончательное завершение

При продолжении фиксировать один выбранный незакрытый пункт перед изменением кода, результат, относящиеся проверки, новые ограничения и остаток. Не повторять выполненное без причины. Прогресс повышать только после квалификации соответствующего пункта. Локальные запуски: почта и фоновые службы явно выключены; на восстановленной БД notifications.email.enabled=false; каталог собственных БД проверять до/после, вручную базы не удалять.

Общий проект завершён, когда закрыты согласованные функциональные планы, бизнес-решения, полный выпускной барьер и рабочая приёмка. Только тогда архивировать завершённые планы. Сейчас это условие не выполнено. Текущий пакет можно использовать для следующей отдельной команды на техническое продолжение, публикацию ответов или установку — он сам таких действий не запускает.

Контроль публикации 9 октября: оба дополнительных ответа PAY-14/PAY-20 опубликованы с правильной кодировкой и проверены. Пользователь удалил два повреждённых сообщения первой отправки; отсутствие этих ID, сохранность правильных ответов и всей другой переписки проверены. См. [актуальный индекс](yougile-current-roadmap-2026-10-09.md).
