## Текущий этап — новый документ и неизменность выданного снимка

Подтверждённый счёт проверяется общим сервисом при создании документа и новой фиксации реквизитов. Собственная компания и подразделение читаются под прежней транзакционной границей; банковский источник и явный денежный счёт сверяются по сохранённой идентичности. Закрытие/скрытие/исчезновение/смена источника или владельца не разрешают новый снимок. Возвращение того же открытого источника допускается; старый снимок остаётся прежним. Недоступный подтверждённый счёт подразделения не заменяется основным.

В новый снимок записываются серверные ID подтверждения/банка/явного денежного счёта и источник/валюта. Эти поля — исторические сведения, не полномочие для текущих действий; после переноса истории нельзя открывать текущий счёт по одному старому ID. Ручные совпадающие счета не объединяются: без явной денежной ссылки MoneyAccountId остаётся null. Для рублёвых счетов и актов подтверждённая валюта должна быть RUB; для договора валюту произвольного шаблона не угадываем, но профиль/банк/денежный счёт обязаны совпадать.

## Завершённый серверный этап — административный API и архивный профиль

Подключены POST подтверждения и отзыва; GET возвращает конечный набор активных серверных подтверждений с полным локальным ID, ID банка, сохранёнными номером/БИК/валютой и временем. Текущие одобренный администратор, версия сеанса и транзакционные блокировки обязательны для обеих команд, в том числе повтора. CanBind показывает только допуск компании; доступность каждого выбранного источника проверяется отдельно командой.

Контракт: `POST /api/bank-connections/{id}/profile-account-bindings` принимает BankAccountId, ProfileAccountId и ExpectedVersion; `POST /api/bank-connections/{id}/profile-account-bindings/{bindingId}/revoke` — ExpectedVersion. Оба возвращают BindingId, State и IsReplay. Подтверждение при отзыве принадлежит компании выбранного подключения. `GET /api/bank-connections/{id}/profile-account-matches` возвращает согласованную версию и активные подтверждения этой компании. Чтение и команды no-store; 400 для неверного выбора, 401/403 для отсутствия допуска, 404 для недоступного ID, 409 для устаревших данных или блокировки.

Новая связь разрешена только активной собственной компании. Для архивного профиля и исключённой из реестра компании — только чтение/отзыв существовавших типизированных подтверждений. JSON не доказывает такое право. В режиме очистки кандидаты профиля/банка/денежного журнала не обходятся; повреждённый старый список не мешает снять подтверждение. История отзыва не удаляется. Статус профиля и принадлежность включены в версию; старый выбор требует обновления.

## Первый серверный этап

Добавлен `GET /api/bank-connections/{id}/profile-account-matches`. Существующие Admin-policy и строгий текущий одобренный администратор обязательны. Отчёт доступен только для подключения активной собственной компании из существующего реестра; нет подстановки основной/чужой компании. Возвращаются ID/название локальных кандидатов, группы одинаковых известных идентичностей банка, явные денежные ссылки и отдельные ручные кандидаты. Неполные данные, архив профиля, закрытие/скрытие/недоступность банка, несколько источников, чужая/неверная денежная ссылка и неактивный денежный счёт обозначаются отдельно. UniqueCandidate означает только одного активного кандидата профиля по известному кортежу, не подтверждённую связь всех трёх моделей.

Номер и БИК используют существующее удаление пробелов/верхний регистр BankStatementImportRules, валюта — прежнее trim/upper MoneyBalanceIdentity. Нет default RUB, преобразования RUR→RUB, поиска по имени, сумме или основному признаку. Локальные ID не генерируются и не исправляются при чтении; отсутствующие/повторённые ID, неверный JSON и неоднозначные признаки дают явные issues. Уже известный BankConnectionAccountId денежного счёта принимается только при совпадении компании, источника Bank и всех трёх полей. Ручной денежный счёт с похожими данными остаётся кандидатом на отдельный разбор; неподтверждённые исторические владельцы не угадываются.

Чтение выполняется в одном коротком Serializable-снимке. Версия привязана к компании, запрошенному подключению и всем влияющим сохранённым входам; не является разрешением записи или заменой прав. Учитываются банковские записи других подключений этой же компании, включая исторические закрытые: они не теряются при определении неоднозначности. Проекции не читают токены, изображения, контакты компании и финансовую историю. Неподтверждённые счёта без владельца не сканируются по всей БД. Прежние tracked-правки не сохраняются/не стираются; чужая открытая транзакция не подхватывается.

Пределы: 128 записей профиля, 500 банковских записей компании, 1000 относящихся денежных записей, JSON профиля 16000 символов. Запросы берут limit+1; превышение даёт отказ, а не частичное «уникальное» совпадение. Для oversized legacy JSON сама проекция возвращает null/признак размера, без загрузки и разбора большого поля. Общие локальные/ручные/банковские кандидаты передаются один раз на группу идентичности; строки ссылаются на группу. Это сохраняет линейные объём/обработку вместо повторения массивов на каждом дубле. Ответ задаёт no-store. Записей/аудита/синхронизации этот GET не выполняет.

## Предпосылки следующего этапа

Существующий BankAccountsJson сохраняет неизвестные поля от клиента/импорта. Наличие числового bankConnectionAccountId в таком JSON нельзя считать доверенным выбором администратора. Запись связи должна иметь типизированное серверное хранение и явную проверку происхождения/принадлежности, а общий save/import — сохранять ограничения стабильного локального ID и идентичности. Не внедрять доверие к старому произвольному JSON-полю по догадке. Если потребуется новая схема — обе миграции и upgrade/clean-проверки обязательны. Не связывать исторические ручные MoneyAccount автоматически: существующий unique банковского ID не доказывает принадлежность старого ручного счёта. Оставшиеся четыре этапа плана выше сохраняются целиком.

Для команд добавлена версия v2: закреплены Provider/ExternalAccountId, активные серверные подтверждения и последний исторический ID компании. Старая версия v1 не допускает запись. Версия не заменяет текущие права, явные ID и проверку под собственной транзакционной границей.
