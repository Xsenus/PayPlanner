## Исправления по результатам проверки

1. **Заявки:** неверный тип/сумма проверяются до создания контакта; сохранение заявки, событий и задач атомарно. Конкурентные переходы сериализуются по заявке, а одновременное создание контакта через заявки — по нормализованному телефону. Задачи покинутого этапа отменяются, вместо фиктивного выполнения. Список получил пагинацию; поздние ответы поиска/списка/карточки не заменяют более новые данные.
2. **Автоматизация:** прежние `Take(200)`/`Take(500)` могли навсегда оставлять последующие заявки без обработки. Теперь обрабатываются все страницы по устойчивому ключу, память фонового контекста освобождается. Уже зарегистрированная просрочка исключается серверным запросом; запись SLA защищена от повторов. Конструктор запрещает циклы и автоматический переход в успех, требующий проверки оплаты.
3. **Права:** общий доступ к задачам/календарю/отчётам не открывает задачу чужой заявки. SQL-фильтр использует актуальные права роли и область заявки, применяется к обоим окнам задач, чтению файлов, отчётам и уведомлениям. Область подразделения соответствует существующему доступу к заявке: учитываются справочник и прежнее текстовое поле, неактивные коллеги исключены. Восемь отдельных сценариев покрывают обе формы подразделения, активность и чужой отдел; на прежней сборке два сценария воспроизвели расхождение. Назначение автоматических задач сотруднику без доступа к заявкам отклоняется; конструктор проверяет доступ всех выбранных исполнителей одним запросом вместо запроса на каждого. Исключение для юриста не вводилось без решения владельца. Дополнительно устранён обход проверки через готовый объект задачи в уведомлении: проверяются актуальные права на конкретную заявку для внутренних сообщений, почты, Telegram и web push. Проверка исполнителя ручной и автоматической задачи теперь учитывает область конкретной заявки, а не только общее право просмотра. На прежней сборке 6 из 12 сценариев уведомлений воспроизвели утечку; после исправления все 12 и ещё 4 сценария назначения прошли.
4. **Регистр:** создание и корректировка раньше могли оставить часть данных без истории; все изменения теперь в одной транзакции. Блокировка компании предотвращает гонки редактирования с утверждением, корректировки с закрытием года и повторного закрытия. Устаревшее состояние записи перечитывается под блокировкой. Неоднозначные ошибки БД больше не маскируются как повторная корректировка.
5. **Денежный источник регистра:** у записи из выписки нельзя подменить исходную операцию или её сумму/дату/направление, в том числе при повторной отправке без идентификатора источника. Положительная сумма, округляющаяся до нуля, отклоняется. Ошибки загрузки книги позволяют повторить запрос; черновики выдаются постранично. XLSX сохраняет корректные Unicode-символы и эмодзи.
6. **Банковская основа:** явная ручная загрузка периода не обрезается последним курсором. Фоновая загрузка остаётся инкрементальной. Обработанные операции освобождаются из контекста по страницам. Конкурентное назначение основного счёта разных подключений одной компании оставляет один основной счёт. Реальные адаптеры от этого не появились.
7. **Счета и акты:** документы с явными ставками используют одинаково округлённые суммы строк в интерфейсе, отправке и печати. Дробные количества/цены проверены; десятичные середины (`10.075 → 10.08`) не зависят от двоичной погрешности JavaScript. Старый расчёт без заданных ставок сохранён. Несоответствующая строкам сумма нового/редактируемого счёта отклоняется сервером. Дополнительно подтверждено расхождение при сохранении 1,5 × 10,075: отправка 15,11, сохранённая цена даёт 15,12. Новые/редактируемые позиции теперь проверяются по действующей точности хранения (цена 2 знака, количество 4); интерфейс и API отклоняют лишнюю точность, включая частичный акт. Исторические документы не переписываются. Есть отдельная проверка повторной загрузки допустимых позиций и итогов из реальной PostgreSQL.
8. **Календарь:** после переключения календаря в список завершённые задачи больше не остаются в фильтре активных только из-за первоначального режима экрана.
9. **Границы API:** недопустимые годы, крайние даты, переполнение номера страницы и неверный период возвращают управляемую ошибку. Неверный SLA не сохраняет часть изменений статуса.
