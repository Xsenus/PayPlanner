Старые сообщения/комментарии извлекаются из EventHistory, Id=index+1; это не устойчивый message ID для новой объединённой ленты. Спроектировать additive мост/проекцию с устойчивым source+ID, сохранностью старой истории/вложений и без переписывания исходного audit. Определить модель принадлежности чата делу, использовать существующие InternalChat API, сообщения/вложения/audit/SignalR, сохранять один канонический экземпляр нового сообщения; сводная лента как разрешённая проекция, а не копирование и массовая пересылка. - Правила: доступ к делу не даёт автоматически доступ к закрытому чату задачи; архив/удаление задачи не уничтожают общую историю; перемещение задачи в другое дело не переносит историю скрыто. Последнее поведение и состав общей ленты необходимо согласовать как бизнес-решение внутри пакета, безопасный default — не расширять аудиторию и не переносить старую историю автоматически.
- До реализации согласовать: включение старых сообщений/системных событий, точка отправки общего сообщения и привязки новой задачи, поведение при смене дела. Сохранить исходный вопрос на обсуждение; предложенные фильтры не выдавать за утверждённое ТЗ.
- Проверки C1: два дела и две роли, 51+ задач/сообщений, скрытая задача, отозванный участник и файл/direct API, одинаковые IDs в обоих представлениях, отправка/retry/lost ACK/reconnect/edit/delete/reply, отсутствие дублей и второго уведомления, поиск и unread по доступной выборке, переход в обе формы задачи и переключатель карточек.

Существующая вкладка «Дела → нужное дело → Переписка» и её API не заменяются вторым независимым механизмом. Сохранить добавление сообщения/файлов, обработку ошибки загрузки и read-only роль из `CaseDetailPage.test.tsx`. [Свежий источник и черновик ответа](max-latest-reply-drafts-2026-10-15.md).

## Доступ, проверки и закрытие

C0 — исходники, безопасные макеты, mock API без БД/VPS: подходит Claude Code. C1 — отдельные синтетические SQLite/PostgreSQL, локальный API и mock внешних служб без рабочих секретов. C2 — VPS, разрешённый внешний sandbox, физические устройства или реальные роли: только необходимая приёмка. Быстро — до рабочего дня при неизменном контракте; средне — несколько дней; длительно — несколько этапов. Оценка уточняется после характера дефекта.

Сначала использовать существующие модули. Две карточки задачи и глобальная настройка их переключения входят в каждый затрагивающий задачи пакет. Проверять успех/отказ, прямые API ограниченной роли, другой объект/компанию, повтор, конкурентное изменение и сохранность истории. На больших списках серверные страницы/индексы и ограниченные payload; не заменять это загрузкой всей организации. В разработке адресные проверки, перед окончательным выпуском полный применимый gate. Local backend: `BackgroundServices__Enabled=false`, `Email__Enabled=false`; отдельно отключить SMTP/очередь и `notifications.email.enabled` в копии production. Внешние уведомления только согласованным адресатам при специальной приёмке.

`[x]` ставится после полного указанного объёма и подтверждения тестов/кодировки/данных/среды. Текущий частичный механизм описан отдельно и не подменяет полную приёмку. Для пользовательских изменений общая запись «Что нового» согласно принятому формату. YouGile — локальный черновик, отдельная команда на публикацию и только после неё изменения карточек. После полной приёмки блок архивируется независимо от остальных.
