## Локальный результат

Сценарий распределения вынесен из Payments в компактный `AdvanceAllocationModal`: тот же guarded Apply, metadata-only UUID и общий `BalanceApplicationRecovery`, без второго механизма повторов. Клиент/организация и sourcePaymentId сохраняются в команде; среди обычных frontend-вызовов legacy Apply больше нет. Старые методы API оставлены для совместимости. Backend C#, расчёты, схема, миграции, документы, задачи и реальные денежные записи не менялись.

Форма и все продолжения принадлежат исходной карточке, пользователю, родительскому чтению журнала, правам и отбору. Захваченный родительский guard предотвращает новые чтения старого контрагента в промежутке смены токена и обновления React-профиля. Переоткрытие имеет собственную ревизию. Три первоначальных чтения отменяются при закрытии/смене контекста; поздние ответы/ошибки не меняют новое окно. Форма может закрыться даже во время отправки: уже отправленный запрос не отменяется, UUID остаётся для явной проверки. Нет автоматического нового ключа после неизвестного результата.

Payments передаёт существующему usePaymentsPaged владельца данных с пользователем/ролью/правами и всеми полями запроса, включая страницу. Отозванный просмотр отключает загрузку; после смены владельца старые строки/итоги скрываются. Распределение требует редактирования и права полного просмотра баланса. Из списка долгов отбрасываются чужой владелец, исходный платёж, расходные, завершённые/отменённые и некорректные строки.

Остаток источника считается за один проход по существующему ответу транзакций: его кредит минус применения с точным префиксом sourcePaymentId и минус проведённый возврат с точным ключом. Префикс901 не принимает9010. Результат ограничивается общим балансом и долгом; правило уже существовало на сервере, исправлен клиентский показ, ранее пропускавший возврат. Невалидные/неподтверждённые данные запрещают новое списание. Четыре обычных метода чтения баланса/транзакций принимают AbortSignal, обходят кеш и требуют HTTP200;202 не становится подтверждённым остатком.

После Committed используются канонические значения из общего драйвера. Передача того же proof-bearing результата родителю отмечает принятие и в форме, и в журнале, затем обновляет только принадлежащий операции список. Собственная очистка не создаёт лишнюю повторную проверку. Cancelled отмечает принятие без денежного refresh; перед новым распределением форма отдельно перечитывает остаток/долги. Сумма и выбор сохраняются при ошибке обновления. После Committed свежая попытка не разрешается на основании старого остатка, даже если другая поверхность уже удалила metadata. При неизвестном исходе карточка остатка просит проверить зачёт вместо показа старой суммы как актуальной.

## Восстановление без исходной строки

Прямо в журнале есть общий ограниченный список попыток текущего пользователя для всех контрагентов. Он использует тот же hook с явным allOwners и тот же recovery-компонент. Это необходимо: после полного распределения источник уже может иметь Allocated, а целевой платёж может отсутствовать в текущей странице долгов. Проверка/закрытие попытки остаются доступны без открытия источника. Команда, сумма, описание и токен в metadata не добавлялись — по-прежнему девять полей.

Чужое удаление metadata по-прежнему требует явного GET и принятия канонических данных; новый POST при этом не выполняется. Возвращённый уже исполненный результат не складывается с прежней оплатой. Принятие принадлежит текущему view/auth и точному объекту proof. Общая форма PaymentModal использует прежний режим hook по одному владельцу; его политика не ослаблена.
