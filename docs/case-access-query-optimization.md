# Единый снимок прав и видимости дел

Дата проверки: 5 августа 2026 года.

## Назначение

Все действия карточки и реестра дел должны одновременно проверять право операции и область видимости данных. Ранее `CasesV2Controller` отдельно читал признак администратора, право раздела, пользователя, роль и область видимости. После этого действие ещё раз проверяло наличие доступного дела. Такая последовательность сохраняла безопасность, но повторяла одни и те же SQL-запросы в пределах одного HTTP-запроса.

## Текущее правило

- пользователь, роль и право раздела «Дела» подтверждаются актуальными данными БД, а не только claim из JWT;
- право операции и область видимости формируются одним неизменяемым снимком;
- снимок кэшируется только внутри экземпляра контроллера, то есть только на время одного HTTP-запроса;
- область `own` и `all` требует один служебный SQL-запрос;
- область `department` выполняет второй ограниченный запрос только для идентификаторов активных сотрудников того же отдела;
- область `specific` для календаря сохраняет отдельную выборку явно разрешённых сотрудников;
- отключённый пользователь, роль с другими настроенными правами без права «Дела» или `CanView = false` дают отказ без выполнения бизнес-запроса;
- для старой роли без единой записи прав сохранён прежний режим: разрешена только область видимости `own`, но операции создания, изменения, удаления и экспорта не разрешаются без явного права;
- фактическое действие (`CanCreate`, `CanEdit`, `CanDelete`, `CanExport`) проверяется по тому же снимку и не инициирует повторное чтение роли.

## Влияние на запросы дел

Единый снимок используется всеми 86 действиями `CasesV2Controller`, которые вызывают проверку права раздела. Повторный вызов проверки видимости в том же действии использует уже загруженные данные.

Контрольный сценарий чтения статуса внешнего согласования заказ-наряда выполняет:

1. один SQL-запрос для пользователя, роли, права и scope;
2. один SQL-запрос `Any` для проверки доступности конкретного дела;
3. бизнес-вызов сервиса внешнего согласования.

Количество служебных SQL-запросов не зависит от числа прав роли и не увеличивается при последовательной проверке права и видимости.

## Внешнее согласование заказ-наряда

Прямыми controller-тестами закреплены три защищённых действия:

- `GET /api/v2/cases/{id}/work-order/external-approval` — чтение последнего статуса;
- `POST /api/v2/cases/{id}/work-order/external-approval` — создание запроса с передачей автора и данных получателя;
- `DELETE /api/v2/cases/{id}/work-order/external-approval` — отзыв либо понятный `404`, если активного запроса нет.

Дополнительно проверено, что сервис не вызывается без права редактирования и для дела вне области видимости пользователя.

## Проверки

- профильный набор `CasesV2ControllerTests`: 137 сценариев;
- пять прямых сценариев `ResolveSectionAccessAsync` проверяют набор операций, области `own` и `department`, административный доступ, отказ при отсутствии права и legacy-роль без настроенных прав;
- контроль фиксированного числа SQL-команд через `DbCommandInterceptor`;
- миграции и трансляция единого снимка подтверждены на чистой временной PostgreSQL-БД;
- полный backend-набор: 2618 из 2618 сценариев, включая PostgreSQL-проверки;
- frontend: 1261 unit- и 286 integration-сценариев, lint, TypeScript и production-сборка;
- Release-сборка backend без предупреждений, форматирование и аудит NuGet/npm-зависимостей без замечаний;
- рабочие локальные SQLite- и PostgreSQL-БД находятся на последней миграции, расхождений модели со снимками миграций нет;
- проверки кодировки, дат, активных roadmap и актуальности инвентаризации прошли успешно.
