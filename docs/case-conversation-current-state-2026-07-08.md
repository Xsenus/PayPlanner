# Аудит текущей переписки дела

Дата проверки: 8 июля 2026.
Связанный roadmap: `docs/tz-crm-case-conversation-workorder-roadmap-2026-07-08.md`.

## Что уже реализовано

- В карточке дела есть вкладка "Переписка". Она загружает сообщения только при открытии вкладки и позволяет отправить текстовое внутреннее сообщение.
- Backend предоставляет два endpoint:
  - `GET /api/v2/cases/{id}/conversation` для чтения переписки.
  - `POST /api/v2/cases/{id}/conversation` для добавления сообщения.
- Чтение требует права просмотра дел, отправка требует права редактирования дел.
- Оба endpoint применяют общую модель видимости дел: пользователь с ограничением "свои" не получает чужие дела.
- Сообщение нормализуется как запись истории дела, ограничено 2000 символами и возвращается в общей ленте переписки вместе с комментариями по делу.
- Автор хранится в тексте истории как отображаемое имя пользователя.
- Новые сообщения могут отправляться с файлами. Вложения сохраняются как документы этого же дела с типом "Переписка", а в истории сообщения хранится явная ссылка на id документа.
- Текущие frontend-тесты проверяют отображение вкладки и отправку сообщения.
- Backend-тесты теперь отдельно фиксируют права доступа и видимость переписки прямыми вызовами API.

## Текущая модель хранения

Переписка не хранится отдельной таблицей. Она собирается из `ClientCase.EventHistory` по текстовым префиксам:

- "Внутреннее сообщение:" для сообщений переписки.
- "Комментарий по делу:" для комментариев, которые также показываются в переписке.
- "Вложения:" для списка id документов дела, прикрепленных к сообщению.

Идентификатор записи переписки вычисляется из позиции строки истории. Поэтому он не является стабильным внешним идентификатором сообщения и может измениться при изменении истории дела.

## Ограничения и риски

- Нет отдельной сущности сообщения, поэтому нельзя надежно привязать вложения, адресатов, статус прочтения, редактирование или удаление сообщения.
- Вложения привязаны к сообщению через текстовый маркер истории. Сами файлы не дублируются и хранятся в документах дела, но связь с конкретным сообщением пока не имеет отдельной таблицы.
- Автор сообщения хранится как текстовое имя, без постоянной связи с `UserId`.
- Нет отдельной истории доставки уведомлений по сообщению переписки.
- Нет уведомлений участникам дела о новом сообщении или вложении.
- Текущий формат зависит от текста префиксов в истории дела, поэтому будущие изменения формулировок истории могут повлиять на парсинг переписки.

## Вывод для следующих задач roadmap

Для вложений, уведомлений и стабильной связи с пользователями нужна отдельная модель сообщений переписки. Рекомендуемый следующий шаг:

- добавить отдельные записи сообщений дела с `ClientCaseId`, `AuthorUserId`, текстом, датой создания и типом;
- оставить чтение старых записей из `EventHistory` как совместимость, чтобы не потерять существующую историю;
- заменить текстовый маркер вложений на отдельную таблицу связи сообщения с документом дела, если понадобятся редактирование, удаление или статусы прочтения;
- после создания сообщения записывать событие в историю дела и отправлять уведомления участникам дела по общей системе уведомлений.
