## Цель

Защитить наиболее чувствительные поля на уровне приложения и управления ключами, сохранив поиск, резервное копирование, миграции и восстановление.

## Текущее состояние

- `[x]` OAuth-токены Google и Яндекс защищены ASP.NET Data Protection.
- `[x]` Интеграционные секреты не должны возвращаться клиенту целиком.
- `[x]` В production используется TLS и ролевое ограничение данных.
- Паспортные, адресные и иные персональные поля хранятся в обычных колонках.

## Решения заказчика

- `[decision]` Утвердить перечень персональных и специальных категорий данных.
- `[decision]` Утвердить требования регулятора, срок хранения и право удаления.
- `[decision]` Выбрать KMS/HSM/Vault либо защищенное файловое хранилище ключей.
- `[decision]` Определить допустимые ограничения поиска по зашифрованным полям.

## Этап 1. Инвентаризация и threat model

- `[ ]` Составить каталог таблиц, колонок, DTO, экспортов, логов, backup и индексов.
- `[ ]` Классифицировать поля: public/internal/confidential/highly sensitive.
- `[ ]` Зафиксировать угрозы: утечка БД, backup, логов, admin account, сервера и ключей.
- `[ ]` Определить, что закрывается disk/TDE, а что требует field-level encryption.
- `[ ]` Проверить все места поиска, сортировки, уникальности и отчетов.
- `[ ]` Подготовить план key loss/recovery и разделение полномочий.

## Этап 2. Криптографическая архитектура

- `[ ]` Использовать стандартное AEAD-шифрование с версией формата и key id.
- `[ ]` Ввести envelope encryption: data key и master key в KMS/Vault.
- `[ ]` Использовать уникальный nonce и authenticated context с entity/field id.
- `[ ]` Для точного поиска применять отдельный keyed blind index только где необходимо.
- `[ ]` Не поддерживать небезопасный contains-поиск по чувствительным данным.
- `[ ]` Подготовить key rotation без одновременной расшифровки всей базы в памяти.

## Этап 3. Реализация

- `[ ]` Создать единый encryptor и EF value conversion/interceptor policy.
- `[ ]` Разделить ciphertext, key version и blind index.
- `[ ]` Исключить plaintext из audit before/after, exceptions и structured logs.
- `[ ]` Маскировать поля в UI, экспортах и уведомлениях по правам.
- `[ ]` Пересмотреть кэш, SignalR payload, email, документы и внешние интеграции.
- `[ ]` Добавить feature flag/read-old-write-new для пошаговой миграции.

## Этап 4. Миграция данных

- `[ ]` Создать обратимую schema migration без удаления plaintext на первом шаге.
- `[ ]` Реализовать batch backfill с checkpoint, метриками и ограничением нагрузки.
- `[ ]` Проверять decrypt/compare перед очисткой исходной колонки.
- `[ ]` Выполнить dry run на копии production с измерением времени и размера.
- `[ ]` После приемки очистить plaintext и старые backup по утвержденной политике.
- `[ ]` Проверить PostgreSQL и SQLite либо официально ограничить локальный режим.

## Этап 5. Ключи и эксплуатация

- `[ ]` Настроить выдачу ключа только сервисной identity.
- `[ ]` Добавить rotation, revocation, audit доступа к ключам и alert.
- `[ ]` Включить ключи в disaster recovery без хранения рядом с backup БД.
- `[ ]` Подготовить runbook потери ключа, компрометации и восстановления.

## Производительность

- Измерить overhead чтения/записи, размер ciphertext и влияние на списки.
- Проецировать и расшифровывать только нужные поля после фильтрации.
- Не расшифровывать полные наборы ради поиска; использовать разрешенные индексы.
- Кэшировать ключевой материал безопасно и кратковременно, не plaintext записи.

## Проверки

- `[ ]` Криптографические unit-тесты tamper, wrong key, rotation и legacy format.
- `[ ]` Интеграционные тесты CRUD, поиск, экспорт, аудит и права.
- `[ ]` Проверка дампа БД/backup/log на отсутствие plaintext-маркеров.
- `[ ]` Нагрузочные сравнения до/после.
- `[ ]` Тест backup/restore с отдельным восстановлением ключей.
- `[acceptance]` Security review архитектуры и реализации.
- `[acceptance]` Восстановление тестовой среды из backup с ключами.
- `[acceptance]` Подтверждение бизнесом ограничений поиска и маскирования.

## Definition of Done

- Утечка БД или backup без ключей не раскрывает выбранные поля.
- Ключи ротируются, восстанавливаются и аудируются отдельно.
- Логи, аудит, экспорты и интеграции не обходят защиту.
- Производительность приемлема, миграция обратима, есть runbook и release note.
