## Цель

Защитить наиболее чувствительные поля на уровне приложения и управления ключами, сохранив поиск, резервное копирование, миграции и восстановление.

## Текущее состояние

- `[x]` OAuth-токены Google и Яндекс защищены ASP.NET Data Protection.
- `[x]` Интеграционные секреты не должны возвращаться клиенту целиком.
- `[x]` В production используется TLS и ролевое ограничение данных.
- Паспортные, адресные и иные персональные поля хранятся в обычных колонках.

- `[decision]` Утвердить требования регулятора, срок хранения и право удаления.
- `[decision]` Выбрать KMS/HSM/Vault либо защищенное файловое хранилище ключей.
- `[decision]` Определить допустимые ограничения поиска по зашифрованным полям.

## Этап 1. Инвентаризация и threat model

- `[x]` Составить каталог таблиц, колонок, DTO, экспортов, логов, backup и индексов.
- `[!]` Классифицировать поля: public/internal/confidential/highly sensitive — окончательная классификация персональных и специальных категорий требует решения заказчика.
- `[x]` Зафиксировать угрозы: утечка БД, backup, логов, admin account, сервера и ключей.
- `[!]` Определить, что закрывается disk/TDE, а что требует field-level encryption — техническая граница описана, но конкретные поля зависят от утверждённой классификации и требований регулятора.
- `[x]` Проверить все места поиска, сортировки, уникальности и отчетов.
- `[!]` Подготовить план key loss/recovery и разделение полномочий — конкретный runbook зависит от выбранного KMS/HSM/Vault и service identity.

## Этап 2. Криптографическая архитектура

- `[!]` Использовать стандартное AEAD-шифрование с версией формата и key id — реализация заблокирована до выбора KMS и формата хранения ключей.
- `[!]` Ввести envelope encryption: data key и master key в KMS/Vault — KMS/HSM/Vault не выбран.
- `[!]` Использовать уникальный nonce и authenticated context с entity/field id — набор шифруемых entity/field не утверждён.
- `[!]` Для точного поиска применять отдельный keyed blind index только где необходимо — допустимые поиски не утверждены.
- `[!]` Не поддерживать небезопасный contains-поиск по чувствительным данным — требуется бизнес-приёмка ограничений поиска.
- `[!]` Подготовить key rotation без одновременной расшифровки всей базы в памяти — rotation API зависит от выбранного key store.

## Этап 3. Реализация

- `[!]` Создать единый encryptor и EF value conversion/interceptor policy — криптографическая архитектура и поля не утверждены.
- `[!]` Разделить ciphertext, key version и blind index — схема зависит от KMS и поисковой политики.
- `[!]` Исключить plaintext из audit before/after, exceptions и structured logs — конкретный redaction-план зависит от утверждённого перечня полей.
- `[!]` Маскировать поля в UI, экспортах и уведомлениях по правам — уровни классификации и права маскирования не утверждены.
- `[!]` Пересмотреть кэш, SignalR payload, email, документы и внешние интеграции — состав защищаемых полей не утверждён.
- `[!]` Добавить feature flag/read-old-write-new для пошаговой миграции — dual-read схема появится после выбора ciphertext layout.

## Этап 4. Миграция данных

- `[!]` Создать обратимую schema migration без удаления plaintext на первом шаге — перечень колонок и ciphertext layout не утверждены.
- `[!]` Реализовать batch backfill с checkpoint, метриками и ограничением нагрузки — миграционная схема и KMS отсутствуют.
- `[!]` Проверять decrypt/compare перед очисткой исходной колонки — encryptor и целевые поля отсутствуют.
- `[!]` Выполнить dry run на копии production с измерением времени и размера — реализация миграции ещё не может быть создана.
- `[!]` После приемки очистить plaintext и старые backup по утвержденной политике — retention и право удаления не утверждены.
- `[!]` Проверить PostgreSQL и SQLite либо официально ограничить локальный режим — provider strategy зависит от выбранного encryptor и схемы.

## Этап 5. Ключи и эксплуатация

- `[!]` Настроить выдачу ключа только сервисной identity — key store и production identity не выбраны.
- `[!]` Добавить rotation, revocation, audit доступа к ключам и alert — возможности зависят от выбранного KMS/HSM/Vault.
- `[!]` Включить ключи в disaster recovery без хранения рядом с backup БД — DR-модель key store не выбрана.
- `[!]` Подготовить runbook потери ключа, компрометации и восстановления — невозможен без выбранного key store и разделения полномочий.

## Производительность

- Измерить overhead чтения/записи, размер ciphertext и влияние на списки.
- Проецировать и расшифровывать только нужные поля после фильтрации.
- Не расшифровывать полные наборы ради поиска; использовать разрешенные индексы.
- Кэшировать ключевой материал безопасно и кратковременно, не plaintext записи.

## Проверки

- `[!]` Криптографические unit-тесты tamper, wrong key, rotation и legacy format — encryptor и формат не выбраны.
- `[!]` Интеграционные тесты CRUD, поиск, экспорт, аудит и права — поля и правила доступа не утверждены.
- `[!]` Проверка дампа БД/backup/log на отсутствие plaintext-маркеров — применима после backfill и redaction.
- `[!]` Нагрузочные сравнения до/после — реализация шифрования отсутствует.
- `[!]` Тест backup/restore с отдельным восстановлением ключей — key store и DR-процесс не выбраны.
- `[acceptance]` Security review архитектуры и реализации.
- `[acceptance]` Восстановление тестовой среды из backup с ключами.
- `[acceptance]` Подтверждение бизнесом ограничений поиска и маскирования.

## Definition of Done

- Утечка БД или backup без ключей не раскрывает выбранные поля.
- Ключи ротируются, восстанавливаются и аудируются отдельно.
- Логи, аудит, экспорты и интеграции не обходят защиту.
- Производительность приемлема, миграция обратима, есть runbook и release note.
