**Последующее выполнение:** после отдельного разрешения пользователя удалены все 3 930 776 согласованных повторов, сохранились 55 295 записей. Задачи и связи прошли сверку, уплотнение не запускалось. ## Итог для решения

Можно убрать **3 930 776 полностью одинаковых повторов старых массовых ошибок**, сохранив **55 295 записей**. В предлагаемый первый этап входят только две причины: отсутствовавший ключ шифрования подключения и временная недоступность ожидаемого сервера провайдера. Все остальные причины ошибок сохраняются целиком.

Размер остающихся таблиц с теми же индексами измерен на новой локальной копии: **76 808 192 байт = 73,25 MiB**. Сейчас на VPS оба журнала занимают **5 782 028 288 байт = 5,385 GiB**. Ориентир возврата места после удаления согласованных повторов и последующего физического уплотнения — **около 5,3 GiB**. Расчётная разность — 5 705 220 096 байт; это оценка по локальному PostgreSQL 17.2 относительно рабочего PostgreSQL 18.6, а не обещание точного размера производственных файлов.

Само удаление строк преимущественно освобождает место для повторного использования внутри PostgreSQL. Возврат места файловой системе — отдельный этап с планированием нагрузки, свободного места и блокировок.

Ошибки отсутствующего ключа последний раз отражены 7 октября; соответствующие ключи сейчас есть. Это не заменяет ручную приёмку каждого внешнего события. Отдельные ошибки Яндекса, включая Gateway timeout 22 октября, не объявляются устранёнными и сохраняются.

## Порядок будущей очистки после отдельного разрешения

1. Использовать только окончательные списки `*-safe-candidate-ids.csv.gz`. Проверить доступность резервной копии и её сохранённые хеши, правила и фиксированный cutoff. Не повторять уже успешное восстановление без изменения/повреждения соответствующих входных данных.
2. На VPS повторно проверить свободное место, длительные транзакции, блокировки, состояние очистки, WAL и репликации. На 02:09 UTC было свободно 5,24 GiB, диск заполнен на 91%, WAL — 80 MiB, archive_mode выключен, слотов репликации нет. `max_wal_size=1 GiB` — ориентир для checkpoint, не жёсткий предел роста WAL.
3. Сначала выполнить только сверку кандидатов: существование ID, совпадение полного содержимого с остающимся представителем, дня, статуса и подключения. При несовпадении остановиться и пересмотреть затронутую часть. Сохранять сами ID представителей; обновление/удаление представителя вне плана — причина остановки. Не искать новые кандидаты расширенным условием «все старые ошибки».
4. После сверки удалять только согласованные ID, небольшими транзакциями, первоначально по 500 строк, с ограничением ожидания блокировок и длительности запроса. Контролировать объём удалений, нагрузку, WAL и запас места; при проблеме останавливаться. Держать отчёт по завершённым порциям для безопасного продолжения. Точное содержимое удалённых записей восстанавливается из проверенной копии БД.
5. Не изменять задачи, суммы, события, подключения, `*CalendarTaskLinks`, ключи и настройки email/MAX. В проверенной схеме нет внешних ключей других таблиц, ссылающихся на эти журналы; это не повод пропускать сверку схемы перед фактической операцией.
6. После удаления сверить фактические числа и неизменность рабочих объектов, проверить чтение журналов и состояние синхронизации. Использовать уже сохранённые прикладные проверки неизменённого a83c70b9; новый полный прогон приложения ради операционной очистки не нужен.
7. Отдельно выбрать обслуживание для возврата места диску. Обычный VACUUM в основном обеспечивает повторное использование места внутри БД. VACUUM FULL требует эксклюзивной блокировки и места под оставшиеся данные/индексы/WAL; выполнять его можно только после расчёта запаса и согласования окна, по одной таблице. Сейчас не запускался ни один из вариантов.

## Защита от повторного разрастания — отдельная доработка

Сохранить постоянный путь и резервирование ключей Data Protection. При системной ошибке расшифрования/доступности подключения прекращать заведомо безуспешную обработку этого подключения с ограниченной повторной попыткой; фиксировать одну понятную причину и число пропущенных операций. Уникальные ошибки отдельных задач не подавлять, состояние задач/связей и ожидающие изменения не терять, ложный успех не записывать. Проверять актуальные права и границы подключения.

Для повторов хранить первую/последнюю дату и счётчик; предусмотреть ограничение объёма подробной диагностики. Одно сокращение хранения с 90 до 30 дней недостаточно: оно затрагивает лишь около 4% текущих строк. Эта доработка пока не реализована; адресные проверки и один полный применимый прогон относятся к будущему изменённому кандидату, а не к повторному испытанию установленной версии.
