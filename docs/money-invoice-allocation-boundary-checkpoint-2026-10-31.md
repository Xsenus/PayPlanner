# Финансовая граница сопоставления денег со счётом — 31 октября 2026

Локальная реализация от `ebe707d4`, продолжение [фоновой сверки](invoice-reconciliation-boundary-checkpoint-2026-10-31.md). CMP-05 / SEC-01 / DOC-09 остаются открытыми. Общий расчёт MoneyOperationInvoiceAllocationService для LinkInvoice, Create/Update денежной операции и импорта выписки защищён общей финансовой границей.

План: сохранить текущие права money/accounts/компании/полного агрегата и ручной выбор бухгалтера; ручные финансовые пути и импорт выполняются в общей lease с актуальными правами. В общем расчёте — обязательная транзакция, упорядоченные блокировки и повторное чтение полного графа, отказ для истории отмены/неоднозначных связей/прежней переплаты, проверка кредитного минимума после сохранения. Не подменять отдельные поступления итогом и не менять исторические суммы/связи. Сохранить нормальную частичную оплату, рассрочку, переплату клиента и идемпотентный повтор вызывающих механизмов.

Обнаруженные при внедрении регрессии не объявляются успехом: переход EF из Modified в Unchanged восстанавливал старые значения при обновлении кэша, поэтому перед принятием состояния теперь явно обновляются OriginalValues. Проверка действующего пользователя при повторе native-загрузки выявила отсоединение объектов длинного контекста: импорт использует отдельный вариант той же lease, сохраняющий только чистые отслеживаемые чтения. Несохранённые изменения по-прежнему запрещены, платежи обновляются из БД целиком под блокировками. Прежние BeginAsync/BeginSystemAsync сохраняют поведение.

## Подтверждённые дефекты и границы

`baseline-v1.trx`: **4 failed из 4** за 6 секунд. Новая банковская оплата проходила поверх сохранённого аванса аннулирования/возврата; прежний overpayment по ключу операции менял сумму и описание; общий расчёт позволял стадировать изменения без транзакции. Отрицательные проверки усилены подтверждением конкретной причины отказа, чтобы ранняя посторонняя ошибка не дала ложный успех.

Ручные LinkInvoice, Create со счётом и Update с существующим/новым счётом используют RunMoneyInvoiceMutationAsync и BalanceApplicationLease. До lease сохраняются прежние проверки доступа к операции; внутри — чистый собственный контекст, SERIALIZABLE/NOWAIT PostgreSQL или прежняя немедленная SQLite-транзакция, блокировки пользователя/роли/разрешений/доступа к компаниям. Порядок company→bank→money-account→operation не менялся. Состав/видимость полного счёта и права money/accounts повторно проверяются, успешный ответ возвращается после commit. Изменение описания с защищённой скрытой ссылкой не превращается в повторное распределение. Путь без счёта сохраняет прежний MoneyMutationScope и не объявляется полностью переработанным этим этапом.

Общий расчёт требует транзакцию и сохранённую денежную операцию. Выбираются максимум 5001 ID полного графа, чтобы отказать при размере свыше 5000 без усечения; затем упорядоченные блокировки платежей, повторная проверка состава, неоднозначных связей и общей защиты отмены/компенсации. Проверяются компания денежного счёта и направление всех связанных платежей. Оптимизационный loadedPayments не считается авторитетным неполным/устаревшим графом. Все mapped scalar/скрытые поля обновляются одним запросом под блокировками, с сохранением идентичности уже отслеживаемых сущностей; нет Reload по каждой строке. Поздняя заметка и более свежая оплата не теряются. Перед принятием обновлённого состояния OriginalValues заполняются актуальными значениями.

Обычная математика распределения по срокам, действующая рассрочка, рублёвая граница и переплата клиента сохранены. Прежняя переплата по внешнему ключу больше не загружается для редактирования: требуется сверка истории, существующие сумма/владелец/описание/связь не переписываются. Новый overpayment создаётся один раз в той же транзакции. После сохранения проверяется кредитный минимум платежей и агрегата; нарушение откатывает связь операции, оплату, переплату и аудит. Ручной механизм дополнительно проверяет инвариант перед commit. Уже сверенная известная операция не получает второе применение; перенос/отвязка по-прежнему требуют отдельной операции.

Файл и native-страница импорта используют ту же lease. BeginWithTrackedReadsAsync сохраняет чистые account/user-ссылки длинного банковского контекста; pending/foreign работа по-прежнему запрещена. Разрешения и банковская привязка проверяются после блокировок. Успешный replay файла завершает собственную транзакцию, не отсоединяя чтения. Сохранённый/проверенный граф платежей отсоединяется после каждого распределения; следующие строки перечитывают его, память не растёт вместе со всеми счетами файла. Контроллер файлового/автоматического импорта возвращает понятный 400 для истории/инварианта, 403 при изменении доступа и 409 при известном конфликте. Файл атомарен в своей транзакции; native-загрузка сохраняет прежнюю границу страницы и возобновление ранее завершённых страниц.
