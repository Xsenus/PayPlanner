## Изменения

- Планировщик может использовать среднее время случая по методу из прежнего полного прогона. Все строки теории остаются вместе, новые методы входят автоматически с оценкой по медиане. Без профиля сохраняется прежнее распределение по количеству. Оценки входят в producer manifest; проверка назначения, хеша, артефактов, native exit и точного объединения случаев сохраняется.
- Команда `timings` сначала проверяет полноту четырёх частей и только затем создаёт агрегированный профиль и список дорогих методов. Неполный/неуспешный результат не становится успешной базой. Профиль влияет только на распределение, а не на выбор тестов.
- CI восстанавливает необязательный профиль времени из cache, а новый сохраняет после квалификации полного результата. Jobs, проверки, зависимости выпуска и browser gate не удалены и не пропущены. Запуск Actions пока зависит от восстановления GitHub Billing.
- ManagedCaseDocumentWireTests использует существующий class-owned SQLite-шаблон. Все синтетические runtime получают собственные файлы БД; новая проверка покрывает изоляцию, обе настройки карточки, сохранность при перезапуске и отключённую почту. Сценарии чистых миграций и прежний путь запуска без шаблона остаются.
- Карточка счёта использует общий `downloadBlob` вместо собственного варианта с немедленной очисткой URL. Форматы, API, права, имена и финансовые данные не меняются. Подготовлена неактивная запись «Что нового» 1.14.102.

## Использование профиля

Существующая команда discovery принимает необязательную пару `--timings <profile.json>`. Профиль создаётся командой:

```text
dotnet <PayPlanner.TestShards.dll> timings --manifest <test-plan.json> --manifest-sha <producer SHA256> --results-root <full-results> --output <new timing-profile.json>
```

Использовать неизменённые артефакты, указанные в исходном manifest. Сохранённые доказательства не перезаписывать. Большие TRX, БД, приватные логи и профили конкретных запусков хранить вне Git. Профиль старой версии является оценкой длительности, а не основанием пропускать новые или изменённые случаи.


## Ранняя проверка документной инвентаризации

22 октября полный запуск выявил один устаревший документный guard после сдвига строк C#. Перед следующим долгим backend gate при изменениях контроллеров или файлов с ExecuteUpdateAsync/ExecuteDeleteAsync сначала выполнить существующий `BatchOperationAuditCoverageTests` адресно на окончательной тестовой сборке (`dotnet vstest <test.dll> /TestCaseFilter:FullyQualifiedName~BatchOperationAuditCoverageTests`), с обязательными Email__Enabled=false и BackgroundServices__Enabled=false. Проверка занимает долю секунды и сверяет все 129 операций с документом; число операций и её утверждения не ослабляются. `docs/batch-operations-audit-coverage-2026-06-10.md` является тестовыми данными и должен входить в хеши квалификации, даже при общем исключении описательных Markdown-документов. Это ранний контроль, полный обязательный backend/CI барьер сохраняется.
