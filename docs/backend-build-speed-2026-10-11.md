# Скорость сборки backend — измерения 11 октября 2026

Машина измерений: 4 ядра, 15 ГБ ОЗУ, без параллельных тяжёлых процессов, SDK 10 с `DOTNET_ROLL_FORWARD=Major`, `net9.0`, Debug.

## Причина

В `PayPlanner.Api` компилировалось ≈ 1,8 млн строк сгенерированных миграций и снимков модели (454 файла, 141 МБ). Любая правка контроллера или сервиса запускала `Csc` для всей сборки.

| Измерение (правка одной строки в контроллере, `dotnet build backend/PayPlanner.Api.csproj`) | До | После |
| --- | --- | --- |
| `Csc` (компилятор) | 213,4 с | 26,7 с |
| Всё время сборки | 3 мин 49 с | 29 с |

Контрольный опыт: исключение `Migrations/**` из компиляции API дало `Csc` 24,7 с — то есть остальной код стоит ≈ 25 с, а миграции ≈ 190 с.

## Что сделано

- Миграции и снимки обеих баз перенесены (`git mv`, история файлов сохранена) в проект `backend/PayPlanner.Api.Migrations`. Пространства имён (`PayPlanner.Api.Migrations`, `...PostgreSql`), идентификаторы, провайдеры и содержимое миграций не менялись.
- Проект миграций ссылается на API только ради типов контекстов (`[DbContext(typeof(...))]`) и собирается по эталонной сборке API: если публичный контракт API не менялся, `Csc` для миграций пропускается.
- `PayPlanner.Api.csproj` после копирования результата вызывает сборку миграций и кладёт `PayPlanner.Api.Migrations.dll` рядом с собой и в публикацию (прямая ссылка проекта невозможна — получился бы цикл). Пропуск шага: `-p:PayPlannerSkipMigrationsBuild=true`.
- `PaymentContext.OnConfiguring` сам указывает сборку миграций, если она не задана явно, поэтому ни один из ≈ 430 способов создания контекста в приложении и тестах менять не пришлось.
- Проект тестов ссылается на проект миграций; проект добавлен в `PayPlanner.Api.sln` (restore/аудит NuGet в CI покрывает его).

## Правила работы

- Обычная сборка: `dotnet build backend/PayPlanner.Api.csproj` (собирает и миграции, если нужно).
- Новая миграция: сначала собрать API, затем
  `dotnet ef migrations add <Имя> --context PaymentContext --project backend/PayPlanner.Api.Migrations/PayPlanner.Api.Migrations.csproj --startup-project backend/PayPlanner.Api.csproj --output-dir Migrations --no-build`
  и то же для `PostgreSqlPaymentContext` с `--output-dir Migrations/PostgreSql`.
- Если правка меняет **публичный** контракт API (новый публичный тип, свойство модели), миграции пересобираются полностью (≈ 2,5 мин): так и должно быть, потому что модель изменилась.
- Холодная Release-сборка тестов (`restore` + `build --no-restore -c Release`): 3 мин 4 с.

## Проверки

- 146 миграционных/модельных тестов и тесты заявок/регистра на PostgreSQL: зелёные (4 мин 50 с).
- `dotnet ef migrations list`, `has-pending-model-changes` для обеих баз работают с новой раскладкой; пробная миграция сгенерирована в новом проекте с прежним пространством имён и удалена.
- `dotnet publish --no-build` включает `PayPlanner.Api.Migrations.dll`.

## Прочие измерения (кандидаты, не изменялись)

- Сборка проекта тестов после правки одного тестового файла: 58 с; после правки контроллера: 56 с (API 27 с + тесты ≈ 26 с).
- `TaskJournal.test.tsx` отдельно, без параллельных процессов: 368 сценариев, 124 с (медиана 256 мс на сценарий; самые долгие — «refreshes published files…» по 5,2 с в старой и новой карточке). Для ускорения нужно разделить файл по независимым группам с общими фикстурами в отдельном модуле — это изменение 10-тысячестрочного файла, оно выполняется отдельно и с сохранением каждого сценария обеих карточек.
- `ElectronicSignaturePreparationRaceTests` (5 частичных файлов): каждый вариант на PostgreSQL создаёт базу и применяет всю историю миграций, 5,6–7,2 с на вариант (один выброс 29,8 с при общей нагрузке), всего 16 вариантов только в одном из файлов. Существующий `PostgreSqlMigratedTemplate` (шаблон на класс, отдельный клон на сценарий) подходит, но эти тесты проверяют собственные имена баз и очистку, поэтому перевод делается отдельным шагом с проверкой владения.
