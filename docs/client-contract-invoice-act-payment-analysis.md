# Анализ связей клиент ↔ договор ↔ счет ↔ акт ↔ начисление/оплата

## Как это работает сейчас (по коду)

### 1) Базовые сущности
- **Клиент (`Client`)** имеет коллекции `Payments`, `Acts` и M:N связь с договорами через `ClientContracts`.
- **Договор (`Contract`)** не владеет финансовыми документами напрямую, а хранит **ручные привязки** через таблицы-связки:
  - `ContractActs`
  - `ContractInvoices`
  - `ContractPayments`
- **Счет в системе** фактически не отдельная таблица: это запись `Payment`, где заполнено поле `Account` (номер счета).
- **Акт (`Act`)** хранит `InvoiceNumber` (строковый номер счета), `ClientId` и прочие поля.

Итого: в текущей модели есть два разных механизма связи:
1. Явные M:N связи через `Contract*` таблицы.
2. Неявная связь счет↔акт по строке `Payment.Account == Act.InvoiceNumber`.

### 2) Клиент и договор
- Клиент и договор связаны **многие-ко-многим** через `ClientContracts`.
- В API договора при создании/обновлении **обязательно хотя бы один клиент** (`Clients` с `MinLength(1)` + серверная проверка).
- Это значит: договор без клиентов сейчас создать нельзя.

### 3) Клиент и счет/начисление/оплата
- У `Payment` поле `ClientId` nullable.
- С технической точки зрения запись `Payment` может существовать и без клиента.
- Но в `InvoicesController` (модуль счетов) создание/обновление счета требует **валидный `ClientId`**.

Практический вывод:
- **Счет без клиента через `/api/invoices` создать нельзя**.
- **Начисление/оплату через `/api/payments` без клиента создать можно** (если UI это позволяет).

### 4) Договор и счет/акт/начисление
- В `ContractsController` можно вручную передавать массивы `ActIds`, `InvoiceIds`, `PaymentIds`.
- На сохранении они пишутся в `ContractActs`, `ContractInvoices`, `ContractPayments`.
- Никакого автоматического каскада "если счет привязан к договору, то связанные начисления/оплаты/акты автоматически относятся туда же" нет.
- Это независимые наборы связей: можно привязать к договору счет, но не привязать платежи, и наоборот.

### 5) Как сейчас работает связка счет ↔ акт
- В `InvoicesController.BuildInvoiceQuery()` акты подмешиваются к счетам через `join act in acts on payment.Account equals act.InvoiceNumber`.
- Берется максимум один акт (последний по дате/id) на счет в выдаче списка счетов.
- То есть связь **не по FK**, а по совпадению номера счета в строковом поле.

Последствия текущего подхода:
- Если номер счета изменили, связь с актом в выдаче счетов может "пропасть".
- Возможны коллизии (одинаковые номера в разных контекстах).
- Нет жесткой референциальной целостности между счетом и актом.

### 6) Что с "начислениями" относительно счета/акта
- Отдельной сущности "начисление" нет: это тот же `Payment` (обычно без `Account`).
- Отдельной таблицы связи "счет ↔ начисления" тоже нет.
- Привязка начислений к договору реализована только через `ContractPayments` (ручной список IDs).
- Привязка актов к договору — через `ContractActs` (тоже ручная).

Итого: сейчас модель допускает раздельное существование и ручную оркестрацию, но не формирует строгую иерархию "договор → счета → акты/начисления/оплаты" автоматически.

---

## Проблемы текущей схемы
1. **Смешение семантики**: `Payment` одновременно счет и платеж/начисление.
2. **Слабая связь счет-акт**: строка к строке, без FK.
3. **Дублирование контуров связи**: есть и `ClientId`, и договорные M:N привязки, которые могут расходиться.
4. **Нет единого источника правды**: к какому договору относится операция — по `ContractPayments` или по клиенту и номеру счета?

## Предложение по целевой модели

### Вариант A (минимально инвазивный, рекомендую как этап 1)
Сохраняем текущие сущности, но вводим явные внешние ключи и правила:

1. В `Act` добавить `InvoiceId` (nullable FK на `Payment.Id`) и постепенно уйти от `InvoiceNumber` как основной связи.
2. В `Payment` добавить `ContractId` (nullable FK) как "основная принадлежность договору".
3. Для платежей, создаваемых из модуля счетов, хранить признак/тип записи (например `DocumentKind = Invoice|Accrual|Payment`) вместо эвристики `Account != null`.
4. Правило целостности: если у `Payment` заполнен `ContractId`, то клиент платежа должен входить в `ClientContracts` этого договора.
5. В API при привязке счета к договору — опционально авто-предложение подтянуть связанные акты и начисления (но с подтверждением пользователя).

Плюсы: небольшая миграция, минимум ломающих изменений, быстро получаем прозрачные связи.

### Вариант B (чистая доменная модель, этап 2)
Развести сущности полностью:
- `Invoice` (счет)
- `Act`
- `Accrual` (начисление)
- `PaymentTransaction` (факт оплаты)

И связать их FK:
- `Invoice.ContractId` (nullable)
- `Invoice.ClientId` (nullable или required по бизнес-правилу)
- `Act.InvoiceId` (nullable)
- `Accrual.InvoiceId`/`Accrual.ContractId` (по выбранной логике)
- `PaymentTransaction.AccrualId` или `PaymentTransaction.InvoiceId`

Плюсы: идеальная читаемость бизнес-логики, проще отчеты и контроль консистентности.
Минусы: дороже внедрение (миграции, переписывание API/UI).

## Рекомендованные бизнес-правила (как вы описали)
1. **Клиент может существовать без договоров.**
2. **Счет можно выставлять без договора** (но с клиентом или без клиента — решается отдельно политикой).
3. **Начисление/оплату можно заводить без счета и без договора.**
4. **Если документ привязан к договору, он должен быть согласован по клиенту** (клиент документа входит в клиентов договора, если клиент указан).
5. **Акт лучше связывать с конкретным счетом по FK**, а не по строковому номеру.
6. **Связь договора с документами должна быть единообразной**: либо прямой `ContractId` в документе, либо только через связки, но не смешивать без четкого приоритета.

## Предлагаемый план внедрения
1. Утвердить словарь терминов: что в системе называется "счет", "начисление", "оплата".
2. Ввести FK для счет↔акт (`Act.InvoiceId`) с обратной совместимостью через `InvoiceNumber` на период миграции.
3. Добавить `ContractId` в `Payment` как каноническую связь.
4. Обновить API фильтров и DTO (чтобы в ответах были явные `contractId`, `invoiceId`).
5. Выполнить миграцию данных (best-effort маппинг по `Account`/`InvoiceNumber`, затем ручная валидация конфликтов).
6. Только после стабилизации — решать, нужен ли полный переход на отдельные таблицы документов (вариант B).
