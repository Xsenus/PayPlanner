## Цель

Дать клиенту безопасный способ просмотреть конкретную версию заказ-наряда, согласовать ее или вернуть замечания без доступа к внутренним данным CRM.

## Текущее состояние

- `[x]` Заказ-наряд существует в карточке дела и содержит позиции, суммы и сроки.
- `[x]` Есть внутренний workflow отправки, согласования и доработки.
- `[x]` Из принятого заказ-наряда можно создавать счет, акт и договор.
- Внешней формы и надежной идентификации клиента нет.

## Решения заказчика

- `[x]` Канал: одноразовая ссылка из email и шестизначный OTP; токен не передаётся в query string и хранится только в виде hash.
- `[x]` Решение принимает один явно выбранный клиент или представитель; отправитель указывает подтверждённые ФИО и email.
- `[x]` Наружу показываются организация, клиент, дело, версия, услуги, количество, цена, итог и сроки. Внутренние заметки, себестоимость, исполнители и скрытые документы исключены.
- `[x]` Действие является операционным согласованием, а не квалифицированной электронной подписью; сохраняются версия, решение, время, подтверждённый контакт, hash IP и user agent.
- `[x]` Ссылка действует 72 часа, допускает не более пяти неверных OTP; новая отправка отзывает предыдущую ссылку.

## Этап 1. Модель согласования

- `[x]` Создать отдельную сущность запроса с immutable snapshot версии заказ-наряда.
- `[x]` Хранить token hash, срок действия, статус, число попыток и канал доставки.
- `[x]` Хранить решение, комментарий, время, hash IP, user agent и подтвержденный контакт.
- `[x]` Запретить изменение snapshot после отправки; новая версия создает новый запрос.
- `[x]` Сделать предыдущие ссылки недействительными при отзыве или новой версии.
- `[x]` Обеспечить идемпотентность повторного нажатия «Согласовать».

## Этап 2. Публичный API и безопасность

- `[x]` Создать отдельный anonymous endpoint с узким DTO без внутренних идентификаторов.
- `[x]` Хранить только hash токена; использовать криптографически стойкий одноразовый токен.
- `[x]` Добавить rate limit, блокировку перебора и безопасные ошибки.
- `[x]` Добавить подтверждение решения через email OTP.
- `[x]` Запретить index/cache/referrer leakage, настроить CSP и security headers API.
- `[x]` Не отдавать внутренние комментарии, себестоимость, исполнителей и скрытые документы.

## Этап 3. Интерфейс клиента

- `[~]` Адаптивно показать компанию, дело, услуги, количество, цену, итог и сроки; выдача разрешённых вложений ещё не добавлена.
- `[x]` Добавить действия «Согласовать» и «Вернуть с замечаниями».
- `[x]` Требовать явное подтверждение и OTP перед окончательным решением.
- `[x]` Показать срок действия, номер версии и результат уже принятого решения.
- `[x]` Обеспечить доступность с клавиатуры и телефона.

## Этап 4. Интерфейс CRM и автоматизация

- `[x]` Добавить выбор клиента или представителя с явным указанием ФИО и email.
- `[x]` Показать статус отправки, открытия, решения, отзыва, блокировки и истечения.
- `[x]` Записывать отправку и решение в историю дела и аудит.
- `[x]` Уведомлять ответственных о согласовании, замечаниях и истечении — решение клиента сразу уведомляет ответственного по делу и отправителя, а истечение обрабатывается фоновой очередью пачками без дублей.
- `[x]` После согласования предлагать создание счета/договора/акта без автоматического дублирования.
- `[x]` После замечаний возвращать заказ-наряд в доработку, сохраняя предыдущую версию.

## Производительность и хранение

- Публичный запрос должен читать один snapshot без загрузки всей карточки дела.
- Вложения выдавать через короткоживущие подписанные ссылки.
- Очистку истекших токенов выполнять пачками; аудит решений хранить по утвержденному сроку.

## Rollout

- Включать feature flag только для выбранных сотрудников и тестовых клиентов.
- Сначала разрешить просмотр, затем решения.
- Иметь кнопку отзыва всех активных ссылок.

## Definition of Done

- Клиент согласует только неизменяемую версию и видит только разрешенные данные.
- Решение доказуемо, идемпотентно и связано с историей дела.
- Истекшие и отозванные ссылки безопасны.
- Есть тесты, release note, успешный deploy и production-приемка.
