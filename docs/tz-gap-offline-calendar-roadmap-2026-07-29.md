## Цель

Обеспечить предсказуемый календарь при нестабильном интернете: просмотр ранее загруженных событий и, если утверждено, безопасное создание/изменение с последующей синхронизацией.

## Текущее состояние

- `[x]` Есть service worker для Web Push.
- `[x]` Интерфейс календаря адаптивен и синхронизируется с API онлайн.
- Кэш приложения, IndexedDB-модель, очередь изменений и разрешение offline-конфликтов отсутствуют.

## Решения заказчика

- `[decision]` Выбрать уровень: только просмотр, создание черновиков либо полное редактирование.
- `[decision]` Утвердить максимальный срок и объем локального хранения.
- `[decision]` Определить допустимость хранения названий дел и задач на устройстве.

## Этап 1. Архитектура PWA

- `[x]` Отделить push worker от versioned application cache без конфликта scope.
- `[x]` Добавить manifest, installability и стратегию обновления версии.
- `[x]` Кэшировать только статические assets и безопасный app shell.
- `[!]` Создать IndexedDB schema для минимальных calendar DTO, sync metadata и outbox — состав локальных данных зависит от выбранного уровня офлайн-режима и допустимости хранения названий.
- `[!]` Версионировать локальную схему и мигрировать ее без потери очереди — очередь появляется только в режимах с офлайн-изменениями.
- `[!]` Шифровать чувствительные локальные данные либо минимизировать их до безопасного состава — требуется утверждённый состав и срок локального хранения.

## Этап 2. Офлайн-чтение

- `[!]` Сохранять ограниченный диапазон календаря после успешной загрузки — диапазон, срок и состав локальных данных не утверждены.
- `[!]` Показывать время последней синхронизации и явный offline badge — применимо после появления локального календарного снимка.
- `[!]` Не выдавать старые данные за актуальные — правила устаревания зависят от максимального срока локального хранения.
- `[!]` Очищать кэш при logout, отзыве устройства и смене пользователя — пользовательский календарный кэш пока не создаётся; правила появятся вместе с IndexedDB-моделью.
- `[x]` Не кэшировать документы, комментарии и персональные карточки без отдельного решения.

## Этап 3. Офлайн-изменения

- `[!]` Создавать client-generated id и outbox-команды — офлайн-создание и редактирование не утверждены.
- `[!]` Поддержать утвержденные операции: create/update/move/duration/delete — перечень разрешённых операций не выбран.
- `[!]` Хранить base version/etag для optimistic concurrency — применимо после утверждения офлайн-изменений.
- `[!]` Отправлять очередь последовательно, идемпотентно и с retry/backoff — очередь не создаётся в режиме «только просмотр».
- `[!]` Не отправлять изменения после logout или смены tenant/company — применимо после утверждения outbox.
- `[!]` Предоставить экран зависших и отклоненных изменений — применимо после утверждения офлайн-изменений.

## Этап 4. Конфликты

- `[!]` Определить правила server-wins/client-wins/manual для каждого поля — требуется решение об уровне офлайн-редактирования.
- `[!]` Показать пользователю локальную и серверную версии — локальная редактируемая версия пока не утверждена.
- `[!]` Не перезаписывать согласование, статус или участников молча — набор разрешённых офлайн-операций не утверждён.
- `[!]` Перепроверять пересечения задач после восстановления сети — применимо после утверждения офлайн-переноса/редактирования.
- `[!]` Синхронизировать внешние календари только после принятия изменения CRM — применимо после утверждения офлайн-изменений.

## Производительность и безопасность

- Ограничить диапазон, число событий и размер записи; не хранить полные задачи.
- Синхронизировать дельту по cursor/version, а не перечитывать весь журнал.
- Избегать фонового spin/retry при отсутствии сети.
- Учитывать общие и чужие компьютеры: короткий TTL и remote wipe/revocation.

## Проверки

- `[!]` Unit-тесты IndexedDB, outbox, idempotency и conflict resolver — соответствующие механизмы зависят от выбранного уровня офлайн-режима.
- `[!]` Browser E2E online→offline→edit→online — офлайн-редактирование не утверждено.
- `[!]` Тест обновления service worker во время незавершенной очереди — outbox не утверждён; обновление versioned app-cache без очереди покрыто unit-тестом.
- `[!]` Тест logout, смены пользователя, отзыва доступа и удаления задачи на сервере — пользовательские данные пока намеренно не кэшируются.
- `[!]` Lighthouse/PWA и проверка Chrome/Edge/mobile Safari с зафиксированными ограничениями — требует ручного browser/device-прогона после утверждения целевого уровня офлайн-режима.
- `[acceptance]` Проверить ноутбук и телефон при полном отключении сети.
- `[acceptance]` Подтвердить понятность конфликтов и отсутствие потери изменений.

## Rollout и Definition of Done

- Сначала read-only offline, затем черновики, затем редактирование.
- Каждый уровень включать отдельным feature flag.
- Готовность: нет утечки между пользователями, очередь идемпотентна, конфликты не теряют данные, обновление PWA безопасно, тесты и production smoke успешны.
