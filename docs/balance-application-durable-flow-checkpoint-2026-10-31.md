## Реализовано локально

Новый `balanceApplicationAttempts` сохраняет до денежного POST только девять полей: версию, пользователя, API, вид/ID контрагента, ID платежа, случайный UUID, SHA256 команды и время. Сумма, описание, финансовая команда и токен не сохраняются. Проверяются допустимый API без credentials/query/hash, размеры, точные поля, UUID и read-back. Повреждённая/недоступная запись запрещает новую отправку. Существующая неизвестная попытка запрещает другой UUID и повторный POST; проверки и закрытие попытки выполняются только явно.

Используются существующие auth/session owner и короткая общая Web Lock для мутаций metadata; финансовая блокировка отдельна для каждого платежа/контрагента. Ограничения: 64 незакрытых записи пользователя, 4096 ключей в storage, 4096 символов на запись. При отсутствии Web Locks/WebCrypto механизм останавливается до списания. Для одного результата не создаются фоновые опросы или повторяющиеся таймеры. Один срок 45 секунд ограничивает активное действие; abort и логические проверки запрещают поздние продолжения даже при транспорте, игнорирующем abort. Смена владельца сразу прерывает активные действия; слушатель существует только при наличии активных операций. Событие освобождения посылается после фактического отпускания Web Lock, чтобы пассивная форма не осталась занятой.

Apply/Inspect/Cancel и оба канонических GET связаны с одним actor/API/session/generation. Инъецированный обязательный guard проверяет также фактический JWT до чтения/записи metadata; API-порты сохраняют эту связь до/после запроса и чтения тела, включая подготовку/refresh сессии. Драйвер не импортирует API и не создаёт циклическую зависимость.

Новые методы `applyClientBalanceGuarded` / `applyLegalEntityBalanceGuarded` используют только отдельный managed-маршрут; fallback на legacy отсутствует. После каждого Committed, включая свежий ACK и результат отмены уже исполненной попытки, загружаются актуальные платёж и баланс. Они проверяются на владельца/ID/допустимые суммы. Исторический остаток операции хранится отдельно от текущего остатка; прибавления к устаревшей форме здесь нет. Неопределённый исход сохраняет запись. Cancelled не возвращает деньги и требует явного принятия результата.

Принятие результата связано с точным объектом в WeakMap, текущим сеансом и точной сохранённой записью. Копия объекта или ответ старой попытки не могут удалить новую запись. Стирание происходит только после явного подтверждения принятия, под короткой блокировкой, с read-back. Уведомления metadata не должны становиться частью ключа владельца будущей формы.

**Это ещё не включено в денежные кнопки.** Прежние UI-вызовы legacy API пока сохранены, чтобы не подменить финансовый контракт до готовности формы восстановления. Backend, модель, миграции, задачи и исторические документы не менялись. Неактивные записи 1.14.478–480 описывают готовящийся механизм; отдельная запись для неиспользуемого внутреннего этапа не добавлялась.

## Следующий этап

Подключить компактный общий блок проверки/закрытия попытки к PaymentModal и распределению аванса. Сначала защитить тип callback: он должен вернуть proof-bearing Committed с каноническим платежом, затем переключить все прямые вызовы и ClientDetail на guarded API. Обрабатывать текущий и выбранный платёж рассрочки; после повторного открытия показывать неизвестную попытку даже если полностью оплаченный целевой платёж уже исчез из списка долгов. Каноническая оплата и сумма зачтённого аванса заменяют старую финансовую часть формы, остальные введённые поля сохраняются; replay не увеличивает локальный минимум второй раз. До подтверждённого закрытия запретить новое денежное действие/сохранение, но оставить восстановление доступным вне disabled fieldset. Внешние callbacks/refresh принимают только текущий контекст; поздняя ошибка не должна затрагивать следующую карточку.

Добавить адресные компонентные сценарии с реальным lifecycle, проверку обеих форм/обоих владельцев, переоткрытие/параллельные вкладки, потерянный ACK, отказ GET, Cancel обнаруживает Committed, смену прав/пользователя/карточки и сохранение ввода. Браузерная проверка должна использовать настоящие storage/Web Locks. Затем продолжить оставшиеся callbacks, CMP-05 и справочники/CMP-04/CMP-06.
