## Воспроизводимый запуск

Следовать [quality gates](quality-gates.md). Существующий локальный PostgreSQL 17.2: `127.0.0.1:5433`, отдельная роль `payplanner_ci`, управляющая БД `postgres`, тестовые данные в существующем tablespace `payplanner_local` на E. Пароль находится в локальном DPAPI-хранилище; его нельзя добавлять в командную строку или Git. Рабочая БД `payplanner` не используется для разрушительных проверок.

В обычной разработке сначала посмотреть область изменений командой `node scripts/verification-scope.mjs`. Она печатает план и не запускает проверки. Для изменения автоматизации задач адресный frontend-пример: `npm run test:unit -- src/components/Tasks/TaskJournal.automation.test.tsx`. При изменении другого блока выбрать его тестовые файлы; после правок типизированного frontend использовать существующие кэшируемые `npm run lint` и `npm run typecheck`.

Backend во время работы проверять существующим `dotnet test` с фильтром `FullyQualifiedName` на затронутые методы/классы, используя заранее настроенное безопасное локальное окружение из quality gates. `--no-build` допустим только после сборки актуальных исходников в той же конфигурации. Один адресный успех не заменяет полный gate. Production UI build и полный применимый набор выполняются после завершения связанного пакета; успешные доказательства затем сохраняются для commit/push/передачи при совпадении входов.

1. Подготовить зависимости и существующий браузер/CLI; выставить обязательные ограничения локальной почты и фоновых служб. Подробные предпосылки проверяет runner.
2. Выбрать новый каталог на E с запасом места. По умолчанию сборка требует не менее 8 ГиБ свободной RAM. Команда `node scripts/run-backend-gate.mjs --results E:/ProjectTemp/PayPlanner/<run> --prepare-only --detach` строит и фиксирует кандидат без запуска тестов. Пользователь разрешил продолжить при текущей нагрузке: для этого предусмотрен явный `--workers 1 --allow-memory-pressure`. Ограничения GC, проверка диска и полноты результатов сохраняются; фактическая память и выбранный режим записываются в результат. Это разрешение на запуск, а не гарантия скорости или успешного завершения при нехватке ресурсов.
3. После адресных проверок и фиксации окончательных входов запустить тот же каталог с `--resume --detach` без `--prepare-only`. Автоматически выбирается один работник либо два при не менее 10 ГиБ свободной RAM и четырёх процессорах. Не запускать тяжёлые frontend и backend проверки одновременно на перегруженном ПК.
4. Проверять `state.json` и stage logs. `prepared` означает только сборку и каталог. Успех backend требует `qualified: true`, результатов всех частей и пяти восстановленных browser-сценариев. Отдельно необходимы frontend, форматирование и security gates.
5. Повторно использовать успешные результаты только для неизменных проверяемых входов и среды. Изменение кода, зависимостей, проверяемых документов или среды требует нового кандидата. Отчёты без влияния на тесты допускается явно перечислить через `--untested-doc`; известные тестируемые документы исключать нельзя.
