# Текущее состояние запроса переноса срока задачи

Дата аудита: 9 июля 2026.
Связанный roadmap: `archive/roadmaps/task-deadline-change-approval-roadmap-2026-07-09.md`.

## Что уже есть

- В настройках журнала задач есть переключатель `allowExecutorDeadlineChangeRequests`, который включает или отключает возможность исполнителю запросить перенос срока.
- В старой и новой карточке задачи исполнитель без права редактирования видит блок "Запрос переноса срока", если он является исполнителем задачи, не является постановщиком и настройка включена.
- Frontend отправляет запрос через `apiService.createTaskJournalDeadlineChangeRequest(taskId, { requestedDueAt, reason })`.
- Backend endpoint `POST /api/tasks/{id}/deadline-change-requests` проверяет доступ к задаче, включенную настройку и то, что текущий пользователь является исполнителем, но не автором задачи.
- Запрос сохраняется как запись истории задачи: `TaskJournalComment` с `Kind = "system"` и `MetadataJson.type = "deadlineChangeRequest"`.
- Текущий backend-тест подтверждает, что запрос добавляет историю и не меняет фактический срок задачи.
- Текущий frontend-тест подтверждает, что исполнитель отправляет запрос через карточку задачи, а срок задачи напрямую не меняется.

## Что сейчас не работает как процесс согласования

- У запроса нет отдельной сущности, статуса и жизненного цикла. Он существует только как комментарий в истории.
- Причина переноса сейчас необязательная: пустой `reason` принимается backend и UI не блокирует отправку без причины.
- После создания запроса backend не вызывает уведомление постановщику. В отличие от обычного комментария, endpoint не вызывает `NotifyTaskCommentAsync`.
- Для постановщика нет отдельного действия "согласовать перенос" или "отказать".
- Нет API, которое применяет согласованный новый срок и фиксирует решение по запросу.
- Нет API отказа с комментарием.
- Раздел "Согласования" сейчас работает вокруг статусов `onApproval`, `approved`, `revision`, `overdueApproval`, но не показывает запросы переноса срока.
- В карточке задачи запрос виден только в истории комментариев, если пользователь открыл конкретную задачу.
- Нет принудительного центрального окна для постановщика.
- Нет счетчика или отдельного фильтра активных запросов переноса срока.
- Нет защиты от повторных активных запросов по одной задаче.

## Текущий пользовательский сценарий

1. Исполнитель открывает задачу в режиме просмотра.
2. Если у него нет права редактирования и включена настройка запросов, он видит блок запроса переноса.
3. Исполнитель выбирает новую дату и может ввести причину.
4. CRM отправляет `POST /api/tasks/{id}/deadline-change-requests`.
5. Backend создает системную запись в истории задачи.
6. Исполнитель видит toast о добавлении запроса в историю.
7. Постановщик не получает отдельного рабочего действия и должен сам найти запись в истории задачи.

## Вывод

Жалоба клиента подтверждена: текущая функция технически фиксирует просьбу исполнителя в истории, но не создает управляемый процесс. Для закрытия задачи нужен отдельный поток согласования переноса срока: модель или расширенный контракт запроса, обязательная причина, уведомление/принудительное окно постановщика, действия согласовать/отказать, отображение в "Согласованиях", история решений и тесты.

## Следующий безопасный шаг

Спроектировать модель запроса переноса срока так, чтобы ее можно было хранить, находить как активный запрос, показывать постановщику и закрывать решением. Минимальный вариант: отдельная таблица запросов с привязкой к задаче и комментариями истории. Временный вариант на `TaskJournalComment.MetadataJson` технически возможен, но хуже для статусов, фильтров, прав и раздела "Согласования".
