## Исправленные границы

Два отказа воспроизведены до реализации: после смены сеанса без rerender поздний список дел показывал приватное название в открытом выборе; после перехода к другой компании загруженные подробности прежнего платежа открывали её редактор. `reproduction-v1.json`: 0 успехов / два ожидаемых отказа.

Чтение списка дел InvoiceModal теперь использует существующий срок жизни операции и снимок сеанса. Область включает open/режим/представление/счёт/контрагента/тип/пользователя/роль/действующий доступ и ограничения видимости. Проверяется принадлежность ответа текущему запросу, включая возврат прежних прав или прежней карточки. Старый ответ/ошибка не принимаются без нового render после смены входа. Обычное обновление токена того же входа не создаёт новый GET. Поколение списка после успешного создания дела из предыдущего этапа сохранено.

Кэш имён/ошибок и открытый выбор очищаются до показа новой области через layout-effect; несохранённый счёт целиком не сбрасывается. GET и обработчик выбора требуют актуального аутентифицированного сеанса, права просмотра дел и действующего доступа к счёту; создание нового счёта допускает разрешение создания вместо просмотра раздела. Ответ должен быть массивом с положительными целыми ID, каждый элемент относится к запрошенному clientId либо legalEntityId. Второй допустимый владелец исторической строки не отрезается: проверяется именно запрошенная связь. Исторические строки не фильтруются и не переписываются.

Выбранные ID не удаляются при отзыве права чтения. Уже включённые в полученный с сервера счёт сведения остаются частью его прежнего договора данных; новый запрос списка без права не отправляется. Связь сохранённого счёта проверена отдельным тестом. Защита нового создания дела и его ответов из предыдущего этапа не ослаблена.

Открытие платежа в LegalEntityModal привязано к компании/версии профиля/форме/сеансу/правам/фильтру дела и текущему окну платежа. Пока детали одного ID загружаются, повторное нажатие не отправляет ещё один GET. Выбор другого ID заменяет прежнее намерение; открытие нового платежа и закрытие редактора сразу отзывают старое намерение. Ответ с другим ID не открывает редактор. Старое завершение не очищает новое намерение, старые ошибки не показываются в новой карточке. Текущая ошибка позволяет явный повтор. Обе формы page/modal сохранены.

Принадлежность платежа не сужена по одному полю DTO. Неизменённый QueryExtensions.ApplyPaymentFilters допускает основную/расходную компанию и связи через InvoicePayments одной группы. Поэтому для деталей проверяются актуальная разрешённая область чтения и точный запрошенный ID; права на этот ID остаются серверными. Допустимый платёж через связанный счёт с иными собственными полями не отклоняется по догадке. Стороны/суммы/начисления не менялись.
