# Аудит результата задачи перед согласованием

Дата: 9 июля 2026.
Связанный roadmap: `docs/task-result-approval-roadmap-2026-07-09.md`.

## Что проверено

- Backend API создания и редактирования задач в `TasksController`: `CreateTask`, `UpdateTask`, `UpdateStatus`, `UpdateApproval`.
- Модели запросов `UpsertTaskJournalItemRequest`, `UpdateTaskJournalStatusRequest`, `UpdateTaskJournalApprovalRequest`.
- Frontend-пути в `TaskJournal.tsx`: быстрое завершение из списка, сохранение старой карточки, сохранение нового окна задачи, действия согласующего.
- Тесты `TaskJournal.test.tsx` по завершению, отправке на согласование, возврату на доработку и сохранению результата.
- Уведомления и история через `AddTaskHistory`, `NotifyTaskApprovalRequestedAsync`, `NotifyTaskApprovalDecisionAsync`, `NotifyTaskCompletedAsync`.

## Текущее поведение

- При завершении задачи в статус `done` результат уже обязателен, если включена настройка обязательного результата завершения. Это проверяется на frontend и backend.
- Быстрое действие "Завершить" при наличии несогласованных согласующих переводит задачу не в `done`, а в `onApproval`.
- Для статуса `onApproval` backend сейчас проверяет только наличие хотя бы одного согласующего. Пустой результат не блокирует отправку на согласование.
- В старой и новой карточке задачи поле результата в обычном режиме доступно только при статусе `done`. При отправке на `onApproval` отдельного окна ввода результата пока нет.
- При сохранении существующей задачи со статусом `onApproval` backend перезапускает очередь согласования и отправляет уведомление согласующим, если задача вошла в активное согласование.
- Раздел "Согласования" показывает задачи текущему согласующему по очереди, а также уже имеет принудительное окно для запросов переноса срока. Отдельного принудительного окна именно для результата задачи перед согласованием пока нет.
- Решение согласующего уже фиксируется в истории задачи как системный комментарий с metadata `approvalDecision`; возврат на доработку требует рецензию, согласование может передать `resolution`.
- Если последний согласующий завершает задачу, backend сейчас подставляет результат "Задача выполнена.", если результат пустой. После усиления правила до отправки на согласование этот fallback должен стать аварийной защитой, а не обычным сценарием.

## Найденные разрывы

- Исполнитель может отправить задачу на согласование без результата через быстрый путь завершения, если у задачи есть ожидающие согласующие.
- Исполнитель может сохранить задачу в статусе `onApproval` без результата из карточки задачи.
- API `PATCH /api/tasks/{id}/status` и `PUT /api/tasks/{id}` принимают `onApproval` без результата, если есть согласующий.
- UX не объясняет исполнителю, какой результат увидит согласующий, потому что окно ввода результата появляется только для завершения `done`.
- Согласующий видит задачу и может принять решение, но нет отдельного центрального окна, которое явно показывает результат задачи и требует принять или вернуть работу.

## Рекомендации для следующих пунктов

- Усилить `ValidateStatusRules`: при переходе в `onApproval` или `overdueApproval` требовать непустой результат, если включено правило обязательного результата.
- Передавать результат в `updateTaskJournalStatus` при отправке задачи на согласование, а не только при `done`.
- Для старой и новой карточки открыть обязательное окно "Добавить результат по задаче" перед переводом в `onApproval`, если результат пустой.
- Разрешить редактирование поля результата в момент отправки на согласование, но не открывать свободное редактирование результата в любых статусах без явного сценария.
- В разделе "Согласования" добавить центральное окно для текущего согласующего: задача, исполнитель, результат, срок согласования, действия "Согласовать" и "Вернуть на доработку".
- Историю результата и решения согласующего вести через уже существующие системные комментарии, расширив текст/metadata только там, где согласующему или исполнителю нужен более понятный след.

## Проверки аудита

- Код прочитан статически, изменений в поведении, схеме БД и пользовательском интерфейсе в рамках аудита нет.
- Новых миграций не требуется.
- Запись в "Что нового" не добавлялась, потому что аудит не меняет продукт для пользователя.
