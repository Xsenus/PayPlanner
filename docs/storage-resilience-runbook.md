# Регламент отказоустойчивого хранения PayPlanner

Документ описывает безопасную эксплуатацию механизма хранения и резервного копирования. Он не является разрешением на работу с production: включение маршрутизации, реальный backfill, проверка внешних провайдеров и восстановление PostgreSQL выполняются только в согласованное окно изменений.

## Безопасные значения по умолчанию

- `StorageOrchestration:Enabled=false` — существующие загрузки продолжают работать по прежним путям.
- `StorageOrchestration:WorkerEnabled=false` — очередь репликации не обрабатывается автоматически.
- Политика по умолчанию — одна локальная копия; внешнее назначение не подставляется молча.
- `DatabaseRestoreDrill:PostgreSqlExecutionEnabled=false` — PostgreSQL проходит только проверку комплекта, пока оператор явно не настроит отдельную тестовую БД.
- Для локального запуска обязательны `BackgroundServices__Enabled=false` и `Email__Enabled=false`. На копии production-БД настройка `notifications.email.enabled` в самой БД также должна быть выключена.

## Проверка резервной копии

1. Откройте «Настройки → Обслуживание БД → Резервные копии».
2. Нажмите «Проверить» у выбранного файла.
3. Успех означает, что manifest существует, статус комплекта завершён, размеры и SHA-256 основной БД и обязательных файловых частей совпадают.
4. Legacy-копия без manifest показывается как непроверенная и не должна быть единственной точкой восстановления.
5. При ошибке не удаляйте предыдущий полный комплект. Сохраните `BackupId`, имя части и текст ошибки без секретов.

## Журнал комплектов и копий

- На вкладке «Резервные копии» администратор видит отдельный журнал комплектов. Он загружается страницами; «Следующие копии» открывает более старые записи, «Обновить журнал» возвращает к свежим.
- «Проверено при создании» относится к локальному комплекту; «Проверено после отправки» означает, что обязательные облачные части были прочитаны обратно и сверены. Время последней проверки показано рядом. Эти отметки не гарантируют текущую доступность и не заменяют restore drill.
- «Ошибка» и «Загрузка не подтверждена» не считаются проверенной облачной копией. «Удалено» у локального файла не удаляет сведения о копиях в облаке. Отдельные ключи шифрования этим журналом не проверяются.
- Регистрируются новые комплекты и старые комплекты при проверенной повторной отправке. Автоматический импорт всех старых manifest пока не реализован; отсутствие записи в журнале не доказывает отсутствия старого файла.
- Read-only API: `GET /api/database/backups/catalog?pageSize=20&after=<BackupId>`, только администратор; максимум 100 комплектов за запрос. `nextCursor=null` означает последнюю страницу. API не выполняет облачных запросов и не меняет копии.

## Тестовое восстановление

1. Сначала выполните обычную проверку комплекта.
2. Нажмите «Тест восстановления». SQLite восстанавливается в новый уникальный каталог, затем выполняются `integrity_check`, `foreign_key_check` и подсчёт таблиц. Рабочий файл БД не заменяется.
3. Для PostgreSQL по умолчанию формируется validation-only отчёт. Фактическое восстановление разрешается только в отдельную БД из allowlist (либо с именем `payplanner_restore_*`), с отличающейся от рабочей строкой подключения и confirmation token.
4. После PostgreSQL-drill в восстановленной БД принудительно отключается почтовая настройка.
5. Отчёт хранится в каталоге drill и содержит длительность, результат целостности и число нарушений связей.

## Отказ провайдера и UNKNOWN

- Ошибки `Unavailable` и `Unknown` учитываются отдельно по провайдеру. После порога circuit breaker временно исключает его из новых попыток; бизнес-ответы `NotFound` и `Conflict` не считаются сетевым отказом.
- Неизвестный исход записи никогда не запускает слепую запись в другое место. Worker сначала выполняет `Head` и сверяет generation, размер и SHA-256.
- Если пригодна другая проверенная реплика той же generation, чтение переключается до начала отдачи тела ответа. Части разных поколений не смешиваются.
- Dead-letter и старейшая ожидающая операция видны в `GET /api/storage/health`; повтор операции выполняется администратором только после устранения причины.

## Возврат провайдера

1. Дождитесь окончания cooldown и проверьте состояние через admin health.
2. Запустите reconciliation сначала с `apply=false`.
3. Проверьте missing/corrupt/delete debt. При `apply=true` система ставит repair/delete в durable queue, но не воскрешает объекты с tombstone.
4. Не меняйте preferred provider глобально, пока debt и corrupt не равны нулю и контрольные чтения не прошли.
5. Автоматический глобальный failback намеренно отсутствует: окончательное переключение требует решения оператора.

## Удаление и удержание

- Логическое удаление сразу скрывает объект и создаёт tombstone.
- При retention физические операции получают `NextAttemptAt` не раньше даты окончания хранения.
- При legal hold физическое удаление не ставится в очередь. Reconciliation показывает состояние `retained`.
- Legacy-файлы read-only: provider `legacy-local` не поддерживает физическое удаление. Исходники сохраняются до отдельной приёмки миграции.

## Исторический backfill

1. Используйте `POST /api/storage/legacy-backfill` только под ролью администратора.
2. Обязательно начните с `apply=false`; укажите один source, `afterId` и batch не более 500.
3. Допустимые sources: `task-files`, `case-documents`, `internal-chat`, `messenger-snapshots`, `electronic-signatures`, `profile-photos`.
4. Сохраните `NextAfterId`, повторяйте пакет до `HasMore=false`. Повтор безопасен: идентификаторы детерминированы, исходные bytes не копируются и не удаляются.
5. Статусы `missing` и `invalid` не скрывайте из отчёта. Назначьте владельца исключения и устраните причину до включения чтения через каталог.
6. После dry-run выполните `apply=true` на canary-пакете, затем reconciliation. Реальный массовый backfill относится к отдельной production-приёмке.

## Потеря ключей Data Protection

- S3 Secret Key хранится защищённым и мигрирует из plaintext при чтении.
- Каталог ключей Data Protection должен быть персистентным (`/opt/payplanner/shared/data-protection-keys` в deploy workflow) и иметь отдельную защищённую резервную копию.
- Если key ring потерян, не перезаписывайте значения пустыми: восстановите соответствующий key ring по `RecoveryKeyReference`. Без него расшифровка существующих секретов невозможна.

## Откат

1. Выключите `StorageOrchestration:Enabled` и `WorkerEnabled`.
2. Legacy-пути продолжают обслуживать прежние файлы; catalog/outbox не удаляйте — они нужны для расследования и повторного включения.
3. Не откатывайте additive schema, если появились catalog rows.
4. Не удаляйте исходные файлы, старый backup или tombstones в ходе отката.
5. Зафиксируйте ревизию, значения flags, backlog, последний проверенный BackupId и результаты контрольного чтения.

## Обязательный gate перед production

- Полные backend/frontend tests, lint, typecheck, encoding audit и production build зелёные.
- SQLite clean/upgrade migration paths пройдены; PostgreSQL migration SQL проверен и отдельный тестовый restore выполнен оператором.
- Есть минимум один проверенный полный BackupSet и успешный restore drill.
- Подтверждены разрешения, квота, versioning/retention и failure-domain внешних провайдеров.
- Утверждены RPO/RTO, число обязательных копий, классы данных, сроки хранения и владелец alert-ов.
- Только после этого: schema → shadow catalog → canary backfill → dual-write → canary read → наблюдение → поэтапное включение классов.
