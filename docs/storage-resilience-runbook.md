# Регламент отказоустойчивого хранения PayPlanner

## Статус известной попытки документа дела

Read-only batch известных keys различает waiting (очередь ожидает копий/обработки), retrying (временный отказ с автоматическим повтором), paused (режим/worker выключен или worker не зарегистрирован), failed (окончательный отказ/недоступный receipt), manualRetry (назначения нет), uploaded (проверенный документ и binding) и unknown (попытка не подтверждена). Автоматическая обработка не обещается по одному изменению configuration: нужны global storage/write/capacity flags, AutoCaseDocumentPublicationEnabled, WorkerEnabled и startup registration snapshot. Статус читает только свои actor/case keys (до 50), перед/после metadata повторно проверяет текущие права, не читает файлы и не выдаёт provider errors.

Очередь сопоставляется по canonical publication key/object/generation. Если между commit read и queue read публикация завершилась, terminal попытки перечитываются одним ограниченным запросом; свежий receipt имеет приоритет перед окончательным статусом очереди. Pending batch без receipt использует три metadata reads; already uploaded — прежние три; refresh race с receipt — пять. Окончательные 444/444 backend, frontend320/320, tsc/eslint/encoding2515 прошли; TRX case-queue-status-expanded-final.trx. Это status известных attempts, а не discovery или UI polling: ранее открытые ограничения в этом runbook по отсутствию queue-aware status относятся к предыдущему этапу. Поиск pending после открытия карточки, управление новой попыткой, операторский backlog/retry, полный release gate и рабочая приёмка ещё открыты.

## Автоматическое завершение загрузок документов дела — локальный opt-in

Фоновая публикация реализована отдельно от discovery/UI. Для runtime нужны StorageOrchestration:Enabled, UploadCapacityChecksEnabled, case-document в ProductWriteEnabledClasses, AutoCaseDocumentPublicationEnabled, WorkerEnabled и зарегистрированный storage worker. Новый флаг по умолчанию false. Для всех локальных запусков по-прежнему обязательны BackgroundServices__Enabled=false и Email__Enabled=false: тесты вызывают processor явно на собственных синтетических БД, включать фоновые службы ради проверки нельзя.

Тип операции publishCaseDocument, ключ case-document-publication:{commitId:N}; новая схема БД не требуется. Producer добавляет назначение в общей транзакции; scheduler ограничен WorkerBatchSize (1–200) и может восстановить старые pending назначения. Task-file case copies исключены по владельцу. До domain commit повторно проверяются текущие права исходного автора, включённый режим и исходная живая lease. Ожидание копий/отключённого режима не расходует попытки, временный отказ повторяется с задержкой, постоянный отказ или исчерпание попыток переходит в deadLetter. Settlement условный; замена/истечение lease не позволяет старому worker завершить чужую операцию. Потеря подтверждения commit восстанавливается по сохранённому domain/binding/generation receipt, без повторного PUT или уведомления. Доставка уведомлений документа остаётся Silent/InApp-only через существующую очередь после commit.

Квалификация: адресные 46/46; расширенные 823/824, новый consumer 16/16, отдельный повтор отказавшего браузерного метода 5/5. Исходный timeout и оба TRX сохранены в .codex-build/case-queue-20260930/. Локальная 1.14.47; полного release gate/rollout/реальной приёмки нет. Статус известной pending загрузки пока не различает эту очередь и может предлагать ручной повтор: queue-aware status — следующий обязательный этап, до UI polling. Discovery, список pending, operator backlog/deadLetter/retry, остальные writers и рабочие решения о копиях/ключах/retention остаются открытыми. Последующие описания отсутствия automatic consumer относятся к прежним этапам, а не текущему состоянию.

Документ описывает безопасную эксплуатацию механизма хранения и резервного копирования. Он не является разрешением на работу с production: включение маршрутизации, реальный backfill, проверка внешних провайдеров и восстановление PostgreSQL выполняются только в согласованное окно изменений.

## Управляемая загрузка самостоятельного документа дела

Внутренний `IManagedCaseDocumentUploadService.ResumeAsync` может завершить сохранённый commit intent из проверенной копии без исходного браузерного File. Это service-level prerequisite: HTTP endpoint, automatic publication worker и discovery этим этапом не добавлены. Caller передаёт внешнюю authority/lease callback и общие persist/atomic callbacks того же scoped context; собственные текущие права автора проверяются самим writer. Отказ authority до/после provider I/O либо под lock не публикует domain rows; исходные данные попытки сохраняются. Размер/SHA/key/owner/generation проверяются до чтения, source reader проверяет фактические байты, ordinary upload сохраняет bounded staging/required-copy gate/transaction. `VerifyPublishedAsync` — внутренний read-only receipt proof после racing publisher, без provider I/O; не выдавать этот метод как HTTP read без actor/case authorization. Новый контекст, first/version/replay, role revoke during read, intent mutation, rollback/lost commit ACK и immutable receipt квалифицированы в **419/419 без пропусков**, `.codex-build/case-resume-20260930/case-resume-expanded-final.trx`; 25 новых cases на SQLite/owned PostgreSQL. Schema/default flags не менялись, полного release gate/browser/VPS приёмки нет.

Ручная загрузка файла дела и новой версии подключены к managed writer при `StorageOrchestration:Enabled=true`, наличии `case-document` в `ProductWriteEnabledClasses` и `UploadCapacityChecksEnabled=true`. Для чтения требуется тот же класс в `ProductReadEnabledClasses`. Настройки по умолчанию не включаются этим изменением. Один и тот же class flag используется также документами, связанными с файлами задач: при его включении нужно учитывать оба пути. Обновлённый frontend передаёт ровно один непустой GUID в `X-Upload-Key`; старый клиент без этого заголовка получает 400, не скрытый переход к legacy записи.

Идентификатор сохраняется отдельно по API, сотруднику, делу/документу и параметрам загрузки в пределах вкладки. При потерянном ответе повтор той же попытки сохраняет ключ; после подтверждённого ответа следующая намеренная загрузка получает новый. Размер/имя/время браузерного File служат только для выбора попытки: сервер независимо проверяет точные байты и параметры. 503 с `Retry-After: 5` означает, что обязательные копии или authority ещё не подтверждены. Ручное завершение pending отправляет файл в API для проверки; чтение уже опубликованного receipt по правилам ниже обходится без повторного multipart. Не подменять исходный файл другим содержимым при повторе: несовпадение получает 409.

Миграции `AddStorageUploadProductContexts` / `AddStorageUploadProductContextsPostgres` добавляют nullable JSON исходного intent в первичную локальную строку `StorageCapacityReservations`. Данные не дублируются на каждой копии. После local ACK loss новый контекст использует прежние document key, версию и время; локальный объект проверяется по SHA/размеру до повторного PUT. Изменённая или неизвестная копия не перезаписывается. В PostgreSQL исходное время нормализуется до сохраняемой микросекундной точности. Прежние pending строки имеют NULL: у них нельзя восстановить несуществующие исходные параметры из одного хеша, поэтому при несовпадении резерв остаётся для отдельной сверки, автоматическая очистка/новый intent не разрешаются.

Документ, история дела, audit, уведомление, передача владельца объекта, product binding и результат intent публикуются в одной короткой транзакции после provider I/O и обязательных копий. Права и feature flags проверяются ещё раз под блокировкой дела. Потерянный commit ACK сохраняет байты; точный повтор возвращает receipt без дублирования доменных записей. Изменение редактируемых типа/статуса документа между повторами не отменяется прежним receipt. Удалённый документ или tombstone каталога не восстанавливается повторной отправкой.

Шаблоны, заказ-наряды и вложения чата этим writer не покрыты. Автоматическая case publication, read-only статус pending и явное управление новой попыткой после окончательного конфликта остаются отдельной работой TASK-014/020/022. Не объявлять этот подпункт переключением всего класса или полной границей резервного снимка. Реальная независимость обязательных копий, Linux/cloud, retention/ключи и рабочая приёмка остаются условиями rollout.

## Чтение результата самостоятельной загрузки дела

`GET /api/v2/cases/{caseId}/documents/uploads?uploadKeys={guid}` читает только 1–50 известных ключей текущего сотрудника и дела. Пустой список, нулевой GUID и более 50 ключей дают 400; отсутствие текущего доступа — 403 без названий и metadata. Fresh active/approved/Cases.CanEdit/visibility проверяются до и после чтения. Заголовок `Cache-Control: no-store`, nullable поля явно сериализуются как null. Ответ не раскрывает payload, физические пути, locator, provider connection или технические ошибки.

Сначала читается pending primary local reserve, затем catalog commits; это позволяет видеть intent до catalog commit и не терять committed receipt при освобождении резерва. Domain receipts/bindings проверяются одним exact-ID batch, без N+1. Для 50 ключей с опубликованным receipt выполняются ровно три metadata query на SQLite/PostgreSQL; при отсутствии document IDs третий запрос не нужен. Состояния: `uploaded` только при совпадении intent/domain/binding/current generation/SHA/size/owner; `manualRetry` для подтверждённого pending без автоматической publication; `paused` при выключенном writer/capacity; `failed` при недоступном прежнем domain receipt; `unknown` для отсутствующего/повреждённого/несовпадающего intent. Unknown/failed не раскрывают прежнее имя или SHA. Имя в pending не доказывает физическую сохранность байтов.

При неопределённой ошибке POST общий frontend обеих карточек проверяет только этот ключ, с общим лимитом 5 с и abort/no-store. Успех без повторного multipart требует SHA выбранного File, первоначальных filename/MIME/type/status/target key и точных ID/case/document key/version/size полученного документа. Опубликованный receipt содержит исходные параметры intent: редактируемые тип/статус текущего документа могут отличаться и не откатываются. Definitive 4xx не запускают recovery; сомнительная metadata, другой файл с теми же именем/размером, недоступная проверка или timeout сохраняют исходную ошибку и идентификатор. Для новой версии карточка передаёт известные case ID и document key только как клиентские данные проверки, не как дополнительные form поля. Вызов API без этих данных остаётся без автоматического recovery.

Это однократная проверка результата потерянного ответа. Discovery/polling всех pending, завершение без браузерного File, автоматическая case publication и явное управление новой попыткой после окончательного конфликта остаются в TASK-014/020/022. Рабочая приёмка и полный новый release gate не заменяются отдельным HTTP/component qualification.

Другие типы уведомлений этим этапом не переводились на post-commit очередь.

Загрузка файла, новой версии, формирование шаблона и заказ-наряда используют общий `CaseDocumentAtomicSave` из `Services/Cases`; HTTP-контроллер делегирует ему сохранение, а сервис доступен будущему durable consumer без HTTP-контекста. После подтверждённого отката он восстанавливает прежние scalar values, original values, состояния insert/update и временные ключи отслеживаемых записей; граф неудавшейся попытки отсоединяется. Прежние несохранённые изменения остаются для следующей операции. Ранний отказ не оставляет запись истории или ссылку, которую последующий `SaveChanges` мог бы сохранить после удаления файла. Дополнительных запросов БД на успешном пути восстановления tracking нет: снимок берётся только из уже отслеживаемых данных.

Если commit был начат или rollback не подтверждён, файл сохраняется для сверки. Потеря commit ACK может означать уже сохранённые документ/аудит/уведомление; их нельзя считать отсутствующими по ответу запроса. Ошибка rollback добавляется к диагностике первоначального исключения, не подменяя его. Байты после неопределённого результата не очищаются автоматически. Общий helper сам не включает managed storage; отдельный writer ручной загрузки и версий описан выше. Шаблоны и заказ-наряды пока используют прежний файловый путь с этой защитой отката.

## Подготовка документов мессенджера в управляемом хранилище

Подключение класса `messenger-delivery` к записи требует `StorageOrchestration:Enabled=true`, включения этого класса в `ProductWriteEnabledClasses` и `UploadCapacityChecksEnabled=true`. Все эти режимы остаются выключенными по умолчанию; текущая разработка не включает их на рабочем сервере. Для чтения используется уже существующий per-class `ProductReadEnabledClasses`. Перед production-включением нужны приёмка, резервная копия и проверка обязательных провайдеров по утверждённой политике.

Копирование в provider выполняется до короткой транзакции записи доставки. До подтверждения обязательных копий нет готовой доставки или одноразовой ссылки; интерфейс получает явную ошибку с предложением повторить подготовку после восстановления хранилища. Фоновый worker копирует ожидающие реплики существующей очередью. Повтор подготовки тем же сотрудником для того же содержимого/версии/получателя использует неизменный ключ и сохранённый резерв, а не создаёт новую передачу. После потерянного local ACK общий writer проверяет размер/SHA уже существующего файла до PUT. Unknown HEAD или несовпадение сохраняют резерв и запрещают перезапись.

После подтверждения копий владелец storage object, запись доставки и product binding сохраняются одной транзакцией. Прежний локальный снимок остаётся совместимой копией для отключения managed-read режима. Если commit или rollback не подтверждён, связанный снимок не удаляется; лишние байты требуют отдельной сверки, автоматическая уборка по предположению запрещена. Бюджет прежнего snapshot-пути до его копирования, смена сотрудника при незавершённой подготовке, конкурентная подготовка, cancelled-key lifecycle и native Linux/cloud остаются отдельными условиями полной квалификации TASK-014/020/024.

Две тестовые копии в разных локальных provider-папках доказывают gate обязательных реплик, но не независимость двух production-копий. Полный gate и rollout этого этапа ещё впереди.

## Исходный PDF электронной подписи — локальный writer, приёмка хранения открыта

Для записи класса `esign-original` нужны `StorageOrchestration:Enabled=true`, этот класс в `ProductWriteEnabledClasses` и `UploadCapacityChecksEnabled=true`. Чтение доказательного пакета использует существующий `ProductReadEnabledClasses` для `esign-original`. Default flags не менялись. Пока не утверждён и не реализован перенос срока архива подписи в защиту удаления, этот режим не принимается для production; это отдельная граница TASK-014/017/019.

Подготовка PDF создаёт совместимую неизменяемую копию, затем передаёт байты общему writer до транзакции envelope. Недостаток обязательных копий/неопределённый ACK не создаёт envelope, подписантов, prepared-event или binding. Worker завершает pending replicas, а повтор той же подготовки тем же сотрудником использует прежний content-keyed резерв и проверенную генерацию. Условный owner handoff и binding атомарны с envelope/подписантами/событием. Размер/SHA, класс, тип, имя и поколение проверяются до публикации.

Если результат commit неизвестен, PDF сохраняется даже при фактическом откате; поздний SaveChanges не воскрешает неудавшийся граф, потому что envelope/подписанты/события отсоединяются после любого исключения. При подтверждённом откате до вызова commit удаляется только совместимый файл попытки. После unconfirmed rollback могут остаться лишние совместимые PDF: требуется отдельная сверка, автоматическое удаление не разрешается по отсутствию ответа. Managed-копия с pending owner также не удаляется как предполагаемый orphan. После публикации доказательный пакет может читать managed PDF без исходного совместимого файла.

Не закрыты: архивный срок и удаление, резерв до записи совместимого исходника, concurrent prepare, native Linux/cloud, остальные signature artifacts и общий release gate. Тестовые локальные копии не подтверждают независимость production destinations.

## Пакетная проверка каталога

### Общий статус и готовность к переключению

Проверка `GET /api/storage/health` больше не приравнивает отсутствие `corrupt`/`deadLetter` к исправному состоянию. Незавершённые операции, missing/suspect/pending/repairPending/deletePending/retainedCorrupt копии и open/halfOpen провайдеры дают `degraded`; неизвестные состояния также не считаются исправными. Подробные счётчики и возраст ожидающей операции сохраняются, provider snapshot берётся один раз. Endpoint остаётся только для администратора и не запускает сетевые проверки или восстановление. `storage-health-debt-targeted-20260929.trx` прошёл **26/26 без пропусков**: 20 SQLite/controller/authorization cases плюс provider circuit/policy regression. Data cases подтвердили ровно три SQL-запроса без provider I/O. Это локальная проверка, не publication/full release gate.

`healthy` — сводка текущих известных состояний, **не разрешение global failback**. Для переключения по-прежнему нужны проверенные обязательные назначения/копии, отсутствие долга и неопределённых проверок, актуальные generations/tombstones, recovery epoch/cooldown и отдельное решение оператора. Эти требования не заменяются одним зелёным статусом или удачным чтением отдельного файла. Production-переключение этим изменением не выполняется.

### Проверка выдаваемого потока

Локальный UI gate выявил отдельную проблему холодного старта Vite: библиотека lucide-react была исключена из pre-bundling, поэтому браузер запрашивал её 1517 модулей по одному и не доходил до формы входа за прежние 25 секунд. Согласно [официальной документации Vite](https://vite.dev/config/dep-optimization-options), эти опции относятся к dev optimizer, не к production build. Это не доказательство исправления прежних production-сбоев входа. Чистый повтор всего browser набора на новой конфигурации прошёл **11/11 без пропусков** (`verified-storage-read-browser-final-20260929.trx`, 20:05:58–20:16:08). Оба режима карточки проверены с неизменёнными deadline/проверками доступа и требованием отсутствия отдельных icon-module requests. Предыдущий mixed expanded run — 176/184 с восемью startup failures — не заменяет этот результат и не считается зелёным. Diagnostic учитывает только пути, статусы и длительность запросов; не выводит заголовки, тела или секреты.

Во время provider read может измениться и сама связь документа с CRM. Восемь baseline-сценариев подтвердили выдачу устаревшего файла после замены/удаления/смены версии привязки, появления новой привязки или изменения владельца/имени/типа/класса. Теперь одна свежая SQL-проверка сверяет текущий pointer ID/version, версию объекта/поколение и идентичность документа с отсутствием tombstone непосредственно перед выдачей. До успешной передачи вызывающему коду reader владеет подготовленным потоком и закрывает его при отказе, отмене или ошибке запроса. Последняя редакция прошла **201/201 без пропусков** (`product-storage-pointer-qualified-20260929.trx`, 11 мин 39 с): восемь actual PostgreSQL гонок после миграций (18,46 с), SQLite boundary/cleanup, обе карточки и object/native/backup/restore регрессия. В настоящем PostgreSQL HTTP task-file стенде проверены partial Range/suffix/416 и удаление подготовленного spool после ответа. Это локальная квалификация указанного подпункта, не полный release gate и не квалификация Range всех классов файлов.

Локально проверенный reader заменяет отдельный HEAD одним чтением файла с полной проверкой фактического размера и SHA256 до начала ответа. Буфер ограничен 81920 байт, содержимое временно хранится в приватном DeleteOnClose-файле, привязанном к objectId конкретного запроса. После I/O проверяются действующая версия, поколение, exact replica binding/status и отсутствие tombstone. При замене только копии можно попробовать здоровую sibling той же версии; при изменении самого объекта/поколения старый результат не выдаётся. Подозрительный статус записывается условно, чтобы не затереть изменённую другим запросом привязку.

Остаются отдельные gates: Linux private-temp permissions, HTTP Range/клиентские маршруты остальных классов, large/concurrent memory/disk benchmark и полный release gate. Адресные cancellation/transport/oversize/cleanup, native wire, actual PostgreSQL и product-pointer race проверены указанными прогонами; это не доказательство выполнения оставшихся gates.

Первый представительный workload прошёл отдельно: `verified-storage-read-load-20260929.trx` — **2/2**, один и четыре non-seeking generated источника по 32 MiB. Read+consumer phase: 469 ms / 337328 managed allocation bytes для одного; 1387 ms / 4584736 bytes для четырёх (128 MiB payload). Все size/SHA и cleanup совпали; запросы к источнику ограничены 81920 байт, HEAD отсутствует. Тест не содержит полного payload в памяти. Числа получены без подготовки БД, не являются peak resident memory или гарантией производительности и не заменяют реальный облачный/capacity benchmark. Порог на эти значения не добавлялся, чтобы CI не зависел от фоновой нагрузки компьютера. Собственные synthetic DB-папки после проверки отсутствуют; старые Temp-артефакты из предыдущих прогонов не затрагивались.

Новый обход `POST /api/storage/reconcile` остаётся доступен только администратору. Подготовленная реализация обрабатывает до 100 объектов/поколений и 200 копий в порции. Общий граф каталога и вся история операций в память не загружаются. Перед обращением к файловому провайдеру поток чтения БД закрывается; приватные временные файлы содержат только идентификаторы и отпечатки привязок, удаляются при завершении, исключении или отмене. Для каждого запуска задаётся `scanId`; временные записи относятся именно к этому запуску.

`issues` содержит первые 1000 замечаний, `totalIssues` и `issueCountsByKind` считают все найденные замечания. `issuesTruncated=true` означает, что подробный список неполон, а не что остальные файлы исправны. Отсутствие текущей версии, копий либо противоречие между действующим объектом и отметкой удаления — отдельные замечания. `catalogChanged` требует повторного обхода: изменившиеся привязки не дают права восстанавливать файл по старым данным. Пакетные записи проверяют прежнюю привязку копии и актуальную версию перед изменением; worker сохраняет собственную повторную проверку перед физической операцией.

Локальная квалификация: `storage-paging-targeted-20260929.trx` — 58/58; расширенный `storage-paging-qualified-20260929.trx` — 466/467, ошибка ожидания штатного аудита в новом тесте исправлена; `storage-paging-final-20260929.trx` — 81/81, в том числе повтор исправленного теста и дополнительные archive/restore/health checks; `storage-paging-cleanup-final-20260929.trx` — 5/5 после усиления отмены/сбоя на уже заполненном списке повреждений. Использовались owned SQLite/PostgreSQL, штатные миграции, реальные local/S3 loopback repair и PostgreSQL restore сценарии. Кодировка 2440, JSON1038 и scoped diff проверены. Подтверждён именно пакетный обход, а не завершение TASK-016, общая готовность переключения хранилищ или production-квалификация. Linux-ветка приватных прав временных файлов требует отдельной проверки на Linux.

## Индекс списка ожидающих загрузок

Миграция PostgreSQL `20260929080553_AddTaskUploadDiscoveryPrefixIndexPostgres` добавляет partial `varchar_pattern_ops` индекс `IX_StorageOperations_CommitIdempotencyPrefix` только для commit-операций. Она не изменяет данные и не заменяет уникальный индекс ключей операций. SQLite-схема не меняется. Перед публикацией оцените размер StorageOperations и выберите согласованное окно: обычное создание индекса может временно задержать запись операций. Миграция сама по себе не включает новое хранилище или автоматическую публикацию файлов.

Reader выбирает до 51 исходной записи для определения следующей страницы, затем читает состояния очереди одним exact-key batch до 50 ключей. Чужие key/object/generation не используются. Если публикация завершилась между чтением страницы и очереди, точные terminal receipts обновляются отдельной ограниченной выборкой; существование доменного файла и доступ сотрудника проверяются перед ответом. Пустой список не запускает запрос очереди. Проверка плана должна охватывать оба SQL-запроса, а не только наличие индекса: предыдущая версия ускоряла страницу, но продолжала отбрасывать тысячи операций в коррелированном подзапросе.

## Доменное удаление вложений

### Привязка connected locator и порядок чтения

#### Длительные операции и lease

Обычный обработчик использует существующую IDbContextFactory для продления только текущей running execution, без параллельного доступа к основному DbContext. Интервал — треть ограниченного WorkerLeaseSeconds (15–3600 секунд); запрос продления имеет отдельный deadline и command timeout. Уникальный owner каждой попытки защищает от повторного использования worker ID. Уже expired, foreign или terminal строка не продлевается; смена неизменяемой привязки object/generation/type/provider/connection также отменяет I/O. Стандартный DI подключает фабрику автоматически. Прямые изолированные тестовые вызовы без фабрики сохраняют прежнее поведение без heartbeat.

Пачка задаёт только bounded список кандидатов; каждое задание захватывается непосредственно перед исполнением. После прекращения heartbeat терминальный physical-operation результат сохраняется только под свежей lease-row блокировкой. Если право потеряно, статус чужого worker и каталог не изменяются. Пользовательская отмена передаётся вызывающему коду; внутренний отказ продления оставляет running запись до восстановления/истечения lease, не превращая её в ложный успешный результат. Определять доступность файла следует по подтверждённой catalog/receipt, а не по наличию provider bytes. Metadata-only file publication/notification сохраняет отдельный короткий протокол без heartbeat.

Локальная квалификация: `storage-lease-final-20260929.trx` — 341/341; затем штатное автоматическое разрешение DI-фабрики и ошибки продления отдельно усилены в `storage-lease-di-qualified-20260929.trx` — 17/17. SQLite и PostgreSQL реально передавали дольше исходного lease; второе задание оставалось незахваченным и исполнялось конкурирующим worker без duplicate PUT. Это не общий release gate и не production qualification.

Старые repair-задания, которые ещё указывают на повреждённый оригинал, обрабатываются без перезаписи: подтверждённое несовпадение размера/SHA и полностью проверенный источник позволяют сохранить новый адрес и repairPending короткой транзакцией до передачи. Номер задания, ключ и история попыток остаются прежними. При отказе сохранения нет новой передачи; потерянное подтверждение commit сверяется с БД, повтор использует тот же адрес. При утрате lease новое metadata state не публикуется поздним SaveChanges. Уже исправный target может получить receipt без доступного источника, неизвестный HEAD не означает повреждение. Автоматического открытия DeadLetter нет: действуют прежний лимит попыток и отдельное административное решение.

Этот legacy upgrade локально проверен в `legacy-repair-upgrade-final-20260929.trx`: 222/222, реальные PostgreSQL и local/AWS loopback S3. Native Яндекс.Диск wire, Linux permissions/длительная lease и весь production rollout этим отчётом не квалифицированы.

Для S3/Яндекс.Диска connection задаётся самим locator. Поэтому worker до HEAD/read/PUT/delete проверяет его connection против ConnectionId операции; original recovery locator тоже должен совпадать. Repair source обязан иметь Available binding того же поколения с фактической connection, и проверка повторяется после чтения. Неверная или отсутствующая connection не разрешает обращения к иной учётной записи. Scanner оставляет `locatorConnectionMismatch` issue и прежние metadata без remote probe; это не доказательство повреждения байтов и не разрешение переназначить запись автоматически.

Managed reader до probe проверяет ту же привязку, отмечает неверную реплику suspect и ищет следующую допустимую копию. Политика read/write сохраняет настроенный порядок после нормализации и исключения неподдерживаемых providers; alphabetical display решений не меняет выбор первой копии. Backup требует ненулевую совпадающую ConnectionId connected replica: при отсутствии безопасного кандидата поколение не пропускается и полный комплект не публикуется. Opaque/local adapters не получают придуманной connected-семантики. Квалифицировано локально: 28 адресных и 208 расширенных сценариев; native Яндекс.Диск wire, полный release gate и rollout остаются открытыми.

### Неопределённая проверка и подтверждённое повреждение

#### Изолированная замена повреждённых байтов — новые операции проверены локально

Новый repair для подтверждённо повреждённой копии использует отдельный recovery locator, который строит сам адаптер local/S3/Яндекс.Диска. Ключ зависит от поколения и durable idempotency key цикла, поэтому повтор и одновременное планирование получают один адрес. Операция и replica `repairPending` сохраняются одной транзакцией SaveChanges; повторная сверка не создаёт для неё отдельный repair. Внешняя запись остаётся `Overwrite:false`: чужие или ранее повреждённые байты не перезаписываются.

После проверки целого результата короткая транзакция блокирует object, generation, соответствующие replica и lease, повторно проверяет актуальное назначение и вместе сохраняет Available receipt и Succeeded операции. У старой копии появляется `retainedCorrupt`: она не участвует в чтении/кворуме, не запускает бесконечный repair и остаётся отдельным issue в отчёте. Это долг сохранённого повреждённого файла, не свидетельство его физической очистки. Автоматическое удаление такого долга этой реализацией не разрешается; существующие tombstone/retention и проверка точных байтов перед удалением сохраняются.

При потерянном ACK или неудачном сохранении receipt следующий запуск проверяет тот же recovery locator; совпавшие size/SHA подтверждают результат без нового PUT. Для подтверждения уже записанного файла исправный источник больше не требуется, но object/generation/target/lease должны оставаться действительными. При необходимости новой записи источник по-прежнему полностью проверяется до PUT. Неопределённый ответ, неверные байты по запланированному адресу, утрата lease или смена binding не разрешают перезапись или публикацию.

Адаптер без безопасного построения отдельного locator не получает автоматическую замену повреждённой копии. Старые уже запланированные repair, которые указывают непосредственно на повреждённый исходный адрес, остаются отказавшими без перезаписи; их преобразование требует отдельной проверки и ещё не реализовано. Квалификация нового пути, Linux, полный release gate и rollout должны быть завершены перед production включением.

#### Проверка источника до записи

Перед repair PUT processor доказывает фактические размер и SHA исходника в отдельном временном spool, не полагаясь только на metadata. Избыточный/усечённый/повреждённый поток отклоняется до отправки; non-seeking input допустим. Spool удаляется при success, failure и отмене, его объём ограничен размером поколения, память — постоянным буфером. Unix create mode 0600 задан до открытия, Windows использует FileShare.None; квалификация Unix-разрешений на Linux ещё требуется перед публикацией.

Точная operation/payload/provider/connection, generation metadata, bindings и lease повторно проверяются после чтения. Изменение задания, tombstone или потеря lease подавляет запись и не даёт прежнему worker сохранять чужой terminal result. ACK должен совпасть с ожидаемыми locator/size/SHA; если байты записаны, но ответ неверен, последующая попытка проверяет HEAD и не делает второй PUT. Это проверка безопасного источника, **не разрешение overwrite существующего повреждённого файла**: новые операции используют описанную выше изолированную замену. Преобразование старых операций и полная provider-specific qualification остаются открытыми.

Reconciliation различает невозможность проверки и подтверждённую потерю байтов. `verificationUnavailable` означает неопределённый ответ провайдера либо недостаточные сведения о целостности. Такой ответ не меняет последнюю подтверждённую запись копии и не запускает её перезапись. `NotFound` подтверждает отсутствие; успешный HEAD с неправильным размером или контрольной суммой подтверждает повреждение. Без SHA и при совпадающем размере подтверждения целостности нет; без SHA, но с неверным размером повреждение уже установлено.

Нулевые MissingReplicas/CorruptReplicas не доказывают готовность failback, если в Issues остаются `verificationUnavailable`/`providerUnavailable`. Восстановите доступ и повторите проверку; не утверждайте целостность по одному счётчику. Повторное восстановление пропавшей копии теперь создаёт новый детерминированный цикл только после успешного завершения всей её прежней истории. Незавершённые и dead-letter операции новая проверка не переоткрывает; повтор failed/dead-letter требует отдельного административного действия. Конфликт двух проверок не создаёт дубль и не удаляет несвязанные изменения. Безопасная замена существующего повреждённого файла (сейчас он отвечает Conflict на Overwrite:false) и ограниченный обход большого каталога остаются открыты в активном плане. Автоматического global failback и разрешения на production этим документом не предоставляется.

### Удаление задачи или дела целиком

Обычный `PaymentContext` включает audit/soft-delete. В этих endpoint удалённый родитель скрывается фильтром; его managed objects не получают tombstone, файлы и связи сохраняются для восстановления дела. На время сохранения soft parent cascade переносится на SaveChanges, чтобы audit успел заменить физическое удаление родителя пометкой. Это защищает также уже tracked dependents; исходный режим cascade возвращается в finally. Восстановление дела через `ObjectAuditController` должно вновь показывать тот же документ и выдавать исходные байты обеих копий. У задач отдельного restore API пока нет; сохранение их скрытых записей не является новым интерфейсом восстановления.

При модели без soft-delete single/bulk task delete и case delete в одной транзакции регистрируют удаление файлов через `ProductStorageDeletionService`, затем удаляют родителя. Файлы читаются порциями по 128 по возрастающему ID, только для разрешённых родительских записей. Ошибка любой привязки возвращает 409/503 и откатывает уже зарегистрированные tombstones. При обычной работе исходные legacy-файлы остаются защищены: обхода read-only provider нет. Окончательная очистка корзины отдельным purge API ещё не реализована; модель без audit используется также в синтетических проверках, а не как пользовательская команда включить стирание.

Отвязка платежей и удаление дела имеют общий commit. Сбой второго сохранения не оставляет ранее отсоединённые платежи. Изменения проверяются на одноразовых SQLite/PostgreSQL БД без настоящих уведомительных транспортов. Проверки сроков хранения и физического IO описаны ниже и остаются обязательными для дальнейшего rollout.

## Одновременная повторная загрузка

В отдельно включаемой managed-загрузке задачи один ключ относится к одному запросу сотрудника, задаче и содержимому. Два одновременных multipart-запроса с одинаковым ключом и байтами возвращают один ID вложения; разное содержимое получает 409 без подмены победившего файла. Это проверено на отдельной мигрированной PostgreSQL БД через настоящий MVC HTTP endpoint, с принудительным пересечением обеих записей до регистрации каталога. Связанный набор задач, фотографий, прав и ошибок сохранения прошёл 76/76.

Storage writer повторно читает победившую операцию только после точного нарушения уникальности `StorageOperations.IdempotencyKey` и только вне транзакции вызывающего кода. Другие ошибки БД не считаются повтором. Отсоединяются только собственные незаписанные сущности загрузки; остальной контекст сохраняется. Проигравшая приватная копия удаляется только после проверки отсутствия собственного объекта и ссылок на её locator. При неопределённом commit физические файлы сохраняются; общее reconciliation/retention остаётся отдельной незавершённой работой. Локальная квалификация не разрешает production-включение и не заменяет полный release gate.

`IManagedTaskFileUploadService.ResumeAsync` принимает ID сохранённой commit operation и обязательный callback проверки актуальных прав actor/task. До чтения копии проверяются структура intent, канонический upload key, принадлежность объекта исходной загрузке и неизменная связь задачи с делом. При публикации тот же callback вызывается под блокировкой задачи. Размер и SHA каталога должны совпадать с intent; фактический поток повторно ограничивается и хешируется прежним UploadAsync. Поток не обязан поддерживать seek и не загружается целиком в память. Повторное завершение принимает только ту же опубликованную пару документов; конкурирующая передача владельца не считается другой загрузкой.

Сам ResumeAsync не является публичным endpoint. Теперь его вызывает отдельно включаемая очередь с общим resolver текущих прав; сообщения об итоговом результате и клиентский статус остаются открытыми. Нельзя подключать callback, безусловно возвращающий true: такие callbacks используются только для изолированной квалификации publisher в синтетических тестах, не как production-авторизация. Флаги managed writes остаются выключенными по умолчанию. История квалификации prerequisite: первый адресный SQLite прогон прошёл 26/26; расширенная проверка выявила exception вместо 409 в HTTP сценарии разных байтов под одним ключом (77/78). Исправлена обработка подтверждённого несовпадения сохранённого intent, добавлен детерминированный winner-before-replay тест; повтор прошёл 80/80 за 1 мин 39 с, включая две конкурентные PostgreSQL ResumeAsync из свежих контекстов и сохранность единственной пары документов/истории. Права задачи/дела проверяются до обращения к каталогу; для успешного скачивания документа дела сохраняется действующий аудит. Эта настройка пока не подключает другие разделы или запись новых файлов.
- Политика по умолчанию — одна локальная копия; внешнее назначение не подставляется молча.
- `DatabaseRestoreDrill:PostgreSqlExecutionEnabled=false` — PostgreSQL проходит только проверку комплекта, пока оператор явно не настроит отдельную тестовую БД.
- Для локального запуска обязательны `BackgroundServices__Enabled=false` и `Email__Enabled=false`. На копии production-БД настройка `notifications.email.enabled` в самой БД также должна быть выключена.

## Проверка резервной копии

1. Откройте «Настройки → Обслуживание БД → Резервные копии».
2. Нажмите «Проверить» у выбранного файла.
3. Успех означает, что manifest существует, статус комплекта завершён, размеры и SHA-256 основной БД и обязательных файловых частей совпадают.
4. Legacy-копия без manifest показывается как непроверенная и не должна быть единственной точкой восстановления.
5. При ошибке не удаляйте предыдущий полный комплект. Сохраните `BackupId`, имя части и текст ошибки без секретов.

### Подготовка локальных файлов для пробного чтения

`DatabaseRestoreDrill:PrepareLocalRuntime` по умолчанию выключен. При отдельном включении для комплекта формата 5 или новее после проверки восстановленной БД и файлов программа перенастраивает выбранные реплики, подписи и локальные фотографии только в пробной базе. Прежние задания хранилища не выполняются повторно.

До создания папок подготовки рассчитывается дополнительный объём для копий подписей и локальных фотографий с запасом 64 МиБ. Документы, которые уже читаются из распакованной общей папки, не считаются повторно; внешние фото не скачиваются. При нехватке или невозможности определить свободное место операция прекращается. Расчёт не резервирует место на диске и не заменяет обработку ошибки поздней записи: другие программы могут занять место после проверки. Он также не является полной проверкой места для первоначальной распаковки архива и восстановления БД.

В той же транзакции отключаются отправители email, Telegram, MAX и SMS и сохранённые токены этих каналов. Незавершённые отправки MAX и документов в мессенджеры отменяются; ссылки на получение документов, перенесённые из исходной базы, отзываются. История уже отправленных, доставленных и прочитанных сообщений остаётся в пробной базе. Старые задания синхронизации календарей получают состояние `failed` с явной причиной изоляции, поэтому фоновый обработчик не выбирает их как ожидающие передачи. Нельзя вручную повторять эти задания или включать каналы в пробной среде.

При ошибке подготовки изменения документов и этих очередей откатываются вместе. Исходная БД не изменяется. Результат `restored-storage-paths.json` содержит только пути хранилищ и `completeRuntimeConfiguration=false`: **это не готовые настройки запуска приложения**. До отдельной проверки изоляции всех внешних интеграций, конфигурации авторизации и ключей не запускайте CRM на восстановленной базе. Обязательные локальные ограничения фоновых служб и email сохраняются.

## Запрет исходящих транспортов пробного приложения

Отдельная настройка `RestoredRuntimeIsolation__Enabled=true` блокирует новые запросы клиентов, созданных через общую HTTP-фабрику, а также создание транспорта SMTP, S3, web push и Telegram, включая вариант с прокси. При выключенной или отсутствующей настройке обычная работа не меняется. HTTP-отказ происходит до обработчиков журналирования запроса; URL запроса не должен попадать в их журнал при отказе. Ошибочное значение настройки приводит к отказу, а не к разрешению отправки.

Настройку следует задавать до создания приложения и его клиентов. Она не отзывает уже отправленные запросы и не блокирует операции ранее созданного S3 SDK-клиента. Это не сетевой экран всей операционной системы и не запрет внешних запросов браузера. Нельзя считать её самостоятельным разрешением на запуск копии: обязательны прежнее отключение email/фоновых служб, очистка настроек пробной БД, отдельная авторизация и ключи, проверка startup-операций и изоляция браузера. Подготовка файлов пока не создаёт полную конфигурацию запуска автоматически.

В этом режиме запуск дополнительно требует явных `BackgroundServices__Enabled=false` и `Email__Enabled=false`. Эффективный адрес прослушивания (с учётом приоритета `ASPNETCORE_URLS`) должен состоять только из HTTP/HTTPS-адресов с явным loopback IP, например `http://127.0.0.1:5080` или `http://[::1]:5080`. `localhost`, wildcard и внешние адреса не принимаются. Несоответствие останавливает запуск до разрешения подключения к БД и создания каталога ключей. Этот барьер не проверяет принадлежность самой базы, отдельные JWT/ключи или браузерную изоляцию: эти условия пока остаются открытыми, запуск копии не разрешён.

Новая подготовка пробных файлов также сохраняет `runtimeInstanceId` в описании и метку этой среды в самой пробной БД в общей транзакции. Настройка `RestoredRuntimeIsolation__InstanceId` должна точно соответствовать этому ID. При включённой изоляции перед созданием папки ключей выполняется только чтение метки: SQLite открывается с ReadOnly без создания отсутствующего файла, PostgreSQL принимается только на literal loopback IP. База без нужной метки не допускается. Миграции, начальные данные, обновление записей «Что нового» и стартовые backfill в этом режиме не выполняются; схема должна быть заранее подготовлена и проверена отдельно. Этот контроль не является полной конфигурацией запуска, а метка не заменяет проверку авторизации, ключей и источников файлов.

## Отдельная авторизация пробного процесса

### Data Protection и отдельные прикладные ключи

JWT пробного процесса не восстанавливает защищённые настройки и данные. Data Protection зависит одновременно от правильных сохранённых key files, application discriminator/name и purpose конкретного сервиса. Не заменяйте отсутствующий key ring новым: новый ключ не расшифрует прежние значения. При переносе должны сохраняться все ещё необходимые версии ключей, не только самая новая. Если `DataProtection:ApplicationName` не задан явно, необходимо отдельно зафиксировать эффективный исходный discriminator; каталог файлов на новом сервере не доказывает его совместимость. Текущий storage-only artifact этих параметров и полного состава key IDs ещё не сохраняет, поэтому `completeRuntimeConfiguration=false` остаётся обязательным ограничением.

`RestoredDataProtectionRecoveryTests` проверяет SDK на собственных синтетических ключах: перенос ring при недоступном исходном пути, Unicode, неправильный purpose/application name, отсутствующие/чужие ключи и необходимость прежнего ключа после ротации. При проверочном чтении автоматическая генерация выключена и SHA файлов не меняется. Это не файловая sandbox/read-only гарантия всего SDK, не работа с ключами VPS и не подтверждение recovery рабочего ring, особенно если его descriptors зашифрованы OS-bound механизмом. Прикладное `ppenc:v1` использует другой key store: master/blind-index keys не появляются из файлов Data Protection и восстанавливаются по отдельному runbook и утверждённой custody-политике. Материал ключей не записывайте в БД, Git, описание копии или диагностические сообщения; способ внешнего резервного хранения и ответственные пока требуют решения владельца.

### Выбор API в клиентской части

Отдельная клиентская настройка `VITE_RESTORED_RUNTIME_ISOLATION=true` требует явный `VITE_API_URL`, например `http://127.0.0.1:5080/api`, и `VITE_RESTORED_RUNTIME_INSTANCE_ID` с точным `runtimeInstanceId` подготовленной копии (32 строчные hex-цифры, не нулевой GUID). Допустимы только HTTP/HTTPS и literal loopback IP (включая `[::1]`) с путём `/api`. Внешний адрес, параметры URL, credentials и HTTPS-страница с HTTP API приводят к отказу без fallback на рабочий сервер. Настройки Vite входят в клиентскую сборку: это не автоматическое следствие backend-флага. Без отдельной проверки browser CSP, других внешних запросов и dev/preview bind этот guard не разрешает пробный запуск интерфейса.

В этом режиме Vite также проверяет API при загрузке конфигурации, задаёт loopback bind dev/preview и повторно проверяет итоговые настройки после их объединения с аргументами запуска. Внешний host, wildcard allowedHosts, proxy и внешний HMR host приводят к отказу. Обычный режим не меняет прежние настройки. Это ограничение локального сервера, а не полная политика запросов HTML/браузера; также ещё требуется handshake принадлежности выбранного API пробной среде.

При включённой изоляции после сверки ID пробной БД приложение добавляет в память свежий случайный ключ JWT и отдельные issuer/audience с ID этой среды. Этот последний provider имеет приоритет над прежними settings/environment/user secrets. Ключ не пишется в описание копии, БД или файл и меняется при каждом запуске; вход нужно повторить после перезапуска. Обычный режим использует прежние настройки без изменений. Это только разделение токенов входа, а не восстановление защищённых документов и Data Protection key ring: последние требуют отдельного проверенного восстановления. Полноценный запуск копии по-прежнему не считается разрешённым.

## Какие локальные файлы входят в комплект

### Политика ресурсов пробного интерфейса

В opt-in HTML и ответах Vite dev/preview задаётся CSP с точным адресом локального API и отдельным ws/wss адресом для него. Локальные script/style assets, data/blob изображения и перечисленные локальные источники не открывают произвольные внешние hosts. `frame-ancestors` задаётся только заголовком, не HTML meta. Политика вставляется после HTML-преобразований первой в head, до скриптов. В dev-режиме служебный inline-скрипт React разрешён только по SHA-256 его точного содержимого, а HMR — по конкретному локальному WebSocket-адресу. Production/preview не получают это dev-разрешение. Нельзя добавлять script-src unsafe-inline или unsafe-eval ради обхода отказов. Проверка настоящего HTML-преобразования Vite подтверждает совпадение хеша и политики заголовка, но не выполнение ограничений браузером. Внешние пользовательские переходы и полный обмен идентификатором выбранного API ещё требуют реализации/проверки; полный пробный запуск по-прежнему не разрешён.

### Проверка принадлежности запросов пробной среде

Серверный барьер после CORS и до авторизации предоставляет только неизменяющий `GET /api/restored-runtime/identity`: ответ содержит `isolated=true` и ID, ранее сверенный с подготовленной БД, и запрещает кеширование. Вход и рабочие запросы восстановленного API требуют единственный заголовок `X-PayPlanner-Restored-Instance` с точным ID. Для GET допускается вместо него один параметр `pp_restored_instance` — это необходимо для браузерных WebSocket/SSE и изображений, не поддерживающих пользовательские заголовки. POST/PUT/DELETE с одной только query-меткой не разрешаются. Неверная, дублированная или конфликтующая с заголовком query-метка также даёт 409. Обычный сервер не предоставляет этот endpoint (404) и отклоняет обе формы пробной метки (409); запросы обычной CRM без них не меняются. ID — метка соответствия, не секрет и не замена аутентификации.

Общий клиентский transport для api/auth/internal-chat сверяет ID единственным общим GET без credentials до первого рабочего запроса. Ошибка или несовпадение запрещают рабочую отправку, не приводя к fallback/автоматическому повтору на другой API; перенаправления рабочих fetch запрещены. Каналы уведомлений и заметок дожидаются той же сверки до передачи токена и negotiation, затем передают ID в HTTP headers и URL. Локальные фотографии профиля, сотрудника, верхней панели и чата получают query-метку; сохранённые внешние avatars не запрашиваются. Прямые ресурсы, browser workers/storage, успешное подключение WebSocket и применение CSP ещё требуют сквозной проверки настоящим браузером. Сам этот барьер не разрешает полноценный запуск интерфейса копии.

### Отдельный браузерный профиль и кеширование

Используйте отдельный чистый профиль браузера и отдельный literal-loopback адрес для пробной копии. Не открывайте её на прежнем origin рабочего или другого локального приложения. В пробном режиме App монтируется только после проверки браузерной среды: старый controller, любая registration service worker или CacheStorage приводят к отказу без unregister/delete. При первом открытии localStorage, sessionStorage и IndexedDB должны быть пустыми; если inspection недоступна или содержит прежние данные, запуск не продолжается. После успешной проверки local/session storage получают `pp_restored_browser_instance` с ID копии. Данные той же среды допускаются при повторном входе; другая метка не заменяется, старые токены или данные автоматически не удаляются. Это проверка принадлежности при запуске, а не защита от ручной подделки метки или последующих вмешательств других вкладок.

Регистрация рабочего PWA/cache/push worker в пробном режиме отключена, включая вызов общей функции регистрации. Обычный режим не меняется. При отказе вместо CRM выводится пояснение о чистом профиле. Проверка не может гарантировать исполнение нового кода, если прежний worker уже отдал старый HTML/скрипты без этих ограничений: чистый профиль и отдельный origin являются обязательными предпосылками, а не способом «почистить всё» в рабочем браузере. Реальная browser/network квалификация ещё открыта; приложения на восстановленной БД пока не запускались.

Базовые механизмы отдельно проверяются командой `npx vitest run vite.restored-browser.integration.test.ts --maxWorkers=1`. Нужен установленный Edge, Chrome или bundled Chromium; тест не скачивает браузер. Он открывает собственные временные loopback-фикстуры и отдельные непостоянные браузерные contexts, а не рабочий профиль/CRM/БД. Проверяются HMR, API identity, PNG, фактические байты Blob download, запрет внешних fetch/image до сети, отказ при чужих storage/cache/worker/IndexedDB без их удаления и отсутствие рабочих POST при несовпадении ID. В положительной фазе проверяется отсутствие ошибок страницы и консоли; преднамеренные CSP-отказы в отрицательной фазе ожидаемо дают диагностические сообщения. Успех этого теста не является разрешением полноценного запуска копии и не заменяет проверку входа, настоящих hubs, всех классов файлов и расшифровки защищённых данных в восстановленном приложении.

При `DatabaseBackup:IncludeFileStorage=true` собираются действительные рабочие пути: общая папка `FileStorage:RootPath` (по умолчанию `App_Data` внутри корня приложения), фотографии профилей, электронные подписи и `StorageOrchestration:LocalRoot` (по умолчанию `objects` внутри общей папки). Относительные настройки разрешаются от корня приложения, не от рабочего каталога процесса. Существующие прежние папки `wwwroot/user-photos` и `storage/electronic-signatures` тоже включаются: программа ещё читает данные оттуда. Вложенный или совпадающий корень не архивируется повторно; каталог самих резервных копий исключается.

Отсутствующая явно настроенная папка, путь к файлу вместо каталога или отказ доступа означают ошибку, а не полный успех. Неиспользуемые стандартные и прежние папки могут отсутствовать. Если все такие папки отсутствуют, файловая часть не создаётся; это не доказывает отсутствие потерянных ссылок в базе. Выключенное резервирование файлов по-прежнему создаёт только копию БД. Состав новых архивов не исправляет прежние комплекты. Согласованность снимка БД и файлов при конкурентных изменениях остаётся отдельным открытым требованием.

## Сопоставление папок с архивом

В новых комплектах файловая часть описания хранит `FileRoots`: логическое имя папки и её фактический архивный префикс. Например, фото внутри общей папки имеют префикс `file-storage/user-photos`, а отдельно настроенная папка — `profile-photos`. Исходные абсолютные пути сервера в этом перечне не публикуются. Вложенные и совпадающие папки остаются представлены, хотя их байты не упаковываются повторно.

Пустые, неоднозначные, выходящие за границы и ссылающиеся на неописанный архивный корень сопоставления отвергаются. Старая копия без поля `FileRoots` остаётся совместимой: её контрольные суммы проверяются, файлы можно извлечь. Отсутствие новых сведений не означает проверки всех ссылок БД. Папки, которые сами являются символическими ссылками, не принимаются источником; укажите исходную папку. Корень целого диска, сам каталог резервных копий и его подпапки также запрещены как источники. Обычная рабочая папка с вложенным каталогом резервных копий поддерживается: вложенные копии не включаются в файловый архив.

Этот этап сохраняет схему расположения байтов, но пока не доказывает их соответствие ссылкам в момент дампа. Общий снимок БД, потоковый перечень обязательных файлов, ключи и полная проверка восстановления остаются отдельными требованиями.

## История запусков резервирования

При отмене PostgreSQL-запуска приложение останавливает именно запущенный `pg_dump` и его дерево, дожидается завершения и закрытия перенаправленных потоков независимым ограниченным токеном, затем удаляет незавершённый дамп. Общая блокировка каталога удерживается во время этой уборки. Если остановку подтвердить не удалось, возвращается явная ошибка, а не подтверждение безопасной отмены; требуется разбор серверного журнала. Проверенные прежние комплекты не затрагиваются.

Каждый producer получает уникальную метку `PGAPPNAME`. Серверная отмена и подтверждение окончания ограничены точным совпадением этой метки, текущей базой и аутентифицированным пользователем; другие ожидающие запросы не отменяются. Это необходимо потому, что завершение клиентского процесса само по себе не обязательно убирает ожидающий блокировку запрос. Если роль не может отменить собственный серверный запрос, срабатывает явный отказ подтверждения, а не массовое завершение сессий. Права функции описаны в [документации PostgreSQL](https://www.postgresql.org/docs/17/functions-admin.html).

На вкладке «Резервные копии» администратору доступен отдельный журнал запусков. Он показывает источник (ручной или по расписанию), начало и окончание, последний этап, результат и идентификатор связанного комплекта, если он успел пройти локальную проверку. Ранний отказ создания или сбора файлов сохраняется даже без готового комплекта. Отмена и частичный облачный отказ отличаются от успешного завершения.

История начинается с новых запусков после обновления; импорт старых комплектов не создаёт вымышленных запусков. Попытка записывается после получения блокировки и проверки слота расписания, до создания дампа. Ожидание блокировки, пропуск уже выполненного слота и невозможность подключиться к самой БД для записи попытки не создают отдельной строки. При недоступной БД сохранение ошибки не гарантируется; исходная ошибка остаётся ошибкой операции.

При следующем запуске под блокировкой прежние незавершённые записи того же каталога отмечаются прерванными. До этого «Выполняется» означает только сохранённое состояние, а не подтверждение живого процесса. Успешный запуск сам по себе не доказывает независимость облачных копий, доступность ключей или результат полного восстановления. Для этого используйте журнал комплектов и пробное восстановление; в истории запусков нет кнопок восстановления.

Read-only API: `GET /api/database/backups/attempts?pageSize=20&after=<AttemptId>`, только администратор, от 1 до 100 записей. Порядок — время начала и ID по убыванию; `nextCursor=null` завершает просмотр. Ответ не содержит внутреннего идентификатора каталога. Журнал не делает внешних облачных запросов и не обновляет состояния при чтении.

## Журнал комплектов и копий

- На вкладке «Резервные копии» администратор видит отдельный журнал комплектов. Он загружается страницами; «Следующие копии» открывает более старые записи, «Обновить журнал» возвращает к свежим.
- «Локальная целостность подтверждена» относится к локальному комплекту; «Проверено после отправки» означает, что обязательные облачные части были прочитаны обратно и сверены. Время последней проверки показано рядом. Эти отметки не гарантируют текущую доступность и не заменяют restore drill.
- «Ошибка» и «Загрузка не подтверждена» не считаются проверенной облачной копией. «Удалено» у локального файла не удаляет сведения о копиях в облаке. Отдельные ключи шифрования этим журналом не проверяются.
- Регистрируются новые комплекты и старые комплекты при проверенной повторной отправке или явном импорте. Автоматический обзор всех прежних файлов пока не выполняется; отсутствие записи в журнале не доказывает отсутствия старого файла.
- Read-only API: `GET /api/database/backups/catalog?pageSize=20&after=<BackupId>`, только администратор; максимум 100 комплектов за запрос. `nextCursor=null` означает последнюю страницу. API не выполняет облачных запросов и не меняет копии.

### Как понимать общее состояние комплекта

Общее состояние оценивается по текущим выбранным хранилищам. История прежних отправок сохраняется, но успех в отключённом или заменённом назначении не подтверждает копию в новом.

- «Подтверждена локальная целостность» — локальный комплект проверен, облачная отправка сейчас не выбрана.
- «Нет всех выбранных копий» — локальный комплект проверен, но для части выбранных назначений ещё нет результата.
- «Отправка не завершена» — для выбранного назначения записана незавершённая попытка. Это не доказательство, что отправка работает прямо сейчас.
- «Выбранные копии подтверждены» — локальный комплект и копии во всех выбранных назначениях прошли проверку целостности.
- «Есть ошибка или неполная настройка» — хотя бы одна обязательная выбранная копия не подтверждена, либо S3 включён без подключения.
- «Нет подтверждённой локальной копии» — локальная запись отсутствует или отмечена удалённой; сведения о других копиях остаются видимыми.

Ни одно из этих состояний само по себе не подтверждает независимость хранилищ, наличие ключей расшифровки или успешное полное восстановление. Проверка выполнялась в указанное время, а не при каждом открытии журнала.

### Повтор ошибочной или прерванной облачной отправки

1. В истории S3 или Яндекс.Диска найдите запись «Ошибка» или «Отправка не подтверждена». Убедитесь, что нужное подключение настроено и доступно для отправки.
2. Нажмите «Повторить». Для неподтверждённой попытки система запрашивает отдельное подтверждение; отмена этого окна ничего не отправляет.
3. Сервер дожидается общей блокировки каталога, перечитывает результат и заново проверяет локальный комплект. Если действующая отправка к этому времени успешно закончилась, повтор не выполняется. Если локальная часть повреждена или отсутствует, облачная отправка также не начинается.
4. Во время повторной отправки создание, очистка и удаление в том же каталоге ожидают освобождения блокировки, в том числе в другом экземпляре backend. При отмене ожидания активная попытка не меняется.
5. Отмена самой отправки сохраняет ошибку ограниченной по времени независимой попыткой записи. Если журнал недоступен, может остаться неподтверждённый результат; он не считается успехом и доступен для следующего ручного повтора. После остановки приложения автоматический повтор этих записей не запускается.

Повтор относится к тем же локальным файлам и назначению из истории, а не создаёт новую резервную копию. Подтверждение успеха требует обратного чтения и проверки всех обязательных частей. Общая блокировка защищает операции приложения, но не предотвращает ручное изменение файлов сторонней программой.

### Добавление старых локальных комплектов

1. В журнале раскройте «Добавить старые локальные копии». Из списка файлов ниже скопируйте относительные пути (или укажите известные пути более старых комплектов), по одному на строку, до 20 за один пакет.
2. Нажмите «Проверить перед добавлением». Эта операция проверяет описание, контрольные суммы БД и обязательных частей, но не записывает комплект в каталог. Файл без полного manifest не получает новый manifest автоматически.
3. Подтвердите «Добавить проверенные». Сервер повторно проверяет файлы: изменение после предварительной проверки приводит к отказу. Список ошибок не останавливает регистрацию других пригодных комплектов; повтор одного пути не создаёт дубликат.
4. В журнале появляются только локальные копии. Исторический успех S3/Яндекс.Диска не переносится как доказательство проверки; нужна проверенная повторная отправка. Файлы не изменяются и не удаляются, восстановление и внешние запросы не запускаются.
5. Комплект регистрируется с исходными ID и датой из manifest. Изменённый manifest с прежним ID, несоответствие пути, выход из корня или символическая ссылка дают ошибку. Импорт не превращает удалённую запись локальной копии в новую проверенную запись автоматически.

API для пакетного повторяемого импорта: `POST /api/database/backups/catalog/import`, только администратор; тело `{ "relativePaths": ["2026/09/20/file.zip"], "dryRun": true }`. По умолчанию `dryRun=true`, от 1 до 20 путей. После просмотра результата явно передайте `dryRun=false`. Статусы отдельных элементов: `ready`, `imported`, `alreadyRegistered`, `failed`; ошибки содержатся в `error`. При отмене уже записанные элементы остаются, тот же пакет можно повторить безопасно. Операция разделяет блокировку каталога с созданием, очисткой и удалением.

## Автоматическая очистка старых локальных комплектов

- Сохраняются самый новый файл и последний целый локальный комплект. При включённой отправке в облако дополнительно сохраняется последний целый комплект, который был успешно прочитан обратно из каждого настроенного S3-подключения и Яндекс.Диска.
- Очистка после создания выполняется после облачных попыток. Пока новый комплект не подтверждён во всех настроенных назначениях, предыдущий подтверждённый комплект не удаляется по сроку хранения.
- Если подтверждённого комплекта нет (включая новое назначение, отсутствующую запись каталога или S3 без выбранных подключений), автоматическая очистка ничего не удаляет. Это может увеличить занятое место; нужно устранить отказ, а не сокращать защиту вручную.
- Сведения об облачной проверке используются только для того же неизменённого manifest. Это защита локальной очистки, а не новая проверка текущей доступности облака, независимости провайдеров или восстановимости ключей. Ручное удаление остаётся отдельным действием администратора.

## Тестовое восстановление

1. Сначала выполните обычную проверку комплекта.
2. Нажмите «Тест восстановления». SQLite восстанавливается в новый уникальный каталог, затем выполняются `integrity_check`, `foreign_key_check` и подсчёт таблиц. Рабочий файл БД не заменяется.
3. Для PostgreSQL по умолчанию формируется validation-only отчёт. Фактическое восстановление разрешается только в отдельную БД из allowlist (либо с именем `payplanner_restore_*`), с отличающейся от рабочей строкой подключения и confirmation token.
4. После SQLite- и PostgreSQL-drill в восстановленной БД принудительно отключается почта: общие SMTP-настройки очищаются, отдельные отправители канала email отключаются и теряют сохранённую конфигурацию, а ожидающие/ошибочные email-доставки получают статус `skipped`. Отправители других каналов не изменяются. Исходная БД и backup остаются неизменными. Для любого последующего локального запуска по-прежнему обязательны отключённые почта и фоновые службы в конфигурации приложения; drill не очищает внешние переменные среды или секреты запуска.
5. Отчёт хранится в каталоге drill и содержит длительность, результат целостности и число нарушений связей.

На время проверки и чтения исходного комплекта удерживается общая блокировка каталога. Создание, отправка, очистка и удаление ждут её освобождения; это действует и между экземплярами backend с общим каталогом. Отмена ожидания не создаёт отчёт об успехе и не меняет комплект. Структура SQLite без очереди доставок поддерживается: отключаются существующие общие настройки; при отсутствии или несовместимости обязательной таблицы настроек операция завершается ошибкой. Изменения почтовых данных одной тестовой базы выполняются транзакционно.

## Отказ провайдера и UNKNOWN

- Ошибки `Unavailable` и `Unknown` учитываются отдельно по провайдеру. После порога circuit breaker временно исключает его из новых попыток; бизнес-ответы `NotFound` и `Conflict` не считаются сетевым отказом.
- Неизвестный исход записи никогда не запускает слепую запись в другое место. Worker сначала выполняет `Head` и сверяет generation, размер и SHA-256.
- Если пригодна другая проверенная реплика той же generation, чтение переключается до начала отдачи тела ответа. Части разных поколений не смешиваются.
- Dead-letter и старейшая ожидающая операция видны в `GET /api/storage/health`; повтор операции выполняется администратором только после устранения причины.

## Возврат провайдера

1. Дождитесь окончания cooldown и проверьте состояние через admin health.
2. Запустите reconciliation сначала с `apply=false`.
3. Проверьте missing/corrupt/delete debt. При `apply=true` система ставит repair/delete в durable queue, но не воскрешает объекты с tombstone.
4. Не меняйте preferred provider глобально, пока debt и corrupt не равны нулю и контрольные чтения не прошли.
5. Автоматический глобальный failback намеренно отсутствует: окончательное переключение требует решения оператора.

## Удаление и удержание

- Логическое удаление сразу скрывает объект и создаёт tombstone.
- При retention физические операции получают `NextAttemptAt` не раньше даты окончания хранения.
- При legal hold физическое удаление не ставится в очередь. Reconciliation показывает состояние `retained`.
- Legacy-файлы read-only: provider `legacy-local` не поддерживает физическое удаление. Исходники сохраняются до отдельной приёмки миграции.

## Исторический backfill

1. Используйте `POST /api/storage/legacy-backfill` только под ролью администратора.
2. Обязательно начните с `apply=false`; укажите один source, `afterId` и batch не более 500.
3. Допустимые sources: `task-files`, `case-documents`, `internal-chat`, `messenger-snapshots`, `electronic-signatures`, `electronic-signature-originals`, `profile-photos`.
4. Сохраните `NextAfterId`, повторяйте пакет до `HasMore=false`. Повтор безопасен: идентификаторы детерминированы, исходные bytes не копируются и не удаляются.
5. Статусы `missing` и `invalid` не скрывайте из отчёта. Назначьте владельца исключения и устраните причину до включения чтения через каталог.
6. После dry-run выполните `apply=true` на canary-пакете, затем reconciliation. Реальный массовый backfill относится к отдельной production-приёмке.

Повтор не должен считаться успешным по одному ID объекта. Проверка сначала потоково хеширует ограниченную порцию исходников, затем одним bounded catalogue query сверяет текущую identity, поколение/размер/SHA, отсутствие удаления/tombstone и единственную проверенную доступную legacy-копию с тем же locator. Несовпадение даёт `invalid`; исходник, прежний каталог и другие документы не переписываются. Baseline подтвердил 30 случаев ложного alreadyRegistered, адресный повтор прошёл 42/42; финальный `legacy-backfill-drift-qualified-20260929.trx` — **146/146 без пропусков**, включая два actual PostgreSQL случая по 16 изменений и migration/reader regression. Повтор 125 файлов в dry-run/apply подтвердил ровно два SQL-запроса (страница источников + snapshot), без per-file catalogue query. Исходные байты и полный снимок каталога сохраняются; synthetic fixture-папки после проверки отсутствуют. Это защита регистрации, не CLI или перенос обязательных реплик: TASK-020 остаётся открытой.

## CLI предварительной проверки и регистрации (TASK-020, не полная миграция)

`node scripts/storage-legacy-backfill.mjs --help` описывает локальный административный инструмент. Он обращается только к существующему `/api/storage/legacy-backfill` с Admin bearer token. Токен передаётся через `PAYPLANNER_STORAGE_ADMIN_TOKEN`, а не аргументом; stdout содержит только счётчики/позицию. Для работы требуется Node с native fetch. HTTP разрешён только на loopback, остальные адреса требуют HTTPS; redirects не выполняются. Production-запуск требует отдельного разрешения и окна работ; приведённые команды — образец для изолированной синтетической CRM, не команда запуска на VPS.

Предварительная проверка по умолчанию:

```text
node scripts/storage-legacy-backfill.mjs --url http://127.0.0.1:LOCAL_PORT --source task-files --output ABSOLUTE_NEW_INVENTORY_DIRECTORY --batch-size 100 --max-batches 100 --interval-ms 1000
```

Повтор с теми же параметрами и `--resume` продолжает этот каталог. После полностью успешного dry-run отдельная регистрация использует **новый** output-каталог и `--apply --inventory ABSOLUTE_COMPLETED_INVENTORY_DIRECTORY`; продолжение регистрации также требует тех же scope, inventory и `--resume`. `--source` выбирает один из семи legacy-источников; начальная граница `--after-id` исключает меньшие/равные ID. Tenant/end-ID filters и полноценный copy/verify пока не реализованы: неизвестные параметры отклоняются. Не использовать этот инструмент как сертификат полной миграции.

`checkpoint.json` содержит фазу, точный scope и последнюю успешно обработанную страницу. `batches.jsonl` — ограниченные по размеру страницы с именами, владельцами, путями и контрольными суммами; это защищаемые сведения, не публичный лог. Выбирать закрытую локальную папку и ограничить её Windows ACL; режимы 0700/0600 действуют на системах с POSIX permissions, но сами по себе не подтверждают Windows ACL. Журнал синхронизируется до записи checkpoint. При сбое между этими шагами повтор страницы может добавить ещё один attempt в отчёт; **не суммировать attempts как уникальные документы**, сверять последние результаты по source/sourceId. Ни токен, ни API error body в отчёт/console не попадают.

Код выхода 0 означает только завершение inventory/catalog-фазы, всегда `replicaMigrationComplete=false`. Код 2 — лимит страниц или missing/invalid; проблемная страница остаётся текущей, исправить причину и повторить без пропуска. Код 1 — ошибка/отказ API, 130 — прерывание. После потери HTTP ответа регистрация могла сохраниться на сервере: resume повторяет ту же страницу и использует проверку уже зарегистрированных объектов. Ошибки 401/403/429/5xx и redirects автоматически не повторяются. Завершённый checkpoint при resume не делает новый delta scan; для новой проверки нужен новый output-каталог.

`run.lock` не позволяет двум процессам писать один отчёт. После аварийного завершения lock не снимается автоматически: перед его ручным удалением оператор должен подтвердить, что прежний процесс завершён. Утраченный журнал, изменённый scope, oversized checkpoint, файловые ссылки и multiply-linked artifacts отклоняются. Исходные legacy-файлы и ссылки CRM не удаляются/не переключаются. Mandatory replicas, capacity, сверка всех копий и cutover — следующие обязательные этапы TASK-020/021.

## Подготовка обязательных копий legacy-объектов (отдельная Admin API-фаза)

### Локальная запись и незавершённый capacity gate

Локальный writer с известным ожидаемым размером запрашивает preallocation временного файла до чтения исходного потока. Отрицательный размер отклоняется, отменённый вызов не создаёт папки. Превышение размера останавливается до записи лишнего блока, недобор/неверная SHA не публикуются. При IO/permission отказе записи возвращается Unavailable, при отмене — cancellation; временный файл удаляется, уже существующий документ до успешного promote не заменяется. Ошибка создания папки также обрабатывается этим путём.

Это **не подтверждение capacity/quota для всего переноса**. По [документации .NET](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestreamoptions.preallocationsize?view=net-9.0) preallocation является hint, может игнорироваться неподдерживаемой платформой и не гарантирует свободное место другим конкурентным операциям. Нужны отдельные бюджеты целевых volumes и source spool, учёт durable pending/unknown очереди, группировка папок общего диска, резервы/квоты облачных destinations и проверка реальных поддерживаемых файловых систем. Не утверждайте, что две папки на C: являются независимыми носителями. Не заполняйте рабочий диск специально для проверки ENOSPC.

Адресные проверки локального writer прошли **13/13**, `local-storage-bounded-write-20260929.trx`. Расширенный `local-storage-bounded-write-final-20260929.trx` прошёл **346/346 без пропусков за 8 мин 2 с**, включая managed file/profile/worker, actual owned PostgreSQL и 11 HTTP/browser сценариев обеих карточек задач. Проверены non-seeking oversized source без второго чтения, сохранность original при overwrite, отрицательный/нулевой/недостаточный размер, directory failure без чтения источника и pre-cancel без новых папок. Реальная нехватка места и Linux preallocation этими тестами не квалифицированы; глобальные quotas/reservations не добавлены.

Для общего capacity gate подготовлен отдельный bounded budget kernel: group IDs должен подтверждать adapter, а не имя папки. Он учитывает pending copy/spool demands, proposed bytes и минимальный свободный остаток группы; повтор одной точной identity не удваивает долг. Неизвестные или старые observations, конфликт identity/ресурса и арифметическое переполнение не разрешают планирование. Native observation и предварительный planner подключены отдельно включаемой настройкой и проверены локально на Windows, SQLite и owned PostgreSQL. Расчёт не читает cloud quota и не создаёт atomic reservations. Не используйте успешный локальный тест как доказательство наличия места на VPS.

`StorageOrchestration:MigrationCapacityChecksEnabled` по умолчанию false. При true legacy replica planner наблюдает свободное место до короткой транзакции, а перед сохранением очереди проверяет итоговый бюджет. `MigrationMinimumFreeBytes` по умолчанию 64 MiB на группу. Windows использует volume GUID и доступные текущему пользователю bytes; Linux parser группирует bind mounts по major:minor с boot epoch, но реальная Linux-среда ещё не квалифицирована. Идентификаторы групп в отчёте — непрозрачные хэши. Это группы общей ёмкости файловой системы, **не доказательство независимости физических носителей**.

Учитываются незавершённые Replicate/Repair, кроме Succeeded/DeadLetter; неизвестные и failed результаты сохраняют долг. Теперь SQL агрегирует bytes и invalid authority по provider/connection: число строк приложения ограничено группами (до 40 ресурсов и spool), а не 5000/10000 заданиями. Нормализованный регистр provider не разделяет один ресурс на разные долги. Decimal SUM сохраняет точный результат до явного отказа при превышении long.MaxValue; отсутствие generation, отрицательный размер или пустая identity также запрещают новую очередь. Новый ресурс, появившийся после внешних observations, требует нового preview без provider I/O внутри транзакции. Смена настройки/остатка резерва меняет fingerprint; перед сохранением настройки проверяются повторно.

При apply с включённым preflight долговечный долг читается **в той же Serializable transaction**, которая сохраняет новые copy/verify операции. Participating planners не могут оба сохранить несовместимые планы из одного snapshot: PostgreSQL serialization failure возвращается как отказ с queued=0, без повторного SaveChanges на прежних данных. Нужен полный новый preview/apply, а не повтор одной записи. Обработка использует существующий FinancialConcurrencyGuard; schema/migrations не изменены. Обоснование полного повтора транзакции: [PostgreSQL Serialization Failure Handling](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html). Decimal aggregate поддерживается SQLite EF9: [официальные mappings](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/functions).

Это **не общий storage reservation certificate**: участие обязательно для всех конкурирующих planners. Обычные загрузки, другие queue writers, внешние записи, несколько конфигураций/узлов, provider/root epochs и cloud quotas ещё требуют общего admission/reservation механизма. Флаг по умолчанию false; production readiness этим этапом не подтверждается.

Аудит writer-путей 30 сентября: `StorageObjectService.WriteAsync` сначала физически записывает локальный файл, затем создаёт объект и задания дополнительных копий; подключение capacity потребует не удалять файл при неопределённом исходе commit и корректно разбирать идемпотентное повторение. `StorageReconciliationService.RunAsync` ставит repair после проверки повреждённых копий, но также обновляет метаданные и запускает delete. Для новых repair-заданий добавлен отдельный `StorageOrchestration:RepairCapacityChecksEnabled` (по умолчанию false), с `RepairMinimumFreeBytes` 64 MiB: provider HEAD и наблюдения места идут вне транзакции; размер generation, source/target binding, агрегированный долг и свободное место проверяются перед записью очереди в Serializable transaction. Отказ не ставит repair и не удаляет повреждённый оригинал, следующая сверка может повторить попытку. Это gate только на планирование repair, а не гарантия места при будущей физической записи. `LegacyStorageReplicaMigrationService` отдельно выполняет preflight для своих copy jobs. `TaskFilePublicationProcessor` ставит служебное задание прикрепления без создания новой managed-копии; delete/notification/verify также не резервируют новые байты. Общая логика наблюдений и SQL-долга вынесена в `StorageCapacityAdmission`; обычная загрузка ещё не подключена, не считать механизм полным gate.

Следующая предпосылка для обычных загрузок: предварительно подготовленные вложения задач и фотографии профиля передают точный размер в managed-local writer. Он может заранее выделить место и отклонить изменившийся поток, не регистрируя неполный объект. Само по себе это не допускает новую загрузку по общему бюджету. Проверка остатка лишь после физической записи не разрешает гонку двух local-only загрузок: нет durable pending demand, который обе транзакции могли бы прочитать. Нужен отдельный долговечный prewrite-intent/reservation, созданный до provider I/O и снятый только после надёжной регистрации байтов; при lost commit ACK нельзя угадывать и удалять локальную копию. Product staging, локальный managed writer и worker spool могут делить один физический том, поэтому бюджет должен учитывать пиковые временные байты, а не складывать якобы независимые свободные объёмы.

Для будущего prewrite-intent подготовлены `StorageCapacityEpochs` (единственная монотонная версия) и `StorageCapacityReservations` (идемпотентный ресурсный долг, binding hash, локальный locator и статус). Версия нужна, чтобы короткая Serializable-транзакция могла отвергнуть наблюдение свободного места, сделанное до чужого выделения или снятия резерва; без неё уже записанный файл мог бы исчезнуть из pending debt раньше, чем другой план получит свежий остаток. Ожидающие строки резерва уже входят в общий бюджет migration/repair planner; ресурс с нераспознаваемым ключом или изменившейся физической группой останавливает планирование. По сравнению с прежним включённым preflight это два дополнительных ограниченных групповых SQL-запроса, а не чтение резерва по каждому файлу. Действующие загрузки ещё **не создают и не снимают** эти строки и не используют epoch: не принимать это за работающий upload admission. Миграции добавочные, без преобразования прежнего файлового каталога. ### Планирование копий через API

Историческая проверка первоначального preflight: `capacity-preflight-query-budget-20260929.trx` — **2/2**, 6 SQL без preflight / 7 SQL с ним. После переноса долга внутрь транзакции текущий путь использует 6 / 8 SQL: один запрос ресурсов для внешних observations, один агрегированный долг в транзакции. Observations кешируются в пределах вызова; SQL-запросов на каждый файл не добавлено. Новая ветка прошла **323/323** расширенной SQLite/owned PostgreSQL/API/CLI/worker регрессии за 3 мин 35 с, `capacity-serializable-final-20260929.trx`, и **14/14** адресных negative/terminal/large-debt cases за 1 мин 41 с, `capacity-aggregate-boundaries-20260929.trx`. PostgreSQL overlap вызвал один serializable rollback и отказ повторного плана при занятой ёмкости. Нет SQL-запросов на каждый файл; это не подтверждение общих quotas/reservations для всей CRM.

`POST /api/storage/legacy-replicas` доступен только администратору. Он принимает `source`, неизменный для запуска `runId` (непустой GUID), `afterId`, optional inclusive `endId`, `batchSize` 1..100 и `apply=false` по умолчанию. Эта фаза требует уже зарегистрированные legacy-объекты: незарегистрированные источники возвращают `registrationRequired`, изменённые — `sourceConflict`. API повторно потоково хеширует выбранную страницу через существующий backfill, но не меняет исходные bytes или product pointers.

Preview возвращает `policyFingerprint`. Для `apply=true` обязательно передать его как `expectedPolicyFingerprint`. Фиксируются policy version, required copies, write/read providers и явные connection IDs; изменение настроек между preview и apply останавливает запуск без новых операций. Для каждой destination существуют stable copy key и отдельный verify key, связанный с run ID и fingerprint. Пустая/invalid/disabled policy, readonly writer, отсутствующее connected storage соединение или конфликт locators не маскируются выбором другого хранилища.

Apply сохраняет `replicate` и `verify` в существующей durable очереди. Это не мгновенное выполнение и не включение worker: общие флаги/background services не меняются. Никакие источники, повреждённые копии, tombstones, завершённые операции или product pointers не перезаписываются. Read/write provider settings сами по себе не подтверждают физическую независимость копий; реальные аккаунты и размещение требуют отдельной приёмки.

`BatchVerified=true` означает только, что **эта выбранная страница** прошла проверки данного запуска и все её write destinations имеют succeeded verify receipt с соответствующими bytes/identity. Это не сертификат всего каталога, не global zero-debt/failback gate и не разрешение удалять legacy-файлы. Новый run ID или новый policy fingerprint требует новых verify receipts, а не reuse старых. При `pending` нужно дождаться очереди, при `conflict`/ошибках — остановиться и устранить причину без пропуска страницы. Источник сохраняет `legacy-v1`, immutable поколение не переписывается ради новой политики копирования.

Legacy replication до PUT получает bounded full-source spool и свежую authority по объекту/версии/поколению/связям/lease. После PUT и при восстановлении UNKNOWN читается полное содержимое target; правильный HEAD или ACK без правильных байтов недостаточен. Отдельная legacy verify операция использует ту же полную проверку target и актуальные SQL-связи перед receipt. Receipt сохраняется под короткими row locks без provider I/O; отмена и потеря lease не публикуют stale metadata. Потерянный ACK подтверждается чтением уже записанной копии, без второго PUT и без обязательной доступности прежнего источника.

Квалификация API и защиты копирования: baseline **15 отказов / 3 успеха из 18**, исправленный processor **87/87**, расширенный source guard **232/232** с actual PostgreSQL 20 сценариями. Первичный planner набор **29/29** прошёл; единственный отказ следующего набора **222/223** был в SQL-выражении времени synthetic retry helper. После исправления тестового parameter и добавления fingerprint проверок финальный набор `legacy-replica-migration-final-20260929.trx` прошёл **224/224 без пропусков за 3 мин 22 с**. Выполнены чистые PostgreSQL миграции, две настоящие локальные копии, конкурентные Admin HTTP запросы без дублей и новая проверка после смены run. Это не квалификация production облаков или независимых физических носителей.

### CLI-подготовка и проверка копий

В обеих фазах доступен `--end-id <ID>`: обрабатывается диапазон `(after-id, end-id]`. Верхняя граница применяется в запросе БД до загрузки страницы и сохраняется в плане и checkpoint. Повторите её неизменной в apply и resume; новые записи выше этой границы в план не включаются. `after-id == end-id` допускает пустую завершающую страницу, отрицательная граница или граница ниже cursor отвергаются. Ответ API обязан подтвердить ту же границу; строки выше неё и `hasMore` на самой границе не принимаются. Это не замороженный снимок: изменения/удаления внутри выбранного диапазона по-прежнему требуют сверки. Tenant filter пока отсутствует.

Квалификация EndId: Node **53/53**, адресный backend **59/59** и расширенный `legacy-end-id-final-20260929.trx` **225/225 без пропусков за 2 мин 35 с**. Actual CLI catalog/replicas preview/apply/resume с EndId=2 завершает ровно два выбранных документа, не включает третий и не создаёт дополнительных copy, оригиналы сохранены. В тестовом backend email/background отключены, server errors отсутствуют. Новая схема БД для EndId не требуется. Область этого доказательства — локальный ID-диапазон, не production/cloud/capacity/tenant или согласованный снимок всей CRM.

Отдельно запускайте `node scripts/storage-legacy-backfill.mjs --phase replicas --url <CRM origin> --source <source> --output <новая папка плана>`. Токен администратора остаётся только в `PAYPLANNER_STORAGE_ADMIN_TOKEN`; по умолчанию запросы не ставят задания в очередь.

После завершения плана используйте те же параметры с новой папкой результата и `--apply --inventory <папка плана>`. Run ID и настройки копий закрепляются за этим планом. Перед постановкой заданий каждая страница вновь проверяется и сопоставляется с сохранёнными исходными документами и адресами назначения. Изменение файлов, их связей, состава страницы или настроек требует нового плана, а не молчаливого продолжения. План читается последовательно порциями; весь архив не загружается в память.

`pendingCopies` (exit 2) означает, что существующая очередь ещё не подтвердила все копии текущей страницы. Cursor остаётся прежним. Этот инструмент **не включает worker и routing автоматически**: их состояние проверяет администратор отдельно. После обработки очереди повторите команду с `--resume` и той же папкой результата/плана. Пока копии не проверены, страница не считается обработанной; повторные операции используют прежний run, а новые файлы не добавляются незаметно к утверждённому плану. Частота запросов и число страниц ограничиваются прежними `--interval-ms`/`--max-batches`; одно apply использует preview и apply запросы на страницу.

`replicaPlanComplete` подтверждает только готовность выбранного плана; `replicaScopeVerified` — проверенные копии его выбранных страниц на момент запросов. `replicaMigrationComplete` остаётся `false`: это не атомарное подтверждение всего меняющегося архива, разрешение failback, переключения product pointers либо удаления исходников. Ни этот CLI, ни Admin API исходники не удаляют. Capacity/tenant scope, согласованный снимок/delta, real cloud/Linux qualification, source cleanup/cutover и полный release gate остаются открытыми.

## Потеря ключей Data Protection

Отдельная сквозная проверка `RestoredFullModelQualifiesProtectedSettingsWithCopiedKeysWithoutSourceRing` запускает настоящий backend с собственной восстановленной синтетической SQLite-БД, выключенной почтой и background services. Два native сценария `FullModelBackupRestoresReadableManagedGenerationsWithoutSource` выполняют такой же запуск на восстановленной PostgreSQL после pg_dump/psql; допускаются только собственные pp_runtime_target_GUID базы на 127.0.0.1. HTTP-часть обязательна в backend suite. Для браузерной части требуется `PAYPLANNER_TEST_RESTORED_BROWSER=true`, установленный Chromium/Chrome/Edge и frontend-зависимости; deploy workflow выполняет её отдельным обязательным шагом после установки Chromium. В чистом профиле настоящий интерфейс проходит вход, отображает фото и скачивает документ кнопкой в карточке дела с проверкой имени и точных bytes. Исходные файлы и исходный ring недоступны. Разрешён только точный loopback origin тестового интерфейса; внешние запросы и ошибки приводят к отказу. Только browser phases сериализуются bounded semaphore из-за общего Vite dependency cache. Дочерние процессы ограничены timeout и закрываются владельцем теста. Успешные сценарии не доказывают все классы вложений, field encryption или production readiness.

Новые комплекты, созданные приложением с зарегистрированным `DataProtectionRecoveryInventory`, сохраняют необязательное поле `dataProtectionRecovery`: фактический `ApplicationDiscriminator` из SDK, уникальные идентификаторы всех доступных версий ключей и UTC-время наблюдения. Снимок снимается до копирования БД и повторно перед записью manifest; исчезновение прежнего ключа или смена discriminator останавливает создание комплекта. Новые версии, появившиеся за это время, также включаются. Чтение идентификаторов не генерирует ключи и не экспортирует descriptors/секреты. Это не атомарный снимок хранилища ключей вместе с БД и не гарантия того, что все исторические protected values доступны.

`restored-storage-paths.json` переносит эти сведения без ключевого материала и сохраняет `completeRuntimeConfiguration=false`. Проверка manifest отвергает некорректные версии/ID/время, но допускает отсутствие сведений в прежних копиях. `RequireCompatible` требует совпадение discriminator и наличие всех сохранённых ID; пустой или неизвестный ring не подтверждает совместимость. Успешная сверка ID сама по себе НЕ доказывает чтение ключевого материала (например, OS-bound/KMS), правильный purpose или расшифровку данных. Секреты самостоятельно не копировать и не включать в общий файловый архив.

В opt-in изолированном запуске теперь обязательны абсолютные `RestoredRuntimeIsolation:StorageSettingsPath` (подготовленный artifact) и `RestoredRuntimeIsolation:KeysPath` (отдельно восстановленный key ring в дочерней папке artifact). Файл связан с ожидаемым ID пробной БД; отсутствующие/неизвестные metadata, другой ID, внешняя папка или файловые ссылки в пути/каталоге ключей отвергаются. Program отключает автоматическую генерацию ключей, использует точный discriminator исходного приложения, а не неявный путь нового content root, и до открытия HTTP выполняет квалификацию ключей и потоковую расшифровку сохранённых значений. Исходный путь DataProtection и его ApplicationName не используются как fallback. Это не защищает от оператора, который подменяет файлы во время запуска; чистая изолированная среда и отдельное хранение ключей по согласованной политике всё ещё обязательны.

Квалификация читает только колонки protected contacts/signers, messenger recipient addresses/link tokens, Google/Yandex calendar tokens, MAX correspondence/outbox, а также S3/Yandex/MAX/SMS protected settings. Все версии ring должны присутствовать; создание encryptor и каждый Unprotect должны пройти. Она не мигрирует legacy plaintext, не вызывает API интеграций, не сохраняет расшифрованные строки и не записывает их в лог/отчёт. SQLite открывается read-only; PostgreSQL допускается только на literal loopback, в отдельной REPEATABLE READ READ ONLY транзакции от проверки ID до последнего защищённого значения. Повреждение, неверный purpose, отсутствующая таблица или ошибка JSON останавливают запуск с общим сообщением без ключей/содержимого/путей. Сканирование потоковое (один запрос на таблицу и один на выбранные настройки), ограничено отменой/двухминутным startup timeout. Проверки SQLite и PostgreSQL не заменяют полный HTTP/browser launch, восстановление field-encryption keys или утверждение KMS/OS-bound custody. Остальные launch safety gates остаются обязательными.

PostgreSQL-квалификация доказана четырьмя full-model backup→pg_dump→psql→restore сценариями (обычный/удержанный удалённый объект, с native-документами и без них). В двух native-сценариях схема исходной пустой БД создана настоящими миграциями; история миграций переносится без повторного запуска. Синтетические S3/Yandex settings, Google/Yandex tokens, contact подписанта и адрес получателя читаются с отдельной копией ring после отключения исходного пути. Позднее повреждение S3 значения отвергается, не исправляется и не заменяется plaintext; key hashes и защищённая настройка сохраняются при проверке. Пакет подписи с protected contact также собирается восстановленным provider. Совместный PostgreSQL/SQLite/SDK набор прошёл 43/43 без пропусков; тестовые pp_runtime_source_/pp_runtime_target_ базы после завершения отсутствуют. Это не проверка рабочего сервера и не полный запуск восстановленной CRM.

- S3 Secret Key хранится защищённым и мигрирует из plaintext при чтении.
- Каталог ключей Data Protection должен быть персистентным (`/opt/payplanner/shared/data-protection-keys` в deploy workflow) и иметь отдельную защищённую резервную копию.
- Если key ring потерян, не перезаписывайте значения пустыми: восстановите соответствующий key ring по `RecoveryKeyReference`. Без него расшифровка существующих секретов невозможна.

## Откат

1. Выключите `StorageOrchestration:Enabled` и `WorkerEnabled`.
2. Legacy-пути продолжают обслуживать прежние файлы; catalog/outbox не удаляйте — они нужны для расследования и повторного включения.
3. Не откатывайте additive schema, если появились catalog rows.
4. Не удаляйте исходные файлы, старый backup или tombstones в ходе отката.
5. Зафиксируйте ревизию, значения flags, backlog, последний проверенный BackupId и результаты контрольного чтения.

## Постраничный поиск прежних локальных копий

Администратор запускает поиск явно в блоке импорта старых копий. `POST /api/database/backups/discovery` принимает `pageSize` от 1 до 20 и необязательный `cursor` предыдущего ответа. Поиск ограничен текущим настроенным корнем резервных копий, поддерживает прежние форматы `.zip`, `.sqlite`, `.backup`, `.dump`, `.sql` и не проходит через символические ссылки. Каталог БД читается одним запросом только для найденной страницы; регистрация, хеширование и облачная проверка не выполняются.

Курсор хранит только активные предки обхода, максимум 32 уровня; за запрос выполняется до 64 шагов обхода. Пустая страница с курсором не означает завершение. Для выбора очередного окна перечисляются записи текущей папки: память ограничена размером окна, но время зависит от размера папки. Изменения файлов между страницами не образуют согласованный снимок: после изменений поиск нужно начать заново. Ошибки чтения возвращаются отдельно, остальные папки продолжают обходиться.

Передача найденных путей заменяет список ручного импорта и сбрасывает прежнюю предварительную проверку. Далее действуют прежние dry-run и подтверждённый импорт с повторной проверкой целостности. Найденный manifest сам по себе не доказывает пригодность комплекта.

## Обязательный gate перед production

- Полные backend/frontend tests, lint, typecheck, encoding audit и production build зелёные.
- SQLite clean/upgrade migration paths пройдены; PostgreSQL migration SQL проверен и отдельный тестовый restore выполнен оператором.
- Есть минимум один проверенный полный BackupSet и успешный restore drill.
- Подтверждены разрешения, квота, versioning/retention и failure-domain внешних провайдеров.
- Утверждены RPO/RTO, число обязательных копий, классы данных, сроки хранения и владелец alert-ов.
- Только после этого: schema → shadow catalog → canary backfill → dual-write → canary read → наблюдение → поэтапное включение классов.

## Резерв места для новых загрузок (пока выключен)

`StorageOrchestration:UploadCapacityChecksEnabled` по умолчанию `false`; включение относится к отдельному canary после обязательного gate выше. При включении запись требует заранее известные точный размер и SHA-256. Управляемые загрузки задач и фотографий передают эти значения из своей проверенной временной копии; другие вызывающие пути без них получают отказ до записи. Порог `UploadMinimumFreeBytes` по умолчанию 64 МиБ.

Управляемые загрузки задач и фото сначала создают отдельный резерв под временный файл. Пока он записывается, резерв защищает весь заявленный объём. После подтверждения полного размера временной копии резерв снимается: её байты уже вычтены из реально свободного места тома, и повторный учёт резерва ошибочно отказал бы допустимой загрузке. Постоянная копия резервируется дополнительно. При создании старой совместимой копии задачи, документа дела или фото место резервируется отдельно до физического копирования; каталог старых файлов и каталог управляемых объектов на одном томе делят один бюджет. Временный резерв совместимой копии снимается только после исчезновения её временного пути: постоянный файл уже занимает реальное свободное место тома. На каждую попытку с устойчивым ключом также создаётся резерв локального тома, удалённых назначений и временного spool. Если запись прервалась до подтверждения физической копии, ожидающий резерв остаётся в БД, чтобы занятое место не было ошибочно обещано другой загрузке. Повтор с тем же ключом сверяет содержимое и продолжает публикацию; заменять ожидающую запись другим файлом нельзя. Снятие основного резерва и постановка копий в очередь происходят одной транзакцией. Не удаляйте ожидающие резервы вручную без проверки точного файла, ключа и состояния каталога.

После аварийного прерывания администратор может вызвать `POST /api/storage/capacity/stages/reconcile` без `apply`: ответ постранично показывает резервы старше десяти минут, которые уже подтверждены полным обычным файлом, и причины, по которым остальные сохраняются. `nextAfterKey` передаётся как `afterKey` на следующей странице; за вызов проверяется не более 200 строк. Только явный `apply=true` снимает резервы с полным файлом на той же физической группе. Сверка не удаляет файлы и не освобождает резерв у отсутствующей, неполной, недоступной или находящейся за пределами разрешённой папки копии. Это не фоновая очистка всех аварийных остатков: такие остатки нужно расследовать отдельно, предварительно остановив активные записи.

Тот же ограниченный preview доступен администратору в «Настройки → Хранилище файлов». Экран отдельно показывает резервы всех загрузок и резервы временных файлов; список ниже содержит только временные файлы с резервом старше десяти минут. Для каждой записи показаны причина сохранения, относительный путь только после его проверки, ожидаемый и найденный размер, время обновления; страницы содержат по 50 строк. Абсолютный путь и содержимое не возвращаются; недоверенный относительный путь скрывается. Кнопка применения требует отдельного подтверждения; сервер повторно проверяет файлы, поэтому итоговое число может отличаться от предварительного просмотра. После применения обновите страницу и разберите оставшиеся резервы вручную, не удаляя файлы или записи БД по одному только возрасту.

Служебное состояние `GET /api/storage/health` показывает число ожидающих резервов и дату старейшего. Резерв старше десяти минут переводит состояние хранилища в `degraded`, но кратковременный резерв действующей загрузки не считается аварией. Проверка состояния не очищает записи автоматически.

Это ещё не полный допуск по ёмкости для всей CRM: после аварийного завершения могут остаться временные файлы и ожидающие резервы, требующие безопасной сверки, а внешние хранилища должны возвращать проверяемую квоту и физическую группу. Остальные файловые writer-пути также нужно квалифицировать. Не включать флаг как общий production-гарант до завершения этих этапов, отказных сценариев и согласованного наблюдения.
