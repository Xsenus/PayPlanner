# Roadmap: точечный доступ к календарям сотрудников

Дата старта: 2026-06-17
Критичность: высокая
Контекст заказчика: нужно дать секретарю или другой роли не общий доступ ко всем календарям, а выборочный доступ к календарям конкретных сотрудников. Если сотрудник выбран в правах, его календарь должен появиться у пользователя. Если доступ забрали, календарь и события этого сотрудника должны исчезнуть из видимости. Отдельно нужно решить, распространяется ли это только на календарь внутри CRM или также на внешние Google/Яндекс календари.

## Как работать с этим roadmap

Статусы:

- `[ ]` не начато.
- `[~]` в работе.
- `[x]` выполнено и проверено кодом, тестами, кодировкой и локальной БД, если пункт требует БД.
- `[!]` заблокировано, причина указана рядом.
- `[decision]` требуется решение пользователя или бизнеса.
- `[acceptance]` требуется ручная приемка на реальных данных или окружении заказчика.

Правила обновления:

- Перед началом реализации открыть этот файл и проверить все связанные пункты.
- При начале работы заменить `[ ]` на `[~]`.
- После закрытия пункта добавить строку `Выполнено:` с кратким фактом, проверками и коммитом, если он уже есть.
- Не отмечать `[x]`, пока не пройдены нужные проверки: backend/frontend tests, сборка, UTF-8, локальная БД, ручная приемка, если она указана.
- Если найден новый риск, обход доступа или дополнительный сценарий, добавить его сюда отдельным пунктом.
- После user-facing изменений добавить запись в `backend/AppReleases/releases.json`.

## Цели

1. В правах роли для раздела "Календарь" появляется режим "Конкретные сотрудники".
2. Администратор может выбрать сотрудников, чьи календари видны пользователям этой роли.
3. Если сотрудник добавлен в список, его календарные задачи появляются в CRM у пользователя с этой ролью.
4. Если сотрудника убрали из списка, его календарные задачи сразу исчезают из CRM-видимости.
5. Администраторские и существующие режимы "Только свой", "Отдел", "Все сотрудники" продолжают работать без регрессий.
6. API календаря не отдает события сотрудников, которые не входят в разрешенный список.
7. Если будет включен внешний сценарий, Google/Яндекс календари выбранных сотрудников создаются, обновляются и удаляются синхронно с правами доступа.

## Текущие факты из анализа

- Текущая модель видимости календаря использует `RolePermission.ViewScope`.
- Сейчас доступны режимы видимости данных `own`, `department`, `all`.
- Для раздела календаря UI уже показывает настройку "Видимость календарей".
- Расчет видимых пользователей выполняется через `DataVisibilityService.ResolveDataVisibilityAsync`.
- `DataVisibilityAccess.VisibleUserIds` уже используется как набор пользователей, по которым можно фильтровать данные.
- Для режима "Отдел" список пользователей рассчитывается по отделу текущего пользователя.
- Для режима "Все сотрудники" доступ фактически не ограничивается списком пользователей.
- Внешние Google/Яндекс подключения сейчас привязаны к текущему вошедшему пользователю.
- Админский режим внешней синхронизации `adminByAssignee` уже умеет раскладывать задачи по отдельным календарям сотрудников.
- Уже есть логика удаления календарей/связей во внешних календарях при отключении соединения, но ее нужно аккуратно применить к отзыву точечного доступа.

## Область реализации

### Обязательная часть

- Точечная видимость календарей сотрудников внутри CRM.
- Настройка выбранных сотрудников в карточке роли.
- Серверная фильтрация событий календаря по выбранным сотрудникам.
- Тесты backend и frontend.
- Проверка на локальной БД.
- Запись в "Что нового".

### Расширенная часть после решения

- Синхронизация выбранных сотрудников во внешний Google Calendar секретаря или другой роли.
- Синхронизация выбранных сотрудников во внешний Яндекс.Календарь.
- Автоматическое удаление внешних календарей и связей при отзыве доступа.
- Логи и диагностика удаления внешних календарей при изменении прав.

## Milestone 1. Бизнес-решения и границы сценария

Цель: не смешать CRM-видимость и внешнюю синхронизацию, чтобы права не оставляли лишние данные во внешних календарях.

- [x] Подтвердить основной сценарий: точечный доступ нужен сначала внутри CRM.
  - Выполнено: основной реализуемый сценарий принят как CRM-видимость выбранных сотрудников; внешние Google/Яндекс календари остаются отдельным decision-блоком до явного подтверждения.

- [x] Решить, нужен ли внешний сценарий в этом же релизе.
  - Вопрос: должны ли выбранные сотрудники появляться отдельными календарями в Google/Яндекс аккаунте секретаря?
  - Выполнено: внешний сценарий включен в доработку по повторному запросу на полную реализацию.

- [x] Определить, кто может выбирать сотрудников.
  - Выполнено: используется существующий доступ к редактированию ролей: администратор или роль с правом редактирования раздела ролей.

- [x] Определить, применяется ли список к роли или к конкретному пользователю.
  - Выполнено: первый этап хранит список на уровне роли. Все пользователи роли получают одинаковый список календарей; персональные исключения можно добавить отдельным расширением.

- [x] Определить поведение для уволенных/неактивных сотрудников.
  - Выполнено: неактивные сотрудники исключаются из фактической видимости; UI выбора будет ориентирован на активных пользователей.

## Milestone 2. Модель данных и миграции

Цель: добавить хранение точечных сотрудников без поломки текущей модели `own/department/all`.

- [x] Добавить новый режим видимости календаря `specific`.
  - DoD: режим поддержан на backend и frontend; старые значения `own`, `department`, `all` продолжают работать.
  - Выполнено: `specific` разрешен только для календаря; для остальных разделов нормализация остается прежней.

- [x] Добавить сущность для выбранных сотрудников календаря роли.
  - Предлагаемая модель: `RoleCalendarVisibleUser` или похожее название.
  - Поля: `Id`, `RoleId`, `UserId`, `CreatedAt`, `CreatedByUserId`, `CreatedByUserName`.
  - Индексы: уникальный индекс `RoleId + UserId`, индекс по `UserId`.
  - Выполнено: добавлена сущность `RoleCalendarVisibleUser` с уникальным индексом по роли и пользователю.

- [x] Добавить DbSet и конфигурацию EF для новой связи.
  - DoD: каскадное удаление связи при удалении роли; пользователь не должен удаляться каскадом через эту связь.
  - Выполнено: связь с ролью удаляется каскадом, связь с пользователем настроена без опасного каскада.

- [x] Создать миграции SQLite и PostgreSQL.
  - DoD: миграции применяются на чистой и существующей БД.
  - Выполнено: созданы миграции SQLite и PostgreSQL; SQLite проверен стартом backend на временной локальной БД.

- [x] Добавить безопасную нормализацию прав.
  - DoD: если `ViewScope = specific`, но список пуст, пользователь видит только свой календарь или ничего сверх своего календаря.
  - Предложение: свой календарь всегда остается видимым, как сейчас в `VisibleUserIds`.
  - Выполнено: пустой список `specific` дает текущего пользователя без дополнительных календарей.

## Milestone 3. Backend API ролей и DTO

Цель: администратор должен получать и сохранять выбранных сотрудников вместе с правами роли.

- [x] Расширить DTO прав роли для календаря.
  - Новое поле: `visibleUserIds` или `selectedUserIds` только для `calendar`.
  - DoD: поле сериализуется и десериализуется без влияния на остальные разделы.
  - Выполнено: `calendar.visibleUserIds` добавлен в backend и frontend-типы.

- [x] Обновить сохранение прав роли.
  - DoD: при сохранении роли список выбранных сотрудников полностью синхронизируется: добавленные появляются, удаленные удаляются.
  - Выполнено: сохранение роли синхронизирует список, удаляет отозванный доступ и не создает дубли.

- [x] Добавить валидацию выбранных пользователей.
  - DoD: нельзя сохранить несуществующего пользователя; неактивные пользователи либо отбрасываются, либо возвращают понятную ошибку согласно решению milestone 1.
  - Выполнено: несуществующие, неактивные и неподтвержденные пользователи отклоняются понятной ошибкой.

- [x] Обновить audit прав роли.
  - DoD: в аудите видно, что изменился список сотрудников для видимости календаря.
  - Выполнено: при изменении списка обновляется существующий audit-след роли (`PermissionsUpdatedAt`, автор изменения) и объектный аудит роли. Отдельный детальный журнал "кого добавили/убрали" оставлен вне текущей задачи.

- [x] Обеспечить обратную совместимость.
  - DoD: старый payload без `visibleUserIds` сохраняет прежнее поведение и не очищает список случайно, если UI старой версии отправит только базовые поля.
  - Выполнено: список синхронизируется только когда `visibleUserIds` явно пришел в payload.

## Milestone 4. Расчет видимости календарей в backend

Цель: все серверные выборки календаря должны использовать точечный список как источник истины.

- [x] Расширить `DataVisibilityService.ResolveDataVisibilityAsync` для `calendar + specific`.
  - DoD: `VisibleUserIds` содержит текущего пользователя и выбранных активных сотрудников.
  - Выполнено: сервис возвращает текущего пользователя и выбранных активных/подтвержденных сотрудников.

- [x] Проверить все endpoints календаря задач.
  - DoD: события, summary, analytics и связанные календарные ответы используют один и тот же расчет видимости.
  - Выполнено: журнал задач и список исполнителей получают параметр `calendarView` и используют права раздела «Календарь».

- [x] Проверить календарные endpoints дел, если они используют отдельный раздел прав.
  - DoD: точечный доступ применяется только там, где бизнес-смысл именно "календарь сотрудников", и не раскрывает дела/финансы сверх прав.
  - Выполнено: точечный список применен к календарным задачам сотрудников; календарь дел не расширялся, чтобы не открыть дела/финансы сверх текущих прав.

- [x] Закрыть прямой API-обход.
  - DoD: пользователь не может получить события сотрудника вне списка через фильтр assignee/userId/date range.
  - Выполнено: фильтрация выполняется на backend через `VisibleUserIds`, а не только на frontend.

- [x] Обновить backend permission matrix.
  - DoD: тестами подтверждены `own`, `department`, `all`, `specific`, пустой список и неактивный сотрудник.
  - Выполнено: добавлены тесты на `specific`, невыбранного и неактивного сотрудника; существующие backend-тесты прошли полностью.

## Milestone 7. Внешние Google/Яндекс календари

Цель: реализовать только после подтверждения, что точечный доступ должен управлять внешними календарями.

- [x] Подтвердить, что внешний сценарий нужен.

  - Выполнено: внешний сценарий реализован для Google Calendar и Яндекс.Календаря на базе фактической видимости календаря роли.

- [x] Добавить режим внешней синхронизации "Выбранные сотрудники".
  - DoD: режим не требует выдавать пользователю роль admin.

  - DoD: если роль дает доступ только к выбранным сотрудникам, внешний календарь не создает события остальных сотрудников.

  - Выполнено: создание/удаление календарей и удаление событий при отзыве доступа пишутся в существующие Google/Яндекс sync logs.

## Definition of Done

Задача считается закрытой, когда:

- В роли можно выбрать режим "Конкретные сотрудники" для календаря.
- Список сотрудников сохраняется и отображается повторно после открытия роли.
- В CRM пользователь видит календарные события только своего календаря и выбранных сотрудников.
- Удаление сотрудника из списка сразу убирает его события из доступной видимости.
- Серверные endpoints не позволяют получить события неразрешенного сотрудника прямым запросом.
- Старые режимы `own`, `department`, `all` не сломаны.
- Backend и frontend тесты пройдены.
- TypeScript, lint и build пройдены.
- Кодировка проверена.
- Локальная БД проверена.
- Запись в "Что нового" добавлена.
- Roadmap обновлен.
- Коммит создан.
- После деплоя VPS проверен.
- Реальная роль секретаря принята заказчиком.

## Риски и меры защиты

- Риск: выбранные сотрудники в CRM и внешние календари разойдутся.
  - Защита: не включать внешний сценарий без отдельного milestone 7 и тестов удаления.

- Риск: при отзыве доступа события останутся во внешнем календаре.
  - Защита: обязательная очистка внешних календарей и связей при изменении списка.

- Риск: пользователь получит события сотрудника прямым API-запросом.
  - Защита: фильтрация только на backend через `DataVisibilityService`, frontend не считается источником безопасности.

- Риск: режим `specific` с пустым списком будет трактоваться как "все".
  - Защита: пустой список должен давать только собственный календарь или другое явно принятое ограниченное поведение.

- Риск: список выбранных сотрудников на уровне роли окажется слишком грубым.
  - Защита: после первого этапа можно добавить персональные исключения на уровне пользователя.
