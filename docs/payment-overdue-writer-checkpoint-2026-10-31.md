# Фоновая просрочка платежей — 31 октября 2026

Локальный этап от `757b647a`, ветка `feature/company-image-sequencing`. Продолжение [обхода авансов](advance-review-cursor-checkpoint-2026-10-31.md). CMP-05 / SEC-01 / DOC-09 остаются открытыми.

## Реализация

PaymentStatusUpdater больше не загружает весь журнал в один контекст. Он проходит кандидатов по ID порциями до 200, с верхней границей ID, зафиксированной в начале запуска. Строки, ещё не просроченные по локальному дню ответственного, не задерживают следующую порцию. Профиль timezone и прежнее правило выбора ответственного сохранены. Локальный семафор исключает перекрытие запусков одного экземпляра; штатная остановка отменяет незаписанную порцию без ошибки просрочки.

Каждая порция использует существующую BalanceApplicationLease.BeginSystemAsync: собственную Serializable-транзакцию, SQLite BEGIN IMMEDIATE и общие PostgreSQL NOWAIT-блокировки. Вместе с выбранными платежами блокируются все строки их связанных счетов, в порядке ID, одним запросом. После блокировки проверяется состав кандидатов и группы. Граф ограничен 5000 строками; превышение останавливает порцию до записи, а не квалифицирует усечённую историю. Слишком большие группы требуют отдельного разбора; это не автоматически исправленные данные.

Противоречивые связи исключаются существующим ApplyUnambiguousInvoiceLinks. Закрытая и компенсированная история исключается тем же предикатом PaymentCreditInvariantScope, который используется интерактивными писателями: аннулированный статус/процесс счёта, кредит при отмене и возврат оплаты. Общий предикат выделен в запрос без дополнительных загрузок и без AsNoTracking внутри изменяющего запроса; скалярные проверки существующих писателей сохранены.

Итог счёта вычисляется существующими EvaluateInvoiceAggregate/ApplySnapshot по уже загруженной группе, без запроса на каждый счёт. Переход в просрочку не имеет права менять Amount/PaidAmount; если старый итог требует денежной сверки, порция откатывается. Проверка зачтённого баланса дополнительно не допускает сохранения оплаты ниже подтверждённого зачёта. Баланс, проводки, номера и исторические связи не меняются. Сохраняется прежняя логика статуса/дат согласованного итога; финансовые расхождения не ремонтируются.

Атомарность — на порцию. Ошибка следующей порции не отменяет ранее сохранённые; повторный запуск завершает оставшиеся Pending. Денежные данные не переписываются при ошибке SQL или потере подтверждения уже выполненного commit.

## Уведомления

Уведомления запускаются после commit и освобождения блокировок. Для выбранных сохранившихся Overdue перечитываются ответственные; активность, согласование и право просмотра фильтруются прежними методами, а NotificationService централизованно повторно проверяет видимость объекта. Каждый получатель использует отдельную DI-область: ошибка и грязный контекст одной отправки не затрагивают следующего получателя и сумму платежа. В production NotificationService/INotificationService scoped.

Все получатели текущей порции проверяются; сохраняются первые 32 подробных исключения и полное число ошибок. Задание не объявляется успешным при сбое уведомления, единственная обычная ошибка сохраняет исходный стек; отмена задания отличается от тайм-аута доставки. Для счёта текст говорит о статусе оплаты, а не о произвольном переходе документооборота из черновика.

Остаётся отдельная незакрытая граница: если статус уже сохранён, но уведомление вообще не создалось либо подтверждение commit потеряно до отправки, повторная проверка только Pending не создаёт это уведомление заново. Созданные сообщения обслуживает прежняя очередь доставки; новое гарантированное создание пропущенного сообщения этим этапом не заявлено. Это следующий этап до объявления всего фонового механизма завершённым.
