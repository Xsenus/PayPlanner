# Решения владельца для продолжения YouGile

Подготовлено 12.10.2026 по [плану исполнения](archive/roadmaps/unified-2026-10-14/yougile-execution-roadmap-2026-10-12.md), [операционной спецификации](claude-yougile-operations-development-spec-2026-10-10.md) и [финансовой спецификации](claude-yougile-finance-development-spec-2026-10-10.md). Варианты ниже — вопросы, а не утверждённые правила. Не начинать зависимую реализацию по первому варианту автоматически. Ответ фиксировать с PAY-ID, выбранным вариантом, исключениями, датой и примером результата.

## PAY-2 — зарплата

**Известно:** расчётное ТЗ ещё пишется. Реальные начисления и выплаты не утверждены.

**Нужно решить:** модель вознаграждения, источник работы, момент признания, периоды, возвраты, исторические ставки, утверждение и права просмотра.

| Вариант | Последствия |
| --- | --- |
| Оклад с ручными премиями, утверждаемыми руководителем | Нужны ставка с периодом действия, правила неполного месяца и корректировок; выполненные задачи не начисляют деньги автоматически |
| Процент от фактически полученных денег | Нужны источник поступления, распределение между исполнителями, частичная оплата и возврат; сумма счета не равна начислению |
| Сдельная оплата принятой работы, возможно с окладом | Нужны тариф/единица работы, факт приёмки, запрет повторного начисления и правила отмены |

Для выбранной модели предоставить 3 расчёта: обычный период, частичная оплата/работа, отмена или возврат после закрытия. Указать, кто видит чужую зарплату и кто утверждает выплату.

## PAY-8 — телефония

**Известно:** блок отложен, перечень функций есть; модель и протокол действующей АТС не получены.

**Нужно решить:** возобновлять ли сейчас, какая АТС/версия/протокол, граница первого пилота и доступ к записям.

| Вариант | Последствия |
| --- | --- |
| Оставить отложенным | Документируем зависимость, не создаём условный адаптер и реальные звонки |
| Пилот только входящих событий и истории | Нужны обезличенные callbacks, подпись, call-ID, конечное состояние пропущенного; одна задача на звонок, без управления АТС |
| Дополнить пилот звонком по клику и записью | Дополнительно нужны разрешённые команды, роли, срок хранения/ссылки, тестовый номер и отдельное разрешение реального пилота |

Указать правила создания контакта/заявки при неизвестном номере и доступ сотрудников к чужим звонкам. Пароли передавать через локальную конфигурацию, не через этот документ.

## PAY-9 — телефонный справочник

**Известно:** прежняя схема CRM → файл на REG.RU → телефон сохраняется; звонки относятся к PAY-8.

**Нужно решить:** возобновление, формат/кодировка файла, модель устройства, защищённое чтение, частота и удаление архивных контактов.

| Вариант | Последствия |
| --- | --- |
| Оставить отложенным | Не публикуем адресную книгу и не меняем устройство |
| Ручная выгрузка по существующему образцу | Нужны обезличенный образец и проверка устройства; обновление выполняет уполномоченный сотрудник |
| Автоматическая публикация того же формата | Нужны расписание, атомарная замена, контроль последнего успеха и правила отзыва данных; недоступность не затирает рабочий файл |

Подтвердить состав контактов: все активные или только доступные конкретному устройству/группе. Указать максимальный размер и реакцию на архивирование клиента.

## PAY-17 — общая карточка дела

**Известно:** общее ТЗ ещё пишется. PAY-21–28 уже задают конкретные экраны; их макеты можно разбирать отдельно.

**Нужно решить:** недостающие поля, стадии и действия, границы общего ТЗ, обязательность и права изменения.

| Вариант | Последствия |
| --- | --- |
| Сейчас только каркас PAY-21–28 с нынешними правилами | Дизайн не меняет переходы, историю и сохранение; отсутствующие требования остаются открытыми |
| Сначала завершить единое ТЗ дела | Общие бизнес-изменения ждут утверждения; подготовка карт текущих действий продолжается |
| Утвердить один тип дела как первый этап | Нужны конкретные стадии, роли, обязательные поля и примеры; другие типы сохраняют нынешнее поведение |

Для каждого нового поля указать источник, тип, обязательность, право редактирования и поведение старых записей. Для перехода — условия, побочные действия и отмену.

## PAY-18 — права

**Известно:** действующие проверки и ограниченный доступ Анны должны сохраняться; новое ТЗ экрана неполное.

**Нужно решить:** только группировка или новая модель прав, индивидуальные исключения, приоритет запрета и область данных.

| Вариант | Последствия |
| --- | --- |
| Перегруппировать нынешние права без изменения модели | Самый узкий этап; существующие серверные ограничения остаются эталоном |
| Роль плюс индивидуальные исключения с явным запретом | Нужны правила наследования, отзыв действующего токена и матрица конфликтов; нельзя расширять доступ по умолчанию |
| Права по роли и области: свои/отдел/организация | Нужны владельцы данных, принадлежность сотрудника и прямые проверки API, поиска, файлов и экспорта |

Дать примеры для администратора, бухгалтера, секретаря, исполнителя и наблюдателя: просмотр, изменение, удаление, экспорт, финансовые действия, чужие данные. Синтетические роли среды не утверждают эту модель.

## PAY-30 — бизнес-процессы

**Известно:** общего ТЗ нет; конкретная автоматизация заявок PAY-31 самостоятельна, существующие scheduler/outbox переиспользуются.

**Нужно решить:** первый процесс, триггер, переходы, владелец правил, разрешённые внешние действия и требования к версиям.

| Вариант | Последствия |
| --- | --- |
| Один фиксированный процесс поверх нынешней автоматизации | Нужен утверждённый пример; минимальная новая конфигурация, без универсального редактора |
| Редактор ограниченных правил: триггер/условия/действия | Нужны разрешённые операции, проверка циклов, предварительный просмотр, публикация и аудит |
| Полный процесс с версиями и согласованием | Нужны миграция активных экземпляров, остановка/повтор/отмена и права автора/публикующего; объём существенно больше |

Для первого сценария описать успешный путь, повтор события, частичный отказ, отмену и запрет внешнего действия. Не добавлять интеграции по одному заголовку карточки.

## PAY-34 — оплата акта

**Известно:** нужны сквозные финансовые документы; существующие исправления НДС и копеек сохраняются. Факт оказания услуг и факт денег должны быть различимы.

**Нужно решить:** что означает действие «оплатить акт», к какому денежному основанию оно относится и как работают частичная оплата/возврат.

| Вариант | Последствия |
| --- | --- |
| Только привязать существующее поступление | Не создаёт вторую денежную операцию; нужен остаток распределения и защита от повторной привязки |
| Создать поступление из акта и связать его | Нужны дата, способ, сумма и идемпотентность; сам акт не означает уже полученные деньги |
| Оплата через связанный счёт/договор | Нужны правила распределения одного платежа по нескольким актам и расхождения сумм |

Предоставить примеры акта 1000: поступление 400, доплата 600, возврат 200, отмена документа. Указать, кто вправе выполнить и отменить распределение.

## PAY-33 и PAY-34 — нумерация

**Известно:** в прежней передаче сохранялась общая ручная модель; полный Word-ТЗ требует автоматическую последовательность, префиксы и сброс. Это явное расхождение, действующие номера пока не менять. Собственные организации общие, ИНН уникален; филиал наследует ИНН, КПП может переопределяться — эти решения уже приняты.

**Нужно решить:** режим, область последовательности, префикс, период сброса, момент выдачи номера, ручное исключение и совместимость старых документов.

| Вариант | Последствия |
| --- | --- |
| Сохранить ручные номера | Автоматизация раздела Word-ТЗ откладывается; уточнить проверку дубликатов |
| Автоматическая отдельная последовательность на организацию/тип/год | Нужны точный формат, граница года, атомарная выдача и подтверждённое правило использования отменённых номеров |
| Автоматический номер с разрешённым ручным исключением | Нужны роли, аудит и правила конфликта; старые документы остаются со своими номерами |

Указать 5 ожидаемых номеров для двух компаний, филиала и смены года. Отдельно решить резервирование номера у черновика и повторное использование после отмены.

## PAY-33 и PAY-34 — PDF и выдача документа

**Известно:** снимки реквизитов и неизменяемые версии изображений при первой выдаче уже реализованы; это не закрывает полный архив/печатную модель. Форматы, лимиты, прозрачность и параметры печати требуют подтверждения.

**Нужно решить:** момент фиксации, исправление выданного документа, единый шаблон или версии по организациям, применимость логотипа/подписи/печати.

| Вариант | Последствия |
| --- | --- |
| Один согласованный шаблон, фиксация при первой выдаче | Сохраняется текущая база; нужен эталон для 1/50/многих строк и формат исправления |
| Версии шаблонов по организации и типу | Нужны правила выбора, история версии и повторная печать именно выданной версии |
| Правка черновика до отдельного действия «выдать» | Нужен явный переход и права; после выдачи изменения оформляются отдельной версией/коррекцией по решению владельца |

Предоставить эталон PDF и размеры изображений. Не регенерировать старые выданные документы по новым реквизитам без отдельного согласованного правила.

## PAY-35 — налоговая модель КУДиР

**Известно:** регистр, CSV/XLSX и закрытие периодов уже опубликованы; экспорт сам по себе не подтверждает налоговую готовность. Нужен единый денежный источник.

**Нужно решить:** организации и налоговые режимы, форма/период, момент признания дохода и расхода, возвраты и корректировки. Конкретные правовые правила должен подтвердить бухгалтер по актуальным требованиям до реализации.

| Вариант | Последствия |
| --- | --- |
| Управленческий регистр поступлений/расходов без заявления налоговой готовности | Можно сверять денежные источники; налоговая форма и признание остаются отдельным этапом |
| Налоговая книга для одного выбранного режима/организации | Нужны утверждённые бухгалтером правила и примеры признания; охват ограничен этим режимом |
| Несколько режимов и организаций | Нужны независимые правила, периоды, права и сверка каждой книги; существенно шире первый этап |

Дать эталоны: аванс, частичная оплата, возврат, расход с первичкой, корректировка закрытого периода. Указать, кто закрывает и открывает период и как сохраняется история.

## PAY-36 — банк и протокол

**Известно:** общий интерфейс и каркас есть; реальный адаптер/банк не подтверждены. Первый этап предусматривает чтение, без платёжных полномочий.

**Нужно решить:** один первый банк, официальный протокол/версия, sandbox и способ авторизации; отдельно — сопоставление поступлений документам.

| Вариант | Последствия |
| --- | --- |
| Импорт обезличенной файловой выписки согласованного формата | Нет API-авторизации; нужны образец, кодировка, идентификаторы операций и повторный импорт без дублей |
| Официальный read-only API одного банка | Нужны документация, sandbox, scopes, callback/refresh и все страницы выписки; токены только в защищённой конфигурации |
| Сначала документация и sandbox, адаптер позже | Не имитируем работающую интеграцию; фиксируем недоступные входные данные и критерии пилота |

Подтвердить банк и точную ссылку на официальную документацию. Не выводить протокол из названия банка. Для разнесения дать однозначное основание; неоднозначное поступление требует отдельного решения, сумма распределений не больше поступления.

## PAY-37 — значение «аннулирована» для календаря

**Известно:** настройка показа завершённых задач уже выпущена, внешняя приёмка и [новое уточнение](archive/roadmaps/unified-2026-10-14/calendar-terminal-task-visibility-roadmap-2026-10-12.md) остаются открытыми. Отмена задачи и финансовое аннулирование — разные источники состояния.

**Нужно решить:** какое состояние имеется в виду, скрывать ли событие или показывать отметку, кому и в каких режимах календаря.

| Вариант | Последствия |
| --- | --- |
| Только задача со статусом cancelled | Правило ограничено самой задачей; статус счета/акта не меняет её календарное событие |
| Отдельно отменённая задача и аннулированный финансовый документ | Нужна явная связь и две независимые настройки/индикации, без автоматической отмены работы |
| Сохранять терминальные события с отметкой вместо скрытия | Нужны фильтр и визуальное состояние; история остаётся видимой, текущая рабочая выдача должна быть согласована |

Указать примеры для связанного судебного события, простой задачи и задачи к аннулированному счёту. Подтвердить различие administrator/исполнитель/наблюдатель и настройку по умолчанию.

## Как передать ответы

Ответить по разделам: PAY-ID → вариант или своё правило → исключения → примеры → утверждающий. Доступы, токены, клиентские документы и банковские пароли в этот файл не добавлять. До ответа соответствующие `[decision]` и `[acceptance]` в roadmap сохраняются.
