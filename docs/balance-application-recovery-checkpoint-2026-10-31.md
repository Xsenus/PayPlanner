## Реализация и границы

Оба балансовых контроллера получили чтение `applications/{requestId}?paymentId=...` с запретом кеширования. Оно проверяет активность/согласование пользователя, актуальный доступ к контрагенту, редактированию платежей и полному балансу; использует существующую транзакционную защиту и блокировку доступного платежа. Результат выбирается по ключу, первому отправителю, контрагенту и целевому платежу, без раскрытия чужой операции. Чтение не создаёт receipt, денежную запись, аудит или отмену.

Подтверждённый результат возвращается как `Committed` с исходными суммами и `isReplay=true`. Отсутствующий/неподходящий результат — **202 `Unconfirmed` с явным `result:null`**, а не успешная отмена или разрешение нового списания. Pending PostgreSQL writer даёт409 вместо преждевременного ответа; после его завершения результат читается. Глобальная производственная настройка пропуска null не убирает обязательное поле результата в этом контракте. Исторический результат не является текущим балансом и не должен прибавляться к уже обновлённой оплате.

В клиентском API подготовлены два метода чтения с отменой и `no-store`. Проверяется контрагент/платёж/UUID до сети; неизвестное состояние, несоответствие ключей/платежа, неверный replay, отсутствие явного результата и некорректные суммы отклоняются. Возвращаются только известные поля. **Экран восстановления и передача стабильного ключа в POST ещё не включены**, прежний UI пока использует старый контракт зачёта. Новая схема БД не добавляется, ApplyAsync и его lease/расчёты не меняются.

## Обнаруженная предпосылка

Существующий механизм создания платежей намеренно сохраняет в браузере только ограниченные метаданные, без команды, суммы, персональных данных и токена. Для баланса следует сохранить этот принцип: actor/API/контрагент/платёж/UUID/хеш команды, read-back перед отправкой и короткая защищённая мутация между вкладками. Не сохранять весь финансовый payload ради удобного повтора.

**Нельзя предлагать «удалить попытку и начать заново», пока сервер не умеет закрывать неизвестный исход с защитой от позднего исходного POST.** Один GET этого не решает. Нужна отдельная согласованная серверная запись отмены/состояние и атомарное разрешение гонки commit/cancel: уже состоявшийся зачёт возвращает результат, отменённый UUID навсегда блокирует позднее списание. Суммы, документы и прошлые записи журнала при отмене попытки не меняются. Это следующий технический этап до активации frontend, не бизнес-решение и не повод вручную очищать localStorage.

## Очередь и прогресс

Сначала серверная отмена неизвестной попытки с fencing позднего запроса и native commit/cancel гонками; затем metadata-only устойчивый ключ, явное восстановление/отмена в frontend и канонические чтения платежа/остатка. После этого — собственный контекст внешних callbacks/refresh и остальная матрица CMP-05 (поля/архив/назначения/подразделения/роли, обе БД), затем справочники и CMP-04/CMP-06. Linux native CMP-01 подготовлен, не выполнен. Успешные неизменившиеся проверки не повторять; один обязательный полный CI всех семи jobs перед выпуском.
