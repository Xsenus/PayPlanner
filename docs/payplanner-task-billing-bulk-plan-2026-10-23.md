# PayPlanner — массовая смена учёта задач, DOC-11 / TSK-10

**Текущий итог:** базовая массовая смена учёта с обоими утверждёнными режимами входит в R8: fresh backend9808+restored5 и сохранённый frontend3372 после original verify0; exact final receipts находятся в handoff. Старые168 backend и62 frontend — scoped исторические доказательства, не новый full union. Отдельная contract-task policy138 подготовлена только в будущем SETTINGS; новые правила/проверки не включены в текущий R8. DOC-11/TSK-10 целиком не закрыты.

**Сохранённый срез подготовки 23–24 октября:** План реализации от 23 октября 2026 года. Источники требований — [активный план задач](payplanner-task-workflow-roadmap-2026-10-14.md), раздел TSK-10, и [активный план финансовых документов](payplanner-financial-documents-roadmap-2026-10-14.md), раздел DOC-11. **24 октября начата отдельная реализация backend и общего интерфейса в изолированной рабочей копии. Backend прошёл 168/168 адресных проверок, включая 82 новые регрессии; полный frontend/backend-барьер окончательного связанного пакета и выпуск ещё впереди.** Текущий замороженный кандидат P0/MAX/TSK-12 не расширяется этим механизмом; его успешные проверки не повторяются ради данного плана.

Согласованы оба режима массовой операции:

1. По умолчанию — только выбранные незавершённые задачи без связанного счёта.
2. По отдельной явной отметке — также выбранные завершённые задачи без связанного счёта.

Новых тарифных категорий не требуется. Переиспользуются существующие `billable` и `internal`: платная и неоплачиваемая/внутренняя. `legacy` остаётся состоянием отсутствующего решения, а не третьим новым целевым классом. Отсутствие клиентской связи определяет структурную внутреннюю задачу; изменение учёта не должно очищать клиента или дело.

`approved` не подменяет `done`: согласованная, но не завершённая задача остаётся в текущем статусе. `cancelled` не считается выполненной и не включается вторым режимом. Инициатива автоконтроля и тип `control` сами по себе не делают работу платной; целевой класс выбирает пользователь, автоматического массового начисления нет.

Первый этап **не охватывает все задачи без InvoiceId**. Договорные строки явно исключены до решения ниже. Нельзя представить частичное внедрение этого ограниченного механизма как полное закрытие DOC-11/TSK-10.

## Счёт, завершение и финансовая история — разные признаки

### Любой связанный счёт закрывает массовую смену

Защитная проверка — `entity.BillingInvoiceId.HasValue`, до изменения класса и до вычисления отображаемого `BillingStatus`. Сейчас `ResolveTaskBillingStatus` сначала возвращает `legacy/internal`, поэтому старая неконсистентная запись с InvoiceId может не выглядеть `invoiced`. UI-label не заменяет проверку внешнего ключа.

Первый этап не меняет учёт при **любом** связанном счёте: черновом, выставленном, отменённом, частично или полностью оплаченном. Не выяснять по наличию номера или `PaidAmount == 0`, можно ли обойти связь. Не читать пользователю чужой номер/сумму для объяснения отказа: достаточно «Задача связана со счётом; исправление выполняется в финансовом разделе».

Факт оплаты хранится отдельно: [Payment](../backend/Models/Payment.cs#L230) содержит `IsPaid/PaidAmount`, [PaymentStatus](../backend/Models/PaymentStatus.cs) и [InvoiceWorkflowStatus](../backend/Models/InvoiceWorkflowStatus.cs) отражают состояния. Новая операция не записывает ни одно из этих полей, не создаёт платёж и не снимает InvoiceId.

### `done` без счёта не означает «финансовой истории нет»

Завершённая работа может иметь результат, файлы, согласования, договорный снимок, решение о типе учёта, выплату исполнителю либо ранее законно аннулированный счёт. Разрешение включить `done` даёт право поменять **текущий клиентский класс учёта в выбранной безопасной области**, а не пересчитать эту историю.

- Сохраняются статус/результат/срок/участники/доказательства выполнения, клиент/юрлицо/дело, реквизиты документов и денежные суммы.
- `ContractorPaymentId`, `ContractorPaymentAmount`, `ContractorPaymentEnabled`, сроки и правила выплаты исполнителю независимы от выставления клиентского счёта. Их не менять, не отзывать и не генерировать повторно. Пользовательская граница «задачи с выставленным счётом или оплатой сохраню без изменений» означает пропуск всей такой задачи, а не только сохранение суммы выплаты. В первом безопасном этапе пропускается любая уже созданная выплата по FK либо существующему служебному маркеру, даже ожидающая: так массовая операция не конкурирует с её оплатой. Проверка выполняется до no-op. Настройки будущей выплаты без созданного платежа сами по себе не означают уже состоявшуюся оплату; завершение/перерасчёт вознаграждения не вызываются.
- Историческое `BillingDecisionAt` не доказывает наличие счёта и не является основанием повторно запускать backfill/resolver для всей истории. При новом реальном решении сохранить прежний класс и дату в записи истории, записать новую дату решения только для изменённой строки. Не переписывать предыдущие записи и не трогать no-op.
- Аннулирование счёта уже имеет отдельный финансовый маршрут: [ReleaseCancelledInvoiceBillingTasksAsync](../backend/Controllers/InvoicesController.cs#L1276) снимает связь и добавляет историю после обработки денег. Bulk не повторяет этот маршрут. Если связь уже снята штатным маршрутом, он не восстанавливает и не переписывает прежний документ/возврат/аванс.
- Отсутствие прямой ссылки не позволяет угадывать финансовые связи по совпавшему номеру, тексту истории или сумме. При обнаружении иной реальной финансовой зависимости, не покрытой моделью проверки, строку пропустить и вынести конкретное основание в план, а не исправлять исторические деньги автоматически.

Дополнительная подтверждённая граница 24 октября: завершённая задача с `ContractorPaymentEnabled && ContractorPaymentOnResult` пропускается до no-op, даже без созданной выплаты. Позднее восстановление выплаты использует `(UpdatedAt ?? CreatedAt).Date + delay`; запись нового `UpdatedAt` могла бы сдвинуть её дату. Защита не зависит от текущего признака внешнего исполнителя, суммы и задержки: старые настройки могут быть неполными или измениться отдельно. Статус, версия, история и финансовые поля защищённой строки сохраняются; автоматического ремонта нет. Незавершённая задача с будущей выплатой и завершённая с фиксированной датой без созданной выплаты остаются в исходной безопасной области. Причина `contractorPaymentProtected` описывает и существующую выплату, и требующий проверки расчёт.

### Оставшаяся граница Fixed / Actual

Пользователь решил режимы завершённости; это не решение о снятии договорных связей.

1. `Fixed` без InvoiceId может уже означать работу в оплачиваемом фиксированном договоре. Массовое превращение в «без счёта по факту» способно изменить очередь/смысл учёта, хотя сумма договора останется прежней.
2. `Actual` с `BillingContractId` также имеет существующую связь. При индивидуальном переводе в `internal` resolver очищает её. Этот побочный эффект нельзя незаметно переносить на массовую операцию.
3. **Консервативный первый этап:** пропускать все строки с существующим `BillingContractId` или непустым `BillingModeSnapshot`, независимо от `Fixed/Actual`, даты договора, `done` и выбранного целевого класса. Существующие значения не исправлять даже при конфликтующем снимке.
4. Для расширения требуется отдельное решение: сохранять ли привязку/снимок при `internal`, можно ли снимать их у ранее завершённых работ и как вернуть платный учёт без переоценки прошлого. До решения нет нового третьего класса, смены тарифа, массовой замены договоров или исторического перерасчёта.

## Контракт и конкурентная защита

Минимально расширить существующий bulk DTO для отдельной операции учёта: целевой `billable|internal`, `includeCompleted=false`, фиксированные ID и ожидаемые версии/состояния по каждому ID. Точные имена полей выбрать при реализации; не выдавать пример структуры за уже существующий API.

1. **Проверка запроса.** Только положительные уникальные ID; пустой набор и более 500 ID — объяснимый `400`, без молчаливого усечения. Поля учёта не смешиваются с текущими исполнитель/приоритет/статус/срок. Не принимать произвольный целевой `legacy` и не запускать backfill. Набор expected entries должен точно соответствовать переданным ID, включая явное допустимое `null` старого UpdatedAt.
2. **Права.** Использовать свежую серверную видимость и `CanFullyModifyTask` каждой строки с текущими настройками, а не frontend editable-флаг. Ограниченный исполнитель не получает прав по разрешению сдавать результат. Сохранить семантику собственных/чужих задач; верхняя проверка новой ветки не должна ошибочно отвергать единственное `canEditOthers`, если индивидуальный маршрут его допускает.
3. **Транзакция.** `ReadCommitted`, PostgreSQL `SELECT ... WHERE Id = ANY(...) ORDER BY Id FOR UPDATE`, затем прочитать доступные строки и финансовые связи. Не начинать блокировку связанных Payments после task locks: это создаёт обратный порядок относительно link invoice. Для первого этапа достаточно отказа по любому InvoiceId без записи Payment.
4. **Свежие условия.** Под блокировкой повторно проверить видимость, полные права, статус/режим включения `done`, InvoiceId, ContractId/ModeSnapshot, клиентское основание и ожидаемую версию. Совпадение целевого класса в безопасной строке возвращает no-op: повтор уже выполненного запроса не создаёт конфликтную новую историю.
5. **Версия.** Переиспользовать имеющийся `UpdatedAt` в [DTO задачи](../backend/Models/Responses/TaskJournalDtos.cs#L65); сравнивать канонически с точностью существующей сериализации, не строками разного timezone-формата. Если версия изменилась, не перетирать новое решение второй вкладки. Точная проверка версии добавляется на прикладном уровне; нельзя объявлять нынешний UpdatedAt уже работающим EF concurrency token.
6. **Запись.** Менять только классификацию, новую дату решения и UpdatedAt у реально изменённых строк; добавить историю с actor/старым/новым классом и прошлой датой решения. Не вызывать общий UpdateTask с полным присланным payload, завершение задачи, создание счёта, смену контрагента/дела/договора или календарную синхронизацию без необходимости.
7. **Завершение.** Детерминированные отказы отдельных строк не мешают разрешённым изменениям. Save/commit завершить до уведомления realtime. Техническая ошибка сохранения откатывает всю транзакцию; она не должна возвращать успешные построчные обновления. При повторе с потерянным ответом достигнутые значения становятся no-op.
8. **Нагрузка.** Один ограниченный набор ID, пакетное чтение/блокировка и настройки/права в подходящем существующем контексте. Не выполнять запрос договора/счёта на каждую строку, не загружать все страницы журнала и историю комментариев ради eligibility. После commit — одно обновление realtime и адресное обновление списка/summary.

## Построчный итог и повтор

Сохранить совместимые `requested/updated/skipped`; добавить отдельный счётчик неизменённых и список исходов для новой ветки. Старым массовым действиям не менять контракт молча.

| Исход | Пользовательский смысл | Повтор |
| --- | --- | --- |
| `updated` | Учёт изменён, добавлена одна запись истории | Уже достигнутое значение — no-op |
| `unchanged` | Целевой учёт уже установлен | Не повторять без нового выбора |
| `completedExcluded` | Завершённая задача не включена отметкой | Можно выбрать явное включение, заново подтвердить область |
| `cancelledOrUnknownState` | Отменённая/неизвестная запись вне области | Разобрать отдельно, не выдавать за выполненную |
| `invoiced` | Есть связанный счёт | Массовый повтор не обходит ограничение |
| `paid` / `contractorPaymentProtected` | Уже есть оплаченная / иная созданная выплата исполнителю | Вся задача пропускается, включая класс, дату решения и историю |
| `contractualAccounting` | Есть договор/финансовый снимок; вне первого этапа | Только после отдельного решения и расширения механизма |
| `invalidBinding` | Для платного учёта не хватает допустимого клиента/дела | Исправить связь отдельно, затем новый выбор |
| `unavailable` | Строка отсутствует или недоступна/нет полномочий | Одинаковая нейтральная причина без раскрытия чужих данных |
| `conflict` | Данные изменились после подтверждения | Обновить эти строки, заново подтвердить версии |

Идентификаторы в исходах — только из запроса. Не возвращать сведения о скрытых задачах/счетах. Для смешанного набора — успешный ответ с честными исходами; полное отсутствие права операции — `403`, неуспешный запрос/технический конфликт транзакции — соответствующий неуспешный ответ. Обработать `409` без очистки черновика/фиксированного набора.

Повтор после ошибки использует сохранённые ID исходной попытки, а не новый результат фильтра. После частичного успеха окно показывает изменено/уже было/пропущено и причины; кнопка повтора не включает успешные строки или вновь появившиеся задачи. Перед повтором конфликтов обновить доступное состояние и получить новое явное подтверждение пользователя.

## Интерфейс и обе формы

- Одна переиспользуемая модалка массового учёта для общего журнала и таблицы задач дела; существующие checkboxes и доступные действия сохраняются.
- При открытии фиксируются ID/версии и число выбранных строк. Ясно указать «выбрано на этой странице» для текущего механизма. «Выбрать всё» не означает скрытые страницы/весь фильтр. При будущем выборе нескольких страниц сохранять явный конечный набор ID, не передавать серверу открытый фильтр для mutation.
- Целевой класс и выключенная отметка «Также изменить завершённые задачи без счёта»; до применения видны общая область и исключения. Предварительная клиентская оценка не выдаётся за серверную гарантию.
- Отмена не отправляет mutation и сохраняет выбор. Во время отправки нельзя повторно нажать «Применить», изменить область или закрыть окно с потерей статуса ожидания. Изменение страницы/фильтра во время подтверждения аннулирует устаревшую область либо оставляет явно зафиксированный набор с понятной подписью.
- При отказе не теряются параметры/ID, при частичном результате показывается раздельный итог. После успешной записи обновляются строки и billing summary; значения не подменяются длиной страницы.
- Индивидуальный общий `TaskBillingEditDialog` и защищённые действия счёта остаются доступны по прежним правам. Legacy и modern показывают новый класс из одной модели, сохраняют результат/файлы/статус, а глобальный `taskCardWindowMode` продолжает выбирать единую форму для всех пользователей.
- Новая функция после реализации получает отдельную понятную запись «Что нового» по принятому формату. Данный план сам по себе не публикует release note и не обещает доступность на сервере.
