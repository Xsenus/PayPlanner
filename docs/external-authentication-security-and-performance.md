# Внешняя авторизация: безопасность и производительность

Документ описывает публичный контур входа через Google, VK, Яндекс и Telegram. Он предназначен для разработчиков и администраторов CRM и фиксирует правила, которые нельзя ослаблять при последующих изменениях.

## Назначение маршрутов

- `GET /api/auth/providers` возвращает только признаки готовности провайдеров и публичное имя Telegram-бота. Секреты и внутренние причины отключения в ответ не входят.
- `POST /api/auth/external/start` создаёт одноразовый OAuth `state` сроком на 10 минут. Поддерживаются только `google`, `vk` и `yandex`.
- `GET /api/auth/external/status/{state}` проверяет результат OAuth. Успешный результат входа можно получить только один раз.
- `GET /api/auth/external/callback/{provider}` принимает ответ провайдера и показывает безопасную HTML-страницу во всплывающем окне.
- `POST /api/auth/telegram/widget` проверяет время и HMAC-подпись Telegram Login Widget до поиска или создания пользователя.
- `POST /api/auth/telegram/bot/start` создаёт одноразовую ссылку с `state` для диалога с Telegram-ботом.
- `GET /api/auth/telegram/bot/status/{state}` проверяет результат диалога с ботом. Токен также выдаётся только один раз.
- `POST /api/auth/telegram/webhook` принимает тело не более 64 КиБ и требует точного совпадения заголовка `X-Telegram-Bot-Api-Secret-Token`.

## Ограничения публичных запросов

Лимиты разделяются по внешнему IP после обработки одного доверенного proxy-hop от локального nginx. Очередь запросов отключена: при превышении порога сервер сразу отвечает `429`.

| Группа | Лимит |
| --- | ---: |
| Публичный список провайдеров | 60 запросов в минуту |
| Запуск OAuth, Telegram Widget или Telegram Bot | 10 запросов в минуту |
| Проверка `state` | 120 запросов в минуту |
| OAuth callback | 30 запросов в минуту |
| Telegram webhook | 300 запросов в минуту |

Лимит polling выше стартового, потому что штатный интерфейс проверяет короткоживущий `state` раз в две секунды. Увеличивать стартовый лимит без оценки риска перебора и роста таблиц запросов нельзя.

## Валидация и безопасные ответы

- provider, intent, state, return URL, OAuth code и поля Telegram ограничены по формату и длине до обращения к сервису;
- `returnUrl` допускает только локальный путь CRM: абсолютный или protocol-relative адрес заменяется безопасным корнем;
- Telegram Widget принимает числовые `id` и `auth_date`, SHA-256 hash из 64 шестнадцатеричных символов и URL фотографии ограниченной длины;
- callback экранирует текст перед вставкой в HTML;
- анонимные ответы не содержат `Exception.Message`, адресов внешнего API, конфигурационных ключей или ответов провайдера;
- полная техническая причина остаётся только в серверном журнале с контекстом провайдера;
- отмена HTTP-запроса передаётся в SQL и внешние сетевые операции и не преобразуется в ошибку авторизации.

## Одноразовая выдача результата

После успешного callback запись имеет состояние `completed`. При polling сервис сначала строит ответ, затем выполняет условный `UPDATE`, который меняет только ещё не использованную запись `completed` на `consumed`. Если два запроса пришли одновременно, обновить строку сможет только один из них. Только победивший запрос получает токен; второй получает состояние `consumed` без токена.

Та же схема применяется к привязке внешнего способа входа и Telegram. Нельзя заменять условный `UPDATE` обычным изменением отслеживаемой EF-сущности: параллельные DbContext снова смогут выдать результат дважды.

## Бюджет запросов к базе

- список публичных провайдеров выполняет ровно два SQL-запроса: одну проекцию нужных `SystemSettings` и один компактный список активных Telegram-отправителей;
- legacy-настройки Telegram загружаются одной порцией, а не отдельным запросом на каждый ключ;
- pending/failed/expired polling выполняет один поиск по уникальному индексу `state`; запись просроченного запроса дополнительно обновляется;
- завершённый polling читает `state` один раз, затем загружает пользователя с ролью и выполняет условное потребление результата;
- запросы используют уникальные индексы `IX_ExternalAuthRequests_State` и `IX_TelegramAuthRequests_State`.

Снимок настроек живёт только во время одного HTTP-запроса. Глобальный кэш намеренно не используется, поэтому сохранённое администратором изменение видно при следующем обращении и не требует сброса процесса.

## Проверки при изменении контура

Обязательные автоматические сценарии:

1. наличие `AllowAnonymous`, правильной rate-limit policy и ограничения размера webhook;
2. серверная валидация некорректных provider, intent и Telegram payload;
3. реальные пороги стартового и polling rate limit;
4. отсутствие внутренних текстов исключений в `ProblemDetails`;
5. два SQL-запроса для публичного списка провайдеров;
6. один поиск OAuth `state` при завершении входа;
7. параллельный polling выдаёт токен ровно одному запросу;
8. отменённый запрос не начинает SQL-операции;
9. миграции и сценарий входа проходят на PostgreSQL, а не только на SQLite.

После публикации дополнительно проверяются `/api/health`, публичная страница CRM, revision, отсутствие новых `5xx` и исключений `payplanner.service`.
