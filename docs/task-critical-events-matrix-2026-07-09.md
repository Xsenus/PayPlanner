# Матрица критичных событий задач для принудительных окон

Дата: 9 июля 2026.
Связанный roadmap: `task-critical-modals-notification-settings-roadmap-2026-07-09.md`.
Основание: аудит `task-critical-notifications-audit-2026-07-09.md` и замечания клиента по запросу переноса срока, согласованию результата и заметности текущих процессов.

## Цель матрицы

Определить, какие события задач должны попадать в общий слой принудительных окон, какие действия должны быть доступны прямо из окна, какие настройки нужны и какие записи обязаны сохраняться в центре уведомлений независимо от показа всплывающего окна.

## Базовые правила

- Принудительное окно не заменяет `UserNotifications`; оно является способом показа уже созданного уведомления.
- Отключение принудительного окна не должно отключать запись в центре уведомлений, историю задачи и счетчики непрочитанных уведомлений.
- Очередь окон должна показывать одно событие за раз и восстанавливаться после обновления страницы по непрочитанным `requiresAction` уведомлениям.
- Критичные события с действием не должны закрываться только по клику вне окна. Для закрытия нужно выполнить действие, открыть задачу или явно подтвердить ознакомление, если событие информационное.
- Если пользователь не имеет права выполнить действие, окно должно объяснить это и дать переход к задаче/центру уведомлений, не скрывая событие из журнала.
- Existing task-card modals остаются источником бизнес-логики, но forced layer должен уметь открыть нужное действие из любой страницы CRM.

## Приоритеты очереди

| Приоритет | События | Правило показа |
| --- | --- | --- |
| 1 | Запрос переноса срока, ожидание согласования результата | Действие требуется от текущего пользователя; показывать первым. |
| 2 | Возврат на доработку, просроченное согласование | Требуется быстрое внимание, но действие может быть в карточке задачи. |
| 3 | Согласовано/отказано по переносу срока, задача согласована и завершена | Информационные события; показывать после actionable-событий или только как обязательное ознакомление для выбранных типов. |

## Матрица событий

| Событие | Тип уведомления | Получатель | Нужно действие | Действия в forced-окне | Источник данных | Текущее состояние | Решение для реализации |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Запрос переноса срока задачи | `taskDeadlineChangeRequested` | Постановщик/ответственный reviewer, при необходимости наблюдатели как информируемые | Да, для reviewer | `Согласовать`, `Отказать`, `Открыть задачу`; при согласовании выбор даты/времени, при отказе обязательный комментарий | `taskId`, `deadlineChangeRequestId`, `requestedDueAt`, `reason`, `reviewerUserId` в metadata; API `approveTaskJournalDeadlineChangeRequest`, `rejectTaskJournalDeadlineChangeRequest` | Backend создает уведомление и metadata; в `TaskJournal` есть `TaskDeadlineChangeDecisionPrompt`, но глобального forced-окна нет | Первый actionable forced-сценарий. Окно должно появляться вне зависимости от текущего раздела CRM, если уведомление unread/requiresAction и пользователь является reviewer. |
| Отправка результата задачи на согласование | `taskApprovalRequested` | Текущий согласующий | Да | `Согласовать`, `Вернуть на доработку`, `Открыть задачу`; при возврате обязательный текст замечаний и при необходимости новый срок | `taskId`, current approver из задачи; API `updateTaskJournalApproval` / `PATCH /tasks/{id}/approval` | Backend создает уведомление; в `TaskJournal` есть `TaskApprovalDecisionPrompt`, но глобального forced-окна нет | Второй actionable forced-сценарий. Окно должно показывать результат задачи и требовать решения согласующего. |
| Возврат задачи на доработку | `taskRevisionRequested` | Исполнитель/постановщик по текущей логике уведомлений | Да, как ознакомление исполнителя | `Информация прочитана`, `Открыть задачу` | `taskId`, `resolution`, `resultingStatus` в metadata | Уже есть `ForcedTaskRevisionModal`, но он отдельный и не входит в общую очередь | Перенести сценарий в общий forced layer без потери текущего поведения и тестов. |
| Просрочено согласование | `taskApprovalOverdue` | Текущий согласующий и/или контролирующие участники по backend-логике | Да | `Открыть задачу`, `Понятно`; опционально быстрый переход к решению согласования | `taskId`, `currentApproverId`, `approvalDueAt` в metadata | Backend создает критичное уведомление; toast/Web Push возможны, forced-окна нет | Добавить как forced-информационное окно высокого приоритета, чтобы согласующий не пропускал просрочку. |
| Задача согласована и завершена | `taskApproved` + `completed=true` или `resultingStatus=done` | Исполнитель/постановщик по backend-логике | Нет, только ознакомление | `Ознакомлен`, `Открыть задачу` | `taskId`, `completed`, `resultingStatus`, `resolution` | Уже обрабатывается в `ForcedTaskRevisionModal` | Перенести в общий forced layer как информационное событие приоритета 3. |
| Перенос срока согласован | `taskDeadlineChangeApproved` | Запросивший перенос и заинтересованные участники | Нет, только ознакомление | `Ознакомлен`, `Открыть задачу` | `deadlineChangeRequestId`, `DecisionDueAt`, `DecisionComment`, `Status` | Backend создает уведомление; forced-окна нет | На первом этапе оставить как обычное уведомление. Можно добавить в forced layer как опциональное обязательное ознакомление, если заказчик попросит. |
| Перенос срока отклонен | `taskDeadlineChangeRejected` | Запросивший перенос и заинтересованные участники | Да, как ознакомление исполнителя | `Понятно`, `Открыть задачу` | `deadlineChangeRequestId`, `DecisionComment`, `Status` | Backend создает уведомление; forced-окна нет | Рекомендуется forced-информационное окно приоритета 3, потому что исполнитель должен увидеть причину отказа. |
| Новый результат задачи без финального согласования | `taskChanged` или `taskCompleted`, если задача закрывается без маршрута согласования | Зависит от задачи | Обычно нет | `Открыть задачу`, `Понятно` | `taskId`, change labels/body | Есть обычные уведомления | Не включать в первую forced-версию, чтобы не перегрузить пользователей. Вернуться после приемки основных сценариев. |

## Настройки forced-окон

| Настройка | Уровень | Значение по умолчанию | Что отключает | Что не отключает |
| --- | --- | --- | --- | --- |
| Показывать окно по запросу переноса срока | Личная настройка + ролевое значение по умолчанию | Включено | Только forced-окно | `UserNotifications`, история задачи, раздел согласований, Web Push/toast по отдельным настройкам |
| Показывать окно согласующему по результату задачи | Личная настройка + ролевое значение по умолчанию | Включено | Только forced-окно | `UserNotifications`, история задачи, маршрут согласования |
| Показывать окно возврата на доработку | Личная настройка + ролевое значение по умолчанию | Включено | Только forced-окно | Уведомление исполнителю, история, комментарий согласующего |
| Показывать окно просрочки согласования | Личная настройка + ролевое значение по умолчанию | Включено | Только forced-окно | Критичное уведомление и Web Push/toast, если включены |
| Показывать информационные окна по решениям переноса срока | Личная настройка + ролевое значение по умолчанию | Выключено для согласования, включено для отказа | Только forced-окно | Центр уведомлений и история |

## Очередь и восстановление после обновления

- Источник очереди: `GET /api/notifications` с `status=unread`, `requiresAction=true`, типами из forced matrix и pageSize, достаточным для первых событий.
- Для событий, где `requiresAction=false`, но forced включен как обязательное ознакомление, нужен отдельный allow-list типов (`taskDeadlineChangeRejected`, completed `taskApproved`) и фильтр по metadata.
- Сортировка: сначала priority из матрицы, затем `createdAt`, затем `id`.
- После действия:
  - успешное бизнес-действие должно обновить задачу;
  - связанное уведомление можно отметить прочитанным;
  - очередь должна перейти к следующему событию;
  - центр уведомлений должен получить `emitUserNotificationsChanged`.
- После простого ознакомления:
  - уведомление отмечается прочитанным;
  - событие уходит из очереди;
  - история задачи не меняется.
- После обновления страницы:
  - очередь заново загружает unread-события;
  - локально подтвержденные, но еще не синхронизированные события не должны дублировать окно.

## Минимальный порядок реализации

1. Добавить общий слой очереди принудительных окон поверх `UserNotifications`.
2. Перенести текущий `ForcedTaskRevisionModal` в общий слой без изменения поведения.
3. Подключить `taskDeadlineChangeRequested` как первое actionable-окно.
4. Подключить `taskApprovalRequested` как второе actionable-окно.
5. Добавить настройки forced-показа отдельно от каналов доставки.
6. Добавить тесты очереди, восстановления, действий и отключения forced-показа без потери центра уведомлений.

## Критерии готовности следующей реализации

- Запрос переноса срока появляется у постановщика как обязательное окно из любого раздела CRM.
- Согласующий получает обязательное окно по задаче на согласовании из любого раздела CRM.
- Возврат на доработку продолжает показываться как обязательное окно, но уже через общий слой.
- Отключение forced-окна не удаляет событие из центра уведомлений.
- После перезагрузки страницы непрочитанное actionable-событие снова появляется в очереди.
- Одновременно несколько событий не накладываются друг на друга, а показываются последовательно.
- Есть backend/frontend тесты на ключевые сценарии.
