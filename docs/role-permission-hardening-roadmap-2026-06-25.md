# Roadmap: закрытие разделов CRM правами ролей

Дата старта: 25.06.2026

## Контекст

Заказчик сообщил, что пользователи с ролью юристов видят слишком много разделов CRM. Ожидаемое поведение: администратор в настройках роли может оставить юристу только нужные рабочие разделы, а закрытые разделы должны пропадать из меню и быть недоступны по прямой ссылке/API.

Связанный срочный вопрос из того же сообщения: платежи юристам и задолженность по исполнителю. Он относится к финансовой привязке платежей к личности и должен проверяться отдельно, чтобы не смешивать бизнес-логику выплат с задачей прав доступа.

## Первичные находки

- [x] В проекте уже есть каталог прав `RolePermissionCatalog` и разделы: календарь, задачи, заметки, отчеты, калькулятор, юрлица, клиенты, дела, счета, акты, платежи, договоры, справочники, уведомления, роли, аудит, интеграции, Яндекс.Диск, S3.
- [x] Frontend уже скрывает многие пункты навигации и страницы через `useRolePermissions`.
- [x] Backend уже имеет общий helper `HasUserSectionPermissionAsync` и механизм `ViewScope`.
- [x] Найденный риск закрыт в коде: для существующего не-admin пользователя отсутствие строки права больше не открывает раздел на backend, а frontend до загрузки прав использует закрытый fallback.
- [x] `notifications` разделен на личный inbox и админские настройки: личные уведомления остаются доступными авторизованному пользователю, админские настройки закрыты правами `notifications`, а переходы из уведомлений в связанные задачи/дела/финансы показываются только при праве на соответствующий раздел.
- [x] Разделы `users`, `userActivity`, `profile`, `companyProfile`, detail/create-страницы и вложенные действия проверены на уровне frontend route map: `profile` оставлен личным разделом, `users/userActivity/companyProfile` оставлены admin-only, detail/create-страницы привязаны к родительскому разделу.

## Цель

Сделать права ролей закрывающими по умолчанию для всех существенных разделов CRM:

- закрытый раздел не отображается в боковом меню, быстрых действиях, карточках и ссылках;
- прямой переход по URL переводит пользователя в доступный раздел или показывает понятный отказ;
- backend возвращает `403`, если пользователь пытается читать/создавать/редактировать/удалять данные закрытого раздела;
- ограничение области видимости данных (`own`, `department`, `specific`, `all`) применяется одинаково в списках, карточках, календарях, отчетах и связанных виджетах;
- администратор может управлять доступом через роли, а изменения применяются всем пользователям роли.

## Подробное техническое задание

### Основной принцип

Права должны работать как замок, а не как косметическое скрытие меню. Если администратор выключил раздел для роли, пользователь этой роли не должен:

1. Видеть раздел в левом меню.
2. Открывать раздел через прямую ссылку или сохраненную вкладку.
3. Получать данные раздела через API.
4. Видеть данные закрытого раздела внутри других карточек.
5. Выполнять действия закрытого раздела через кнопки, контекстное меню, уведомления, связанные ссылки или старые URL.

### Что считать разделом

Каждый пользовательский раздел CRM должен быть привязан к одному ключу прав:

| Раздел в интерфейсе | Ключ права | Что закрывает |
| --- | --- | --- |
| Календарь | `calendar` | Календарь, события, календарные платежи, аналитика календаря |
| Журнал задач | `tasks` | Задачи, контроль, согласования, календарь задач, карточки задач |
| Заметки | `notes` | Личные/совместные заметки |
| Отчеты | `reports` | Все отчеты и аналитические сводки |
| Калькулятор | `calculator` | Калькулятор услуг/стоимости |
| Юрлица | `legalEntities` | Реестр юрлиц, карточки юрлиц, связи юрлиц |
| Клиенты | `clients` | Реестр клиентов, карточки клиентов, контакты-физлица |
| Дела | `cases` | Реестр дел, карточки дел, вкладки дел |
| Счета | `accounts` | Доходные/расходные счета, карточки счетов |
| Акты | `acts` | Акты, создание/изменение/удаление актов |
| Платежи и деньги | `payments` | Платежи, банк, касса, карты, e-money, итоги, авансы |
| Договоры | `contracts` | Договоры, карточки, создание, связанные документы |
| Справочники | `dictionaries` | Просмотр/редактирование справочников |
| Уведомления | `notifications` | Админские настройки уведомлений; личный inbox проверить отдельно |
| Роли | `roles` | Список ролей, настройка матрицы прав |
| Аудит | `audit` | Аудит объектов, восстановление удаленных, техобслуживание |
| Интеграции | `integrations` | DaData, календарные интеграции, импорт, внешние подключения |
| Яндекс.Диск | `yandexDisk` | Раздел диска и настройки синхронизации |
| S3 | `s3Storage` | Раздел S3 и настройки S3 |
| Пользователи | admin-only или новый ключ | Список пользователей, карточки пользователей |
| Контроль пользователей | admin-only или новый ключ | Активность пользователей |
| Профиль | всегда свой | Только личный профиль текущего пользователя |

### Обязательные бизнес-правила

1. `admin` всегда видит и может делать все, если нет отдельного технического ограничения.
2. Обычная роль видит только то, что разрешено в настройках роли.
3. Если строка права по разделу отсутствует в БД, это не должно случайно открывать раздел.
4. Если `canView=false`, все остальные операции раздела должны считаться запрещенными, даже если в БД случайно стоят `canCreate=true` или `canEdit=true`.
5. Если раздел закрыт, связанные данные этого раздела должны исчезать из других карточек:
   - нет права `payments` -> не показывать платежи/деньги/долги/финансы дела;
   - нет права `accounts` -> не показывать счета;
   - нет права `acts` -> не показывать акты;
   - нет права `contracts` -> не показывать договоры;
   - нет права `cases` -> не открывать карточки дел;
   - нет права `clients`/`legalEntities` -> не открывать карточки контрагентов.
6. `ViewScope` должен ограничивать не только списки, но и открытие карточки по ID.
7. Старые и новые формы задач должны проверяться вместе, если меняются права задач, файлов, комментариев, подзадач, исполнителей или результата.

## Матрица разделов для проверки

- [x] Календарь: меню, страница, события, таблица платежей в календаре, аналитика календаря, Google/Yandex calendar panels; таблица и карточки платежей в календаре уже не открывают клиентов/дела без прав `clients/cases`, встроенный CRM-календарь задач открывается только при `tasks.canView`, сводная аналитика календаря скрыта и заменяется сообщением без `calendar.canViewAnalytics`, личные панели подключения Google/Яндекс календарей в профиле скрыты без `calendar.canView`, а backend endpoints Google/Yandex calendar закрыты `RequireSectionPermission(Calendar)`.
- [~] Задачи: журнал задач, контроль, согласования, календарь задач, карточка задачи, старая и новая форма, комментарии, файлы, подзадачи; журнал задач уже скрывает создание, календарное создание, автосоздание контрольных задач, дублирование, удаление и массовое удаление по правам `tasks.canCreate/tasks.canDelete`, включая старую и новую карточку задачи; поле комментария в карточке задачи показывается только пользователям, которым разрешено комментировать эту задачу; отправка файлов задачи на Я.Диск показывается только при правах `tasks.canExport` и `yandexDisk.canCreate`.
- [x] Заметки: список досок, карточки заметок, совместный доступ, SignalR hub, inbox и уведомления проверяют `notes.canView/canCreate/canEdit/canDelete`; toast по заметке без доступа к разделу больше не предлагает открыть доску.
- [x] Отчеты: группы отчетов, финансовые сводки, фильтры, статусные отчеты по счетам/актам/договорам и переходы в задачи/дела показываются и загружаются только при правах на соответствующие разделы.
- [x] Калькулятор: вход в раздел и сохранение/экспорт, если есть. Расчет остается доступен по праву `calculator`, выбор клиентов/юрлиц/дел закрыт через `clients/legalEntities/cases`, сохранение графика в платежи требует `payments.canView` и `payments.canCreate`.
- [~] Контакты/клиенты: физлица, карточка клиента, связи с делами, счета/акты/платежи/договоры в карточке; общий раздел контактов уже фильтрует таблицу, сохраненные колонки, карточные счетчики и реквизиты связанных юрлиц/клиентов через права `cases/contracts/accounts/acts/payments/legalEntities/clients`; карточка юрлица, открытая из контактов или клиента, также получает права на связанные блоки.
- [~] Юрлица: список юрлиц закрывает связанные дела/договоры/счета/акты/платежи по правам разделов; карточка юрлица закрывает связанные дела/счета/акты/платежи, их загрузку, счетчики, блоки, кнопки создания и создание связанного счёта из платежа; отдельные договорные связи в карточке юрлица не найдены и остаются в общей проверке связанных переходов.
- [~] Дела: реестр и карточка дела уже проверяют финансы, владельцев, выбор владельца и связанных участников через права `payments/clients/legalEntities`; задачи внутри карточки дела закрыты через `tasks.canView/tasks.canCreate`; календарь оплат и документы остаются в общей проверке раздела.
- [~] Счета: доходные/расходные, карточка счета, связанные платежи, документы; журнал и форма счета не загружают закрытые справочники клиентов/юрлиц/договоров, не передают переходы в закрытые клиенты/договоры и не применяют сохраненные фильтры по закрытым разделам.
- [x] Акты: список, карточка, общая модалка и страница создания закрывают переходы и загрузку связанных счетов/клиентов через права `accounts/clients`; номер счета и имя контрагента могут отображаться как текст акта без открытия закрытого раздела.
- [~] Платежи: доходные/расходные, деньги/банк/касса/карты/e-money/итого, платежные статусы, авансы; таблица платежей уже не открывает клиентов/дела без прав `clients/cases`, карточка платежа не показывает выбор/создание связанного счёта без прав `accounts`, а денежный журнал не открывает связанные счета и быстрые переходы в счета/клиентов без прав `accounts/clients`.
- [~] Договоры: список, карточка, создание, связанные счета/акты/платежи; карточка закрывает связанные счета/акты/деньги и переходы в клиентов, список договоров не загружает справочник клиентов и не открывает клиента без права `clients`, а создание/редактирование договора не открывает выбор клиентов или юрлиц без прав `clients/legalEntities`.
- [x] Справочники: просмотр, создание, редактирование и удаление справочников подчинены правам `dictionaries.canView/canCreate/canEdit/canDelete`; прежняя жесткая привязка редактирования к admin снята.
- [x] Уведомления: личный inbox оставлен доступным авторизованному пользователю, админские настройки рассылок закрываются через `notifications.canView/canEdit`, а переходы из центра уведомлений и realtime-toast в задачи, дела, платежи, счета, акты и договоры передаются только при доступе к соответствующим разделам.
- [x] Роли: список ролей, копирование, изменение прав и удаление закрыты через `roles.canView/canCreate/canEdit/canDelete`; аудит готовности ролей и история роли дополнительно требуют `audit.canView`.
- [x] Пользователи: список пользователей и карточка пользователя оставлены строго admin-only; рабочие роли не получают доступ через меню, tab/deep-link и backend `/api/users`.
- [x] Контроль пользователей: активность пользователей оставлена строго admin-only; рабочие роли не получают доступ через меню, tab/deep-link и backend `/api/user-activity` admin endpoints.
- [x] Аудит: журнал объектов, история объектов в карточках, восстановление удаленных объектов, техобслуживание БД; встроенные кнопки истории объекта, прямые окна аудита и пункт sidebar скрываются без `audit.canView`, backend журнала аудита и восстановления удаленных объектов возвращает `403` без нужных прав, restricted settings regression подтверждает, что роль с одним `audit.canView` видит только обслуживание БД и не получает интеграции, уведомления, Я.Диск, S3 или версию обновлений, а вкладка удаленных объектов в обслуживании БД скрыта без права просмотра аудита.
- [x] Интеграции: DaData, календарные провайдеры, импорт, внешние настройки; пункт «Настройки» появляется при `integrations.canView`, а restricted-role regression подтверждает, что роль без `integrations` не видит ключи интеграций и не попадает туда через deep link.
- [x] Яндекс.Диск: раздел и вложенные настройки синхронизации закрыты отдельным `yandexDisk`; direct tab guard, backend controller tests и restricted settings regression подтверждают запрет без права просмотра.
- [x] S3: раздел и вложенные настройки закрыты отдельным `s3Storage`; direct tab guard, backend controller tests и restricted settings regression подтверждают запрет без права просмотра.
- [x] Профиль: личный профиль остается доступным самому пользователю; вкладка аудита профиля скрывается без `audit.canView`, вкладка подключения Google/Яндекс календарей скрывается без `calendar.canView`, а `GET/PUT /api/profile`, смена пароля, фото, внешние входы и баланс исполнителя работают только с текущим пользователем.

## План реализации

### 1. Инвентаризация и единая карта доступа

- [x] Сопоставить каждый `Tab` frontend с ключом права из `RolePermissionCatalog`.
- [x] Сопоставить каждый backend controller/action с ключом раздела и требуемым действием: view/create/edit/delete/export/analytics. Контроллеры просканированы рекурсивно; рабочие API закрыты секционными правами, `AuthController` и `ProfileController` зафиксированы как системное/личное исключение.
- [x] Найти все переходы не через боковое меню: ссылки из карточек, топбар, уведомления, breadcrumbs, правый клик, действия в таблицах, deep links. Переходы через `setActiveTab`, `getTabHref`, `onOpen*`, уведомления и прямой `ppTab` проверены; добавлена исчерпывающая frontend-регрессия, что безопасный шаблон юриста имеет явное решение доступа для каждой вкладки из `ALL_TABS`.
- [x] Зафиксировать исключения: личный профиль, личные уведомления, системные health/auth endpoints.

#### Как выполнять

1. Открыть `src/types/tabs.ts` и выписать все значения `Tab`.
2. Открыть `src/appRouting.ts` и `src/App.tsx`, сопоставить каждый `case`/route с ключом права.
3. Открыть `src/components/Navigation/Navigation.tsx` и проверить, что каждый пункт меню строится только при разрешенном `canView`.
4. Найти все `setActiveTab`, `getTabHref`, `open*Detail`, `onOpen*`, `onRoute*` и проверить, что переход невозможен без права.
5. На backend пройти все контроллеры в `backend/Controllers` и составить список endpoint'ов:
   - `GET/list/detail` -> `canView`;
   - `POST/create/import` -> `canCreate`;
   - `PUT/PATCH/status/link/upload` -> `canEdit`;
   - `DELETE/archive/restore` -> `canDelete` или отдельное правило;
   - `export/download/report` -> `canExport`;
   - аналитика календаря -> `canViewAnalytics`.
6. Все найденные несоответствия добавить в этот roadmap отдельными пунктами перед исправлением.

### 2. Закрыть frontend

- [x] Вынести единую `tab -> permission` карту и использовать ее в `App`, `Navigation`, route helpers и тестах.
- [~] Скрывать не только пункты меню, но и вложенные кнопки действий в карточках: список юрлиц фильтрует связанные дела/договоры/счета/акты/платежи по правам; карточка клиента скрывает быстрые финансовые кнопки без права просмотра раздела; карточка дела скрывает быстрые финансовые действия в боковой панели и заказ-наряде без права просмотра финансов; карточка платежа скрывает выбор/создание связанного счёта по правам `accounts`; реестр и карточка дела не открывают закрытые справочники клиентов/юрлиц через владельца и связанных участников; restricted settings regression подтверждает, что Я.Диск/S3/интеграции/обслуживание БД не раскрываются без отдельных прав; остальные вложенные действия еще требуют отдельной проверки.
- [x] Карточка клиента переводит вкладку «Дела», кнопку создания дела, редактирование/удаление дела, загрузку списка дел и финансовую сводку по делам на права `cases`; если роль видит клиента, но не видит дела, связанные дела не загружаются и не показываются.
- [x] Карточка договора скрывает вкладки «Счета», «Акты» и «Деньги», переходы в связанные документы и загрузку связанных списков, если у роли закрыты `accounts`, `acts` или `payments`.
- [x] Карточка договора проверяет связанных клиентов через `clients`: клиент остается текстом без права на клиентов и не открывает закрытый клиентский раздел.
- [x] Список договоров проверяет связанных клиентов через `clients`: клиент остается текстом без права на клиентов, фильтр по клиентам скрыт, справочник клиентов не загружается.
