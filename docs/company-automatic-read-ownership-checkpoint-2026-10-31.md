## Изменение

Два отказа воспроизведены до реализации: поздний GET счёта принимался после смены пользователя без render; уже загруженное дело оставалось видимо при изменении области доступа, пока новый запрос ещё не завершён.

Общие useClientCases/useInvoices/useActs/usePaymentsPaged получили необязательный DocumentReadOwner из существующего useDocumentDeliveryOwner. Владение снимается при смене сеанса/пользователя/контекста, в том числе при возврате прежнего значения. Автоматическое чтение, обычный и post-write refresh проверяют его перед запросом, после успеха/ошибки и перед завершением загрузки. Допуск отдельной операции сохраняется вторым обязательным условием. Устаревший callback не отменяет новый запрос. Уже отправленный GET может завершиться; его данные не принимаются.

Кэшированные строки, пагинация, итоги и ошибки отмечены контекстом чтения и маскируются уже во время render при его смене. Layout-effect сбрасывает прежние данные и отменяет запросы до отображения. Сброс относится только к владельцу, без превращения обычной смены страницы в новый сеанс: независимые summary не перечитываются при пагинации. Тот же владелец сохраняет прежнюю семантику refresh и ошибки. Вызовы без необязательного owner не меняют контракт и прежнюю стабильность refresh; они **не объявляются** автоматически защищёнными для всех остальных экранов.

В page/modal LegalEntityModal отдельный владелец для каждого раздела: компания/открытие/доступ к профилю/сеанс плюс видимость соответствующих дел, счетов, актов или платежей. Изменение доступа к счетам не перечитывает дела, акты и платежи. Изменение режима показа, readonly или версии реквизитов само по себе не создаёт лишнего GET связанных списков; фильтры и необходимые запросы остаются прежними. После logout новые связанные запросы не отправляются. Роль и политика доступа профиля по-прежнему передаются существующим deleteOwnerScope; серверные проверки не заменяются frontend-защитой.

Экономика дел принадлежит одновременно области дел и платежей. Её значения/ошибка помечены владельцем, старые суммы скрыты при изменении области, поздний ответ и finally не завершают новое ожидание. Во время обычного обновления того же владельца прежние суммы остаются до ответа. Количество case finance запросов не увеличивается из-за пустого списка дел; чтение запускается после получения актуальных ID. API не получил нового параметра/маршрута.

Владельцы сохранения дела/счёта/акта дополнительно учитывают область видимости своего раздела: смена all→own при сохранённом canCreate не разрешает старому результату наполнить новый кэш. Уже отправленные записи не отменяются и не повторяются. Права на сервере, суммы, даты, сортировка, фильтры и нормализация не переписаны. Проверен WithCaseIncludes: обычный V1 список не включает платежи по умолчанию; предположение о дополнительном GET дел при смене только платежной области не вводилось.

## Очередь

Продолжение самостоятельных денежных действий общей формы выполнено локально: [checkpoint и следующая очередь](payment-balance-ownership-checkpoint-2026-10-31.md). Их срок завершения не квалифицирован защитой пяти родительских callbacks. Также useClients/useLegalEntities и другие справочники не включены в четыре hooks этого этапа: их кеш/смена сеанса требуют отдельной сверки, без автоматического объявления всех чтений профиля завершёнными.

Далее CMP-04 и реальная приёмка CMP-06; Linux native CMP-01 подготовлен, не выполнен. Использовать последнюю сверку чатов, YouGile не менять без отдельной команды, архивные roadmaps не продолжать.
