## Риск и реализация

Старые ordinary/V1/V2 Create принимают Payment целиком. Помимо связанного графа у входа остаются сохранённый снимок/политика продавца, следы подписания/аннулирования, проверяющий аванса и CreatedAt/выходной аудит. Их нельзя принимать как подтверждённые сведения из запроса.

[x] Узкий этап реализован и адресно проверен. В общий путь после авторизации и проверки графа добавлена инициализация серверных полей. Разрешённые имена берутся из существующего логического PaymentCreateCommand без изменения его версии/формата/идентичности. Отдельно сохранены шесть прежних бизнес-полей API: IsNotForAccounting, ClientCaseReference, CounterpartyName, LegacyAccountNumber/Date и InvoiceDocumentTemplateKey. Остальные writable-поля получают значения новой серверной записи; будущий выходной атрибут не становится входом автоматически. Ссылка на модель сохраняется для совместимости текущих действий. Обычный/V1/V2 Create и строгий create-attempts не смешивают присланный аудит с реальными событиями.

Список свойств к инициализации вычисляется один раз; сохранение не добавляет SQL-запросов и не загружает связанные списки. Пустые коллекции получают собственные значения новой записи. Проверка вложенных объектов выполняется раньше, поэтому запрещённый граф не превращается незаметно в допустимую команду. Обновление существующей записи эту инициализацию не вызывает.

## Следующая очередь

Значения SystemNotes/RescheduleCount/начального решения по авансу остаются частью уже существующей логической команды; структурные маркеры и связанный порядок допуска требуют отдельной проверки, а не скрытого изменения правил этим этапом. Также остаются проверка выбора компании/подразделения старого Create и keyless Create после неизвестного commit. Для последнего ожидается ответ: обязательный ключ операции либо совместимость со старым режимом. Текущий интерфейс уже использует защищённый протокол создания; эта новая защита служебных полей сама по себе не обеспечивает идемпотентность старого POST.

Следующий независимый этап — сверка выбора собственной компании и подразделения в старом Create с существующей проверкой DocumentSellerService, без введения прав редактора профиля как нового правила финансового документа по догадке. Затем структурные заметки/начальное решение по авансу, callbacks и оставшаяся матрица CMP. Исторический долг требует прежнего решения; Linux native decoder и реальная приёмка изображений/документов остаются открытыми. Большие CMP-05/SEC-01/DOC-09 не закрываются этим этапом.

Только адресные проверки, один полный обязательный CI семи jobs перед выпуском. Успешные проверки без изменения влияющих входов не повторять; использовать последнюю сверку чатов, другой выпуск/push/merge/VPS/установщик и публикации чатов не затрагивать.

Продолжение: [выбор собственной компании и подразделения в старом Create](payment-create-seller-selection-checkpoint-2026-11-01.md). Предыдущие 74 сценария не объявляются проверкой этой новой границы выбора.
