# План внедрения аудита объектов

Дата старта: 8 апреля 2026

## Цель

Сделать так, чтобы по основным объектам системы было видно:
- кто создал запись и когда;
- кто изменил запись последним и когда;
- кто удалил запись и когда;
- какие действия происходили с объектом дальше.

Важно: для старых данных нельзя честно восстановить автора создания или удаления, если система раньше этого не сохраняла. Поэтому старые записи получают пустые audit-поля, а новая история начинает заполняться только с момента внедрения.

## Разделение понятий

### Паспорт объекта

Поля, которые хранятся рядом с объектом:
- `CreatedAt`
- `CreatedByUserId`
- `CreatedByUserName`
- `UpdatedAt`
- `UpdatedByUserId`
- `UpdatedByUserName`
- `IsDeleted`
- `DeletedAt`
- `DeletedByUserId`
- `DeletedByUserName`

Этот слой нужен для карточек объекта, таблиц и быстрых сводок.

### История объекта

Отдельная лента событий:
- объект создан;
- объект изменён;
- объект удалён;
- объект восстановлен;
- изменились ключевые поля.

Этот слой хранится отдельно в `ObjectAuditEvents` и нужен для подробной истории на карточке.

## Этап 1. Базовый audit-слой

Сделано:
- в `PaymentContext` добавлены shadow audit-поля для основных бизнес-сущностей;
- `CreatedBy` и `UpdatedBy` заполняются автоматически при `SaveChanges`;
- удаление ключевых бизнес-объектов переведено в мягкое удаление;
- мягко удалённые записи скрываются через глобальные query filters;
- для импорта старой SQLite-БД audit-модель можно отключать, чтобы старые файлы без новых колонок продолжали импортироваться.

Сущности первого этапа:
- `Client`
- `ClientCase`
- `Payment`
- `Invoice`
- `InvoiceLineItem`
- `Act`
- `Contract`
- `LegalEntity`
- `ExternalContact`
- `MoneyOperation`
- `AddressRecord`
- `ClientPassport`
- `PowerOfAttorney`

## Этап 2. Паспорт объекта в интерфейсе

Сделано:
- добавлен общий компонент `AuditInfoCard`;
- паспорт объекта выведен в карточки:
  - клиента;
  - счёта;
  - платежа;
  - акта;
  - договора;
  - юридического лица;
  - стороннего контакта.
- для дел клиента добавлена короткая audit-строка прямо в списке дел;
- для DTO добавлены безопасные audit-поля, чтобы frontend не зависел от EF shadow-свойств.

## Этап 3. История объекта

Сделано:
- добавлена таблица `ObjectAuditEvents`;
- события создания, изменения и удаления пишутся автоматически при `SaveChanges`;
- добавлен endpoint `GET /api/object-audit/{objectType}/{objectId}`;
- добавлен компонент `ObjectAuditHistoryCard`;
- история объекта выведена рядом с паспортом в карточках:
  - клиента;
  - счёта;
  - платежа;
  - акта;
  - договора;
  - юридического лица;
  - стороннего контакта.

Что именно сохраняется сейчас:
- тип объекта;
- ID объекта;
- действие (`Created`, `Updated`, `Deleted`);
- краткое описание;
- автор;
- время;
- JSON-метаданные со списком изменённых бизнес-полей для `Updated`.

## Этап 4. Восстановление и админские сценарии

Сделано:
- добавлен admin API для просмотра мягко удалённых объектов по типу;
- добавлен admin API для восстановления мягко удалённых объектов;
- восстановление теперь пишет отдельное audit-событие `Restored`, а не теряется в общем `Updated`;
- для счетов восстановление поднимает весь агрегат: сам платеж-счёт, связанные платежи рассрочки, сущность `Invoice` и позиции счёта.
- добавлен интерфейс просмотра и восстановления удалённых объектов в разделе обслуживания базы данных.
- добавлены явные права `audit` на просмотр удалённых объектов и восстановление.

Остаётся следующим шагом:
- решить, какие справочники тоже переводить на мягкое удаление.

## Этап 5. Читаемые diff-описания изменений

Сделано:
- для audit-раздела добавлены отдельные права вместо полного CRUD-профиля;
- лента истории теперь показывает не только тип события, но и читаемые названия изменённых полей;
- для `Updated`-событий выводится краткая сводка изменений и список полей прямо в карточке истории.
- новые `Updated`-события теперь сохраняют не только список полей, но и значения `было -> стало` для ключевых бизнес-полей;
- карточка истории умеет безопасно читать и старый формат метаданных, и новый расширенный diff-формат.

## Риски и правила

- Не угадывать старых авторов действий.
- Не переводить на мягкое удаление сразу все таблицы без разбора.
- Не использовать `UserActivityLogs` как единственный источник истории объекта: этот журнал может очищаться по сроку хранения.
- Миграции должны быть только добавляющими: nullable-поля, индексы, фильтры и отдельная таблица истории без переписывания старых строк.

## Текущее состояние реализации

- Базовый audit-слой добавлен в `PaymentContext`.
- Для импорта старой SQLite-БД audit-модель отключается отдельно.
- Мягкое удаление включено для основных бизнес-объектов.
- Паспорт объекта выведен в ключевые карточки.
- Лента истории объекта уже сохраняется и читается через отдельный API.
- Старые записи без автора показываются безопасно, без попытки “придумать” историю задним числом.

2. Решить, какие дополнительные служебные разделы тоже подключать к audit-истории по бизнес-логике.
