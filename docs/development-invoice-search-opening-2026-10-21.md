## Установленные причины

В восстановленной домашней БД выполнены только запросы в транзакции `READ ONLY`: 1396 сущностей счёта, 1385 активных; 355 групп совпадающих номеров. Совпадение номера само по себе не доказывает дубль: есть разные годы и разные контрагенты. Активных сущностей без активных связанных записей не найдено. Не выполнялись удаления, слияния, перенумерация или исправление связей.

В пяти агрегатах выбор ID реестром не совпадает с ID, принимаемым карточкой. В трёх из них контрагент и направление согласованы: реестр выбирает более крупную/активную запись, а карточка принимает первоначальный ID. Это воспроизведено четырьмя синтетическими тестами — без поиска, по номеру, по клиенту и по описанию другой исторической строки.

В интерфейсе раскрытие операций было привязано к отображаемому номеру. Поэтому две самостоятельные строки с одинаковым номером раскрывались одновременно. Два теста воспроизвели дефект для обеих ссылок.

По умолчанию реестр ограничен периодом «С начала года». Поиск не отменяет этот фильтр, но раньше его стандартное значение отсутствовало в списке применённых фильтров. Это объясняет один из способов получить неполную выдачу за несколько лет, но не доказывает, какой именно фильтр был включён у автора исходной жалобы: его точное состояние не сохранено.

## Исправления

Общее правило выбора ID карточки вынесено из существующего запроса счетов без изменения порядка и условий. Реестр получает подходящие ID одним дополнительным запросом только для текущей страницы — до 100 сущностей, с проверкой видимости. При поиске по другой строке того же счёта ссылка остаётся прежней. Замена ID разрешена только при совпадении клиента, юридического лица и направления с отображаемым агрегатом. Финансовый расчёт и выбор строк для раскрытия сохраняют прежнюю основную запись; расчётные суммы и сохранённые оплаты не переписываются. Новых маршрутов и полей публичного API нет.

Раскрытие использует уникальный ключ строки вместо номера. Переход в карточку продолжает использовать числовой ID, без поиска первого совпадения номера.

При непустом поиске показан действующий период. Команда «Искать за всё время» явно снимает только даты, сохраняя строку поиска и остальные фильтры. Открытый диапазон запоминается только существующей настройкой периода реестра; общие правила периодов других разделов не менялись. Сам ввод поиска не снимает фильтры и не расширяет права.

Подготовлены отдельные неактивные записи «Что нового» **1.14.105–1.14.107**.

## Неоднозначные исторические связи — остаток и условие выпуска

Обнаружены три старые сущности, каждая из которых связана с документными строками разных клиентов и направлений. Четвёртая группа уточнена отдельным аудитом: это один клиент, расходный возврат и отменённая строка возврата, а не разные владельцы. Для двух из трёх документных сущностей расходится и ID карточки. Автоматическая подстановка карточки другого контрагента не выполняется. Эти записи не считаются исправленными текущим пакетом; остаточный Not Found и неполная выдача для них возможны.

**Подробный аудит выполнен:** [связи, права и безопасный план](payplanner-invoice-shared-links-repair-plan-2026-10-21.md). Коллизии трёх пар присутствуют уже в снимках апрельского импорта. На синтетическом наборе подтверждена выдача чужих строк/HTML через общее наследование прав и финансовое смешение; группа возврата даёт расхождение статуса и остатка. Реальные права проверены readonly для девяти активных пользователей домашней копии. Успешное выполнение диагностического стенда не означает успешной проверки безопасности. Данные и приложение в этом аудите не менялись; дальнейший приоритет — защита доступа/импорта перед адресной правкой связей.

Нужна отдельная сверка первичных документов администратором: какие строки относятся к одному счёту, каковы правильные контрагент, направление и компания, должны ли сущности быть разными. Приватный реестр с точными ID сохранён вне Git. Риск SEC-01: наследование видимости и объединение финансов по такой общей старой связи требуют отдельной проверки до выпуска исправления этих записей; стандартный тест разных самостоятельных счетов этого не доказывает. Не выдавать чтение чужой карточки за исправление поиска. Не запускать существующие массовые миграции/cleanup для исправления этих связей без конкретного согласованного плана и резервной копии.
