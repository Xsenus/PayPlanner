Подготовлено 24 октября 2026 года **только в отдельном worktree bank-import-context**. Первая адресная проверка форматирования остановилась до сборок; её результат сохранён. Разрешённое исправление пробелов трёх файлов завершилось native0, смысл прежнего кода и 72 исходных случаев сохранён. После выявления риска даты восстановления выплаты добавлены защита и ещё 10 случаев: теперь подготовлено 82 проверки (69 SQLite и 13 PostgreSQL). API собран с полными анализаторами, native0; после добавления единственного отсутствующего using сборка Tests также завершилась native0. Успешная сборка API переиспользована по неизменным исходникам и артефактам, повторно не запускалась. Application tests, discovery и проверки БД этого пакета ещё не запускались. Main и выполняющийся полный прогон срочного кандидата не менялись. Весь DOC-11/TSK-10 не закрыт; общий прогресс 9/167 (5,4%) не изменён.

Основание — [план задач TSK-10](payplanner-task-workflow-roadmap-2026-10-14.md), [финансовый план DOC-11](payplanner-financial-documents-roadmap-2026-10-14.md) и согласованные оба режима завершённости. Прямое требование пользователя: **«Задачи с выставленным счётом или оплатой сохраню без изменений»**. Оно важнее прежнего документационного предположения о возможности менять класс при сохранении выплаты.

## Подготовленная область

- Существующий [POST tasks/bulk](../backend/Controllers/TasksController.cs) получает отдельную ветку смены `billable|internal`, без вызовов N индивидуальных сохранений. Остальные массовые действия сохраняют прежний маршрут.
- По умолчанию меняются выбранные незавершённые задачи. Явный `includeCompleted=true` включает `done`. Каталог допустимых статусов берётся из существующего AllowedStatuses; `cancelled` и неизвестные состояния исключены.
- Набор запроса фиксирован: 1–500 положительных элементов **до** удаления дубликатов, без усечения. Проверяется точное соответствие ключей ожидаемых версий distinct ID, включая явный `null` старого UpdatedAt. Поля иных массовых действий не смешиваются с учётом.
- Права/видимость и полное право изменения каждой строки перепроверяются после блокировки. PostgreSQL удерживает задачи по возрастанию ID, SQLite получает write lock по существующему образцу массового удаления. Право завершить задачу не даёт права менять её учёт. Новых требований доступа к делу поверх существующей видимости задачи не добавлено.
- Для платной задачи набором проверяются существующий контрагент, ровно один ClientId/LegalEntityId и соответствующее ему существующее дело, с действующими фильтрами soft delete. Клиент/дело не исправляются и не очищаются.
- Ответ построчный: changed/no-op/skipped/conflict, честные суммы по исходам, свежие сохранённые версии. Потерянный ответ разрешает повтор уже достигнутого класса без дополнительной истории, только после всех финансовых/правовых защит.
- Сохраняются только класс, новая дата действительного решения и стандартная история с прежними классом/датой. После единого SaveChanges даты перечитываются одним запросом до commit: аудит заменяет UpdatedAt, PostgreSQL хранит микросекунды. Один realtime вызывается после commit. Ошибка публикации не объявляется откатом уже сохранённых данных.
- Известная ошибка конкуренции откатывает весь пакет и возвращает HTTP409, без ложного частичного успеха. Неожиданная ошибка БД передаётся действующему обработчику HTTP500.

## Финансовые защиты до изменения и до no-op

| Факт | Поведение первого этапа |
| --- | --- |
| Любой raw BillingInvoiceId, включая скрытый/черновой/отменённый документ | Полностью пропустить, `invoiced` |
| Существующий платёж исполнителю с PaidAmount>0, IsPaid, Completed, PaidDate или LastPaymentDate | Полностью пропустить, `paid`: класс/DecisionAt/UpdatedAt/история задачи не меняются |
| Любой другой существующий ContractorPaymentId или платёж с системным маркером задачи | Полностью пропустить, `contractorPaymentProtected`; неоплаченные созданные выплаты вне первого subset, их политика не выбрана |
| Завершённая задача с включённой выплатой по результату, даже без созданной выплаты | Полностью пропустить до no-op, `contractorPaymentProtected`, независимо от текущего признака внешнего исполнителя, суммы и задержки: прежний UpdatedAt участвует в расчёте даты позднего восстановления выплаты |
| Raw BillingContractId или непустой BillingModeSnapshot, включая Fixed/Actual/неизвестный snapshot | Полностью пропустить, `contractual`; договорное расширение требует прежнего отдельного решения |
| Настройки будущей выплаты без созданного платежа у незавершённой задачи либо завершённой с точной датой | Допустимая область; настройки/суммы/сроки/режим сохраняются, генератор выплат не вызывается |

Выплаты читаются одной streaming-проекцией Payments с ранним фильтром raw ID/системного маркера. Нет cross join 500 задач со всеми платежами или 500 отдельных запросов. В памяти остаются только наборы выбранных ID и защищённых строк. Читается полный ASCII-десятичный ID после **каждого** маркера: задача 1 не совпадает с 11, повреждённый marker не снимает защиту raw FK. Legacy marker не индексирован, поэтому один проход по таким кандидатам остаётся затратой первого этапа; миграций/индексов не добавлено. Существующий индивидуальный resolver с широким Contains не переписан этим пакетом.

## Контракт для общего окна журнала и задач дела

Request: `{ ids, billingClassification, includeCompleted, expectedUpdatedAtById }`. Ключи версий — строковые ID JSON, значение — исходная UTC-строка API или явный null. Преобразование через JavaScript Date не нужно.

HTTP200: `{ requested, updated, unchanged, skipped, conflicted, items: [{ id, outcome, reason, updatedAt }] }`, где outcome — `updated|unchanged|skipped|conflict`. Причины: `notAvailable`, `forbidden`, `invoiced`, `paid`, `contractorPaymentProtected`, `contractual`, `unsupportedStatus`, `cancelled`, `completedExcluded`, `unknownClassification`, `clientCaseRequired`, `versionConflict`. Недоступный/отсутствующий ID имеет нейтральный `notAvailable`, без номера документа/суммы/времени. HTTP409 означает откат общей попытки; это не ответ с частичным успехом.

Общий frontend должен зафиксировать ID/версии при открытии, показать оба режима и частичный итог, сохранить неуспешную область, перед повтором конфликта перечитать только оставшиеся ID и получить новое явное подтверждение. Backend-проверка двух значений общей настройки карточки не подменяет реальную проверку обеих форм. UI/обе формы/глобальный переключатель пока остаются приёмочными prerequisites отдельного пакета.

## Черновик «Что нового»

**Новая возможность.** В журнале задач и задачах дела можно сразу выбрать несколько задач и изменить их тип учёта на платный или неоплачиваемый. По умолчанию обрабатываются незавершённые задачи; завершённые можно включить отдельно. Задачи со счётом, созданной выплатой исполнителю или договорным учётом сохраняются без изменений. Завершённые задачи с выплатой по результату также пропускаются, чтобы сохранить дату будущего восстановления выплаты. После операции показываются изменённые и пропущенные строки.
