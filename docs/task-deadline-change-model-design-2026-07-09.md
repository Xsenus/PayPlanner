# Модель запроса переноса срока задачи

Дата проектирования: 9 июля 2026.
Связанный roadmap: `task-deadline-change-approval-roadmap-2026-07-09.md`.

## Выбранный подход

Запрос переноса срока нужно хранить отдельной сущностью, а не только системным комментарием. Комментарий остается частью истории задачи, но не является источником статуса процесса.

Новая сущность: `TaskJournalDeadlineChangeRequest`.

Причины выбора отдельной сущности:

- нужен активный статус запроса: ожидает решения, согласован, отклонен, отменен или замещен новым запросом;
- раздел "Согласования" должен быстро находить активные запросы без парсинга JSON комментариев;
- постановщик должен видеть список ожидающих действий;
- нужно надежно запретить несколько активных запросов по одной задаче;
- решение должно хранить кто, когда и с каким комментарием его принял;
- в будущем проще добавить forced modal, счетчики, фильтры и отчеты.

## Поля сущности

- `Id` - идентификатор запроса.
- `TaskJournalItemId` - задача, по которой запрошен перенос.
- `RequestedByUserId` - исполнитель, который запросил перенос.
- `RequestedByName` - имя исполнителя на момент запроса.
- `ReviewerUserId` - постановщик задачи или ответственный за решение.
- `ReviewerName` - имя постановщика на момент запроса.
- `CurrentDueAt` - срок задачи на момент запроса.
- `RequestedDueAt` - срок, предложенный исполнителем.
- `Reason` - обязательная причина запроса.
- `Status` - `pending`, `approved`, `rejected`, `cancelled`, `superseded`.
- `DecisionDueAt` - фактический новый срок, если постановщик согласовал другую дату или подтвердил предложенную.
- `DecisionComment` - комментарий постановщика при согласовании или отказе.
- `DecidedByUserId` - кто обработал запрос.
- `DecidedByName` - имя обработавшего.
- `DecidedAt` - дата и время обработки.
- `CreatedAt` - дата создания запроса.
- `UpdatedAt` - дата последнего изменения.
- `CreatedCommentId` - системная запись истории о создании запроса.
- `DecisionCommentId` - системная запись истории о решении.

## Статусы

- `pending` - запрос ожидает решения постановщика.
- `approved` - запрос согласован, срок задачи изменен.
- `rejected` - запрос отклонен, срок задачи не изменен.
- `cancelled` - запрос отменен инициатором или администратором до решения.
- `superseded` - запрос закрыт новым активным запросом по той же задаче.

На первом этапе достаточно реализовать `pending`, `approved` и `rejected`. `cancelled` и `superseded` оставляются в модели, чтобы не менять схему при расширении.

## Правила создания

- Запрос может создать только исполнитель задачи, если он не является постановщиком и если включена настройка `allowExecutorDeadlineChangeRequests`.
- Причина обязательна, пустой текст отклоняется.
- `RequestedDueAt` должен быть валидной датой.
- Если по задаче уже есть `pending` запрос, backend должен отклонить новый запрос понятным сообщением.
- При создании сохраняется `CurrentDueAt`, чтобы постановщик видел, от какого срока просили перенос.

## Правила согласования

- Согласовать может постановщик задачи, администратор или пользователь с правом редактирования задач, если бизнес-правила проекта разрешают ему менять срок.
- При согласовании постановщик выбирает новую дату и время. По умолчанию UI предлагает `RequestedDueAt`.
- Backend меняет `TaskJournalItem.DueAt`, закрывает запрос статусом `approved`, записывает историю и уведомляет исполнителя.
- Если срок задачи уже изменился с момента запроса, постановщик все равно видит `CurrentDueAt` и текущий срок, а backend применяет выбранный `DecisionDueAt`.

## Правила отказа

- Отказать может тот же круг пользователей, что и согласовать.
- При отказе срок задачи не меняется.
- Комментарий отказа должен быть обязательным или как минимум требоваться в UI; для backend лучше сделать обязательным, чтобы исполнитель понимал причину.
- Backend закрывает запрос статусом `rejected`, записывает историю и уведомляет исполнителя.

## API первого этапа

- `POST /api/tasks/{id}/deadline-change-requests` - создать запрос.
- `GET /api/tasks/deadline-change-requests?status=pending` - получить запросы для раздела "Согласования" и forced modal.
- `GET /api/tasks/{id}/deadline-change-requests` - получить запросы конкретной задачи для карточки и истории.
- `PATCH /api/tasks/deadline-change-requests/{requestId}/approve` - согласовать и применить новый срок.
- `PATCH /api/tasks/deadline-change-requests/{requestId}/reject` - отказать с комментарием.

## История и уведомления

- Создание запроса пишет системный комментарий: кто запросил, старый срок, желаемый срок, причина.
- Согласование пишет системный комментарий: кто согласовал, какой срок установлен, комментарий.
- Отказ пишет системный комментарий: кто отказал, причина отказа.
- Постановщик получает уведомление типа "запрос переноса срока".
- Исполнитель получает уведомление о согласовании или отказе.
- Наблюдатели могут получать обычную запись истории/центра уведомлений, но не должны становиться ответственными за решение.

## UI первого этапа

- В карточке задачи исполнитель видит кнопку/блок запроса переноса с обязательной причиной.
- В карточке задачи постановщик видит активный запрос и действия согласовать/отказать.
- В разделе "Согласования" появляется фильтр или отдельная группа "Перенос срока".
- Forced modal берет данные из `pending` запросов, где текущий пользователь является постановщиком или ответственным за решение.

## Проверки модели

- Миграции SQLite и PostgreSQL создают таблицу и индексы.
- По одной задаче не может быть больше одного активного `pending` запроса.
- API не принимает пустую причину.
- API не меняет срок при создании запроса.
- Согласование меняет срок и закрывает запрос.
- Отказ не меняет срок и закрывает запрос.
