# Финансовая граница фоновой сверки счетов — 31 октября 2026

Локальная реализация от `342d135c`, продолжение [восстановления уведомлений](payment-overdue-delivery-checkpoint-2026-10-31.md). Доверенный писатель CMP-05 / SEC-01 / DOC-09 — InvoicePaymentStateReconciliationService — переведён на общую финансовую границу. Пакеты остаются открытыми.

Сохранить существующий расчёт действующей рассрочки, но выполнять выбранный агрегат в короткой транзакции с теми же блокировками платежей и проверкой кредитного минимума. Историю компенсаций и неоднозначные связи не исправлять автоматически. Источники поступлений, суммы документов, задачи и связи не переписывать. Обход должен быть конечным, память — ограниченной выбранным графом; слишком большой граф не усекать. Один конфликт/небезопасный граф не должен мешать следующим независимым счетам.

Дополнительный найденный риск: старый расчёт выбирает обычные связанные платежи без фильтра направления, а общий guard неоднозначных связей сравнивает направление только у основных записей счетов. В фоновой сверке историческая группа со смешанными направлениями также должна оставаться без изменений до отдельной проверки; автоматически исправлять её привязки или алгоритм остальных писателей не следует.

## Подтверждённые дефекты и исправление

Исходный `baseline-v1.trx`: **6 failed из 6** за 6 секунд. Фоновая сверка уменьшала PaidAmount ниже существующего зачёта, меняла активный агрегат с прежней компенсацией и группу с противоречащим владельцем. IOException после SQL оставлял уже сохранённое изменение вне общего отката. Номера/исторические связи не исправлялись и в новом коде не объединяются.

RunOnceAsync теперь защищён SemaphoreSlim для одного экземпляра. В начале фиксируются конечные верхние границы InvoiceId и ID самостоятельных счетов; страницы содержат только ключи, максимум настроенного BatchSize. Каждый выбранный агрегат загружается и сохраняется в собственном коротком BalanceApplicationLease.BeginSystemAsync: SQLite использует прежнюю немедленную транзакцию, PostgreSQL — SERIALIZABLE и NOWAIT с ограниченным ожиданием. Все ID графа выбираются по порядку, блокируются и повторно сравниваются. Большой граф свыше 5000 строк не усекается и не загружается целиком, а оставляется без изменений. Следующий независимый счёт продолжает обрабатываться.

Повторно используются HasAmbiguousInvoiceLinksAsync, CancellationProtectedPayments и PaymentCreditInvariantScope. Исторические противоречия владельца/продавца, смешанное направление, отмена/компенсация исключают автоматическое изменение. Существующая математика InvoicePaymentStateService не менялась: действующая рассрочка по-прежнему обновляет сохранённый итог, даты и статус основной записи. Источники поступлений и денежные операции не переписываются. После сохранения проверяется кредитный минимум каждого платежа и общий минимум основной записи вместе со взносами; при нарушении транзакция откатывает изменение и аудит целиком. Допустимое повышение/снижение вычисленного итога сохраняется, если известные зачёты покрыты.

Один занятый/отклонённый граф пропускается без повторов в том же обходе; для него остаётся следующая плановая сверка. Ошибка SQL и отмена не объявляются успехом. Неизвестный результат commit не исправляется слепым повтором: следующий запуск читает сохранённое состояние, и уже применённый идемпотентный пересчёт не создаёт новую запись аудита. Новые счётчики Skipped/Conflicted/Oversized добавлены только во внутренний результат сервиса; HTTP/Frontend-контракт не менялся. Причины суммируются одним предупреждением за обход, без отдельного сообщения на каждый спорный счёт.
