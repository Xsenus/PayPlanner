[Замер 11 октября](backend-build-speed-2026-10-11.md): обычная правка API 3:49 → 0:29, tests-only около 58 секунд на другой машине. Старый комментарий про 1,8 млн строк устарел.
- MoneyOperations уже использует process-static SQLite template; ManagedGeneratedCaseDocument имеет class fixtures; ManagedCaseDocumentWire получил template 21 октября. Предлагать им тот же перенос как ещё не сделанный неверно.
- Timing-aware sharding уже внедрён. Расчёт −14,13% относится к максимальной параллельной части, а не сумме четырёх последовательных частей. [Протокол](development-test-acceleration-2026-10-21.md) честно показывает, что короткая выборка runtime не подтвердила ускорение всей системы.
- В CI уже есть npm/NuGet cache, сборка runtime один раз, передача artifact, publish `--no-build --no-restore`. Однако списки Windows timing/NuGet caches в GitHub на момент аудита пусты: успешный новый Windows pipeline ещё их не сформировал; это не доказательство отсутствия локальных packages на runner.
- Frontend уже использует 3 workers для unit, 2 для watch, Node-окружение части pure-тестов, lazy routes, prebundle lucide-react и отключённые legacy chunks. Не нужно снова объяснять проблему отсутствием этих механизмов.

## Почему повторные проверки растягивают работу ещё сильнее

22 октября пять устаревших номеров строк Markdown обнаружились только после 2395 успешных тестов. Неуспешная четвёртая часть заняла примерно 91 минуту и потребовала повторения целой части. Сам документный guard занимает долю секунды. Его ранний запуск теперь описан в протоколе, но автоматический preflight перед большим набором следует закрепить в runner/CI.

Другой запуск потерял 1945 уже выполненных случаев из-за разрыва подключения инструмента без окончательного TRX. Процесс потом отвязали от подключения. Долгий gate должен исполняться устойчивым процессом с журналом состояния, PID, входными хешами и итоговым native exit; закрытие чата не должно его прерывать. Частичный результат при этом остаётся частичным.

Ещё один источник повторов — неполная привязка результатов к входам. `tools/PayPlanner.TestShards/Program.cs:55–57` закрепляет тестовую DLL, deps/runtimeconfig, API DLL и xunit config. Для общего повторного использования нужны также migrations DLL, helper, fixtures, browser scripts/FE inputs и документы, реально читаемые тестами. Во внешнем локальном gate это уже компенсировано расширенным snapshot. Следует перенести проверяемый механизм в штатный runner, сохранив строгий exact-union каталога, native exit и assertions.

Нельзя просто объединять TRX разных тестовых DLL или исключать все Markdown: `docs/batch-operations-audit-coverage-2026-06-10.md` является тестовым входом. Шардер также запрещает xUnit collections; внедрение коллекций ради параллельности требует изменения каталога/атомарных групп и соответствующих проверок. Распределение методов одного класса между shards может повторять class-fixture setup; affinity надо сравнить с балансом, а не закреплять целый огромный класс вслепую.

## Практический порядок ускорения

1. **Быстрый цикл сразу:** один небольшой результат за этап, адресный тест или watch в процессе разработки, один полный применимый gate окончательного кандидата. Уже успешные неизменённые этапы не повторять для документации, передачи или установки. Это уже правило AGENTS; требуется удобная штатная команда, чтобы не собирать процедуру заново в каждом чате.
2. **Ранняя диагностика:** SDK/Node/права/роль БД/почтовая изоляция, документные guards, каталог и fixture smoke до тяжёлого запуска. Исправить текущие CI setup/Billing/audit blockers. Готовность — свежий реальный CI, а не только локальное зелёное состояние.
3. **Кэши и ресурсы:** сохранить bin/obj/.vite и проверяемые build artifacts; добавить локальный ESLint/TS cache. Разобрать сотни фоновых MCP-процессов по владельцу/жизненному циклу, не завершать все Node командой kill. Не запускать одновременно несколько полных тяжёлых проверок разных проектов при 3–4 ГБ доступной RAM.
4. **Повторная подготовка:** один production frontend artifact для backend browser-сценариев, шаблоны оставшихся дорогих fixtures. Готовность — те же случаи и assertions, сравнение до/после на одинаковых входах, отдельная проверка clean migrations и изоляции.
5. **Автоматический выбор области CI и доказательств:** frontend/backend/shared, строгий fallback и полный fingerprint. Чисто визуальная правка не должна ждать шесть часов backend, но пока planner не реализован и не проверен, обязательный текущий workflow нельзя объявлять пройденным или обходить.
6. **Параллельность после измерений:** пилот двух workers, затем решение о четырёх на подходящих ресурсах. При неизменных временах идеальная нижняя оценка ≈3 часа для двух и ≈1,5 часа для четырёх; это арифметика без накладных расходов и конкуренции, не обещание результата. Одновременно сокращать дорогую подготовку, а не просто увеличивать процессы.
7. **Декомпозиция по фактическому профилю:** разделить наиболее дорогие файлы тестов и большие компоненты, разгрузить общий setup. Для каждого этапа сохранить полный каталог/исходы и измерить p50/p95 короткого цикла, wall time, peak memory и хвост самого долгого файла.

Приоритет — сделать обычную правку проверяемой за секунды/несколько минут и реже платить за полный многочасовой прогон. Обещать полный backend за пять минут при нынешнем каталоге и одном worker оснований нет. Покупка ресурсов без устранения повторной работы также не решает причины.

## Команды для ежедневного цикла

Запускать из корня проекта; точные файлы/классы выбирать по изменению, не выдавать выбранный набор за полный release gate.

```powershell
# Интерфейс и повторные адресные проверки
npm run dev
npm run test:watch -- src/components/Tasks/TaskJournal.automation.test.tsx
npm run test:integration -- src/components/Accounts/InvoiceModal.integration.test.tsx

# Настоящая проверка типов приложения; root tsc без -p её не заменяет
npx tsc -p tsconfig.app.json --noEmit

# Backend: явная локальная изоляция, существующая подходящая тестовая БД/роль
$env:BackgroundServices__Enabled = 'false'
$env:Email__Enabled = 'false'
dotnet build backend/PayPlanner.Api.Tests/PayPlanner.Api.Tests.csproj
dotnet test backend/PayPlanner.Api.Tests/PayPlanner.Api.Tests.csproj --no-build --no-restore --filter FullyQualifiedName~BatchOperationAuditCoverageTests
```

Последняя команда — дешёвый конкретный preflight, не проверка бизнес-изменения. `--no-build` использовать только после успешной актуальной сборки той же конфигурации. Общий backend test без фильтра в ежедневной петле не нужен; полный применимый набор остаётся барьером выпуска. В production-копии `payplanner` разрушительные тесты не запускаются; новые серверы/кластеры/контейнеры для ускорения не предлагаются.

Механизмы кэша опираются на [MSBuild incremental builds](https://learn.microsoft.com/en-us/visualstudio/msbuild/incremental-builds?view=vs-2022), [TypeScript incremental](https://www.typescriptlang.org/tsconfig/incremental.html) и [ESLint cache](https://eslint.org/docs/latest/use/command-line-interface#--cache). Ввод параллельности должен учитывать используемый xUnit v2 и его коллекции согласно [официальной документации](https://xunit.net/docs/running-tests-in-parallel); настройки новых версий xUnit не следует автоматически переносить в текущую 2.9.2.

## Границы результата

В рамках исходного аудита проведены Git-синхронизация, статический аудит backend/frontend/CI, чтение реальных Actions и локальные измерения frontend, включая контрольное использование кэша. Build, обе правильные проверки типов, ESLint и 2839 unit-тестов прошли. `npm audit` тогда остался неуспешным по указанным advisories. На том этапе кодировка проверена для 3327 текстовых файлов; исходный документ дополнительно проверен на UTF-8, существование локальных ссылок и отсутствие незаполненных результатов. Холодная полная C# сборка, новый многочасовой backend gate, browser integration и p95 HMR в исходный замер не входили. Последующие Release-сборки, полный frontend 05, адресные проверки и успешный полный backend 08b **9464/9464 + 5/5** зафиксированы в отчёте о внедрении. После отказа FE06 исправлены две dev-зависимости; **полный FE07 и отдельный exact4 proof прошли**. Технический пакет завершён **8/8 (100%) локально**, CI/deploy не подтверждены. p95 HMR остаётся неизмеренным. Производительность рабочих SQL-запросов приложения и пользовательских операций — другая область, не исследованная этим аудитом скорости разработки.

Продуктовые roadmap-пакеты этим анализом не закрываются. Коммит, push и deployment в этом проходе не выполнялись.
