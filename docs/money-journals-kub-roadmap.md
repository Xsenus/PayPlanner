# Деньги, банк, касса и кассовые документы: roadmap реализации

## Назначение документа

Этот документ фиксирует целевую модель раздела `Деньги` в PayPlanner на основе:

- текущей реализации PayPlanner;
- сценариев заказчика по кассе, банку и оплатам;
- публичной документации KUB-24;
- визуальной структуры KUB-24, которую мы сверяли по скриншоту.

Документ нужен как рабочая карта реализации. После каждого этапа можно отмечать чекбоксы и не держать всё в голове.

## Целевая структура раздела Деньги

В PayPlanner раздел `Деньги` должен быть не одним общим списком, а набором рабочих журналов:

- `Банк`
- `Касса`
- `Карты`
- `E-money`
- `Итого`

Каждый журнал должен иметь:

- карточки итогов за период;
- фильтр периода;
- таблицу движений;
- поиск;
- действия над операциями;
- связь с оплатами, счетами, клиентами и делами;
- серверную пагинацию;
- понятные статусы обработки.

## Целевая доменная модель

### MoneyOperation

`MoneyOperation` должен описывать движение денег, которое не обязательно является пользовательским платёжным документом.

Ключевые поля:

- `Id`
- `Source`: `Bank`, `Cash`, `Card`, `EMoney`
- `Direction`: `Income`, `Expense`
- `AccountingType`: `Fact`, `Plan`
- `Date`: дата движения
- `RecognitionDate`: дата признания дохода/расхода
- `Amount`
- `Currency`
- `CounterpartyName`
- `ClientId`
- `LegalEntityId`
- `InvoiceId`
- `PaymentId`
- `ClientCaseId`
- `AccountName`
- `PaymentOrderNumber`
- `Purpose`
- `ImportBatchId`
- `ImportFingerprint`
- `Status`: `Recognized`, `NeedsClarification`, `Linked`, `Ignored`

Сейчас часть этих полей уже есть, часть нужно добавлять постепенно.

### CashOrder

`CashOrder` должен описывать кассовый документ, а не просто строку движения.

Ключевые поля:

- `Id`
- `Number`
- `Type`: `Incoming`, `Outgoing`
- `Status`: `Draft`, `Posted`, `Cancelled`
- `Date`
- `Amount`
- `Currency`
- `ClientId`
- `PaymentId`
- `MoneyOperationId`
- `InvoiceId`
- `Account`
- `PayerName`
- `ReceiverName`
- `Basis`
- `Appendix`
- `Comment`
- `CreatedAt`
- `UpdatedAt`
- `CancelledAt`
- `CancelledReason`

Сейчас базовая модель есть. Нужно расширить её под полноценную карточку и печатные формы.

### BankStatementImport

Для нормальной работы банка нужен отдельный журнал импортов.

Предлагаемые сущности:

- `BankStatementImportBatch`
  - `Id`
  - `FileName`
  - `SourceFormat`: `Csv`, `Tsv`, `ClientBankExchange`
  - `BankAccount`
  - `RowsRead`
  - `RowsCreated`
  - `RowsSkipped`
  - `CreatedAt`
  - `CreatedById`
- `BankStatementImportRow`
  - `Id`
  - `BatchId`
  - `RawDate`
  - `RawAmount`
  - `RawCounterparty`
  - `RawPurpose`
  - `RawDocumentNumber`
  - `ParsedOperationId`
  - `Status`
  - `Error`

Сейчас импорт сразу создаёт `MoneyOperation`. Это удобно для первого этапа, но для качественного разбора выписки лучше хранить batch и строки импорта.

### Статусы банковской операции

- `Recognized`: операция понятна и уже связана.
- `NeedsClarification`: операция импортирована, но не удалось понять, к какому счёту её привязать.
- `Linked`: операция вручную или автоматически привязана к счёту/платежу.
- `Ignored`: операция сознательно исключена из обработки.

### Импорт банковской выписки

Уже есть:

- [x] CSV/TSV/TXT;
- [x] 1CClientBankExchange;
- [x] защита от дублей;
- [x] отображение результата импорта.

Нужно добавить:

- [x] хранение batch импорта;
- [x] хранение строк импорта;
- [x] отчёт по ошибочным строкам;
- [x] возможность открыть batch импорта;
- [x] повторную обработку batch;
- [x] откат batch, если операции импортированы ошибочно.

### Авто-сопоставление выписки со счетами

Правила сопоставления:

1. По номеру счёта в назначении платежа.
2. По номеру счёта в отдельном поле выписки, если банк его передал.
3. По сумме, клиенту и дате.
4. По ИНН/контрагенту, если данные есть.
5. По частичной оплате, если сумма меньше остатка по счёту.
6. По переплате, если сумма больше остатка по счёту.

Результаты:

- [x] если найден один очевидный счёт, привязываем автоматически;
- [x] если найдено несколько вариантов, ставим `Уточнить`;
- [x] если счёт не найден, ставим `Уточнить`;
- [x] если операция уже была импортирована ранее, пропускаем как дубль.

## Связь движений денег со счетами

### Цель

Любая денежная операция должна отвечать на вопрос:

- это оплата какого счёта?
- это частичная оплата?
- это переплата?
- это операция без счёта?
- это аванс?

### Требования

- [x] у операции денег можно открыть связанный счёт;
- [x] у счёта видно связанные денежные операции;
- [x] частичные оплаты отображаются понятно;
- [x] переплаты уходят в баланс клиента;
- [x] зачёты с баланса клиента не конфликтуют с фактической оплатой;
- [x] нельзя случайно задвоить оплату через банк и ручной платёж.

### Сценарии

1. Клиент оплатил счёт полностью через банк.
   - Банк импортирует операцию.
   - Система находит счёт.
   - Счёт становится оплаченным.
   - Операция получает связь со счётом.

2. Клиент оплатил счёт частично.
   - Система находит счёт.
   - Счёт остаётся частично оплаченным.
   - Остаток виден в счёте и платежах.

3. Клиент переплатил.
   - Счёт закрывается.
   - Разница уходит на баланс клиента.
   - В журнале баланса клиента появляется движение.

4. Клиент оплатил наличными.
   - Создаётся фактический платеж.
   - Создаётся ПКО.
   - Движение появляется в кассе.

5. Клиент оплатил картой.
   - Движение появляется в `Карты`.
   - Счёт закрывается или частично оплачивается.

6. Клиент оплатил через электронные деньги.
   - Движение появляется в `E-money`.
   - Счёт закрывается или частично оплачивается.

## Связь с балансом клиента

У нас уже есть логика баланса клиента и зачётов. Её нужно связать с журналом денег так, чтобы не было двойного учёта.
