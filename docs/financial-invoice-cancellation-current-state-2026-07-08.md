# Сверка сценариев аннулирования счетов с ТЗ

Дата проверки: 8 июля 2026.
Связанный roadmap: `docs/tz-crm-financial-scenarios-roadmap-2026-07-08.md`, пункт "Сверить текущие сценарии аннулирования счета с ТЗ".

## Вывод

Текущая реализация уже закрывает базовые сценарии аннулирования счета из ТЗ: полный счет без оплаты, счет с рассрочкой, частично оплаченный график, полученные деньги, неоплаченные остатки, а также связанные акты и отражение денег через аванс, зачет или возврат.

На этом шаге код менять не требовалось. Следующие пункты roadmap должны отдельно проверить удобство мастера в интерфейсе, обязательность сценариев по бизнес-правилам и полную финансовую цепочку в отчетах/деле/истории.

## Что проверено в реализации

### Полное аннулирование счета без оплаты

- `POST /api/invoices/{id}/cancel` требует право редактирования счетов и обязательную причину.
- Для обычного неоплаченного счета выставляется `PaymentStatus.Cancelled` и `InvoiceWorkflowStatus.Cancelled`.
- Дата, пользователь и причина аннулирования сохраняются в полях счета.
- Оплата очищается: `PaidAmount = 0`, `IsPaid = false`, даты оплаты сбрасываются.
- В системные заметки счета добавляется запись об аннулировании.

### Счет с рассрочкой

- Сформированные платежи рассрочки определяются по маркеру `[pp:installment-payment]`.
- При полном аннулировании счета все активные платежи рассрочки переводятся в `Cancelled`.
- Оплаченные суммы на платежах рассрочки очищаются только при полном аннулировании, когда выбран сценарий обработки полученных денег.
- Статус представительного счета пересчитывается по активным платежам; отмененные платежи не искажают сумму к оплате и статус.

### Частично оплаченный график

- Для графика, где есть оплаченные и неоплаченные платежи, поддержан отдельный режим `UnpaidInstallmentsOnly`.
- В этом режиме оплаченные платежи остаются оплаченными, неоплаченные переводятся в `Cancelled`.
- Сам счет не считается полностью аннулированным: дата и причина аннулирования счета не заполняются, статус остается частично оплаченным по сохраненной оплате.
- Денежные операции и баланс контрагента не создаются, потому что полученные деньги остаются оплатой сохраненной части графика.

### Полученные деньги при полном аннулировании

Если по счету или платежам рассрочки уже есть полученные деньги, backend не разрешает полное аннулирование без выбранного сценария:

- `LeaveAsAdvance`: деньги переносятся на баланс клиента или юридического лица как аванс от аннулированного счета.
- `Reallocate`: сначала создается кредит на балансе от аннулированного счета, затем он применяется к другому входящему счету того же контрагента.
- `Refund`: создается расходная денежная операция на сумму возврата; для кассы дополнительно создается posted РКО.

Дополнительно проверяются ограничения зачета:

- целевой счет обязателен;
- нельзя зачесть деньги на тот же счет;
- целевой счет должен быть входящим счетом;
- контрагент должен совпадать;
- нельзя зачесть на аннулированный счет;
- у целевого счета должен быть остаток к оплате.

### Связанные акты

- Акты, явно связанные со счетом, при аннулировании счета переводятся в `Terminated` / `Cancelled`.
- В акт сохраняется дата, пользователь, причина и комментарий об аннулировании вместе со счетом.
- Несвязанные акты не меняются.

### Интерфейс

- В карточке счета есть мастер "Отмена счета".
- Если в рассрочке есть и оплаченные, и неоплаченные платежи, мастер предлагает режим "Только неоплаченные платежи графика".
- При полном аннулировании с полученной оплатой мастер показывает варианты: оставить авансом, зачесть на другой счет, оформить возврат денег.
- Для зачета интерфейс требует ID целевого счета, для возврата - источник и дату возврата.
- Вызов frontend API передает `reason`, `cancellationScope`, `receivedMoneyAction`, `targetPaymentId`, `refundSource`, `refundDate`.

## Существующее покрытие тестами

Backend:

- `Cancel_StoresReasonAndCancelsGeneratedInstallments` - причина и аннулирование платежей рассрочки.
- `Cancel_CancelsLinkedActs` - аннулирование связанных актов.
- `Cancel_RejectsInvoiceWithReceivedMoney` - запрет аннулирования оплаченного счета без сценария денег.
- `Cancel_PaidInvoiceWithAdvanceAction_CreatesClientBalanceCredit` - перенос оплаты клиента в аванс.
- `Cancel_PaidLegalEntityInvoiceWithAdvanceAction_CreatesLegalEntityBalanceCredit` - перенос оплаты юридического лица в аванс.
- `Cancel_InstallmentInvoiceWithPaidGeneratedPayment_TransfersPaidAmountToAdvance` - полный отказ от оплаченной рассрочки с переносом денег в аванс.
- `Cancel_UnpaidInstallmentsOnly_PreservesPaidGeneratedPayment` - отмена только неоплаченного остатка рассрочки.
- `Cancel_PaidInvoiceWithReallocateAction_AppliesCreditToTargetInvoice` - зачет в другой счет клиента.
- `Cancel_PaidLegalEntityInvoiceWithReallocateAction_AppliesCreditToLegalEntityTarget` - зачет в другой счет юридического лица.
- `Cancel_PaidCashInvoiceWithRefundAction_CreatesExpenseOperationAndCashOrder` - возврат денег и РКО.

Frontend:

- `InvoiceModal.integration.test.tsx` проверяет, что мастер не использует старый prompt и отправляет `UnpaidInstallmentsOnly` для частично оплаченной рассрочки.
- `invoicePayments.test.ts` проверяет, что отмененные строки счета исключаются из источников статуса и не ломают расчет представительного счета.

## Остаточные риски для следующих пунктов roadmap

- Нужно отдельно пройти мастер выбора действия с полученными деньгами в UI: тексты, ошибки, доступность, конфликтные варианты и удобство выбора целевого счета.
- Нужно решить с заказчиком, какие сценарии должны быть обязательными, а какие только доступными.
- Нужно проверить полную цепочку после аннулирования на локальной копии БД: счет, платежи, ПКО/РКО, акты, календарь платежей, финансы дела, история, отчеты.
- Нужно отдельно проверить договоры и акты по оставшимся пунктам roadmap.

Первый пункт roadmap 4 можно закрыть как сверенный: реализация и существующие тесты подтверждают основные сценарии аннулирования счета, а оставшиеся вопросы перенесены в следующие рабочие пункты roadmap.
