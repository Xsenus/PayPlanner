## Решение и порядок доставки

[AGENTS.md](../AGENTS.md) требует: «Full CI checks remain a mandatory release barrier.» Штатный путь — исправить обе причины и пройти полный обязательный CI. Альтернативный разовый ручной выпуск допустим только после отдельного явного подтверждения владельцем **этого code SHA и архива с указанным выше SHA-256 при известном неуспешном CI**. До этого PR не сливать и production не изменять. Обычное одобрение документации не выдаётся за зелёный CI.

После такого подтверждения:

1. Повторно проверить host key до аутентификации, архив и provenance, ожидаемую установленную ревизию, фактическую БД/службу/пути/настройки, pending migrations и место. Любой дрейф, неизвестная миграция или нехватка места останавливают установку. На VPS оставить не менее 3 ГиБ после операции; на локальном диске — 20 ГиБ сверх нового объёма. Startup выполняет migrations/seed/backfills, поэтому отсутствие новых migration C# не заменяет эту проверку.
2. Остановить только PayPlanner на время согласованного резервирования и установки. Сохранить исходные защищённые данные, полную БД, backend, обе FE-копии, настройки, ключи Data Protection, вложения и сведения службы с владельцами/правами. До установки получить закрытую offsite-копию, проверить состав и SHA, читаемость PostgreSQL dump через `pg_restore --list` без восстановления. Для крупной копии использовать проверенный отдельный каталог на D с достаточным местом. Старые backup не удалять.
3. Проверить Linux filesystem gates в собственном временном каталоге, удалённый SHA и безопасный состав staging-архива. Установить ровно согласованный пакет, сохранив измеренные runtime/SMTP/WebPush/storage settings, ключи и shared files. Голый `deploy-vps.sh` не заменяет процедуру: он сам не делает DB/offsite backup и безопасную остановку. Записать code SHA в маркеры и запустить службу; все команды должны вернуть фактический exit 0.
4. Сверить четыре маркера, управляемые пакетом backend-файлы и точный состав обеих FE-копий; сохранённые настройки/данные — с исходными отпечатками. Подтвердить active/running, стабильность PID/рестартов и журнал без ошибок startup; локальный/публичный health, frontend, service worker, ревизию и защищённые WebSocket штатной readiness-командой. Реальные письма и финансовые записи ради smoke не создавать. Сохранить native receipts и фактические SHA, затем обновить передачу.
5. При неуспехе остановить новую службу, сохранить диагностику и восстановить прежние файлы/настройки из проверенной копии, не заменяя shared files устаревшим App_Data. БД автоматически поверх новых записей не восстанавливать: если startup изменил данные, применять только заранее подтверждённый сценарий с учётом этих записей. Проверить прежнюю ревизию, health и данные; такой исход считать неуспешным выпуском.
