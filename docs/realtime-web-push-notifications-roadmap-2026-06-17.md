# Roadmap: моментальные уведомления и Web Push во всей CRM

Дата: 17.06.2026

## Контекст

Заказчик описал потерю моментальной связи между сотрудниками: задачи, изменения сроков и другие события попадают в центр уведомлений, но сотрудник узнает о них только когда сам открывает раздел "Уведомления". За день-два там накапливается много записей, и оперативная работа ломается.

Текущее состояние системы:

- Внутренний центр уведомлений уже есть: записи сохраняются в `UserNotifications`.
- Для задач backend уже создает уведомления по назначению, изменениям, комментариям, срокам, согласованиям и конфликтам расписания.
- Есть SignalR hub `/hubs/notifications`, который публикует событие `userNotificationCreated` авторизованному пользователю.
- Frontend уже подключает `RealtimeNotificationToasts`, но всплывающее уведомление сейчас показывается только для `taskAssigned`. `taskChanged`, комментарии, согласования и другие типы обновляют центр уведомлений, но не дают заметного моментального сигнала.
- Есть отдельный SignalR hub `/hubs/notes` для синхронизации досок заметок между пользователями.
- Настоящего Web Push нет: нет service worker, VAPID-ключей, хранения push-подписок и отправки браузерных push-уведомлений, которые приходят при закрытой вкладке.
- На VPS nginx для API проксирует HTTP/1.1, но в конфиге не обнаружены явные WebSocket-заголовки `Upgrade` и `Connection`. SignalR endpoint отвечает, но realtime-канал может быть менее надежным или уходить в fallback.

## Цель

Сделать уведомления не "архивом событий", а рабочим каналом моментальной связи:

- сотрудник сразу видит новую задачу, изменение срока, комментарий, согласование, календарное изменение, заметку или важный платеж;
- если CRM открыта, событие появляется как realtime-toast и обновляет счетчики без ручного перехода в уведомления;
- если CRM закрыта или вкладка спит, важные события приходят через Web Push;
- все события проходят через единый слой прав доступа и персональных настроек;
- система не спамит, не дублирует уведомления, умеет группировать шумные события и имеет журнал доставки.

## Основные решения

- [decision] Определить название пользовательского канала.
  - Вариант: "Пуш в браузере".
  - Важно отделить его от "В системе" и от текущих внутренних уведомлений.

- [decision] Определить уровень обязательности push-уведомлений.
  - Вариант 1: пользователь сам включает push в профиле.
  - Вариант 2: система предлагает включить push при первом входе.
  - Вариант 3: для критичных ролей показывать постоянное предупреждение, пока push не включен.

- [decision] Определить, какие события должны быть срочными.
  - Срочные: новая задача, смена срока задачи, новый комментарий по задаче, запрос согласования, возврат на доработку, календарное событие с ближайшим сроком, заметка с упоминанием/назначением, платеж на контроль, просроченный аванс.
  - Несрочные: массовые системные изменения, фоновые синхронизации, информационные обновления без ответственного действия.

- [decision] Определить политику рабочих часов.
  - Вариант: доставлять все сразу.
  - Вариант: ночью отправлять только критичные, остальные группировать к началу рабочего дня.
  - Вариант: учитывать часовой пояс пользователя из профиля.

- [decision] Определить каналы за пределами браузера.
  - Уже есть Email и Telegram как каналы доставки.
  - Web Push нужен отдельно.
  - SMS/MAX в системе обозначены как будущие каналы, их не включать без отдельного решения.

## Definition of Done

Задача считается завершенной только если:

- важные события по задачам, календарю, заметкам, платежам, счетам, актам, договорам, делам и судам проходят через единый notification pipeline;
- при открытой CRM пользователь получает realtime-toast для всех срочных событий, а не только для новой задачи;
- при закрытой вкладке пользователь получает Web Push по включенным важным типам;
- пользователь и роль могут управлять типами и каналами уведомлений;
- права доступа проверяются до создания/показа/перехода из уведомления;
- nginx/VPS поддерживает WebSocket и service worker/Web Push;
- доставка логируется, ошибки диагностируются;
- тесты backend/frontend проходят;
- кодировка и `releases.json` проверены;
- локальная SQLite-БД и, по возможности, PostgreSQL-БД стартуют с миграциями;
- GitHub Actions зеленый;
- на VPS health ok, revision обновлен, journal без ошибок;
- заказчик вручную подтвердил сценарий "Аня поставила/изменила задачу -> сотрудник увидел сразу".

## Риски

- Браузер может запретить Web Push на уровне пользователя или политики устройства.
- iOS/мобильные браузеры имеют ограничения по push и service worker.
- Слишком много событий может создать шум, если не сделать группировку.
- Push payload может раскрыть чувствительные данные на экране блокировки, если тексты не ограничить.
- Прямые вставки `UserNotifications` в обход общего сервиса могут не попасть в realtime/Web Push.
- Без настройки nginx WebSocket realtime может работать нестабильно.
- Старые роли/личные настройки могут отключать нужные каналы, поэтому нужна диагностика.
