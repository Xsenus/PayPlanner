СПЕЦИФИКАЦИЯ ДЛЯ РАЗРАБОТКИ
Банковские интеграции в профиле компании: Точка, Сбербанк — выписки, списки счетов, статусы счетов.
Версия: 1.1 (обновлено — добавлены разделы 9–11: загрузка списка счетов в профиль компании, статусы счетов, выписки по одному и по всем счетам).
1. Архитектура модуля
Логика CRM одинакова для всех банков: различия изолированы в слое адаптеров.
Слой адаптеров (BankAdapter): BankTochkaAdapter, BankSberAdapter. Общий интерфейс: get_accounts_list(), get_statement(account_id, date_from, date_to), webhooks. Новый банк = новый адаптер, логика CRM не меняется.
Таблицы БД: bank_connections (подключения), bank_accounts (счета банка в профиле компании), statements (загруженные выписки), operations (операции), payment_matches (правила сопоставления), payment_allocation (разнесение оплат).
Планировщик (cron/queue): периодическая загрузка выписок, инкрементальный режим.
Вебхуки: приём событий от банка в реальном времени (Точка), с проверкой подписи и ретраями.

2. Подключение банков
2.1 Точка
Авторизация: OAuth 2.0 / токен с scope ReadAccountsBasic, ReadAccountsDetail, ReadStatements (для выписок).
Вебхуки: incomingPayment, outgoingPayment, события СБП. Проверка подписи JWT RS256 публичным ключом Точки, ретраи при недоступности CRM.
Все запросы к enter.tochka.com/uapi/open-banking/v1.0/... (accounts, statements, balances).
2.2 Сбербанк
Подключение Sber API (набор «Компаниям»): заявка, сертификат .p12, Сбер Бизнес ID (Authorization Code Flow), scope GET_STATEMENT_ACCOUNT.
Методы выписок: GET /v2/statement/summary, GET /v2/statement/transactions (постранично), GET /v2/statement/increment.
Лимиты: ~5 запросов в секунду. Глубина выписок: 5 лет + текущий год.
Для счетов пользователя подписывается Согласие с указанием конкретных счетов — при изменении списка счетов требуется переавторизация.
3. Загрузка списка счетов банка сразу в профиль компании
При подключении банка CRM первым шагом запрашивает список всех счетов организации и автоматически создаёт записи bank_account в профиле компании. Пользователь не вводит счета вручную — они загружаются из банка.
3.1 Точка: Get Accounts List
Запрос: GET https://enter.tochka.com/uapi/open-banking/v1.0/accounts
Ответ: Data.Account[] — по каждому счёту: customerCode, accountId (формат «номер_счёта/БИК», до 40 симв., уникален и неизменен), transitAccount, status, currency (ISO 4217), accountType (Business/Personal), дата изменения статуса.
Необходимые разрешения: ReadAccountsBasic, ReadAccountsDetail.
accountId сохраняется как account_id_ext и используется во всех последующих запросах: баланс, выписка, реквизиты.

3.2 Сбербанк: счета организации
Список счетов организации входит в набор «Компаниям» (атрибуты: стандартный набор + счета организации). Метод списка счетов компании вызывается с access_token пользователя.
Для каждого счёта: номер счёта (40702810...), БИК, корсчёт, валюта.
Важно: доступ выдаётся только к счетам, которые пользователь указал при подписании Согласия в СберБизнес ID. Список доступных счетов = пересечение «счета организации» и «счета в Согласии».
Если пользователь меняет набор счетов в Согласии — CRM отображает статус подключения «Требуется переавторизация» (см. п. 8).
3.3 Логика загрузки списка счетов
1. Кнопка «Загрузить счета из банка» в подключении профиля компании (и автоматический вызов при первом успешном подключении).
2. CRM вызывает адаптер get_accounts_list().
3. Для каждого счёта из ответа: ищется bank_account по account_number + bik внутри этого подключения.
4. Новый счёт → создаётся запись bank_account со статусом из банка (см. п. 4).
5. Существующий счёт → обновляются status, status_changed_at, currency. Номер счёта не редактируется (источник истины — банк).
6. Счёт, который в CRM существует с ручным статусом «Открыт», но отсутствует в ответе банка → помечается «Не найден в банке» (требует проверки пользователем; не удаляется автоматически).
7. Если в банке несколько компаний — счёт сопоставляется с профилем по ИНН из карточки клиента (у Точки — customerCode → карточка клиента → ИНН). Счёт чужого ИНН не привязывается.
8. Пользователь в UI видит список загруженных счетов и может: назначить счёт «По умолчанию» (is_default) для счетов/документов, скрыть счёт (is_hidden — не показывать в выборах, но загружать выписку), отключить счёт от загрузки выписок (is_statement_enabled=false).
9. Повторная загрузка — по кнопке и автоматически раз в сутки (проверка появления/закрытия счетов).

4.2 Сбербанк
Статус открыт/закрыт определяется по списку счетов организации: счёт, присутствующий в списке доступных счетов и в Согласии — «Открыт»; исчезнувший из списка — «Закрыт». CRM хранит дату фиксации статуса.
4.3 Статусная модель bank_account в CRM
Активный (открыт) — используется в выборах счёта при выставлении счетов, приёме оплат, загрузке выписок.
Закрыт — счёт виден в списке (серым), выбирается только для просмотра истории и загрузки выписок за прошлые периоды. Нельзя: назначить счётом по умолчанию, выбрать при выставлении нового счёта, создать разнесение новых оплат (только просмотр).
Открывается (Pending) — в списках с пометкой, в выборах недоступен.
Ограничен (Disabled) — доступен для выписок, но при подборе оплаченного счёта в разнесении выводится предупреждение.
Правило: закрытие счёта в банке не влияет на исторические данные — выписки, операции и разнесения остаются неизменными. CRM только запрещает новые операции по закрытому счёту.
Переходы: статус загружается из банка автоматически (при плановой синхронизации списка счетов раз в сутки и по кнопке «Обновить счета»). Ручное редактирование статуса запрещено (кроме случая «счёт не найден в банке»).
5. Выписки: по одному счёту и по всем счетам сразу
5.1 Точка
Выписка формируется асинхронно: Init Statement (accountId, date_from, date_to) → statementId → Get Statement (statementId).
Get Statements List — список заказанных выписок со статусами.
Ограничения: отражаются только операции в финальном статусе Ready; выписка доступна 24 часа после формирования, затем удаляется — CRM обязана сохранить операции в БД при получении.
Формат запроса — по одному счёту: в запросе указывается один accountId. Выписка «по всем счетам сразу» у Точки не запрашивается одним методом — CRM сама итерирует по всем активным счетам профиля, запуская Init Statement по каждому accountId (см. п. 5.3).
5.2 Сбербанк
GET /v2/statement/transactions?accountNumber=...&statementDate=... — выписка по конкретному счёту за дату, постранично (page).
GET /v2/statement/increment — выписка изменений по счёту с указанного времени (для регулярной синхронизации).
Тоже по одному счёту за один запрос. Групповая выписка по всем счетам одним запросом не предусмотрена.

Параллельность: запросы по разным счетам идут параллельно с ограничением concurrency (Сбер — суммарно не более ~5 rps). Для Точки — по каждому счёту асинхронный цикл Init → ожидание → Get, с ретраями до готовности выписки (но не дольше 24 часов).
5.4 Логика сценария «по всем счетам»
1. Сформировать список: bank_account where connection_id=X AND status IN (Активный, Ограничен) AND is_statement_enabled=true.
2. Определить период: либо пользовательский (date_from–date_to), либо инкрементальный (от watermark).
3. Поставить задачу в очередь по каждому счёту; отображать прогресс в UI: «Счёт ...401464 — загружено 12 операций», ошибки — по счёту отдельно.
4. Ошибка по одному счёту не прерывает загрузку остальных; итоговый статус выгрузки: «Успешно / Частично (N из M) / Ошибка».
5. Каждая операция проходит нормализацию (п. 6) и идемпотентную вставку по dedup_key.

7. Разнесение оплат (автосопоставление)
Правило 1: по назначению платежа — поиск «оплата счёта №X» / номера счёта в payment_purpose.
Правило 2: по ИНН контрагента + точному совпадению суммы ожидаемой оплаты.
Правило 3: FIFO — самые старые незакрытые счета контрагента.
Приход без правил → статус UNMATCHED «Не разнесённая оплата», кнопка «Уточнить»: выбор контрагента, счёта/дела, суммы (полная/частичная/несколько счетов).
Расходные операции — привязка к входящим (расходным) счетам поставщика и статьям расходов.
Автотест-инвариант: одна операция может разноситься на несколько документов; сумма разнесений ≤ суммы операции.
8. Ошибки, статусы подключения, мониторинг
Статусы подключения: Активен, Токен истекает (предупреждение за 14 дней), Требуется переавторизация (Сбер: изменён Согласие), Ошибка авторизации, Отключён.
Ошибки API: 401/403 → переавторизация; 429 → экспоненциальный backoff с учётом лимита rps; 424 (Точка) → повтор; 5xx → ретраи с ограничением.
Журнал синхронизаций: время, счёт, период, результат, количество операций, ошибки — просмотр в UI.
Оповещения ответственному при: ошибке загрузки 2 подряд, расхождении баланса (кэш ≠ баланс банка после сверки), появлении счёта со статусом Disabled/Deleted.

10. Критерии приёмки
После подключения Точки в профиль компании автоматически загружен список счетов со статусами; счёт Enabled виден как «Открыт».
Закрытый счёт (Deleted) отображается как «Закрыт», недоступен для выставления счетов, история сохранена.
Кнопка «Загрузить по всем счетам» формирует выписки по всем активным счетам, прогресс и ошибки видны, ошибки изолированы по счёту.
Инкрементальный режим не дублирует операции (проверка dedup_key), watermark корректно продвигается.
Выписка Точки сохраняется в БД сразу после получения (правило 24 часов), операции в статусе не Ready не теряются в последующих выписках.
Сбер: пагинация выписки обрабатывается полностью; лимит 5 rps не превышается; изменение Согласия переводит подключение в «Требуется переавторизация» с уведомлением.
