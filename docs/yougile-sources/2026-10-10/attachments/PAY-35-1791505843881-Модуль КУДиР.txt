## word/document.xml
Модуль КУДиРкнига учетов и расходов ДЛЯ БУХГАЛТЕРИИ «Учёт доходов и расходов, журналы операций, интеграция с банками»
Для CRM юридической фирмы (с учётом процессов юрфирмы и интеграции Точка/Сбер)
1. Нормативные требования и юридическая основа
Цель: Обеспечить формирование КУДиР (Книга учёта доходов и расходов) в полном соответствии с НК РФ, ведение оперативных журналов для контроля денежных потоков по делам и автоматическую загрузку данных из банков.
Нормативная база:
НК РФ, ст. 346.24 — обязательное ведение КУДиР для УСН.
Приказ Минфина № 135н — форма и порядок заполнения.
ФЗ402 «О бухгалтерском учёте» — требования к первичным документам и регистрам.
Письмо ФНС № СД43/10522@ — правила исправления ошибок (метод «красное сторно», без зачёркиваний).
Критические требования к системе:
Кассовый метод: Доход/расход признаётся по дате фактического движения денег (operation_date), а не по дате документа.
Невозможность прямого редактирования истории: Изменение суммы или даты должно выполняться только через создание корректирующей записи (CORRECTION).
Привязка к первичному документу: Каждая строка КУДиР обязана иметь ссылку на счёт, акт, платёжное поручение или выписку.
Целостность отчётного периода: После закрытия года редактирование операций запрещено; изменения вносятся только в новом периоде через механизм корректировок.

3. Логика формирования и построения КУДиР
Алгоритм попадания операции в КУДиР
Событие: Поступает оплата от клиента (автоматически из выписки банка или вручную бухгалтером).
Создание записи: В OperationJournal создаётся строка типа INCOME.
operation_date: берётся из выписки банка.
document_ref: привязывается к Счёту, по которому платили.
category: автоматически определяется по типу услуги.
Валидация: Система проверяет:
Не дублируется ли платёж (сверка по сумме, дате и назначению).
Соответствует ли сумма сумме в счёте (если есть расхождения — флаг «Требуется уточнение»).
Утверждение: Бухгалтер ставит статус APPROVED. Только после этого запись попадает в текущий лист КУДиР.
Формирование строки КУДиР:
Графа 1 (Номер): Сквозной номер в пределах года.
Графа 2 (Дата и номер): Дата операции + номер первичного документа.
Графа 3 (Содержание): «Оплата по Счёту №123 от 01.10.2024 за юридические услуги по делу №456».
Графа 4 (Доходы): Сумма (если УСН 6%) или детализация (если УСН 15%).
Графа 5 (Расходы): Пусто (для доходов).
Логика расходов (для УСН 15%)
Расходы признаются только при выполнении двух условий:
Оплата прошла (есть запись в OperationJournal со статусом APPROVED и типом EXPENSE).
Есть закрывающий документ (Акт, ТОРГ12, УПД) со статусом Signed.
Логика CRM: При создании расхода система подсвечивает: «Расход не будет учтён в КУДиР, пока не загружен подписанный Акт».
Логика исправлений (Корректировки)
Если обнаружена ошибка:
Создаётся новая запись типа CORRECTION.
sign = -1, сумма = ошибочная.
description = «Исправление ошибки: платёж №… ошибочно отнесён к делу…».
Создаётся правильная запись с верными данными.
В печатной форме КУДиР обе записи будут видны (одна с минусом, другая с плюсом).

4. Логика Журналов (Операционный учёт)
В CRM должны быть три вида журналов для разных ролей:
Журнал «Кассовые операции» (для бухгалтера):
Фильтр: все APPROVED операции.
Вид: таблица с колонками: Дата, Контрагент, Сумма, Статья, Документ, Статус КУДиР (Учтено/Не учтено).
Действие: кнопка «Сформировать КУДиР за период».
Журнал «Исполнение обязательств» (для юриста/менеджера):
Фильтр: операции, привязанные к конкретному Делу/Договору.
Вид: показывает, сколько оплачено по делу, сколько осталось, статус закрывающих документов.
Цель: контроль дебиторки.
Журнал «Корректировки» (для аудита):
Показывает только записи типа CORRECTION.
Обязательные поля: Кто исправил, Когда, Причина.

5. Формирование и печать документа
Структура печатной формы (КУДиР для УСН)
Печатная форма должна содержать:
Титульный лист: Наименование организации, ИНН, КПП, год, объект налогообложения (Доходы/ДоходыРасходы).
Раздел I (Доходы и расходы): Таблица из 5 граф. Строки сортируются строго по operation_date.
Раздел II (Расчёт расходов на ОС — если есть): Амортизация.
Раздел III (Убытки прошлых лет): Для переноса убытков (если УСН 15%).
Итоговые строки: Сумма доходов за год, сумма расходов за год, налоговая база.
Подписи: Поля для подписи руководителя и главного бухгалтера (заполняются из профиля компании).
Процесс печати в CRM
Пользователь выбирает период (год) и компанию.
Система формирует PDFфайл на основе данных из OperationJournal (статус APPROVED).
Защита от изменений: В момент генерации PDF система может ставить цифровой штамп (дата генерации, хеш данных).
Экспорт: Возможность выгрузки в Excel (для внутреннего анализа) и XML (для загрузки в 1С или отправки в ФНС).

6. Интеграция с банками (Точка и Сбер)
Точка
API: OAuth 2.0 со scope ReadStatements.
Сценарий: Init Statement → Get Statement (statementId, выписка живёт 24 часа).
Вебхуки: incomingPayment, outgoingPayment, СБПсобытия.
Обработка: Асинхронный сценарий, проверка подписи JWT RS256, ретраи 30×10 секунд.
Сбер
Подключение: Sber API (набор «Компаниям»), сертификат .p12, Сбер Бизнес ID по Authorization Code Flow.
Методы: /v2/statement/summary, /v2/statement/transactions, /v2/statement/increment.
Лимиты: 5 TPS, глубина выписок 5 лет.
Обработка выписок
Планировщик: Инкрементальный/полный режим.
Нормализация: Операции приводятся к единому формату.
Авторазнесение: По назначению платежа → по ИНН и сумме → FIFO.
«Не разнесённая оплата»: Кнопка «Уточнить» для ручного распределения.

7. Загрузка списка счетов и статусы
Загрузка списка счетов
Точка: Метод GET /uapi/open-banking/v1.0/accounts (Get Accounts List). Возвращает все счета организации: accountId, статус, валюту, тип.
Сбер: Список счетов из набора «Компаниям» (только счета из подписанного Согласия).
Алгоритм: Автозагрузка при подключении, сопоставление по ИНН, пометка «Не найден в банке», счёт по умолчанию, скрытие счёта, отключение выписок по счёту, автосинхронизация раз в сутки.
Статусы счетов
Точка: Enabled → Открыт, Disabled → Открыт (ограничен), Deleted → Закрыт, ProForma → Не активен, Pending → Открывается.
Сбер: Открыт/закрыт по присутствию в списке доступных счетов и Согласии.
Правила: Закрытый счёт — только просмотр истории и выписок за прошлые периоды; нельзя выставлять новые счета и назначать его основным.
Выписки по одному счёту и по всем счетам
Ограничение: API обоих банков возвращает выписки только по одному счёту.
Режимы в CRM:
Ручной (один счёт).
Групповой (кнопка «Загрузить по всем счетам» — CRM итерирует по активным счетам с учётом лимита Сбера ~5 запросов/сек).
Инкрементальный фоновый по расписанию.
Обработка ошибок: Ошибка по одному счёту не блокирует остальные.

8. Интеграция с CRMпроцессами юрфирмы
Источник данных в CRM
Как попадает в КУДиР
Выписка банка (Точка/Сбер)
При загрузке выписки система автоматически создаёт черновики операций в OperationJournal. Бухгалтер проверяет и утверждает их.
Счёт + Акт
При подписании Акта система проверяет, была ли оплата. Если да — фиксирует расход (для УСН 15%) или подтверждает доход.
Возврат средств
Создание документа «Возврат» автоматически генерирует операцию EXPENSE со знаком минус или CORRECTION.
Зарплата
Модуль «Зарплата» должен иметь экспорт в КУДиР: выплаты сотрудникам — это расходы.

9. Сценарии использования (User Stories)
Сценарий «Автозагрузка и сверка»:
Действие: Загрузка выписки из банка.
Логика: CRM ищет счёт по назначению платежа. Если находит — создаёт связь. Если нет — помечает как «Неизвестный платёж».
Сценарий «Ошибка бухгалтера»:
Действие: Бухгалтер видит, что платёж за аренду попал в «Прочие расходы».
Логика: Бухгалтер не редактирует старую строку. Он создаёт запись CORRECTION (-сумма) и новую запись с правильной статьёй (+сумма).
Сценарий «Частичная оплата»:
Действие: Клиент платит 50% по счёту.
Логика: В КУДиР попадает только уплаченная сумма. Остаток будет учтён при следующем платеже. Статус счёта меняется на «Частично оплачен».

10. Технические требования к разработке
Индексы БД: Обязательно проиндексировать поля company_id, operation_date, status, type.
Транзакционность: Создание операции и её утверждение должны быть атомарными или иметь механизм отката.
Архивация: После закрытия года возможность менять статус операций на APPROVED должна блокироваться.
Логирование: Любое изменение статуса операции должно фиксироваться в истории.
