# Служебная записка: автоматизация статусов счетов по платежам

Дата: 07.05.2026

## Зачем появилась записка

Клиент сообщил, что расходный счет на 2 500 ₽ фактически не оплачен и ожидается, но программа показывала его как частично оплаченный. При разборе выяснилось, что в системе были расхождения между связанными платежами и сохраненным состоянием родительского счета.

Эта записка фиксирует, что было закрыто по блоку "счет ↔ платежи", какие правила теперь считаются основными и к чему нужно вернуться отдельно.

## Что закрыто

1. Единое правило пересчета вынесено в `InvoicePaymentStateService`.
2. При изменении платежей через API пересчитывается родительский счет.
3. Списки и карточки счетов используют то же правило, а не отдельную экранную логику.
4. Отмена только неоплаченных платежей рассрочки сохраняет оплаченные платежи и пересчитывает счет.
5. Добавлен ручной repair endpoint для администраторского ремонта старых расхождений:
   - `POST /api/invoices/repair-payment-state`
   - `POST /api/invoices/recalculate-payment-state`
6. Добавлена фоновая сверка `InvoicePaymentStateReconciliationService`.
7. На production первый проход фоновой сверки исправил 116 расхождений из 1487 просканированных агрегатов счетов.

## Текущее правило для счета

Сохраненное состояние счета должно соответствовать связанным платежам:

- если вся сумма счета закрыта оплатами, счет становится оплаченным;
- если есть частичная оплата, счет становится частично оплаченным;
- если оплаты нет и срок прошел, счет становится просроченным;
- если оплаты нет и срок не прошел, счет ожидает оплаты;
- если все платежи графика отменены, счет считается отмененным;
- отмененные платежи графика не должны создавать искусственный долг.

Ключевое правило: экран, API и фоновая сверка должны приходить к одному и тому же состоянию через `InvoicePaymentStateService`.

## Что делает фоновая сверка

Сервис `InvoicePaymentStateReconciliationService`:

- стартует через 5 минут после запуска приложения;
- затем работает раз в 15 минут;
- сканирует счета батчами по 500;
- сравнивает сохраненное состояние счета с состоянием, рассчитанным по связанным платежам;
- применяет исправление только если есть реальное расхождение.

Настройки лежат в `appsettings.json`:

```json
"InvoicePaymentStateReconciliation": {
  "Enabled": true,
  "StartupDelayMinutes": 5,
  "IntervalMinutes": 15,
  "BatchSize": 500
}
```

## Что намеренно не закрывали

Акты не стали автоматически менять при оплате счета.

Причина: "счет оплачен" не всегда означает, что акт должен стать подписанным, закрытым или выполненным. Для актов нужно отдельное бизнес-правило.

## К чему вернуться отдельно

Нужно отдельно согласовать автоматизацию актов:

1. Должен ли оплаченный счет автоматически менять статус акта?
2. Если да, какой именно статус ставить:
   - подготовлен;
   - отправлен на подпись;
   - подписан;
   - закрыт;
   - без изменения статуса, только уведомление/подсказка.
3. Что делать, если у счета несколько актов?
4. Что делать, если акт подписан, а счет отменили или вернули оплату?
5. Нужно ли связывать акт со счетом по FK, а не по строковому номеру счета.
6. Нужен ли отдельный журнал проверки "счет оплачен, но акт не подписан".

Рекомендуемый следующий шаг: не автоматом менять акты сразу, а сначала сделать отчет/виджет контроля:

- "Оплаченные счета без подписанного акта";
- "Подписанные акты без полной оплаты";
- "Отмененные счета со связанными активными актами".

После этого можно безопасно решать, какие переходы актов делать автоматически, а какие оставлять пользователю.
